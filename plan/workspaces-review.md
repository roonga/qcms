# Workspaces area: review (function, UI, decisions, design)

Written 2026-11-08 against `origin/main` at `ff3952e7` (#1236). Untracked working paper; the Code Owner's rulings go into `plan/admin-design-contracts.md`, the ADRs and issues, not here. **Workspace access is specified in [`docs/WORKSPACE_ACCESS.md`](../docs/WORKSPACE_ACCESS.md)**, which supersedes this paper wherever they differ; the rulings in section 7 are corrected to agree with it. Paths are repo-relative; `file:line` cites that commit.

Code Owner's complaint (2026-11-08): the screen is a mess; no way to create a workspace; no way to manage members; Workspace settings and Access audit unclear; Assistant actions show step numbers, not real information; a single-workspace site should not see multi-workspace complexity.

Design principle added 2026-11-08 (Code Owner): each screen has exactly one function (one job, one primary action); navigation is the left rail only; no nested screens, no drill-down, no screen reachable only from inside another screen's body. Tabs are not banned: they may show alternative views of one function. Section 5 applies it; section 2.3 checks what the contracts already record.

## 0. Summary

- The area is five screens per workspace (Members, Access groups, Workspace settings, Access audit, Assistant actions) plus `/workspaces/all`. The API has eleven more acts than the UI exposes: create, archive, mark shared, rename or re-scope a group, move a form, move a question, and installation-wide ones. None of the six workspace-lifecycle acts has a screen.
- Nobody can add a person from the UI. The only account-creation path in the product is the operator CLI `pnpm qcms:create-admin` (`apps/api/src/features/auth/bootstrap.ts:82`); the auth mount allows no sign-up or invite endpoint (`apps/api/src/features/auth/route.ts:7-16`, asserted at `auth-mount.test.ts:26,66`). "Invites in Site configuration" was ruled 2026-11-04 but no Site configuration screen or API exists.
- The screens expose wire vocabulary everywhere: `all.forms.approver`, `<environments>.<role>[.<label>]`, "Member row", `grant`/`revoke`, `access.grant`, `/workspaces/[workspaceId]/access-groups`, raw `userId`s and `teamId`s. Plain role names exist (`membership.role.*.name`) but reach only the Access groups Role column and the create picker.
- Assistant actions is thin because the handler writes only an id as `detail` (`apps/api/src/features/membership/handler.ts:425,475,557,615,688,755`) and the panel prints every column raw. The data to show who, which act, on what, in which environment is already in the row or one lookup away; outcome is implicit (only confirmed, committed steps write a row).
- Single-workspace sites see the full multi-workspace shell: "All workspaces" back link, a three-crumb trail with the workspace name, a "Workspace: Default workspace" line, the workspace table, archive tags, shared-library concepts in help text.
- Several records disagree with the build and each other (section 3). Fourteen decisions need the Code Owner (section 6); a recommendation is given for each.

Grant model in one paragraph: a workspace is better-auth's `organization` row with `isShared`, `requireSecondApprover`, `archivedAt`, `seedNewEditorsWithTestData` (ADR-41; `apps/api/src/features/workspaces/README.md:33-47`). `forms.owner` is the member row's role; every other grant is a team ("access group") carrying one of five roles plus `environments` and `forms` scope; team membership is the grant (`handler.ts:564-566`). Every holder gets a member row with the empty `member` role (`ensureWorkspaceMember`, `handler.ts:598`). The installation claim (`user.role = admin`) is modelled as `forms.owner` in every workspace and holds no member row (`docs/adr/core.md:521`, `lib/server/workspace-context.ts:13-17`); it administers and reads no response data (`core.md:551-555`). A `forms.editor` scoped `all` still cannot act in `prod` (`policy.ts:232-235`), which is what the `scopeNote` sentence explains (`packages/db/src/access-groups.ts:198-199`).

### 1.3 Per function: what exists, where it is thin

Workspaces list and detail. The list is at `/workspaces/all`, the area root redirects away from it. `GET /workspaces` is declared `caller`-scoped but the handler returns every row unnarrowed (`workspaces/handler.ts:131-142`), so a department owner sees every other department's name and counts, which Q35's reasoning for the members list ("information about another department", `membership/route.ts:78-82`) argues against. Known, not yet filed (memory note of 2026-11-07).

Create workspace. API exists (`workspaces/route.ts:45-62`); installation claim only; the caller becomes the owner, which contradicts "the claim holds no member row anywhere" the moment the claim creates one. No UI: task 068 said "There is no screen ... the workspace and membership screens arrive with 069" (`workspaces/README.md:29-30`) and 069 built only the four membership screens (`docs/features/069-membership-and-audit.md:3`). Nothing ever specified a create screen; a fresh installation gets one seeded "Default workspace" (`bootstrap.ts:129-133`) and the `create-qcms-app` scaffold adds no other.

Members. List and owner toggle only. A person enters a workspace only as a side effect of a grant (`handler.ts:598-599`), and a grant can name only an existing account (`findUserByEmail`, `handler.ts:579-583`). There is no remove-member act in the API (removing every grant leaves the empty member row). There is no account creation outside the CLI. Ruling 2026-11-04: grant to existing members only, directory link under Advanced, invites in Site configuration; the first two are built (`access-groups-panel.tsx:163-180`, `:150-160`), the third has no screen and no endpoint. The "no admin screen for adding a new account to a workspace" gap has been open for the Code Owner since 2026-11-06.

Access groups. Grammar `<environments>.<role>[.<label>]` is enforced on save (`handler.ts:220-229`) and the UI derives the name (`lib/membership/access-group-form.ts:95-103`). Roles offered: the five team roles (`access-group-form.ts:4-10`), plain names and one-line descriptions exist (`en.ts:2281-2297`). Scopes: environments (All or a set, in table order), forms (All or picked by name from the caller's own form read). Create, remove, grant, revoke are built; rename and re-scope (`PUT`) are not. Removing a group writes one revoke row per holder (`handler.ts:545-553`).

Workspace settings. Two switches, both audited as `setting` rows (`handler.ts:719-753`). Installation-wide settings (release workflow, environments, accounts) live elsewhere or nowhere. Per workspace but with no UI: name, slug, `isShared`, archive. Name and slug have no update route at all.

Access audit. Six kinds `read, export, erasure, grant, revoke, setting` (`packages/db/src/schema/control/access-audit.ts:13-20`); readable by owners and the claim (`audit:read`). Rows carry actor, workspace, environment, form, kind, time and a free-text `detail` such as `role=forms.editor environments=all forms=all subject=usr_x group=all.forms.editor` (`handler.ts:150-165`). The panel prints `kind` and `detail` raw; the subject is a user id, not an address.

Assistant actions. One row per confirmed step in the step's own transaction (`apps/api/src/features/agent/audit.ts:1-4,45-66`); a failed step writes nothing, so every row is a success. Columns stored: `proposalId, stepIndex, stepCount, actor, workspaceId, environment, formId, kind, screen, proposedAt, confirmedAt, detail` (`packages/db/src/schema/control/agent-actions.ts:18-44`). `kind` is a machine id such as `access.grant` (24 kinds, `apps/api/src/features/agent/actions/*.ts`); `screen` is a route pattern; `detail` is whatever the handler passed: a `teamId` for group create, remove and grant, a `userId` for revoke and role change, the `workspaceId` for settings. Why only step numbers show: the panel renders "{index} of {count}" as its own column and every other column raw, and `detail` is an opaque id. What could be shown from existing data: who (actor email is already resolved, `handler.ts:837-838`); which act in words (every kind has a card title, `en.ts:1611-1707`, and every screen has a label, `en.ts:1538-1542`); the target (resolve `detail` the way the actor is resolved: teamId to group name, userId to address, with "(removed)" fallbacks); the environment and form (stored); the plan the step belongs to (group rows by `proposalId`, which also makes "step 2 of 3" meaningful); when proposed versus confirmed (both stored). Not stored and not recoverable: the before and after values, the subject's email at the time, and the agent's reasoning. A redesign should state that the list is "what the assistant did with a person's approval", not a changelog.

### 1.4 Single versus multi workspace, as built

Nothing in the area branches on the number of workspaces except the switcher (`offersWorkspaceChoice`). A one-workspace site still gets: the Workspaces nav label; `/workspaces/all` with a one-row table; "‹ All workspaces" in the rail (asserted by `apps/admin/e2e/membership.pw.ts:83-95`); the trail "Workspaces / Default workspace / Members"; the "Workspace: Default workspace" line; "Archived" and shared-library wording in help; the all-workspaces column counts. Who sees the area: only holders of `workspace:read`, so owners and the claim; editors never see the nav item but do see the switcher once they hold grants in two workspaces.

### 2.3 Does the contract already record the one-function principle?

§7.00 (`admin-design-contracts.md:946-963`) records: one persistent rail per area, a tree of two levels at most, "every row is a screen", one title per screen, a breadcrumb on every screen, the back link only inside one item. It does not record: one function and one primary action per screen; no screen reachable only from inside another screen's body; what counts as a screen versus a side sheet or dialog; where tabs are appropriate. §7.0 ruling 5 (lifecycle actions in the heading row) and the canvas principle "lists + side sheet, progressive disclosure" (ruled 2026-11-04, recorded in memory, not in the contract) bear on it.

Recommended amendment wording, as a new bullet under §7.00:

> **One function per screen, reached from the rail.** A screen has one job and at most one primary action. Every function is a rail row that is its own route; no screen is reached only from inside another screen's body, and nothing drills down. A list screen may open a side sheet or a dialog for one row's details and that row's own operations; a side sheet is not a screen and has no address. Creation is a screen of its own. Tabs are allowed only for alternative views of the same function (the same data, a different cut), never for different functions.

### 3.2 Records that disagree with each other

- SEC matrix and ADR-41 say workspace creation is the claim's (`SECURITY_DESIGN.md:335`, `route-policy.ts:75-83`); the workspaces route text says "the account making the request becomes the workspace's owner" (`workspaces/route.ts:50`), which presumes an owner who is not the claim. Both true at once only if the claim then hands ownership on, which no screen allows (Members' owner toggle is per existing member).
- Q66 "There is no unarchive ... revisit only if 069's membership screens need a way back. They do not" versus the list showing archived workspaces with live section links (`all/page.tsx:76-80`, every section refuses writes with `WORKSPACE_ARCHIVED`).
- The plan's Q37 table shows the "Derived full name" is for "cross-workspace lists" (`environments-and-workspaces.md:283-293`); the only cross-workspace list, `/workspaces/all`, shows no group names, while the single-workspace page shows the full name under Advanced.

## 4. Single versus multi workspace

Rule: the shell counts the workspaces the signed-in user may open (`WorkspaceContext.choices`, already computed). "One" means one choice; the installation claim on a one-workspace installation also counts as one.

| Surface                                           | One workspace                              | Two or more                                                                                                                 |
| ------------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| Top nav label                                     | "Access"                                   | "Workspaces"                                                                                                                |
| Top-bar switcher                                  | none (as built)                            | menu with check mark (as built)                                                                                             |
| Breadcrumb                                        | Access / Members                           | Workspaces / {name} / Members                                                                                               |
| Rail rows                                         | the functions only                         | "All workspaces" first, then the current workspace's functions; "New workspace" and "Shared question library" for the claim |
| `/workspaces/all`                                 | not linked; redirects to the one workspace | the list                                                                                                                    |
| "Workspace: {name}" line                          | gone                                       | gone (the crumb and the switcher say it)                                                                                    |
| Archived, Forms and Questions columns, shared tag | hidden                                     | shown                                                                                                                       |
| Help text                                         | no "in this workspace" qualifiers          | qualifiers allowed                                                                                                          |
| Audit rows                                        | workspace column absent                    | absent too (the screen is per workspace)                                                                                    |

Promotion path: creating the second workspace (claim only) flips the label, adds the switcher, adds "All workspaces" and the crumb on the next full load; nothing else changes, because every screen already is per workspace. Archiving back to one workspace flips it back; archived workspaces stay in "All workspaces" for the claim only. No data changes, no migration.

Where create lives: "New workspace" is a rail row in the area, visible to the claim. At one workspace it is the only multi-workspace affordance shown, so the claim can create the second; owners never see it.

How the switcher fits (#1236): unchanged. It is the only chooser; the "All workspaces" row is a list, not a chooser, and its row link lands on that workspace's first function, as today.

## 5. Proposed information architecture

Applying the one-function rule. A side sheet is a row's detail and its own operations, not a screen. Filters live in the rail (§7.0 ruling 4).

### 5.1 Rail (one workspace: area "Access"; the same rows under each workspace at 2+)

| Rail row                                    | Route                                                 | One job                                                                                                      | Primary action                               | Row operations (side sheet or dialog)                   | Empty state                                           |

Give access to start."        |

Tabs: appropriate on Audit, as "Access" and "Assistant" views of one function (two tables of acts in this workspace, same readership, same filters), replacing today's two rail rows. Appropriate nowhere else in the area: People versus Access groups are different functions, list versus create are different functions, and the two settings switches are not views.

Where the wire names go: the group's plain title is "{Role}, {environments}, {forms}" (for example "Form editor, all environments, all forms"); the stored name, full name and directory name sit under Advanced on the side sheet; the create screen derives the name silently and shows it under Advanced only. Audit rows read as sentences: "Granted Form editor (all environments, all forms) to a.b@example", "Turned on: require a second approver for production". Assistant rows read as the card title ("Grant the access group {name} to {email}") with "Plan of 3 steps" grouping and the section label instead of the route.
