## 1. Purpose and how to read

Earlier handovers (design-sync-v2 batches 1 to 8 and its addendum) have been applied to the canvas: the glossary sweep, patterns, Workspace area, Site configuration, Account menu, Forms area and phone boards exist. The spec then settled more (second approval for publish, held draft publish, step-up, reset types, audit split, Move form approval). This file lists what is still wrong or missing. It is a delta, not a rebuild.

Order of work:

1. Section 3 "Content errors" first (boards that contradict the spec). Fix these even if nothing else is done.
2. Section 4 per-board changes, section 5 new boards, section 6 design-system cards.
3. Section 7 open items: draw the stated default and mark it "Default, open to revision."
4. Section 8 verification, then section 9 handback.

What wins, highest first:

1. The spec (sections 2, 3, 6, 9, 10, 12, 13, 14, 15 flow table).
2. This file.
3. design-sync-v2-addendum, then design-sync-v2, then rulings G1 to G24 (all already folded into the spec).
4. Anything on the canvas or in the design system.

Never carry forward from `plan/handover-agent-builder-and-workspaces.md` section 2 (stale): "installation administrator", "no Move screen", the per-form selection drawer, and "five open rulings". Only three UI items remain open (section 7).

Vocabulary (spec section 2, use only these): Account, Unclaimed account, Site administrator, Workspace administrator, Workspace, Environment, Access group, People in this group, Members (the list label), View forms, Edit forms, Publish forms, View responses, Erase responses, Publish, Version, Second approval, Approver, Grant, Revoke, Authors, Publishers, Response viewers, Response erasers, Requests. House rules (unchanged): no Unicode em dashes; "QCMS" in prose; addresses `@example.org`; no real secrets or passwords; unshipped behaviour keeps the `(planned)` rail suffix and the `.note` "Ruled, not yet in the product."; read each file live before changing it, send only changed files, send `canvas.json` only when boards, order or notes change; keep the installed design system and shell; `$preview` equals board size; stop and report after three refused publishes.

## 3. Content errors (fix first)

Each is a board that says something the spec forbids or contradicts.

- C1 Form-Publish, Phone-F: an ordinary prod publish is drawn as a request ("Waiting for an Approver", "Publish v4 to prod. Expires in 7 days", Approve and Reject, "You asked for this"). Spec section 6: there is no request. The account that froze the version is refused; a different holder of Publish forms for `prod` presses Publish to prod and is recorded as the approver. It stays inline; no queue, no expiry. See change list 4.12.
- C2 Approval-Requests, Phone-E: lists "Publish a draft to prod (prod-only site)" and says form requests include it. Spec section 6: that approval happens on the form only and appears neither under Approval requests nor in the workspace Requests row. Delete the row and the footnote clause on both boards.
- C3 Site-Audit: shows workspace-level rows (Workspace administrator appointed or removed, form moved, workspace renamed or archived, approval of a workspace request). Spec section 11: Site audit holds account and Site administrator acts and the shared library marking; workspace acts live in the workspace audit and a site act is mirrored there. See 4.7.
- C4 Phone-F: "the frozen version goes live then" for a prod-only held publish. Nothing is frozen until approval. Correct to "the draft is frozen as the next version and goes live when they approve".
- C5 Account-Manage, Phone-E: one "Reset sign-in" with no choice. Spec section 7: a Site administrator resets the password or the second factor. See 4.6.
- C6 Patterns-A: dialog "Add Tom Becker to Response viewers?" says "you are adding yourself" and its button says "Add to Response viewers". Make the example "Add yourself to Response viewers?" with button "Request approval". Patterns-B accessibility panel is fine.
- C7 Three labels for one state: "Needs re-confirmation" (Members, Phone-A), "Suspended after sign-in reset" (People-Person, Phone-D), "Waiting for re-confirmation" (Account-Menu, Phone-E). Use one tag "Suspended" with the cause in text ("after sign-in reset" or "after reactivation"), and the accessible name "Suspended, needs re-confirmation".
- C8 Operations-Unavailable: "Expires in 7 days" on a `prod` endpoint change. Spec section 6 gives endpoint changes no expiry (only workspace requests and held draft publishes expire). Remove it.
- C9 Wording help text "Shared library: Forms in any workspace can use questions from this workspace." Spec section 9: every Edit forms holder in every workspace sees and pins its questions; only Edit forms holders in the shared workspace edit them.
- C10 Main eyebrow "updated to the 2026-11-12 access rulings": update to "2026-11-13 and the spec docs/WORKSPACE_ACCESS.md".
- C11 Members and Phone-D sheets offer "Remove from workspace". The spec has no such act: it names Revoke (per group), Appoint and Remove Workspace administrator, and says "Workspace administrators ... Revoke the person". Treat it as a spec-silent convenience (section 7, item 4).
