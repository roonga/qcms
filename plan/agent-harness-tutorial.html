Agent harness tutorial

Companion to plan/agent-harness-learning-plan.md. Each section explains one harness concern, shows a minimal TypeScript sketch, names the plan phase where you build it, and lists the interview concepts it covers.

Read this first The code here is a teaching sketch, not a library. Provider details (event names, field names, stop reasons, caching rules, prices) change. Confirm them against the provider's current documentation before relying on them, as the plan's first Phase 1 task requires. Do the plan's design-first step for each phase before you read the matching section in full.

1. Mental model

Plan: all phases

A model turns text into text. It cannot read a file, call an API or remember last week. A harness is everything around it that makes it act: the loop, tools, permissions, memory, safety and measurement. An agent is a model plus a role (prompt, tools, goals) running inside a harness.

Build context (prompt, history, tools)→ Model call (streamed)→ Parse output, validate tool calls→ Check permissions, run tools→ Append results, record trace→ Repeat or stop
The model decides
  • Which tool to call and with what arguments
  • How to read the request
  • What to say
The harness enforces
  • Which tools exist for this user
  • That arguments are valid and allowed
  • Budgets, timeouts, approval, audit
Interview concept The core design rule: never rely on the prompt for anything that must be guaranteed. A prompt asks; code enforces. Say this early and give one example (permissions, spend limits, approval).

2. Messages and the tool protocol

Plan: Phase 1 and 2

Most chat APIs share one shape: an ordered list of messages, each holding typed content blocks. Tool use adds two block types: the model emits a tool_use block (an id, a name, JSON input), and you reply in the next user message with a tool_result block that carries the same id.

type Block =
  | { type: "text"; text: string }
  | { type: "tool_use"; id: string; name: string; input: unknown }
  | { type: "tool_result"; tool_use_id: string; content: string; is_error?: boolean };

type Message = { role: "user" | "assistant"; content: Block[] };
The invariant to protect Every tool_use must be answered by exactly one tool_result in the very next user message, or the next request is rejected. When the model emits several tool calls in one turn, all their results go back together. Cancellation, crashes and failed tools must still produce a result (an error result is fine).
Interview concepts Function calling vs structured output; why the model only requests a call and never runs it; the tool_use/tool_result pairing; why history is stateless on the server and resent each call.

3. The agent loop

Plan: Phase 2 and 3

The loop is short. The craft is in what surrounds it.

async function runTurn(ctx: TurnContext): Promise<TurnResult> {
  for (let step = 0; step < ctx.maxSteps; step++) {
    ctx.signal.throwIfAborted();
    const reply = await ctx.model.call(ctx.messages, ctx.offeredTools, ctx.signal);
    ctx.messages.push({ role: "assistant", content: reply.content });
    ctx.trace.step(step, reply.usage, reply.stopReason);

    const calls = reply.content.filter((b) => b.type === "tool_use");
    if (calls.length === 0) return { ended: reply.stopReason, steps: step + 1 };

    const rejected = calls.find((c) => !ctx.offeredNames.has(c.name));
    if (rejected) return { ended: "refused", tool: rejected.name, steps: step + 1 };

    const results = await Promise.all(calls.map((c) => runTool(ctx, c)));
    ctx.messages.push({ role: "user", content: results });
  }
  return { ended: "step_limit", steps: ctx.maxSteps };
}

Stop conditions you need

ConditionWhy it exists
No tool call in the replyThe normal ending: the model answered.
Step limitBounds cost and stops infinite tool loops.
Tool not offeredThe model named something outside its allowlist. End the turn so you stop paying for the rest of the budget.
Output length reachedA truncated reply may hold half a tool call. Never run it.
Content refusalSurface it distinctly, not as a generic failure.
Abort signalThe user cancelled or disconnected.
Wall-clock and token budgetsBound latency and spend independent of step count.

Stop-reason names differ by provider. Map each one to your own enum in the adapter so the loop never sees a provider string.

Interview concepts ReAct (reason, act, observe); why a step limit alone is not enough (cheap loops can still burn tokens; add loop detection on repeated identical calls); distinct ending codes help users and dashboards.

4. Streaming

Plan: Phase 1

Streaming sends the reply as server-sent events (SSE) while it is generated. It cuts perceived latency, but it moves complexity into your code: you assemble the final message yourself.

event: content_block_start
data: {"index":1,"content_block":{"type":"tool_use","id":"tu_1","name":"read_form","input":{}}}

event: content_block_delta
data: {"index":1,"delta":{"type":"input_json_delta","partial_json":"{\"formId\":"}}

event: content_block_delta
data: {"index":1,"delta":{"type":"input_json_delta","partial_json":"\"f_42\"}"}}

event: content_block_stop
data: {"index":1}

Illustrative shape only. Check the provider's event names and fields.

A minimal SSE reader

async function* sseEvents(body: ReadableStream<Uint8Array>) {
  const reader = body.pipeThrough(new TextDecoderStream()).getReader();
  let buf = "";
  for (;;) {
    const { done, value } = await reader.read();
    if (done) break;
    buf += value.replace(/\r\n/g, "\n"); // bug to test: a "\r" split from its "\n" across chunks
    let end;
    while ((end = buf.indexOf("\n\n")) !== -1) {
      const raw = buf.slice(0, end);
      buf = buf.slice(end + 2);
      let event = "message";
      const data: string[] = [];
      for (const line of raw.split("\n")) {
        if (line.startsWith(":")) continue;               // comment or keep-alive
        if (line.startsWith("event:")) event = line.slice(6).trim();
        else if (line.startsWith("data:")) data.push(line.slice(5).trimStart());
      }
      if (data.length) yield { event, data: data.join("\n") };
    }
  }
}

Assembling a tool call from deltas

const partial = new Map<number, string>();

// on delta with partial JSON for block i:
partial.set(i, (partial.get(i) ?? "") + delta.partial_json);

// on block stop for block i:
const text = partial.get(i) ?? "";
let input: unknown;
try { input = text === "" ? {} : JSON.parse(text); }
catch { /* malformed: answer the tool_use with an error result, never run it */ }
Things that bite Partial JSON is not parseable until the block stops. A reply cut off by an output limit leaves a half-built tool call. Errors can arrive inside a 200 stream. Servers send keep-alive pings. A closed client connection must abort the upstream call, or you keep paying for tokens nobody reads.
Interview concepts SSE vs WebSockets (SSE is one-way, plain HTTP, auto-reconnect; fine for token streams); backpressure; cancellation with AbortController; testing the parser with recorded byte-level fixtures that split events mid-line.

5. Tool design

Plan: Phase 2 and 5

Most agent failures are tool-design failures. A tool is an API whose caller is a language model, so design it like one.

interface Tool<I, O> {
  name: string;
  description: string;                 // the model reads this; write it for the model
  schema: JsonSchema;                  // validate before running
  access: { kind: "read" | "propose" };
  run(input: I, ctx: ToolContext): Promise<O>;
}

async function runTool(ctx: TurnContext, call: ToolUse): Promise<ToolResult> {
  const tool = ctx.tools.get(call.name);
  const parsed = tool?.schema.safeParse(call.input);
  if (!tool || !parsed?.success) {
    return errorResult(call.id, "Invalid arguments: " + describeIssues(parsed));
  }
  try {
    const out = await withTimeout(tool.run(parsed.data, ctx), ctx.toolTimeoutMs);
    return okResult(call.id, capSize(frame(out), ctx.maxToolOutputChars));
  } catch (e) {
    return errorResult(call.id, safeMessage(e)); // never leak stack traces or secrets
  }
}

Rules that pay off

  • Errors are results. Return validation and policy errors as readable tool results so the model can correct itself. Write them as prompts: say what was wrong and what to try.
  • Cap output size. One huge result can fill the context window. Truncate reads that are safe to truncate; paginate the rest.
  • Narrow beats broad. Many small, clearly named tools usually beat one tool with a mode flag.
  • Reads and writes differ. Read tools run immediately. Write tools should only propose (section 7).
  • Make writes idempotent. A retry or a repeated call must not repeat the effect.
  • Parallel calls. The model may emit several calls at once. Run independent ones concurrently, and return results paired by id.
Interview concepts JSON Schema for tool input; schema portability (a recursive schema that one provider rejects is a real bug class); treating tool descriptions as part of the prompt; how many tools is too many (selection accuracy and context cost both degrade).

6. Permissions and authority

Plan: Phase 4 and 7

The model holds no authority of its own. Whatever it does, it does as the signed-in user, with that user's rights. Design so that a fully compromised model still cannot exceed them.

Defense in depth: check at four points

#CheckWhy
1Offer only the tools this user may useThe model cannot call what does not exist for it.
2Offer only the action kinds (and environments) this user may useNarrows what a proposal can even name.
3Check each subject at proposal time (this form, this environment)Fails early, with a reason the model can read.
4Re-check at the route that executes the stepRights can change between proposal and confirm. This is the check that counts.
 
function offeredTools(all: Tool[], grants: Grants): Tool[] {
  return all.filter((t) => grants.allows(t.permission));
}

// One refusal ends the turn: stop spending on a model that is off-script.
const stopOnRejectedTool = (offered: Set<string>) => (calls: ToolUse[]) =>
  calls.some((c) => !offered.has(c.name));
Interview concepts Least privilege; confused-deputy problem (a privileged service tricked into acting for someone without the right); allowlist vs denylist (allowlist); offered is not the same as allowed; authorization belongs in the executing service, not in the agent.

7. Proposals and signed confirmation

Plan: Phase 5 and 6

Writes go through a human. The model proposes a plan; the harness validates it and shows a card listing every step and argument; a person confirms once; each step then runs through the ordinary route as that person. The question to answer: how do you prove that what runs is exactly what the card showed?

Model proposes plan→ Validate every step→ Sign a token over what the card shows→ Person confirms→ Each step sent with token and index→ Route verifies token, re-checks rights, runs, records 
import { createHmac, timingSafeEqual } from "node:crypto";

function canonical(v: unknown): string {          // same data, same bytes, every time
  if (Array.isArray(v)) return "[" + v.map(canonical).join(",") + "]";
  if (v !== null && typeof v === "object") {
    const o = v as Record<string, unknown>;
    return "{" + Object.keys(o).filter((k) => o[k] !== undefined).sort()
      .map((k) => JSON.stringify(k) + ":" + canonical(o[k])).join(",") + "}";
  }
  return JSON.stringify(v);
}

interface StepClaim { kind: string; argsDigest: string; environment: string }
interface Claims { proposalId: string; userId: string; steps: StepClaim[]; expiresAt: number }

function sign(claims: Claims, key: Buffer): string {
  const body = Buffer.from(JSON.stringify(claims)).toString("base64url");
  const mac = createHmac("sha256", key).update(body).digest("base64url");
  return body + "." + mac;
}

function verify(token: string, key: Buffer, now: number): Claims | null {
  const [body, mac] = token.split(".");
  if (!body || !mac) return null;
  const want = createHmac("sha256", key).update(body).digest();
  const got = Buffer.from(mac, "base64url");
  if (got.length !== want.length || !timingSafeEqual(got, want)) return null;
  const claims = JSON.parse(Buffer.from(body, "base64url").toString()) as Claims;
  return claims.expiresAt > now ? claims : null;   // inject "now": tests need a fake clock
}

Threats the token and the route must stop

Attack or failureDefense
Arguments changed between card and confirmDigest of canonical arguments is signed; the route recomputes and compares.
Token used for a different actionStep kind is signed and mapped to a route; a mismatch is refused.
Someone else confirmsUser id is signed; the route checks it against the session.
ReplayEach step can be recorded once. A recorded-step check refuses repeats; a unique constraint is the backstop for races.
Stale approvalShort lifetime, and rights re-checked at execution.
Steps run out of order, or after a failureThe server refuses step N unless steps 0 to N-1 are recorded. Do not rely on the client to stop.
Draft changed after the card was shownExpected revision on the save step; a stale revision fails the confirm.
Why this beats "ask the model to confirm" The token adds provenance, never rights. A model that is tricked into proposing something bad still produces a card a human must read, and a confirmation that only authorizes what the card showed.
Interview concepts HMAC vs signatures; canonical JSON and why key order matters; TOCTOU (time-of-check to time-of-use); idempotency keys; replay protection; single-use tokens; constant-time comparison; saga-style partial failure (record per-step outcomes: done, failed, not-run).

8. Context management

Plan: Phase 9

The context window is a budget, and every tool result spends it. Decide what stays, what goes, and what must never be cut.

TechniqueUse it forDanger
Token budgetKnow how full you are before each call.Counting by characters misleads. Use the provider's counter or a margin.
Size-cap tool outputStop one result flooding the window.Never cap data the model must send back whole.
Evict old read resultsDrop stale tool results, leave a stub.Force a fresh read before any write that depends on it.
Summarize (compact) old turnsLong tasks.Summaries lose ids and details. Keep a structured list of ids and decisions outside the prose.
Retrieve on demandLarge stores.Adds latency and a retrieval failure mode.
The wholesale-save trap If a save tool replaces the whole object, truncating that object in context and sending it back silently deletes content. Either never truncate it, or use a patch tool the harness applies to a fresh read. The plan builds the patch tool for exactly this reason. 
function evictOldReads(messages: Message[], keepLast = 2): Message[] {
  const reads = indexToolResults(messages, "read_");       // [{ msgIdx, blockIdx, subjectId }]
  for (const r of reads.slice(0, Math.max(0, reads.length - keepLast))) {
    replaceResult(messages, r, "[evicted: call the read tool again before writing]");
    markNeedsReread(r.subjectId);                          // save is refused until re-read
  }
  return messages;
}

Prompt caching

Providers can cache a prompt prefix: repeated calls that start with identical bytes are cheaper and faster. Order matters (typically tools, then system prompt, then messages), and a single changed byte early in the prefix invalidates everything after it. So: keep the system prompt and tool list byte-stable, put volatile content at the tail, and measure the hit rate from the usage counters. Eviction changes the middle of the conversation, so decide where your cache breakpoints sit relative to it.

Interview concepts Context window vs output limit; prompt caching economics (cache write costs more than a plain read, cache read costs far less); lost-in-the-middle; RAG vs long context; compaction trade-offs; why deterministic prompt construction (stable key order, no timestamps) matters.

9. Untrusted data and prompt injection

Plan: Phase 9 and 10

Anything a user authored (a form title, a ticket body, a web page, a file) can contain instructions aimed at the model. This is indirect prompt injection. The model cannot reliably tell data from instructions, so you cannot fix this inside the prompt.

Mitigations (reduce odds)
  • Fence data and label it as data
  • Tell the model not to follow instructions in data
  • Strip or flag suspicious patterns
Controls (guarantee limits)
  • The model holds no authority
  • Writes need a human-confirmed card showing true arguments
  • Tools scoped to the user's rights
  • No tool exposes data the user may not see

The test that matters: script a model that obeys the injection, and assert the harness still limits the damage (the card shows the real arguments and nothing runs without confirmation).

The risky combination An agent is in trouble when it has all three: access to private data, exposure to untrusted content, and a way to send data out. Remove one and the worst case shrinks a lot.
Interview concepts Direct vs indirect injection; jailbreak vs injection; confused deputy; mitigation vs control; data exfiltration channels (links, images, tool calls); why "ignore previous instructions" filters fail; tool descriptions from third-party servers are themselves an injection surface.

10. Reliability

Plan: Phase 1 and 3 
async function withRetry<T>(
  fn: (signal: AbortSignal) => Promise<T>,
  o: { max: number; baseMs: number; capMs: number; signal: AbortSignal },
): Promise<T> {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn(o.signal);
    } catch (e) {
      if (!isRetryable(e) || attempt >= o.max) throw e;
      const ceiling = Math.min(o.capMs, o.baseMs * 2 ** attempt);
      const wait = retryAfterMs(e) ?? Math.random() * ceiling;   // full jitter
      await sleep(wait, o.signal);
    }
  }
}
  • Retry only what is safe to retry: rate limits (429), overload and 5xx on the model call. Honor a Retry-After header.
  • Never blindly retry a write. Use an idempotency key so a repeat is a no-op.
  • Timeouts everywhere: connection, first token, total, and each tool.
  • Do not retry after streaming has started unless you can discard the partial output cleanly.
  • Provider errors can arrive after a tool call. Map them to retryable or permanent and keep the history valid.
  • Spend limits: per-turn, per-user and per-project caps enforced by the harness.
Interview concepts Exponential backoff with jitter (and why jitter stops thundering herds); circuit breaker; idempotency keys; at-least-once vs exactly-once (you get at-least-once plus idempotency); timeouts vs deadlines; graceful degradation to a cheaper model.

11. Sessions, state and resume

Plan: Phase 3 and 9

Treat the conversation as an append-only log of events. Rebuilding state is replaying the log; resuming after a crash is replaying it and repairing the tail.

function repairTail(messages: Message[]): Message[] {
  const last = messages.at(-1);
  if (last?.role !== "assistant") return messages;
  const open = last.content.filter((b) => b.type === "tool_use");
  if (open.length === 0) return messages;
  const results = open.map((c) => errorResult(c.id, "Interrupted before this tool finished."));
  return [...messages, { role: "user", content: results }];   // no orphaned tool_use
}
  • Persist after every completed step, not at the end.
  • Decide what is stored (messages, step outcomes, prompt version) and what must not be (secrets, raw user data you do not need).
  • A cancel mid-stream must leave history valid and resumable.
  • Give the model back the outcome of anything it proposed that a person later confirmed or declined.
Interview concepts Event sourcing; checkpointing; durable execution; stateless server with client-resent history vs server-side sessions (trade-offs: simplicity and size caps vs resumability and richer context).

12. Observability and audit

Plan: Phase 1 (trace) and 6 (audit)

You cannot debug an agent from its final answer. Record one structured turn record per turn and one audit row per executed step.

interface TurnRecord {
  turnId: string; sessionId: string; userId: string;
  promptVersion: number;
  offeredTools: string[];
  steps: number; stopReason: string;
  inputTokens: number; outputTokens: number; cacheReadTokens: number;
  toolCalls: { name: string; ok: boolean; ms: number }[];   // names and counts, not arguments
  providerError?: { retryable: boolean; status?: number };
  startedAt: number; durationMs: number;
}
  • Log shape, never content. Counts, ids, versions and timings. Not user text, not model reasoning, not tool results that were built from user input.
  • Version your prompt and log the version, so a behavior change maps to a change you made.
  • Answer "why did it do that?" from records: who asked, what was offered, what was proposed, who confirmed, what ran.
  • Trace spans per model call and per tool run give latency breakdowns.
Interview concepts Structured logging; tracing (spans); PII handling; audit trail vs debug log (different readers, retention and content); prompt versioning; cost attribution per user or feature.

13. Evaluation

Plan: Phase 10 and 11

Three groups of checks answer three different questions. Keep them separate.

GroupQuestionHowPass rule
Deterministic harness testsIs my code correct?Scripted fake model, injected clock and ids, recorded stream fixturesAlways passes. Run in CI.
Contract testsDoes the real provider still accept my requests and match my parser?A few real calls, run on demandPasses or the adapter needs a fix.
Live evalsDoes the model plus my prompt and tools do the job?Real model, many trials, named gradersA pass-rate threshold, never 100%.

Why trials, and how many

Model output varies between runs, even at temperature 0. One run proves little. Run each task many times (30 or more for the tasks you care about), record pass rate, steps and cost, and report spread.

Comparing two versions: pair the tasks

Run version A and version B on the same tasks, then look at the per-task differences. Pairing removes task difficulty as noise, so you need far fewer trials to see a real change.

// a[i], b[i] = pass rate of task i under version A and B (0..1)
function pairedBootstrap(a: number[], b: number[], iters = 10_000): [number, number] {
  const diffs = a.map((x, i) => b[i] - x);
  const means: number[] = [];
  for (let k = 0; k < iters; k++) {
    let s = 0;
    for (let j = 0; j < diffs.length; j++) s += diffs[Math.floor(Math.random() * diffs.length)];
    means.push(s / diffs.length);
  }
  means.sort((x, y) => x - y);
  return [means[Math.floor(iters * 0.025)], means[Math.floor(iters * 0.975)]]; // 95% interval
}
// If the interval contains 0, you have not shown an improvement.

Two ways to read k trials

  • pass@k: at least one of k tries succeeds. Fits "can it ever do this?".
  • pass^k: all k tries succeed. Fits "can I rely on it?". It falls fast as k grows.
Grader traps A model judging a model is cheap and noisy: it prefers longer answers, favors its own style, and varies run to run. Prefer programmatic graders (does the draft validate, does it contain the reused id, is the sentinel absent). Use a judge only for what code cannot check, and sample its verdicts by hand. Give the harness a scripted approver so evals do not wait on a person.
Interview concepts Why temperature 0 is not deterministic; golden sets and regression suites; overfitting prompts to a small eval set; contamination; confidence intervals; paired vs unpaired comparison; cost per success as a metric; offline vs online evaluation.

System design prompts

Practice each one out loud for ten minutes: clarify requirements, sketch components, name the failure modes, say how you would measure it.

A. An agent that issues refunds
  • Authority: model proposes, rules in code decide, humans approve above a threshold.
  • Idempotency key per refund; audit row per action; PII kept out of logs and prompts.
  • Failure modes: duplicate refund, injection in a ticket body, approval of one amount and execution of another.
  • Measure: wrong-refund rate (target zero), escalation rate, cost per ticket.
B. A long-running research agent
  • Loop with budgets (tokens, time, money) and loop detection.
  • Context: summarize, keep a structured notes store, retrieve on demand.
  • Durable state: checkpoint each step, resume after a crash, repair the history tail.
  • Measure: task success on a fixed set, cost per success, drift over long runs.
C. An eval system for a support agent
  • Three groups: deterministic, contract, live. A scripted approver. Programmatic graders first.
  • Trial counts, paired comparison, a dashboard of pass rate with intervals, a cost cap.
  • Failure modes: overfitting to the eval set, flaky graders, silent provider changes.
