# Environments and workspaces

**Status:** decided, not built. The four rulings in section 2 are the Code Owner's, taken on 2026-09-25 and recorded verbatim in issue #995. **Two of them are since amended**, and section 2 says which. Seven further questions are answered in section 6; what is still open is section 7, where one entry carries the Code Owner's leaning rather than a decision. This document is the working record behind **ADR-40** (environments) and **ADR-41** (workspaces) in `docs/adr/core.md`, **SEC-14** in `docs/SECURITY_DESIGN.md` section 5a, and the operator recipe in `docs/deploy-ingress.md`. Nothing here is a decision of its own: where the rulings do not reach, section 7 records the question rather than answering it.

**Order:** environments first, workspaces second. They land independently.

## 1. The problem

QCMS is single-tenant (ADR-04) and has no notion of an environment. A form has one mutable draft (`form_drafts`, one row per form) and immutable published versions (`form_versions`, frozen by the `form_versions_reject_update` trigger in migration 0001), and `getFormBySlug` plus `getLatestPublishedVersion` resolve every public link to the newest published version. A session pins the version it resolved at start and never migrates (ADR-07, invariant I4).

Two things are missing, and they are unrelated to each other:

1. **There is no way to change a form, try it with real respondents, get it approved, and only then make it live.** Publishing is the only way to get a definition onto the serving path, and publishing is immediately live for everyone. The closest thing to a rehearsal today is the admin draft preview (`POST /forms/{id}/draft/preview`), which is a dry run in one browser and involves no respondent, no session and no webhook.
2. **There is no way for two groups inside one organisation to share an installation without seeing each other's forms and questions.** Every authenticated administrator sees the whole library; `user.role` carries `admin` for everyone and nothing reads it for an authorization decision (SEC-3, issue #179).

Multi-tenancy was deliberately not built and stays out (R7). Neither of the two gaps above is a request for it.

## 2. The rulings (Code Owner, 2026-09-25, issue #995)

Verbatim, so that the amendments below are visible as amendments rather than as a quietly edited record.

1. **Environments are release states over immutable versions, in one deployment.** A form version is shared across environments; what varies is which version is released to `test` and which to `prod`. Promotion is a release record (who, when, which version, from which environment), never a copy, so form ids and version numbers stay continuous (R6). Approval is recorded on the release.
2. **Isolation level: a Postgres schema per environment for the data plane.** Control-plane tables (forms, versions, questions, links, admin identity) stay in `public`; the session, answer ledger, submission, delivery and outbox tables exist per environment (`env_test`, `env_prod`) and the API connects with the environment's search path, so Postgres enforces the boundary and no per-query filter can be forgotten. Backups, erasure, exports, the restore drill and observability are per environment. An existing installation migrates to one `prod` environment with its current data.
3. **Test is reachable through secure links only, no public test address.** `/f/{slug}` stays prod. A secure link's server-side row carries the environment as well as the ADR-39 target version. Test webhooks and the outbox are per environment, so a test submission can never fire a production endpoint. In addition the design must let an operator protect test (and any unreleased version) at the network layer: a distinct hostname or listener for test traffic, so ingress and firewall rules can restrict it to an allowlisted network, VPN or identity-aware proxy; per-environment egress rules for webhooks; the draft preview never leaves the admin. Defence in depth: network, then link, then schema.
4. **Workspaces are an authorisation grouping, not tenancy.** A workspace owns forms and questions (with an optional shared workspace for org-wide questions any form may pin); admins are members with a role (owner, editor, approver, viewer), which is where RBAC (issue #179) lands; slugs stay unique per installation; release to prod requires an approver in the workspace who is not the author, configurable per workspace. One operator, one configuration, one identity store, authorisation between workspaces rather than isolation guarantees. ADR-04's Note is updated to say exactly that.

**Two amendments, both 2026-09-26.** Ruling 2 above is superseded in two places and stands everywhere else:

- **Q20 supersedes "control-plane tables ... stay in `public`".** They live in a named schema, `control`. `public` is left empty and off every search path. Section 3 is the layout.
- **Q22 withdraws "an existing installation migrates to one `prod` environment with its current data".** This is green field. Section 4 is what that removes.

Ruling 3 gains one addition rather than an amendment: **Q21** puts the environment's name in the path of every non-prod address, which ruling 3's "no public test address" already implied but did not state. Its substance is unchanged: there is no anonymous entry to a non-prod environment, `/f/{slug}` stays prod-only, and `/<env>/f/{slug}` is not a route.

## 3. The target model

Every QCMS object lives in a schema QCMS named. `public` is left empty, off every search path, with `CREATE` on it granted to nobody.

```
                        CONTROL PLANE - schema "control", one copy
 +--------------------------------------------------------------------------+

 |      |  owns                          verification / twoFactor /          |
```

Four properties are worth reading off the picture rather than deriving them later:

- **One version history.** `form_versions` sits in `control` and every environment points at it. Promotion writes a `form_releases` row and copies nothing, which is what keeps `formId`, `questionId` and version numbers continuous (R1, R6, ADR-02, ADR-18).
- **The only schema boundary is the environment.** Workspaces are entirely inside `control` and are enforced by API-layer checks (SEC-3). A workspace is not a schema and never becomes one, because it is not an isolation guarantee.
- **Three foreign keys cross, and the first two are load-bearing.** `sessions_form_version_fk` into `control.form_versions` and `sessions_link_id_secure_links_link_id_fk` into `control.secure_links` are what make "shared version, separate data" expressible in the database rather than in a convention. The third, `webhooks_form_id_forms_form_id_fk` into `control.forms` (migration 0006), is the price of putting `webhooks` on the per-environment side, which Q3 settled. The remaining four foreign keys stay inside one schema: `answers_session_id_sessions_session_id_fk`, `submissions_session_id_sessions_session_id_fk`, `webhook_deliveries_outbox_id_outbox_id_fk` and `webhook_deliveries_webhook_id_webhooks_webhook_id_fk`.
- **`prod` is the unprefixed address shape and every other environment is prefixed.** A non-prod link reads `/test/l/{token}`, so it is legible as non-production before anybody clicks it, and there is no unprefixed non-prod address anywhere. The environment is still not in the token: the path names it, the row decides it, and a token under the wrong prefix is refused (Q21).

### The guards every environment carries

The seven data-plane tables are not bare tables, and an environment created without their guards is an environment whose ledger is mutable. The list is **derived** rather than remembered: `grep` the migration SQL for each of the seven table names and take every `CREATE TRIGGER`, `CONSTRAINT ... CHECK`, `CONSTRAINT ... UNIQUE` and `CREATE INDEX` that names it. That yields twelve objects, and none is optional:

| Kind     | Objects                                                                                                                                                                                                       | From             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| Triggers | `answers_reject_update`, `answers_reject_delete`                                                                                                                                                              | 0001, 0004       |
| CHECKs   | `answers_retraction_value`, `webhook_deliveries_snippet_requires_attempt`, `outbox_redacted_payload_has_no_answers`                                                                                           | 0009, 0015, 0016 |
| UNIQUE   | `webhook_deliveries_event_webhook_uq`                                                                                                                                                                         | 0007             |
| Indexes  | `sessions_status_expires_at_idx`, `answers_session_question_answered_at_idx`, `outbox_delivery_idx`, `webhook_deliveries_due_idx`, `outbox_payload_retention_idx`, `webhook_deliveries_snippet_retention_idx` | 0000, 0007, 0018 |

Primary keys ride the `CREATE TABLE`. The two trigger **functions** stay single, in `control`: a trigger in `env_test` executes `control.answers_reject_update()`, so N triggers share one body.

**This is the list the generator emits, not a list an operator re-creates.** Since Q22 there is no existing installation to move, so the twelve objects are created from the migrations for `env_test` and `env_prod` on a fresh database, and again by the environment command for any environment created later. **The first draft of this document listed four of the twelve**, which is exactly why the list is derived and why the durable form is code: task 064 emits the per-environment set from one schema module, and this table is what that emission is checked against. An environment missing `answers_reject_delete` has an erasable ledger; one missing `webhook_deliveries_event_webhook_uq` fans a webhook out twice. Both are silent.

### The reserved environment names

Because the environment set is configurable (Q1) and the environment's name is its URL prefix (Q21), the name is a URL path segment and a Postgres identifier at once. The environment command therefore refuses a name that is not a legal path segment, that does not fit `env_<name>` inside Postgres's 63-byte identifier limit, or that collides with a route either surface already serves at its root. Derived from disk at this base, the collision set is:

| Source                                              | Reserved                                                                                                   |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Portal root segments (`apps/portal/app`)            | `f`, `s`, `l`, `appearance`, `done`, `expired`, `link-error`, plus Next's own `_next`                      |
| API route paths and mount prefixes (`apps/api/src`) | `forms`, `questions`, `sessions`, `erasures`, `outbox`, `health`, `ready`, `internal`, `admin`, `api`      |
| The address rule itself                             | `prod`, because prod is the unprefixed shape and a prefixed `prod` would be a second spelling of one thing |

As with the guard list, the durable form is a check derived from the route tables rather than a literal list in a source file, for the reason `CONTRIBUTING.md` gives about derived sets: a hand-kept copy goes stale the first time somebody adds a root route. Task 064 owns the derivation and the refusal.

## 4. Green field: there is no migration

**Code Owner ruling of 2026-09-26 (Q22).** Ruling 2 originally ended "an existing installation migrates to one `prod` environment with its current data". That clause is **withdrawn**. There is no existing installation, so this document carries no migration path, and the section that used to hold one is this paragraph.

What that removes, named so that a reader of the earlier ruling text knows which half stands: no `ALTER TABLE ... SET SCHEMA` of live tables, no backfill of one release row per already-published form, no defaulting of existing secure links to `prod`, no rollback stance about a half-moved database, and no deployment-ordering concern about doing the schema move and the search-path switch in one release. Everything else in ruling 2 stands.

What it leaves is simpler. A fresh database gets `control`, `env_test`, `env_prod`, `reporting_test` and `reporting_prod` **from the migrations alone**: the control-plane tables in `control`, the seven data-plane tables with all twelve guards in each environment schema, one view set per environment, and `public` left empty and off every search path. The drizzle chain in `packages/db/migrations` stays **append-only**, as ADR-18's discipline requires and as `migration-chain.test.ts` and `migrations.test.ts` check: a new migration creates the schemas and the tables in their final homes. Resetting the chain to a fresh baseline is not asked for and is not done.

The one thing green field does not remove is the **restore drill**. `docs/backup-restore.md` opens with the claim that a backup nobody has restored is not a backup, and that is as true of a database created in this shape as of one migrated into it; `pnpm qcms:drill-restore` covering every environment in the live set is task 067's, and it is the reason the schema layout has to be something a `pg_dump` and a restore reproduce faithfully.

## 5. What the network design adds

Recorded here only as the shape; the control is SEC-14 (`docs/SECURITY_DESIGN.md` section 5a) and the recipe is the "Restricting the test environment" section of `docs/deploy-ingress.md`.

- **Two handles, not one.** A **hostname** per non-prod environment, and the **`/<env>/` path prefix** on every one of its addresses (Q21). The host is primary, because it is what a network-layer firewall and a DNS split can act on without reading HTTP at all; the path is the second handle, available to an ingress or an L7 firewall as a rule of its own, and it is also what makes a link legible to the person holding it. Both remain because they fail independently: a host rule survives a proxy that rewrites paths, and a path rule survives a wildcard certificate or a shared hostname somebody consolidated onto.
- **Anonymous entry absent from a non-prod surface by ADR-09 mount** rather than by a handler check, which is the half that survives a misconfigured edge. **It is designed and not built** (anonymous and secure-link entry are one route today), and it is task 066's mount work in section 8, so until it lands the edge rules are the whole of this layer.
- An **allowlist** on the non-prod hostname: source network, VPN or identity-aware proxy. The public address is prod only, and `/<env>/f/{slug}` is not a route at all.
- **Per-environment egress** for webhook delivery, stating in firewall vocabulary what the schema split already guarantees.
- A **firewall rule table** by source, destination, port and environment, in SEC-14 and nowhere else, using only ports from `docs/PORTS.md` (R8).
- **What it does not buy:** an insider already on the allowed network, and a leaked non-prod link, are the link layer's problem; a handler that queries the wrong environment is the schema layer's. Defence in depth in that order, network then link then schema.

## 8. Task breakdown

Stage 9, Phase 4. None of this gates launch (038), and no existing task is renumbered. **Task 063 (link version targeting) and task 066 touch the same `secure_links` row**, so whichever lands second rebases onto the other rather than re-deciding the row's shape; ADR-39 now carries a Note saying so.

Gates are named per task. Every task runs `pnpm verify`. A task touching Docker-backed suites also runs the forced run (`pnpm exec turbo run test --force`, confirming `Cached: 0`) and, where it changes the boot environment, `QCMS_PORT_SEAT=<0-9> pnpm up:e2e`. A task touching `apps/portal`, `apps/admin` or `@roonga/qcms-ui` also runs `QCMS_PORT_SEAT=<0-9> pnpm verify:browser`, detached.

### Phase A - environments

**064 - Environment model, the named schema layout, and the environment command.** Depends on 038; blocked on Q17 and on the confirmation of Q2's process half, whose recorded leaning it may follow provisionally; Q1, Q3, Q12, Q20, Q21 and Q22 are answered; Q9 settles during it.

Deliverables: the `environments` table; an **append-only migration** that creates `control`, `env_test`, `env_prod` and a `reporting_<env>` view set per environment in their final homes, with the control-plane tables in `control` and the seven data-plane tables plus all twelve guards of section 3 in each environment schema, leaving `public` empty and off every search path with `CREATE` on it granted to nobody; the `env_<name>, control` search-path selection in the API and its configuration; the `docs/operations.md` role recipe rewritten to grant **per named schema** rather than `IN SCHEMA public`, with the same rewrite in the SEC-10 paragraph of `docs/SECURITY_DESIGN.md` section 7 and in `docs/reporting-view.md`'s sentence about `qcms_reporting` holding nothing on `public`; and `packages/db` schema modules split so the **generator** emits the per-environment set, which is what makes the twelve-guard list a consequence of the code rather than a paragraph to maintain.

Three further deliverables are easy to lose. From Q1: an **operator command** that creates and drops an environment under the migration role, in the `qcms-db-migrate` / `qcms:create-admin` family, with no HTTP surface and a refusal when run as `qcms_app` (the shape `qcms:reset-2fa` already uses, SEC-10), **refusing a reserved or malformed name** per section 3. From Q1 again: **the enumeration rule**, that every per-environment job, export, backup, retention pass, reporting view and telemetry attribute reads the live set rather than a compiled-in pair. From Q20: **better-auth's Drizzle adapter verified against a non-default schema**, because the five auth tables move to `control` with everything else and the library validates the Drizzle schema on the first request through its handler and refuses to run on a mismatch (`apps/api/src/features/auth/instance.ts` maps its five models explicitly). That verification is a real risk item rather than a formality: it is the one table group in this change whose owner is a third party.

Exit criteria: (1) **a fresh database is created in the target shape** and every guard is present in every environment in the live set, asserted against a real Postgres: `control` holds the twelve control-plane tables, each `env_<name>` holds the seven data-plane tables with all twelve guards, and **`public` holds no QCMS object at all**; (2) `public` is on no search path and `CREATE` on it is granted to nobody; (3) **an unqualified data-plane name resolves only inside the connection's own environment schema**, asserted with a positive control in each environment, and no query helper in `@roonga/qcms-db` emits a schema-qualified data-plane name, asserted from the source so no code path can reach across; (4) `qcms_app` can read and write every environment in the live set and can create none; (5) creating and dropping an environment works from the operator command, is refused as `qcms_app`, and refuses every reserved name in section 3 and a name too long for `env_<name>`; (6) a third environment created by that command is reached by every per-environment job without a code change; (7) better-auth signs in, enrols a second factor and verifies a recovery code against its tables in `control`, asserted against a real Postgres rather than by reading the adapter; (8) the drizzle chain is unbroken and no released migration file is edited.

**Criterion 3 is worded deliberately and the first draft was wrong.** "A statement under one search path cannot read the other's tables" is unsatisfiable while criterion 4 holds: `search_path` is a resolution default, so a schema-qualified statement crosses. What the design actually buys is that there is no filter to forget, which is a property of **resolution** plus the absence of any qualified data-plane name in the query layer, and that is what criterion 3 now asserts. Whether the schema is also a privilege boundary is Q17, and if the Code Owner rules for a role per environment then criteria 3 and 4 both tighten in that change rather than in this one.

Gates: `pnpm verify`, forced Docker-backed run, `pnpm up:e2e`.

**065 - Release records and promotion.** Depends on 064; Q4, Q5, Q6 settle during it.

Deliverables: `form_releases`; the release and promotion API on the admin surface; the admin screens that show what is released where and promote between environments; release resolution replacing "newest published version" on the respondent path. No backfill: green field (Q22) means there is no already-published form to write a first release row for, so the first row any form gets is written by a real release.

Exit criteria: (1) a form version released to `test` and not to `prod` is served in `test` and not in `prod`; (2) promotion writes a row and copies nothing, with the form id and version number unchanged; (3) a release never re-pins a live session (ADR-07, I4), asserted with a session open across a release; (4) the release history answers who released what, when, from where, and with whose approval; (5) the admin states which environment each screen is showing.

Gates: `pnpm verify`, `pnpm verify:browser`, forced Docker-backed run.

**066 - Environment-scoped secure links and test entry.** Depends on 064 and 065; coordinates with 063; Q11, Q16 settle during it.

Deliverables: the environment on the `secure_links` row; minting a link for an environment, **required on the API** and taken from the Q6 switcher in the admin (Q19); redemption starting a session in that environment; **the `/<env>/` path prefix on every non-prod address, on the portal and the API alike, with `prod` unprefixed** (Q21), and the refusal of a token presented under the wrong prefix; the portal's non-prod host shape; the SEC-14 operator recipe exercised.

**And the mount work SEC-14 rests on, which does not exist today and is this task's, not an existing property.** Anonymous and secure-link entry are one API route (`POST /sessions` on the `public` group, discriminated by a body refine), so three pieces have to be built for the 404-not-403 claim to be true: each environment's respondent surface as its own mountable group (which is Q2's recorded shape); **anonymous entry split from secure-link entry** so the two can ride different mount decisions; and the portal not serving its `/f` segment on the test host, which is portal routing and not an API mount. The split changes ADR-09's Note that four groups ride three mount flags, so **this task amends that Note**, and ADR-09 already carries a forward pointer saying so.

Exit criteria: (1) a prod link starts a prod session and a test link a test session, with the token format unchanged; (2) **a non-prod link's address carries the environment's name as its first segment and a prod link's does not**, asserted on both surfaces, and the same token presented under the wrong prefix is **refused** rather than redirected or honoured; (3) there is no anonymous entry to a non-prod environment on any address, asserted as a `404` and not a `403` (ADR-09), which requires the split above and is therefore a criterion about built behaviour rather than about configuration, and `/<env>/f/{slug}` does not exist; (4) revocation, expiry, one-time consumption and the challenge behave per environment as they do today, **and the closed state behaves as Q18 rules**, since `forms.status` is one control-plane column and cannot be per environment without a ruling; (5) a prod respondent's address and experience are unchanged; (6) ADR-09's Note is amended in the same PR.

Gates: `pnpm verify`, `pnpm verify:browser`, `pnpm up:e2e`.

**067 - Per-environment delivery, retention and operations.** Depends on 064 and 065; Q6, Q7, Q8, Q9, Q10, Q11 settle during it.

Deliverables: the outbox, endpoints and deliveries per environment; erasure and export per environment, with the environment in the **export filename and in no column** (Q8); a `reporting_<env>` view set per environment replacing the single `reporting` schema, with `docs/reporting-view.md`'s `qcms_reporting` recipe becoming per environment (Q10); `docs/backup-restore.md`, `docs/erasure.md` and `docs/operations.md` updated; the environment as an allowlisted telemetry attribute (SEC-13); the restore drill covering `control` and every environment schema in the live set.

**Scheduler ownership is not settled here and this task does not assume it.** The outbox deliverer and the retention sweep start once per process under `config.mount.internal` (`apps/api/src/main.ts`), and `docs/deploy-enterprise.md` section 5 calls that process a scheduler singleton whose duplication buys nothing. "Running per environment" is therefore either **one singleton iterating the live set** or **one process per environment**, and which of the two is decided by Q2, not by this task. What this task owns either way is that each pass claims and delivers under exactly one environment's search path, that no pass ages a row in another environment, and that the enumeration reads the live set.

Exit criteria: (1) a test submission cannot reach a prod endpoint, asserted against a real Postgres rather than argued; (2) backup, restore and the drill cover every environment in the live set, including one created after the feature shipped; (3) an erasure and an export name their environment and touch no other, and an export's environment is in its filename while its columns are byte-for-byte what they are today; (4) the retention sweep runs per environment and ages nothing across one, under whichever ownership Q2 settles; (5) a trace can be attributed to an environment, and the attribute names no respondent.

Gates: `pnpm verify`, forced Docker-backed run, `pnpm up:e2e`, `pnpm qcms:drill-restore`.

### Phase B - workspaces

**068 - Workspace model and ownership of forms and questions.** Depends on 038; independent of phase A; Q14 and Q15 settle during it.

Deliverables: `workspaces`; the workspace reference on `forms` and `questions`; the shared workspace and the publish-time rule on which question versions a form may pin; the unique constraint on `forms.slug` that does not exist today, which green field makes a plain constraint rather than a data fix; and the seeding of a first workspace so a bootstrapped installation has one to author in.

Exit criteria: (1) a form or question cannot exist without exactly one workspace, enforced by the column rather than by a backfill; (2) publish refuses a pin to a question owned by another non-shared workspace; (3) slugs are unique installation-wide, enforced by the database and not by authoring convention; (4) no published version changes and no public address moves.

Gates: `pnpm verify`, forced Docker-backed run.

**069 - Workspace membership, roles and API enforcement.** Depends on 068. Q12 is answered: the installation-wide claim sees all and edits none without membership, and that account shape is part of the matrix this task extends.

Deliverables: `workspace_members` and the four roles; enforcement in the API layer per route group and per route (SEC-3, never a BFF, never only the UI); the membership screens; the SEC-3 authorization matrix in `docs/SECURITY_DESIGN.md` section 3.2 extended with the four roles **and** with the installation-wide-claim-without-membership column the Q12 answer creates, with `apps/api/e2e/security/01-authorization-matrix.e2e.ts` and `matrix-coverage.e2e.ts` moving with it in the same change, since that test parses the table's Action column by exact wording.

Exit criteria: (1) each of the four roles is probed against every authoring, response and configuration action; (2) an administrator with no membership and no installation-wide claim reaches nothing in that workspace, and one **with** the claim reads and exports but cannot author, publish or release there; (3) approver-not-author refuses the claim holder's own release too; (4) enforcement is in the API and a BFF or UI bypass reaches a refusal, asserted; (5) the section 3.2 table and the probe inventory stay in step, which `matrix-coverage.e2e.ts` already enforces.

Gates: `pnpm verify`, `pnpm verify:browser`, forced Docker-backed run.

**070 - Approver-not-author release approval.** Depends on 065 and 069; Q13 settles during it.

Deliverables: the per-workspace setting; the check at release to `prod`; the approval recorded on the ADR-40 release record; the admin flow that asks for it.

Exit criteria: (1) with the setting on, a release to `prod` by the version's author is refused, and by a different approver in the same workspace succeeds; (2) the approval is on the release row and is readable in the history; (3) with the setting off, behaviour matches 065 exactly; (4) an approver from another workspace is refused.

Gates: `pnpm verify`, `pnpm verify:browser`.

## 9. Non-goals

Multi-tenancy (R7, ADR-04). A second database, a second deployment, or replication between environments. Per-workspace configuration, theming or ports. A workspace segment in any URL. An environment visible in a token. Copying a version between environments, in any form: promotion is a record, and a copy would break R1, R6 and ADR-18 at once.
