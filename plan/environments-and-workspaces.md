# Environments and workspaces

**Status:** decided, not built, and **fully decided**. The four rulings in section 2 are the Code Owner's, taken on 2026-09-25 and quoted verbatim; **ruling 2 is since amended in three places**, and section 2 says which. Section 6 carries **all thirty-one questions** the design raised, each with its answer and where that answer landed: twenty-three from writing it down, and eight more from the Code Owner's two scenario tests of 2026-09-26, beside five findings those tests confirmed rather than numbered. Section 7 records the tests, because **four of their findings changed a decision** rather than filling a gap, and is otherwise empty. This document is the working record behind **ADR-40** (environments) and **ADR-41** (workspaces) in `docs/adr/core.md`, **SEC-14** in `docs/SECURITY_DESIGN.md` section 5a, and the operator recipe in `docs/deploy-ingress.md`. Nothing here was decided by this document: every answer in section 6 cites the ruling that gave it.

**Order:** environments first, workspaces second. They land independently.

## 1. The problem

QCMS is single-tenant (ADR-04) and has no notion of an environment. A form has one mutable draft (`form_drafts`, one row per form) and immutable published versions (`form_versions`, frozen by the `form_versions_reject_update` trigger in migration 0001), and `getFormBySlug` plus `getLatestPublishedVersion` resolve every public link to the newest published version. A session pins the version it resolved at start and never migrates (ADR-07, invariant I4).

Two things are missing, and they are unrelated to each other:

1. **There is no way to change a form, try it with real respondents, get it approved, and only then make it live.** Publishing is the only way to get a definition onto the serving path, and publishing is immediately live for everyone. The closest thing to a rehearsal today is the admin draft preview (`POST /forms/{id}/draft/preview`), which is a dry run in one browser and involves no respondent, no session and no webhook.
2. **There is no way for two groups inside one organisation to share an installation without seeing each other's forms and questions.** Every authenticated administrator sees the whole library; `user.role` carries `admin` for everyone and nothing reads it for an authorization decision (SEC-3, issue #179).

Multi-tenancy was deliberately not built and stays out (R7). Neither of the two gaps above is a request for it.

## 2. The rulings (Code Owner, 2026-09-25, issue #995)

Verbatim, so that the amendments below are visible as amendments rather than as a quietly edited record.

1. **Environments are release states over immutable versions, in one deployment.** A form version is shared across environments; what varies is which version is released to `test` and which to `prod`. Promotion is a release record (who, when, which version, from which environment), never a copy, so form ids and version numbers stay continuous (R6). Approval is recorded on the release.
2. **Isolation level: a Postgres schema per environment for the data plane.** Control-plane tables (forms, versions, questions, links, admin identity) stay in `public`; the session, answer ledger, submission, delivery and outbox tables exist per environment (`env_test`, `env_prod`) and the API connects with the environment's search path, so Postgres enforces the boundary and no per-query filter can be forgotten. Backups, erasure, exports, the restore drill and observability are per environment. An existing installation migrates to one `prod` environment with its current data.
3. **Test is reachable through secure links only, no public test address.** `/f/{slug}` stays prod. A secure link's server-side row carries the environment as well as the ADR-39 target version. Test webhooks and the outbox are per environment, so a test submission can never fire a production endpoint. In addition the design must let an operator protect test (and any unreleased version) at the network layer: a distinct hostname or listener for test traffic, so ingress and firewall rules can restrict it to an allowlisted network, VPN or identity-aware proxy; per-environment egress rules for webhooks; the draft preview never leaves the admin. Defence in depth: network, then link, then schema.
4. **Workspaces are an authorisation grouping, not tenancy.** A workspace owns forms and questions (with an optional shared workspace for org-wide questions any form may pin); admins are members with a role (owner, editor, approver, viewer), which is where RBAC (issue #179) lands; slugs stay unique per installation; release to prod requires an approver in the workspace who is not the author, configurable per workspace. One operator, one configuration, one identity store, authorisation between workspaces rather than isolation guarantees. ADR-04's Note is updated to say exactly that.

**Three amendments, all 2026-09-26.** Ruling 2 above is quoted as it was written, including its schema names, and is superseded in three places while standing everywhere else:

- **Q20 supersedes "control-plane tables ... stay in `public`".** They live in a named schema, `control`. `public` is left empty and off every search path. Section 3 is the layout.
- **Q23 renames the data-plane schemas** from the ruling's `env_test` and `env_prod` to **`data_test` and `data_prod`**, so both planes are named by role with the environment as the suffix and a per-environment schema is found by `data_%`. Everywhere but this quotation reads `data_<env>`.
- **Q22 withdraws "an existing installation migrates to one `prod` environment with its current data".** This is green field. Section 4 is what that removes.

Ruling 3 gains one addition rather than an amendment: **Q21** puts the environment's name in the path of every non-prod address, which ruling 3's "no public test address" already implied but did not state. Its substance is unchanged: there is no anonymous entry to a non-prod environment, `/f/{slug}` stays prod-only, and `/<env>/f/{slug}` is not a route.

## 3. The target model

Every QCMS object lives in a schema QCMS named. `public` is left empty, off every search path, with `CREATE` on it granted to nobody.

```
                        CONTROL PLANE - schema "control", one copy

   are this schema's, separately               are this schema's, separately

```

Four properties are worth reading off the picture rather than deriving them later:

- **One version history.** `form_versions` sits in `control` and every environment points at it. Promotion writes a `form_releases` row and copies nothing, which is what keeps `formId`, `questionId` and version numbers continuous (R1, R6, ADR-02, ADR-18).
- **The only schema boundary is the environment.** Workspaces are entirely inside `control` and are enforced by API-layer checks (SEC-3). A workspace is not a schema and never becomes one, because it is not an isolation guarantee.
- **Three foreign keys cross, and the first two are load-bearing.** `sessions_form_version_fk` into `control.form_versions` and `sessions_link_id_secure_links_link_id_fk` into `control.secure_links` are what make "shared version, separate data" expressible in the database rather than in a convention. The third, `webhooks_form_id_forms_form_id_fk` into `control.forms` (migration 0006), is the price of putting `webhooks` on the per-environment side, which Q3 settled. The remaining four foreign keys stay inside one schema: `answers_session_id_sessions_session_id_fk`, `submissions_session_id_sessions_session_id_fk`, `webhook_deliveries_outbox_id_outbox_id_fk` and `webhook_deliveries_webhook_id_webhooks_webhook_id_fk`.
- **`prod` is the unprefixed address shape and every other environment is prefixed.** A non-prod link reads `/test/l/{token}`, so it is legible as non-production before anybody clicks it, and there is no unprefixed non-prod address anywhere. The environment is still not in the token: the path names it, the row decides it, and a token under the wrong prefix is refused (Q21).

### The guards every environment carries

The seven data-plane tables are not bare tables, and an environment created without their guards is an environment whose ledger is mutable. The list is **derived** rather than remembered: `grep` the migration SQL for each of the seven table names and take every `CREATE TRIGGER`, `CONSTRAINT ... CHECK`, `CONSTRAINT ... UNIQUE` and `CREATE INDEX` that names it. That yields twelve objects, and none is optional:

| Kind     | Objects                                                                                                                                                                                                       | From             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| Triggers | `answers_reject_update`, `answers_reject_delete`                                                                                                                                                              | 0001, 0004       |
| CHECKs   | `answers_retraction_value`, `webhook_deliveries_snippet_requires_attempt`, `outbox_redacted_payload_has_no_answers`                                                                                           | 0009, 0015, 0016 |
| UNIQUE   | `webhook_deliveries_event_webhook_uq`                                                                                                                                                                         | 0007             |
| Indexes  | `sessions_status_expires_at_idx`, `answers_session_question_answered_at_idx`, `outbox_delivery_idx`, `webhook_deliveries_due_idx`, `outbox_payload_retention_idx`, `webhook_deliveries_snippet_retention_idx` | 0000, 0007, 0018 |

Primary keys ride the `CREATE TABLE`. The two trigger **functions** stay single, in `control`: a trigger in `data_test` executes `control.answers_reject_update()`, so N triggers share one body.

**This is the list the generator emits, not a list an operator re-creates.** Since Q22 there is no existing installation to move, so the twelve objects are created from the migrations for `data_test` and `data_prod` on a fresh database, and again by the environment command for any environment created later. **The first draft of this document listed four of the twelve**, which is exactly why the list is derived and why the durable form is code: task 064 emits the per-environment set from one schema module, and this table is what that emission is checked against. An environment missing `answers_reject_delete` has an erasable ledger; one missing `webhook_deliveries_event_webhook_uq` fans a webhook out twice. Both are silent.

### The reserved environment names

Because the environment set is configurable (Q1) and the environment's name is its URL prefix (Q21), the name is a URL path segment and a Postgres identifier at once. The environment command therefore refuses a name that is not a legal path segment, that does not fit `data_<env>` inside Postgres's 63-byte identifier limit, or that collides with a route either surface already serves at its root. Derived from disk at this base, the collision set is:

| Source                                              | Reserved                                                                                                   |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Portal root segments (`apps/portal/app`)            | `f`, `s`, `l`, `appearance`, `done`, `expired`, `link-error`, plus Next's own `_next`                      |
| API route paths and mount prefixes (`apps/api/src`) | `forms`, `questions`, `sessions`, `erasures`, `outbox`, `health`, `ready`, `internal`, `admin`, `api`      |
| The schema names (Q23)                              | `data`, `control`, `reporting`, `public`                                                                   |
| The address rule itself                             | `prod`, because prod is the unprefixed shape and a prefixed `prod` would be a second spelling of one thing |

The third row is not redundant with the `data_<env>` prefix. An environment named `data` would give a schema called `data_data`, which is legal and unreadable; one named `control`, `reporting` or `public` would give `data_control` and the like, which is worse, because the name then reads as though the schema held the control plane. Refusing the four is cheaper than explaining them.

As with the guard list, the durable form is a check derived from the route tables rather than a literal list in a source file, for the reason `CONTRIBUTING.md` gives about derived sets: a hand-kept copy goes stale the first time somebody adds a root route. Task 064 owns the derivation and the refusal.

## 4. Green field: there is no migration

**Code Owner ruling of 2026-09-26 (Q22).** Ruling 2 originally ended "an existing installation migrates to one `prod` environment with its current data". That clause is **withdrawn**. There is no existing installation, so this document carries no migration path, and the section that used to hold one is this paragraph.

What that removes, named so that a reader of the earlier ruling text knows which half stands: no `ALTER TABLE ... SET SCHEMA` of live tables, no backfill of one release row per already-published form, no defaulting of existing secure links to `prod`, no rollback stance about a half-moved database, and no deployment-ordering concern about doing the schema move and the search-path switch in one release. Everything else in ruling 2 stands.

What it leaves is simpler. A fresh database gets `control`, `data_test`, `data_prod`, `reporting_test` and `reporting_prod` **from the migrations alone**: the control-plane tables in `control`, the seven data-plane tables with all twelve guards in each environment schema, one view set per environment, and `public` left empty and off every search path. The drizzle chain in `packages/db/migrations` stays **append-only**, as ADR-18's discipline requires and as `migration-chain.test.ts` and `migrations.test.ts` check: a new migration creates the schemas and the tables in their final homes. Resetting the chain to a fresh baseline is not asked for and is not done.

The one thing green field does not remove is the **restore drill**. `docs/backup-restore.md` opens with the claim that a backup nobody has restored is not a backup, and that is as true of a database created in this shape as of one migrated into it; `pnpm qcms:drill-restore` covering every environment in the live set is task 067's, and it is the reason the schema layout has to be something a `pg_dump` and a restore reproduce faithfully.

## 5. What the network design adds

Recorded here only as the shape; the control is SEC-14 (`docs/SECURITY_DESIGN.md` section 5a) and the recipe is the "Restricting the test environment" section of `docs/deploy-ingress.md`.

- **Two handles, not one.** A **hostname** per non-prod environment, and the **`/<env>/` path prefix** on every one of its addresses (Q21). The host is primary, because it is what a network-layer firewall and a DNS split can act on without reading HTTP at all; the path is the second handle, available to an ingress or an L7 firewall as a rule of its own, and it is also what makes a link legible to the person holding it. Both remain because they fail independently: a host rule survives a proxy that rewrites paths, and a path rule survives a wildcard certificate or a shared hostname somebody consolidated onto.
- **Anonymous entry absent from a non-prod surface by ADR-09 mount** rather than by a handler check, which is the half that survives a misconfigured edge. **It is designed and not built** (anonymous and secure-link entry are one route today), and it is task 066's mount work in section 8, so until it lands the edge rules are the whole of this layer.
- **A privilege boundary underneath both** (Q17). Each environment's pool connects as `qcms_app_<env>`, granted `control` and its own `data_<env>` and nothing else, so a statement that somehow reached the wrong environment fails on permission rather than on a search path. That is not a network control and is listed here only because the three layers are usually read as network, link and schema: the schema layer now has two mechanisms, resolution and privilege.
- An **allowlist** on the non-prod hostname: source network, VPN or identity-aware proxy. The public address is prod only, and `/<env>/f/{slug}` is not a route at all.
- **Per-environment egress** for webhook delivery, stating in firewall vocabulary what the schema split already guarantees.
- A **firewall rule table** by source, destination, port and environment, in SEC-14 and nowhere else, using only ports from `docs/PORTS.md` (R8).
- **What it does not buy:** an insider already on the allowed network, and a leaked non-prod link, are the link layer's problem; a handler that queries the wrong environment is the schema layer's. Defence in depth in that order, network then link then schema.

### The scenario tests, and what they were worth

Recorded because this is the part of the record that changed the design rather than documenting it. **The tests overturned four decisions, and every one of them was in text that read perfectly well**, which is the case for testing a design against a named deployment before building it.

**Scenario one, an insurer.** Three environments, `dev`, `test` and `prod`; then two workspaces, Home and Vehicle, each with separate test and prod user groups, access gated by **workspace and environment together**.

The flow held end to end: publish an immutable version, release it to `dev`, iterate, release to `test`, get it approved into `prod`, roll back by releasing an earlier version. No version is copied, no environment reaches another's data, `formId` and version numbers stay continuous, and a session started in one environment stays where it started. The three-environment case needed no change at all, which is what Q1's configurable set bought. Ten findings, all closed: three written straight into the design (the per-environment credential and runtime discovery, task 064; rollback as a release of an earlier version, ADR-40 and task 065; the hostname choice, SEC-14 and the ingress recipe), four ruled as Q24 to Q26 plus finding 2, and three confirmed as findings 5, 6 and 10.

**Scenario two, a government organisation holding sensitive personal data.** Departments as workspaces, `dev`, `test` and `prod` each, form authors who must **not** see production response data, content viewable only by the employees who action it and possibly only per form, and data handlers who need no authoring rights at all.

Scenario one's workspace-and-environment scope separates departments and environments. It does **not** separate authoring from data access, and that is what this scenario found. Seven findings, all closed: five drew the rulings Q27 to Q31, finding 14 is the surprising half of Q27 and is recorded inside it, and finding 17 was confirmed.

**What the two tests changed, rather than clarified:**

- **Q25** found that per-workspace roles alone would let a Home tester read Home **production** responses. The membership model was one dimension short.
- **Q26** found the same shape one layer down in reporting, where a per-environment view set would have shown each department's responses to the other's analysts.
- **Q27** found that a single role ladder cannot express "authors may not see production data", because every rung above `viewer` contains it. It replaced the ladder with two families that imply nothing about each other, and made `owner` imply no data access at all.
- **Q29** withdrew a promise made the previous day: Q12 had given the installation-wide claim "response reads and exports" across every workspace, and an organisation with personal data cannot have an administrator who reads every department's answers by virtue of being an administrator. That reversal made the workspace a stronger boundary than the first reading claimed.

Q31 is the other kind of finding: not a wrong decision but a missing one. Nothing in the design recorded **who read a response**, and no amount of correct authorisation answers that question after the fact.

### Phase A - environments

**064 - Environment model, the named schema layout, the per-environment roles, and the environment command.** Depends on 038. Q1, Q2, Q3, Q9, Q17, Q20, Q21, Q22, Q23 and Q24 all bear on it and all are answered.

Deliverables: the `environments` table; an **append-only migration** that creates `control`, `data_test`, `data_prod` and a `reporting_<env>` view set per environment in their final homes, with the control-plane tables in `control` and the seven data-plane tables plus all twelve guards of section 3 in each environment schema, leaving `public` empty and off every search path with `CREATE` on it granted to nobody; the `data_<env>, control` search-path selection in the API and its configuration; the `docs/operations.md` role recipe rewritten to grant **per named schema** rather than `IN SCHEMA public`, with the same rewrite in the SEC-10 paragraph of `docs/SECURITY_DESIGN.md` section 7 and in `docs/reporting-view.md`'s sentence about `qcms_reporting` holding nothing on `public`; and `packages/db` schema modules split so the **generator** emits the per-environment set, which is what makes the twelve-guard list a consequence of the code rather than a paragraph to maintain.

Five further deliverables are easy to lose:

- From Q1: an **operator command** that creates an environment under the migration role, in the `qcms-db-migrate` / `qcms:create-admin` family, with no HTTP surface and a refusal when run as an application role (the shape `qcms:reset-2fa` already uses, SEC-10), **refusing a reserved or malformed name** per section 3. It also creates the environment's database role and grants, and sets that environment's per-environment configuration (Q11).
- From Q24: **dropping an environment, narrowly.** `prod` can **never** be dropped. A non-prod environment can be dropped **only when every form in it is closed and it holds zero sessions**, and the command refuses otherwise, **naming the open forms and the session count** rather than reporting a bare refusal, because an operator who has been refused needs to know what to do next. An operator empties a `dev` environment through retention, which is a sanctioned door, and not by dropping the schema out from under it. The reason for the narrowness is precise: `DROP SCHEMA ... CASCADE` would take the answer ledger without passing the `answers_reject_delete` trigger (migration 0004), so a wider drop would be a third whole-session deletion path and ADR-17 says there are two. Under this rule a drop can only ever remove an empty schema, so no door is added, and ADR-17's Note says so.
- **How a credential reaches the API, and how the API learns an environment exists** (scenario finding 1). One role per environment means one credential per environment, and a command that creates an environment at runtime has produced a credential the running API knows nothing about. Three parts, and the design has to name all three rather than leave them to be discovered:
  - **The credential** is a per-environment entry in the typed configuration (ADR-24), one connection string per environment, named after the environment. It arrives the way every other secret does, through the environment, validated at boot and never echoed (SEC-8). It is not read from the database, because a credential the database hands out is a credential the database can be made to hand out.
  - **The environment list** is read from `control.environments`, on a connection the process already has. Postgres is the one place the live set exists, and `data_%` is the fallback shape for a consistency check rather than the source.
  - **A new environment needs a restart**, and that is this task's recommendation rather than a decision this document takes. ADR-24 parses deployment configuration at boot and fails fast, so a reload path would be a new capability in that decision rather than an implementation detail of this one: the process would have to accept a credential it had not validated at startup. Restart is also the honest operational story, since the operator has just run a command with the migration credential and is already in a change window. If reload is wanted, it is an ADR-24 amendment and belongs with one.
- From Q1 again: **the enumeration rule**, that every per-environment job, export, backup, retention pass, reporting view and telemetry attribute reads the live set, found by `data_%`, rather than a compiled-in pair.
- From Q17: **one application role per environment**, `qcms_app_<env>`, each granted `USAGE` and DML on `control` and its own `data_<env>` and nothing else, with the SEC-10 recipe in `docs/operations.md` growing the per-environment roles beside the two it has.
- From Q2: **one connection pool per environment inside one API process**, selected by the request's environment, with the outbox deliverer and the retention sweep starting once and iterating the live set.
- **A control-only application role, recommended and awaiting confirmation when this task is written** (scenario finding 18). Q17 gives each environment a role with rights on `control` and its own `data_<env>`. A **`qcms_app_control`** beside them, with rights on `control` and on **no** data schema, used by better-auth and the authoring routes, would make the pools control plus one per environment and would buy one property an API-layer check cannot: "an author never reads production personal data" would hold **at the database** as well, because the connection those routes run on would have no grant on `data_prod` at all. It is a recommendation rather than a deliverable because it adds a fourth role and a pool to a task that already adds several, and the Code Owner confirms it when 064 is written.
- From Q20: **better-auth's Drizzle adapter verified against a non-default schema**, because the five auth tables move to `control` with everything else and the library validates the Drizzle schema on the first request through its handler and refuses to run on a mismatch (`apps/api/src/features/auth/instance.ts` maps its five models explicitly). That verification is a real risk item rather than a formality: it is the one table group in this change whose owner is a third party.

Exit criteria: (1) **a fresh database is created in the target shape** and every guard is present in every environment in the live set, asserted against a real Postgres: `control` holds the twelve control-plane tables the design starts from plus the `environments` table this task adds, and `form_releases` when 065 adds it, each `data_<env>` holds the seven data-plane tables with all twelve guards, and **`public` holds no QCMS object at all**; (2) `public` is on no search path and `CREATE` on it is granted to nobody; (3) **resolution and privilege are both asserted** (see below); (4) creating an environment works from the operator command, is refused as an application role, and refuses every reserved name in section 3 and a name too long for `data_<env>`; (4a) dropping `prod` is refused unconditionally, dropping a non-prod environment is refused while any form in it is open or any session exists, the refusal names the open forms and the session count, and a drop of a closed and empty environment succeeds; (5) a third environment created by that command is reached by every per-environment job **after a restart** and without a code change, and its role and grants exist; (6) each pool connects as its own environment's role, and a per-environment integration test shows that no request path uses the wrong pool; (6a) the process refuses to boot when the typed configuration names an environment `control.environments` does not hold, or holds one the configuration has no credential for, so the two lists cannot silently disagree; (7) better-auth signs in, enrols a second factor and verifies a recovery code against its tables in `control`, asserted against a real Postgres rather than by reading the adapter; (8) the drizzle chain is unbroken and no released migration file is edited; (9) the outbox deliverer and the retention sweep each run once and reach every environment in the live set.

**Criterion 3 has two halves, and the first draft of this plan had only one.** The **resolution** half: an unqualified data-plane name resolves only inside the connection's own environment schema, asserted with a positive control in each environment, and no query helper in `@roonga/qcms-db` emits a schema-qualified data-plane name, asserted from the source. The **privilege** half, which Q17's answer makes assertable: a schema-qualified read of another environment's data table, issued as that environment's own role, **fails on permission**. The first draft asserted only that a statement "cannot read the other's tables", which was unsatisfiable under one shared application role, because `search_path` is a resolution default and not a grant. Both halves now hold, by two different mechanisms, and `apps/api/e2e/security/03-db-least-privilege.e2e.ts` is where the second one belongs.

Gates: `pnpm verify`, forced Docker-backed run, `pnpm up:e2e` (per Q9, once per environment).

**065 - Release records, promotion, and the admin's environment switcher.** Depends on 064. Q4, Q5, Q6 and finding 2 are answered and are what it builds.

Deliverables: `form_releases`; the release and promotion API on the admin surface; release resolution replacing "newest published version" on the respondent path; the admin screens that show what is released where and promote between environments. From Q6: **one global environment switcher in the admin shell** that sets the environment for every screen, a **persistent coloured banner** on every page while a non-prod environment is selected, and destructive actions (erasure, closing, releasing) **restating the environment in their confirmation**. From Q4: no ordering requirement, so a release straight to `prod` is allowed and the release row's source environment records the path when there was one. No backfill: green field (Q22) means there is no already-published form to write a first release row for, so the first row any form gets is written by a real release.

**Rollback is releasing an earlier version, and there is no other rollback** (scenario finding 3). Nothing is reverted, undone or deleted: the administrator releases a version that was already released in that environment before, a new `form_releases` row records it, and sessions already open stay on the version they started (Q5). The release history has to **show that as a rollback** rather than as an ordinary release, because "released version 4 after version 7" is the shape an incident review reads, and a history that presents it as just another row makes an operator count backwards to see what happened. That is a presentation requirement on this task, not a second mechanism.

Exit criteria: (1) a form version released to `test` and not to `prod` is served in `test` and not in `prod`; (2) promotion writes a row and copies nothing, with the form id and version number unchanged; (3) a release never re-pins a live session (ADR-07, I4, confirmed as Q5), asserted with a session open across a release; (4) the release history answers who released what, when, from where, and with whose approval, **and marks a release of an earlier version than the one it replaces as a rollback**; (5) a release to `prod` with no prior `test` release succeeds and is recorded as such; (6) the switcher sets the environment for every screen, the banner is present on every page under a non-prod environment and absent under `prod`, and each destructive confirmation names the environment, asserted in the browser suite because a banner nobody renders is the failure mode here; (7) releasing an earlier version leaves every prior release row intact, since the history is append-only.

**And the two churn mitigations finding 2 accepted.** Every `dev` iteration publishes an immutable version and R1 keeps it, so a week of iterating leaves a long version list. That cost is accepted rather than designed away, because promotion is a record and not a copy and no cheaper mechanism keeps the audit promise; what this task builds is presentation, not a second model. A combined **"publish and release to `<env>`"** action, so one intent is one act rather than two. A **"released anywhere"** filter in the version list, so the versions that only ever reached `dev` are hideable. Exit criterion: one action publishes and releases atomically or not at all, and the filter's default shows every version so nothing is hidden by surprise.

Gates: `pnpm verify`, `pnpm verify:browser` (once per environment), forced Docker-backed run.

**066 - Environment-scoped secure links, the address prefix, and the per-environment closed state.** Depends on 064 and 065; coordinates with 063. Q11, Q16, Q18, Q19 and Q21 are answered and are what it builds.

Deliverables: the environment on the `secure_links` row; minting a link for an environment, **required on the API** and taken from the Q6 switcher in the admin (Q19); redemption starting a session in that environment; **the `/<env>/` path prefix on every non-prod address, on the portal and the API alike, with `prod` unprefixed** (Q21), and the refusal of a token presented under the wrong prefix; the portal's non-prod host shape; the SEC-14 operator recipe exercised.

**And the per-environment closed state** (Q18), which is the part of this task that reaches furthest into existing code. The per-environment release state gains a closed value; `forms.status` and its `form_status` enum go away or become derived from those states; `POST /forms/{id}/close` and `/reopen` become per-environment operations; and the check in `apps/api/src/features/responses/start-session/handler.ts` that today reads `form.status` after the link's own state and before anything is spent reads the environment's state instead. ADR-39's Amendment records the decision. Per Q11, the challenge provider and the retention TTLs also become per-environment values, read from the environment row rather than from the process environment.

**And the mount work SEC-14 rests on, which does not exist today and is this task's, not an existing property.** Anonymous and secure-link entry are one API route (`POST /sessions` on the `public` group, discriminated by a body refine), so three pieces have to be built for the 404-not-403 claim to be true: each environment's respondent surface as its own mountable group (which is Q2's recorded shape); **anonymous entry split from secure-link entry** so the two can ride different mount decisions; and the portal not serving its `/f` segment on the test host, which is portal routing and not an API mount. The split changes ADR-09's Note that four groups ride three mount flags, so **this task amends that Note**, and ADR-09 already carries a forward pointer saying so.

Exit criteria: (1) a prod link starts a prod session and a test link a test session, with the token format unchanged; (2) **a non-prod link's address carries the environment's name as its first segment and a prod link's does not**, asserted on both surfaces, and the same token presented under the wrong prefix is **refused** rather than redirected or honoured; (3) there is no anonymous entry to a non-prod environment on any address, asserted as a `404` and not a `403` (ADR-09), which requires the split above and is therefore a criterion about built behaviour rather than about configuration, and `/<env>/f/{slug}` does not exist; (4) revocation, expiry, one-time consumption and the challenge behave per environment as they do today; (5) **closing `prod` leaves an open `test` run serving and the reverse holds**, and a closed environment refuses a secure link into it without consuming a one-time link or charging a challenge, which is the property issue #724 already bought for the whole-form state; (6) minting without an environment is refused on the API and cannot be reached in the admin; (7) a prod respondent's address and experience are unchanged; (8) ADR-09's Note is amended in the same PR, and so is ADR-39's Amendment if 063 has not already landed it.

Gates: `pnpm verify`, `pnpm verify:browser` (once per environment), `pnpm up:e2e` (once per environment).

**067 - Per-environment delivery, retention and operations.** Depends on 064 and 065; its reporting half depends on 068. Q7, Q8, Q9, Q10, Q26 and finding 6 are answered and are what it builds.

Deliverables: the outbox, endpoints and deliveries per environment, with **configuring a `prod` webhook endpoint, and minting a `prod` link, requiring the approver role holding `prod` in scope** and, when the workspace's switch is on, a second account (Q30); the same operations in a non-prod environment stay an editor's; export per environment with the environment in the **filename and in no column** (Q8); the per-environment retention TTLs read from the environment row, with **rate limits staying installation-wide** (Q11, finding 6); `docs/backup-restore.md`, `docs/erasure.md` and `docs/operations.md` updated; the environment as an allowlisted telemetry attribute (SEC-13); the restore drill covering `control` and every environment schema in the live set.

**Reporting is per environment and per workspace** (Q10, Q26), and it is the one place in this design where the authorisation model is expressed in database grants rather than in the API, because a reporting consumer writes their own SQL against a role the operator granted. The schema stays per environment, `reporting_<env>`, and holds **a view set per workspace**: `reporting_prod.home_responses`, `reporting_prod.vehicle_responses` and the flat-answers twin of each, every set with **its own read-only role**, so a workspace's analysts are granted exactly their workspace's views in exactly their environment and nothing else. The `qcms_reporting` recipe in `docs/reporting-view.md` becomes per (workspace, environment); `qcms_ro`, the dev-tools viewer role in `docker-compose.dev-tools.yml`, holds `pg_read_all_data` and is a different role that this does not touch. The environment half lands with this task; **the workspace half lands when 068 exists**, since there are no workspaces to name views after until then, so this task ships the per-environment schemas with one view set each and 068's landing adds the split.

**Erasure, which is the deliverable with a person on the other end of it** (Q7). An erasure acts in the **selected environment only**, and its confirmation restates which one, so no single act crosses a boundary and `prod` cannot be reached from `test` by accident. When the same subject identifier also has sessions in other environments, the screen **says so and offers to repeat the erasure there**, each repetition its own confirmed act in its own environment. The cost is that a data subject's request is several deliberate acts rather than one click, and the benefit is that none of them is the wrong one; ADR-17's Note records the trade.

**Scheduler ownership is settled** (Q2): the outbox deliverer and the retention sweep start once per process under `config.mount.internal` (`apps/api/src/main.ts`) and **iterate the live environment set**, so `docs/deploy-enterprise.md` section 5's scheduler-singleton rule holds unchanged. Each pass claims and delivers under exactly one environment's pool and role, and no pass ages a row in another environment.

Exit criteria: (1) a test submission cannot reach a prod endpoint, asserted against a real Postgres rather than argued; (2) backup, restore and the drill cover every environment in the live set, including one created after the feature shipped; (3) an erasure and an export touch one environment and no other, and an export's environment is in its filename while its columns are byte-for-byte what they are today; (4) an erasure offers the cross-environment repetition when the subject has sessions elsewhere and performs nothing without its own confirmation; (5) one deliverer and one sweep reach every environment in the live set, and neither ages or claims a row in another; (6) a trace can be attributed to an environment, and the attribute names no respondent; (7) a reporting role granted one workspace's views in one environment can read those and **cannot read another workspace's views or another environment's schema**, asserted against a real Postgres the way `03-db-least-privilege.e2e.ts` already asserts the reporting role's limits; (8) a **`prod`** webhook endpoint change and a **`prod`** link mint are refused without the approver role holding `prod` in scope, and with the workspace switch on a `prod` endpoint change by a single account is refused; a `dev` or `test` endpoint change stays an editor's, like a `dev` or `test` release.

**Why a prod endpoint change is an approver's act** (Q30): an editor who can point a `prod` webhook at any URL can route production personal data out of the deployment, which is a larger capability than authoring a form and does not belong to the same role. It is narrowed to `prod` deliberately, for the same reason the two-person rule is: a `dev` endpoint routes test data to a test consumer, and gating it would cost a test cycle and protect nothing. SEC-14's per-environment egress allowlist stays the network backstop underneath, because an endpoint that should not have been set is still an endpoint a firewall can refuse.

Gates: `pnpm verify`, forced Docker-backed run, `pnpm up:e2e` (once per environment), `pnpm qcms:drill-restore` (iterating the live set).

### Phase B - workspaces

**068 - Workspace model, ownership, moving and archiving.** Depends on 038; independent of phase A. Q14 and Q15 are answered and are what it builds.

Deliverables: `workspaces`; the workspace reference on `forms` and `questions`; the shared workspace and the publish-time rule on which question versions a form may pin; the unique constraint on `forms.slug` that does not exist today, which green field makes a plain constraint rather than a data fix; and the seeding of a first workspace so a bootstrapped installation has one to author in, with approver-not-author off on it (Q13).

From Q14: **moving a question between workspaces**, which is one `UPDATE` on the identity row and touches no version. Forms elsewhere that already pin one of its versions keep serving and keep that pin in their next draft (ADR-02, R6); a **new** pin from another workspace onto a question outside the shared workspace is refused, through the same path that refuses a pin to a `deprecated` version, so authors meet one mechanism rather than two.

From Q15: **archiving a workspace, never deleting one.** Archiving requires no open form and no released version, and the workspace's forms and questions are reassigned first, so it is the last step rather than a cascade. No response row is reached, which keeps ADR-17's two whole-session delete doors at two.

From finding 10: **the shared workspace is the org-wide library, and its asymmetry is the design.** Every workspace's editors **see and may pin** its questions; **only the shared workspace's own members edit them.** So it is a read surface to everyone else, which is what makes it a library rather than a place three groups overwrite each other's wording. The question's text is the one thing that crosses a workspace boundary, and no response ever does.

Exit criteria: (1) a form or question cannot exist without exactly one workspace, enforced by the column rather than by a backfill; (2) publish refuses a new pin to a question owned by another non-shared workspace, and a form that already pins one keeps serving and keeps it in its next draft; (3) slugs are unique installation-wide, enforced by the database and not by authoring convention; (4) archiving is refused while an open form or a released version remains, and succeeds once they are reassigned; (5) no code path deletes a workspace, and none reaches a response row from one, asserted rather than reasoned; (6) an editor outside the shared workspace can read and pin a shared question and **cannot edit one**, asserted on both halves; (7) no published version changes and no public address moves.

Gates: `pnpm verify`, forced Docker-backed run.

**069 - Membership: two role families, environment and form scope, and the access audit.** Depends on 068. Q12, Q25, Q27, Q28, Q29, Q31 and finding 17 are answered and are what it builds.

**A membership is a set of rows of (user, workspace, role, environments, forms)**, and a user holds as many as their job needs. Two families with **nothing implied between them** (Q27): **authoring** (editor, approver, owner) on the control plane, workspace-wide; **data** (handler: view and export; eraser: erase) on an environment's data plane, scoped to the row's environments and, per Q28, to `all` forms or a list. `owner` implies **no** data access. The two scenarios are the test that the shape is right: the insurer's four groups are four rows, and the government organisation's authors, case officers and workspace owners are rows in different families over the same workspaces.

Deliverables: `workspace_members` carrying both families and all three scopes; **enforcement of every dimension in the API layer** per route group and per route (SEC-3, never a BFF, never only the UI), on every route touching data-plane or environment-scoped state: response reads, exports, erasure, link minting, endpoint configuration, closing, and release to an environment. **Draft authoring and publishing stay environment-agnostic** (Q25), because publishing a version releases it nowhere, and that asymmetry is load-bearing: an author needs one row, not one per environment. The Q6 switcher offers **only the environments the administrator holds** in some row. The **installation-wide claim administers and reads no data** (Q29), which is a withdrawal of what Q12 first granted and has to be built as the narrower rule rather than the wider one. An optional **seed handler row** scoped to `dev` and `test` for a new editor, which shows in the membership list like any other (finding 17), so a convenience is never an implication. The membership screens. And the SEC-3 authorization matrix in `docs/SECURITY_DESIGN.md` section 3.2 extended with **both families**, the environment and form dimensions, and the administer-only claim, with `apps/api/e2e/security/01-authorization-matrix.e2e.ts` and `matrix-coverage.e2e.ts` moving with it in the same change, since that test parses the table's Action column by exact wording.

**And the access audit** (Q31, **SEC-15**): an append-only `control`-schema table recording every response read, export and erasure with actor, workspace, environment, form, kind and time, readable by the workspace's owners and by the installation admin. `two_factor_resets` is the precedent shape, including its deliberate absence of a foreign key to the account, because an audit row that cascades away with what it describes is not an audit row.

**The mechanism is under evaluation, and the model is not** (issue #995, comment 5842366437, which is the record for this paragraph). Whether the rows and checks live in better-auth's `organization` plugin plus QCMS extensions, in a QCMS-authored better-auth plugin, or in QCMS tables with API middleware, is a ruling the Code Owner takes against the pinned version **before this task is written**. The direction on record is to keep authentication and authorisation generic and reusable rather than QCMS-shaped, building on the built-in `organization` plugin and adding only what it lacks, which is **scope on a role**; and the ruling follows a survey of whether an existing plugin or authorisation-engine integration already closes that gap. Every property above holds whichever way it goes, which is why the task can be drafted now and why the work order waits.

Exit criteria, and they are written to probe **both families against every action** rather than each family against its own:

1. Every role in both families is probed against every authoring, response, configuration and release action, so a right that leaks across the families fails a test rather than a review.
2. **An editor with `prod` in scope reaches no response in any environment**, and **an owner reads none without a handler row**. Those two are the surprising half of Q27 and are the reason this task exists in this shape.
3. A **handler** holds no authoring right: it cannot edit a draft, publish a version or release one.
4. **A row scoped to `test` is refused every environment-scoped action in `prod`** on the same workspace, which is scenario one's own case.
5. **A data row scoped to a list of forms is refused the responses of a form not on the list** in the same workspace and environment (Q28).
6. An administrator with **no** membership and no installation-wide claim reaches nothing; one **with** the claim administers settings, users, memberships and environments and **reads no response, exports nothing and erases nothing** anywhere (Q29).
7. Draft authoring and publishing succeed for an editor holding no environment at all, since neither is environment-scoped.
8. The switcher offers exactly the environments held in some row and no others.
9. Approver-not-author refuses the claim holder's own release too.
10. Enforcement is in the API, and a BFF or UI bypass reaches a refusal, asserted.
11. **Every response read, export and erasure writes one audit row**, with the six fields, and no path reads or exports without one; a workspace owner and the installation admin can read the audit and nobody else can.
12. The section 3.2 table and the probe inventory stay in step, which `matrix-coverage.e2e.ts` already enforces.

Gates: `pnpm verify`, `pnpm verify:browser`, forced Docker-backed run.

**070 - The two-person rule for production.** Depends on 065 and 069. Q13, Q30 and finding 5 are answered: **one per-workspace switch**, **off by default** including on the seeded workspace, governs the two-person rule for **both** a `prod` release **and** a `prod` webhook endpoint change, and it gates `prod` alone.

Deliverables: the per-workspace setting, defaulting off; the check at release to `prod` and at no other release, so a release to `dev` or `test` is self-service for an editor holding that environment in scope; **the same check on a `prod` endpoint change** (Q30), which is why this is one switch and not two; the approval recorded on the ADR-40 release record; the admin flow that asks for it. The approver must hold `prod` in their environment scope (Q25), because an approval from somebody who cannot act in production is not an approval of a production act. One person may hold `editor` and `approver` rows together, so the rule is about two accounts rather than about two kinds of person.

Exit criteria: (1) with the setting on, a release to `prod` by the version's author is refused, and by a different approver in the same workspace who holds `prod` in scope succeeds; (2) the approval is on the release row and is readable in the history; (3) with the setting off, which is the default, behaviour matches 065 exactly and a single-administrator installation can release to `prod`; (4) a release to a non-prod environment never asks for an approver, whatever the setting; (5) an approver from another workspace is refused, and so is one in the right workspace who does not hold `prod`; (6) an administrator holding the installation-wide claim but no membership cannot approve, and cannot approve their own release (ADR-41's Q12 Note).

Gates: `pnpm verify`, `pnpm verify:browser`.

## 9. Identity, and a later phase C

**Status: assessed, decided later, not built.** Written at the Code Owner's request on 2026-09-26 so that phase A and phase B are built against a known direction rather than an unexamined one. Nothing in this section is scheduled, and the decisions it names are the Code Owner's to take when it is.

### What better-auth does under this plan, and what it does not

better-auth stays the **authenticator and nothing else**: email and password, TOTP, breach-checked passwords, sign-in throttling and sessions, in process in the API (SEC-1, ADR-06, ADR-35). Its identity tables move to `control` with the rest of the control plane (Q20), and task 064 verifies its Drizzle adapter against a non-default schema, which is the one third-party risk in that move.

**Where authorisation lives is under evaluation, and the model is not.** The record for this subsection is issue #995, comment 5842366437; it supersedes an earlier line in this assessment that said the organisation plugin is not used for membership. Workspace membership, the two role families, the environment scope, the form scope and the access audit are decided exactly as section 6 records them (Q25, Q27 to Q31). What the Code Owner asked to be re-evaluated, before the plan reinvents membership, is the **mechanism**, and whether QCMS's authorisation could be a better-auth plugin at all.

**Three options, evaluated read-only against better-auth 1.7.5 as pinned:** (A) the `organization` plugin plus QCMS extensions; (B) a QCMS-authored better-auth plugin; (C) QCMS tables and API middleware as this plan drafts. The evaluation recommended C.

**The Code Owner's direction is otherwise**, and it is a direction rather than a ruling: keep authentication and authorisation **simple, generic and not tied to QCMS**, so that they can be reused across applications; build on the built-in `organization` plugin and add only what it lacks. What it lacks, per the evaluation, is **scope on a role**: the plugin says what a role may do to a type of thing, and cannot say "handler, but only in environment `test`, only on these forms". Everything else the model needs is either native to the plugin (the workspace row, one member row per user with a role list, custom roles from statements) or QCMS domain code under any option (the two-person rule, the shared-workspace pin rule, the access audit, the switcher list, the installation claim).

**The next step before the ruling is a survey**, not an implementation: whether an existing better-auth plugin, or a better-auth integration with an authorisation engine, already closes the scope gap. The survey reports, the Code Owner then rules on the mechanism and its packaging, and this PR is amended before it merges. Nothing decided above moves either way.

The existing `role` additional field (default `admin`, `input: false`, no request path) becomes the **installation-wide administer-only claim** of Q29. That is the whole of its job.

### Enterprise identity, as a direction rather than a decision

An adopter running Entra ID, Auth0, Okta, Keycloak or AD FS will ask for single sign-on. The shape below is the assessment; each bullet marked **decision** is one to take when phase C is scheduled, not now.

- **Protocol: OIDC first, SAML second.** AD FS is the reason SAML is on the list at all. LDAP and Kerberos against on-premises Active Directory are **out of scope**: that estate fronts itself with AD FS or Entra ID, and QCMS should talk to the front rather than to the directory. better-auth's first-party generic OAuth and SSO plugins are the candidates, and the plugin and its maturity are to be verified against the pinned version at scheduling time rather than assumed from this paragraph.
- **Identity comes in; authorisation stays ours.** Just-in-time user creation on first SSO sign-in, with **no memberships**: a new SSO user can sign in and see nothing until somebody grants them a row. Mapping IdP groups to membership rows is a later option, through a mapping table whose rows are visible in the membership list like any other, so a group-derived membership is not a second invisible mechanism.
- **Deprovisioning is the real enterprise ask.** The 12 h absolute session lifetime bounds the window today, which is a bound rather than an answer; SCIM or a periodic check against the IdP is what ends access properly.
- **MFA policy (decision).** Either accept the IdP's MFA assertion from its claims and skip local TOTP, or refuse sign-in without such an assertion. Never both prompts: double-prompting is how operators end up turning one of them off.
- **Break-glass (decision).** Local email and password kept for the installation administrator only, or switchable off per installation. SEC-1's `qcms:create-admin` and `qcms:reset-2fa` are the existing shapes to build on.
- **Account linking by IdP subject, never by email alone.** Email-collision account takeover is the reason, and it is worth stating as a rule rather than leaving to an implementer.
- **One IdP per installation** to begin with; per-workspace IdPs a later option, and a bigger one than it sounds because it interacts with membership.
- **The access audit (Q31) records the IdP subject as actor**, so a read is attributable to a person the adopter's directory knows.
- **Respondents are untouched.** Respondent identity is separate by design (ADR-06): anonymous sessions and secure links. SSO for respondents on a staff-facing form would be its own feature with its own decision.
- **Configuration** is issuer, client id, client secret and redirect URIs as typed installation configuration (ADR-24, SEC-8). The admin hostname has to be stable, because it is in the IdP's redirect allowlist.

A new ADR (enterprise identity) and a Note on ADR-06 are the artifacts, written when the decisions above are taken. Refs #179.

## 10. Non-goals

Multi-tenancy (R7, ADR-04). A second database, a second deployment, a second API process, or replication between environments. Per-workspace configuration, theming or ports. Per-environment configuration beyond the two settings Q11 names. A workspace segment in any URL. An environment visible in a token, as opposed to in a path. Deleting a workspace. Copying a version between environments, in any form: promotion is a record, and a copy would break R1, R6 and ADR-18 at once.
