## 1. The problem

QCMS is single-tenant (ADR-04) and has no notion of an environment. A form has one mutable draft (`form_drafts`, one row per form) and immutable published versions (`form_versions`, frozen by the `form_versions_reject_update` trigger in migration 0001), and `getFormBySlug` plus `getLatestPublishedVersion` resolve every public link to the newest published version. A session pins the version it resolved at start and never migrates (ADR-07, invariant I4).

Two things are missing, and they are unrelated to each other:

1. **There is no way to change a form, try it with real respondents, get it approved, and only then make it live.** Publishing is the only way to get a definition onto the serving path, and publishing is immediately live for everyone. The closest thing to a rehearsal today is the admin draft preview (`POST /forms/{id}/draft/preview`), which is a dry run in one browser and involves no respondent, no session and no webhook.
2. **There is no way for two groups inside one organisation to share an installation without seeing each other's forms and questions.** Every authenticated administrator sees the whole library; `user.role` carries `admin` for everyone and nothing reads it for an authorization decision (SEC-3, issue #179).

Multi-tenancy was deliberately not built and stays out (R7). Neither of the two gaps above is a request for it.

## 2. The rulings (Code Owner, 2026-09-25, issue #995)

Verbatim, so that the amendments below are visible as amendments rather than as a quietly edited record.

1. **Environments are release states over immutable versions, in one deployment.** A form version is shared across environments; what varies is which version is released to `test` and which to `prod`. Promotion is a release record (who, when, which version, from which environment), never a copy, so form ids and version numbers stay continuous (R6). Approval is recorded on the release.
2. **Isolation level: a Postgres schema per environment for the data plane.** Control-plane tables (forms, versions, questions, links, admin identity) stay in `public`; the session, answer ledger, submission, delivery and outbox tables exist per environment (`env_test`, `env_prod`) and the API connects with the environment's search path, so Postgres enforces the boundary and no per-query filter can be forgotten. Backups, erasure, exports, the restore drill and observability are per environment. An existing installation migrates to one `prod` environment with its current data.
3. **Test is reachable through secure links only, no public test address.** `/f/{slug}` stays prod. A secure link's server-side row carries the environment as well as the ADR-39 target version. Test webhooks and the outbox are per environment, so a test submission can never fire a production endpoint. In addition the design must let an operator protect test (and any unreleased version) at the network layer: a distinct hostname or listener for test traffic, so ingress and firewall rules can restrict it to an allowlisted network, VPN or identity-aware proxy; per-environment egress rules for webhooks; the draft preview never leaves the admin. Defence in depth: network, then link, then schema.
4. **Workspaces are an authorisation grouping, not tenancy.** A workspace owns forms and questions (with an optional shared workspace for org-wide questions any form may pin); admins are members with a role (owner, editor, approver, viewer), which is where RBAC (issue #179) lands; slugs stay unique per installation; release to prod requires an approver in the workspace who is not the author, configurable per workspace. One operator, one configuration, one identity store, authorisation between workspaces rather than isolation guarantees. ADR-04's Note is updated to say exactly that.

**Three amendments, all 2026-09-26.** Ruling 2 above is quoted as it was written, including its schema names, and is superseded in three places while standing everywhere else:

- **Q20 supersedes "control-plane tables ... stay in `public`".** They live in a named schema, `control`. `public` is left empty and off every search path. Section 3 is the layout.
- **Q23 renames the data-plane schemas** from the ruling's `env_test` and `env_prod` to **`data_test` and `data_prod`**, so both planes are named by role with the environment as the suffix and a per-environment schema is found by `data_%`. Everywhere but this quotation reads `data_<env>`.
- **Q22 withdraws "an existing installation migrates to one `prod` environment with its current data".** This is green field. Section 4 is what that removes.

Ruling 3 gains one addition rather than an amendment: **Q21** puts the environment's name in the path of every non-prod address, which ruling 3's "no public test address" already implied but did not state. Its substance is unchanged: there is no anonymous entry to a non-prod environment, `/f/{slug}` stays prod-only, and `/<env>/f/{slug}` is not a route.

## 3. The target model

Every QCMS object lives in a schema QCMS named. `public` is left empty, off every search path, with `CREATE` on it granted to nobody.

Four properties are worth reading off the picture rather than deriving them later:

- **One version history.** `form_versions` sits in `control` and every environment points at it. Promotion writes a `form_releases` row and copies nothing, which is what keeps `formId`, `questionId` and version numbers continuous (R1, R6, ADR-02, ADR-18).
- **The only schema boundary is the environment.** Workspaces are entirely inside `control` and are enforced by API-layer checks (SEC-3). A workspace is not a schema and never becomes one, because it is not an isolation guarantee.
- **Three foreign keys cross, and the first two are load-bearing.** `sessions_form_version_fk` into `control.form_versions` and the link key into `control.secure_links` are what make "shared version, separate data" expressible in the database rather than in a convention; since Q46 that second one is **composite**, on `(link_id, environment)`, so the environment is part of the reference rather than beside it. The third, `webhooks_form_id_forms_form_id_fk` into `control.forms` (migration 0006), is the price of putting `webhooks` on the per-environment side, which Q3 settled. The remaining four foreign keys stay inside one schema: `answers_session_id_sessions_session_id_fk`, `submissions_session_id_sessions_session_id_fk`, `webhook_deliveries_outbox_id_outbox_id_fk` and `webhook_deliveries_webhook_id_webhooks_webhook_id_fk`. All seven are declared **once per environment schema**, the in-plane four pointing inside their own `data_<env>` and the crossing three at the single `control` copy, so the generator owns seven foreign keys per environment beside the thirteen guards below.
- **`prod` is the unprefixed address shape and every other environment is prefixed.** A non-prod link reads `/test/l/{token}`, so it is legible as non-production before anybody clicks it, and there is no unprefixed non-prod address anywhere. The environment is still not in the token: the path names it, the row decides it, and a token under the wrong prefix is refused (Q21).

### The guards every environment carries

The seven data-plane tables are not bare tables, and an environment created without their guards is an environment whose ledger is mutable. Twelve of the thirteen are **derived** rather than remembered: `grep` the migration SQL for each of the seven table names and take every `CREATE TRIGGER`, `CONSTRAINT ... CHECK`, `CONSTRAINT ... UNIQUE` and `CREATE INDEX` that names it. The thirteenth is new with this design and is the one the Code Owner added on 2026-09-30. None is optional:

| Kind     | Objects                                                                                                                                                                                                       | From                        |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| Triggers | `answers_reject_update`, `answers_reject_delete`                                                                                                                                                              | 0001, 0004                  |
| CHECKs   | `answers_retraction_value`, `webhook_deliveries_snippet_requires_attempt`, `outbox_redacted_payload_has_no_answers`, `sessions_environment_matches`                                                           | 0009, 0015, 0016, new (Q46) |
| UNIQUE   | `webhook_deliveries_event_webhook_uq`                                                                                                                                                                         | 0007                        |
| Indexes  | `sessions_status_expires_at_idx`, `answers_session_question_answered_at_idx`, `outbox_delivery_idx`, `webhook_deliveries_due_idx`, `outbox_payload_retention_idx`, `webhook_deliveries_snippet_retention_idx` | 0000, 0007, 0018            |

Primary keys ride the `CREATE TABLE`. The two trigger **functions** stay single, in `control`: a trigger in `data_test` executes `control.answers_reject_update()`, so N triggers share one body.

**The thirteenth guard, and why a link cannot be redeemed into the wrong environment (Code Owner, 2026-09-30, Q46).** Each `data_<env>.sessions` carries an **`environment` column, `NOT NULL`**, the crossing foreign key into `control.secure_links` becomes **composite** on `(link_id, environment)`, and a `CHECK (environment = '<env>')` pins the column to the schema it sits in. `control.secure_links` carries a **matching `environment` column, also `NOT NULL`**, and a **unique key on `(link_id, environment)`** for the composite key to reference; both are control-plane objects and neither is part of the per-environment set. **Task 064's baseline creates all of it**, the `secure_links` column and its unique key included, because a foreign key cannot reference a column a later task adds; task 066 then builds minting and redemption on top of it.

**`NOT NULL` on both columns is what makes the guard a guard.** A `CHECK (environment = '<env>')` **passes when `environment` is NULL**, because SQL comparison with NULL is unknown and a CHECK refuses only on false. So a nullable column would leave the pin open on every row that omitted it. The same is true of the key: a composite foreign key under the default `MATCH SIMPLE` is **not checked at all when any referencing column is NULL**, so a NULL `environment` would skip it. Both columns are therefore `NOT NULL`, asserted in 064's criterion 1a rather than left to the schema module.

**A public session has no link, and that is correct rather than a hole.** `sessions.link_id` is nullable by design, because an anonymous session on `prod` starts from `/f/{slug}` and redeems nothing (`packages/db/src/schema/sessions.ts`). Under `MATCH SIMPLE` a row with a NULL `link_id` skips the composite key entirely, which is exactly what it should do: there is no link row for it to agree with. What still binds such a row to its schema is the **`CHECK`**, which is why that half of the guard has to hold on its own and why `environment` is `NOT NULL` even though `link_id` is not. The key constrains linked sessions; the CHECK constrains all of them.

What the guard buys is a database guarantee where there was an API check: a session in `data_test` can reference only a secure link whose own row says `test`, so a link minted for one environment cannot start a session in another however the request reached the handler. Task 066's API check stays, as defence in depth: this makes the invariant structural, and it does not make the check redundant, because the check is what produces a legible refusal rather than a constraint violation.

**The thirteen are the guards, and the generated per-environment set is larger than the guards.** The seven foreign keys of the previous section multiply too, four inside the plane and three into `control` (the second of the crossing three now composite), so what task 064's generator emits for one environment is **twenty objects**: the thirteen above plus those seven. The thirteen are tabulated on their own because each is a guard whose absence is silent and costs correctness; a missing foreign key fails loudly on the first insert. 064's deliverables and exit criteria name both sets.

**This is the list the generator emits, not a list an operator re-creates.** Since Q22 there is no existing installation to move, so the thirteen objects are created from the baseline migration for `data_test` and `data_prod` on a fresh database, and again by the environment command for any environment created later. **The first draft of this document listed four of the twelve it then had**, which is exactly why the list is derived and why the durable form is code: task 064 emits the per-environment set from one schema module, and this table is what that emission is checked against. An environment missing `answers_reject_delete` has an erasable ledger; one missing `webhook_deliveries_event_webhook_uq` fans a webhook out twice. Both are silent.

### The environment names: the character rule, the length rule, and the reserved set

Because the environment set is configurable (Q1) and the environment's name is its URL prefix (Q21), the name is a URL path segment and a Postgres identifier at once. The environment command therefore refuses a name that breaks the character rule, that is too long for the longest identifier derived from it, or that collides with a route either surface already serves at its root.

**The character rule (Code Owner, 2026-09-30, Q42): a name matches `^[a-z][a-z0-9]*$`.** Lowercase letters and digits, starting with a letter, with **no hyphen and no underscore**. The hyphen is excluded because an access-group name joins a set of environments with hyphens (Q37), so `dev-test` has to be readable as two names and not as one; the underscore is excluded because `data_<env>` and `reporting_<env>` join on it, so `data_my_env` would be ambiguous about where the prefix ends. Neither exclusion is a matter of taste: each is a separator this design already spends elsewhere, and a name that contains one makes a derived string impossible to parse back.

**The length rule (Code Owner, 2026-09-30, Q42): the name is checked against the longest identifier derived from it.** Postgres truncates an identifier over `NAMEDATALEN - 1` (63 bytes by default) **silently**, so a name that fits `data_<env>` but not a longer derived name would create an object whose name is not the one anybody asked for, and two such names could collide with each other with no error anywhere.

**The limit is derived from the prefix list, not written as a constant.** It is **63 minus the length of the longest prefix among every identifier the environment's name is interpolated into**, and the command computes it from that list rather than from a literal, for the reason `CONTRIBUTING.md` gives about derived sets: a number in a source file goes stale the first time somebody adds a longer prefix, and it goes stale silently, because a too-generous limit fails only at the truncation it was meant to prevent. The list today is `data_` (5), `reporting_` (10) and the role prefix `qcms_app_` (9), a role name being subject to the same 63 bytes as a schema name. The longest is `reporting_`, so **the limit today is 53 bytes**; that figure is the current output of the derivation and not the rule.

**One prefix is not named yet and must join the list when it is.** Q26 gives reporting a **read-only role per (workspace, environment)** and task 067 names it. Whatever that name's prefix turns out to be, it is interpolated with an environment name and therefore belongs in this derivation; if it is longer than `reporting_`, the limit drops and 067 is the task that re-derives it. Task 064 owns the derivation and task 067 owns adding its prefix to the list, which is why the rule is stated as the arithmetic rather than as 53. The refusal names the derived identifier that would not fit rather than quoting a bare number.

**The combined-environment spelling (Code Owner, 2026-09-30, Q42): a set is written in the environments table's order.** An access group scoped to more than one environment carries a hyphen-joined set in its name (Q37), and `dev-test` and `test-dev` would otherwise both parse while being two spellings of one grant, which D2's uniqueness by stored string cannot see through. The canonical order is **the order of the rows in `control.environments`**, so `dev-test` is written and `test-dev` never is. The write path **normalises on write** and **refuses** a name whose set is out of order rather than silently rewriting it, so the name a person typed and the name that was stored are never different without them being told.

Derived from disk at this base, the collision set is:

| Source                                              | Reserved                                                                                                   |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Portal root segments (`apps/portal/app`)            | `f`, `s`, `l`, `appearance`, `done`, `expired`, `link-error`, plus Next's own `_next`                      |
| API route paths and mount prefixes (`apps/api/src`) | `forms`, `questions`, `sessions`, `erasures`, `outbox`, `health`, `ready`, `internal`, `admin`, `api`      |
| The schema names (Q23)                              | `data`, `control`, `reporting`, `public`                                                                   |
| The address rule itself                             | `prod`, because prod is the unprefixed shape and a prefixed `prod` would be a second spelling of one thing |

The third row is not redundant with the `data_<env>` prefix. An environment named `data` would give a schema called `data_data`, which is legal and unreadable; one named `control`, `reporting` or `public` would give `data_control` and the like, which is worse, because the name then reads as though the schema held the control plane. Refusing the four is cheaper than explaining them. A few entries in the first row, `link-error` among them, are already unreachable under the character rule above; they stay in the table because the table is derived from the routes rather than filtered against another rule, and a derived set that quietly drops its own members is a set somebody has to re-derive to trust.

As with the guard list, the durable form is a check derived from the route tables rather than a literal list in a source file, for the reason `CONTRIBUTING.md` gives about derived sets: a hand-kept copy goes stale the first time somebody adds a root route. Task 064 owns the derivation and the refusal.

## 4. Green field: there is no migration

**Code Owner ruling of 2026-09-26 (Q22).** Ruling 2 originally ended "an existing installation migrates to one `prod` environment with its current data". That clause is **withdrawn**. There is no existing installation, so this document carries no migration path, and the section that used to hold one is this paragraph.

What that removes, named so that a reader of the earlier ruling text knows which half stands: no `ALTER TABLE ... SET SCHEMA` of live tables, no backfill of one release row per already-published form, no defaulting of existing secure links to `prod`, no rollback stance about a half-moved database, and no deployment-ordering concern about doing the schema move and the search-path switch in one release. Everything else in ruling 2 stands.

What it leaves is simpler. A fresh database gets `control`, `data_test`, `data_prod`, `reporting_test` and `reporting_prod` **from the migrations alone**: the control-plane tables in `control`, the seven data-plane tables with all thirteen guards and all seven foreign keys in each environment schema, one view set per environment, and `public` left empty and off every search path.

### 4a. Re-baselined from scratch (Code Owner, 2026-09-30, Q41)

**This paragraph replaces the one that said the chain stays append-only.** Until 2026-09-30 this section held Q22's reading that the drizzle chain in `packages/db/migrations` stays append-only and that a new migration creates the schemas and the tables in their final homes. The Code Owner has ruled the other way, and the ruling is recorded as an amendment rather than as an edit because the withdrawn reading is what ADR-18's discipline says on its face.

**Task 064 replaces migrations 0000 to 0021 with one new baseline** that creates `control` and each `data_<env>` **in final shape**. There is **no `DROP`** and **no `ALTER TABLE ... SET SCHEMA`** in any migration: nothing is dropped because nothing is moved, and nothing is moved because the baseline creates each table where it belongs the first time. An append-only twenty-second migration could not do that. It would have to create the schemas and then move twenty-one migrations' worth of tables into them, which is a `SET SCHEMA` list against tables the earlier files created in `public`, and the per-environment copies have no expression at all in that shape: there is one `answers` table in the chain and the design needs one per environment.

**This is a one-time, Code Owner-approved exception to the append-only migration rule**, and it is available exactly once, because Q22 says there is no installation to break. **Every existing database is deleted and recreated manually**: the development database, the Docker stack, CI, and any adopter who has applied the published `@roonga/qcms-db` migrations. There is no upgrade path and none is written; an operator drops the database and migrates a new one.

**What 064 must do to keep the two migration tests meaningful**, because a re-baseline is precisely the change that could hollow them out:

- `packages/db/src/migration-chain.test.ts` asserts that every journal entry has a snapshot, that every snapshot names its predecessor, and that nothing sits in `meta/` the journal does not account for. After the re-baseline the chain is **one entry long**, so the test still has to hold: 064 ships the **new baseline snapshot** with the `00000000-0000-0000-0000-000000000000` predecessor sentinel, and deletes the twenty-one snapshots and journal entries it replaces rather than leaving them orphaned in `meta/`, which the test would fail on. The property the test asserts is unchanged; only the length of the chain is.
- `packages/db/src/migrations.test.ts` compares the created table set to an exact list. That list is today one flat set in `public`, and after the re-baseline it becomes **a fixed table list per schema**: the control-plane tables in `control`, the seven data-plane tables in each `data_<env>` in the live set, and **nothing in `public`**. Keeping it an exact comparison per schema is what keeps the test's original purpose, which is that a migration creating a table nobody listed fails naming it (issue #861). A per-schema set also gives the test the disjointness property of criterion 3a for free.

**The baseline is hand-authored where drizzle-kit cannot express it.** The generator diffs a schema source against a snapshot and emits one set of tables; it has no notion of N copies of the same table in N schemas whose names come from a database row. So the per-environment copies, their guards and their foreign keys are hand-authored SQL in the baseline file, in the same way migration 0001's triggers and 0021's revoke block already are, with the generated portion above the hand-authored block and a comment saying which is which. The durable form is still the schema module task 064 builds: the baseline emits the first two environments and the environment command emits every later one, both from that module.

**The release note and changeset impact.** `@roonga/qcms-db` takes a **major** version bump with a breaking-change note: its published migration set is replaced, not extended, and applying it to a database created from an earlier release is not supported. `create-qcms-app` takes a **minor** bump at least, since a fresh scaffold is the supported path onto the new baseline and its database-creation step changes with it; the release note for both says in one line that an existing database is deleted and recreated. Both changesets land with 064, not with this record.

The one thing green field does not remove is the **restore drill**. `docs/backup-restore.md` opens with the claim that a backup nobody has restored is not a backup, and that is as true of a database created in this shape as of one migrated into it; `pnpm qcms:drill-restore` covering every environment in the live set is task 067's, and it is the reason the schema layout has to be something a `pg_dump` and a restore reproduce faithfully.

## 5. What the network design adds

Recorded here only as the shape; the control is SEC-14 (`docs/SECURITY_DESIGN.md` section 5a) and the recipe is the "Restricting the test environment" section of `docs/deploy-ingress.md`.

- **Two handles, not one.** A **hostname** per non-prod environment, and the **`/<env>/` path prefix** on every one of its addresses (Q21). The host is primary, because it is what a network-layer firewall and a DNS split can act on without reading HTTP at all; the path is the second handle, available to an ingress or an L7 firewall as a rule of its own, and it is also what makes a link legible to the person holding it. Both remain because they fail independently: a host rule survives a proxy that rewrites paths, and a path rule survives a wildcard certificate or a shared hostname somebody consolidated onto.
- **Anonymous entry absent from a non-prod surface by ADR-09 mount** rather than by a handler check, which is the half that survives a misconfigured edge. **It is designed and not built** (anonymous and secure-link entry are one route today), and it is task 066's mount work in section 8, so until it lands the edge rules are the whole of this layer.
- **A privilege boundary underneath both** (Q17). Each environment's pool connects as `qcms_app_<env>`, granted `control` and its own `data_<env>` and nothing else, so a statement that somehow reached the wrong environment fails on permission rather than on a search path. That is not a network control and is listed here only because the three layers are usually read as network, link and schema: the schema layer now has two mechanisms, resolution and privilege.
- An **allowlist** on the non-prod hostname: source network, VPN or identity-aware proxy. The public address is prod only, and `/<env>/f/{slug}` is not a route at all.
- **Per-environment egress** for webhook delivery, stating in firewall vocabulary what the schema split already guarantees.
- A **firewall rule table** by source, destination, port and environment, in SEC-14 and nowhere else, using only ports from `docs/PORTS.md` (R8).
- **What it does not buy:** an insider already on the allowed network, and a leaked non-prod link, are the link layer's problem; a handler that queries the wrong environment is the schema layer's. Defence in depth in that order, network then link then schema.

### Access-group names

Ruled on 2026-09-27 (Q37, amended the same day) after testing the convention against the insurer, the government department, a one-person installation, one person in two departments and the shared library.

**The stored team name is `<environments>.<plane>.<role>[.<label>]`**, unique within its workspace, with a dot between every segment. The role token is always exactly two segments, because every one of Q38's six names is, so a reader takes position 1 as the environments, positions 2 and 3 as the role, and anything after as the label: `prod.responses.viewer.claims` is environments `prod`, role `responses.viewer`, label `claims`, and `all.forms.editor` has no label. **The full name is derived** as `<workspace>.<team>` for cross-workspace lists, and the **directory group name at task C3** is that with the product prefix. **Why the stored name drops the workspace.** A team belongs to exactly one organisation already, so a stored workspace segment is a second copy of a fact the row carries, and a second copy is a thing that drifts: renaming a workspace slug would leave every one of its group names wrong. Deriving it means a slug rename changes **display only**, and the C3 mapping is unaffected because it joins on the stored external-group identifier rather than on any name.

**The segments.** The **environments** segment is one environment name, `all`, or a hyphen-joined set such as `dev-test`, which is unambiguous because an environment name carries no hyphen (section 3's reserved names and character rule). The **label** is free text and exists for a form-limited group; **a form list never lives in a name**, because that would be a second copy of the scope, stale the first time somebody added a form.

**Why a dot and not a slash.** The convention was first proposed with a slash, and the test found that a `sAMAccountName` may not contain `/`. The dot survives on-premises Active Directory group rules, and it cannot collide with a slug, which is lowercase letters, digits and hyphens.

**Four rules keep the name from becoming the thing it describes**, and they are the part worth reading twice:

1. **The team's fields are authoritative.** Role and scope are read from the team row. The name is a label the UI keeps in step, and a mismatch is a **validation error on save, never a permission**.
2. **Nothing parses a name to authorise.** If every name in the installation were wrong, no access would change.
3. **The name is never the join key.** C3 maps a directory group to a team by a **stored external-group identifier** on the team.
4. **Uniqueness within a workspace is enforced by the QCMS write path**, because the plugin does not enforce it on team names.

Inside a workspace page the UI shows the stored name, `prod.responses.viewer.claims`; the derived full name appears in cross-workspace lists and in directories. One sentence goes beside the scope chooser: **`all` on a `forms.editor` is `dev` and `test` in effect**, because every production action belongs to a `forms.approver`.

**What Q40 buys that an API check cannot.** Before it, every environment role held DML on the whole of `control`, so a defect on the anonymous respondent path could rewrite a grant row or a staff session: the schema separated one environment's answers from another's and did not separate the respondent path from the tables that decide who may read them. After it, an environment pool has no privilege on `user`, `session`, `account`, `verification`, `twoFactor`, `two_factor_resets`, `invitation`, `member`, `team` or `teamMember` at all, so that class of defect fails on permission. The five `SELECT` grants and the one `UPDATE` are exactly what the respondent and delivery paths need: resolve a form and its released version, redeem and consume a one-time link (`packages/db/src/queries/secure-links.ts`), and read the live environment set. `apps/api/e2e/security/03-db-least-privilege.e2e.ts` asserts the **table list per role**, which is the form that fails when somebody widens a grant rather than the form that passes because nobody looked.

**Why the audit row rides the same transaction.** SEC-15 records a response read, and the read happens under the environment's pool. If the row were written on the control pool it would be a second connection and a second transaction, so a read that succeeded while the audit write failed would leave no record of itself, which is the one failure an audit may not have. The environment role therefore holds `INSERT` on the SEC-15 audit and nothing else on it, and the read and its row commit or fail together. It also means the row's `actor` and `workspace` are values the writing role **cannot verify**, since it holds no `SELECT` on `user` or `member`: membership was resolved on the control pool before the read. That is the no-foreign-key precedent working as intended rather than a gap, and task 069's section says so, so nobody tries to close it with a key.

### The scenario tests, and what they were worth

Recorded because this is the part of the record that changed the design rather than documenting it. **The tests overturned four decisions, and every one of them was in text that read perfectly well**, which is the case for testing a design against a named deployment before building it.

**Scenario one, an insurer.** Three environments, `dev`, `test` and `prod`; then two workspaces, Home and Vehicle, each with separate test and prod user groups, access gated by **workspace and environment together**.

The flow held end to end: publish an immutable version, release it to `dev`, iterate, release to `test`, get it approved into `prod`, roll back by releasing an earlier version. No version is copied, no environment reaches another's data, `formId` and version numbers stay continuous, and a session started in one environment stays where it started. The three-environment case needed no change at all, which is what Q1's configurable set bought. Ten findings, all closed: three written straight into the design (the per-environment credential and runtime discovery, task 064; rollback as a release of an earlier version, ADR-40 and task 065; the hostname choice, SEC-14 and the ingress recipe), four ruled as Q24 to Q26 plus finding 2, and three confirmed as findings 5, 6 and 10.

**Scenario two, a government organisation holding sensitive personal data.** Departments as workspaces, `dev`, `test` and `prod` each, form authors who must **not** see production response data, content viewable only by the employees who action it and possibly only per form, and data handlers who need no authoring rights at all.

Scenario one's workspace-and-environment scope separates departments and environments. It does **not** separate authoring from data access, and that is what this scenario found. Seven findings, all closed: five drew the rulings Q27 to Q31, finding 14 is the surprising half of Q27 and is recorded inside it, and finding 17 was confirmed.

**What the two tests changed, rather than clarified:**

- **Q25** found that per-workspace roles alone would let a Home tester read Home **production** responses. The membership model was one dimension short.
- **Q26** found the same shape one layer down in reporting, where a per-environment view set would have shown each department's responses to the other's analysts.
- **Q27** found that a single role ladder cannot express "authors may not see production data", because every rung above `viewer` contains it. It replaced the ladder with two families that imply nothing about each other, and made `forms.owner` imply no data access at all.
- **Q29** withdrew a promise made the previous day: Q12 had given the installation-wide claim "response reads and exports" across every workspace, and an organisation with personal data cannot have an administrator who reads every department's answers by virtue of being an administrator. That reversal made the workspace a stronger boundary than the first reading claimed.

Q31 is the other kind of finding: not a wrong decision but a missing one. Nothing in the design recorded **who read a response**, and no amount of correct authorisation answers that question after the fact.

Since **Q42** that refusal is three rules and not one: the name matches **`^[a-z][a-z0-9]*$`** with no hyphen and no underscore; it is **length-checked against `reporting_<env>`**, the longest identifier derived from it, because Postgres truncates silently over 63 bytes; and a **combined environment set is written in the environments table's order**, normalised on write and refused when it is out of order, so `dev-test` is the one spelling and `test-dev` is not a second grant. It also creates the environment's database role and grants (the three kinds below), and sets that environment's per-environment configuration (Q11). **Whenever it creates a role it applies the migrate-only revokes** as well, for **every `qcms_app%` role** and not only the shipped names (Q40): all four privileges on `two_factor_resets`, and `UPDATE` and `DELETE` on the SEC-15 audit, each **guarded on its table existing**, since a role may be created before task 069 has added the audit table.
- From Q24: **dropping an environment, narrowly.** `prod` can **never** be dropped. A non-prod environment can be dropped **only when every form in it is closed and it holds zero sessions**, and the command refuses otherwise, **naming the open forms and the session count** rather than reporting a bare refusal, because an operator who has been refused needs to know what to do next. **And it reaches the access groups** (Q37): a drop **refuses** while any access group names the environment, and **names those groups** in the refusal the way `dev:seed:clear` names what it leaves, so an operator sees which grants the drop would silence rather than discovering it afterwards. **It refuses and never archives** (Q43, Code Owner, 2026-09-30): an acceptance case cannot be disjunctive, and an archive would be this command silently editing a grant an owner wrote. The operator removes or re-scopes the groups first, then drops. **The access-group half of that check is task 069's, not this task's** (Q44): a team carrying an `environments` field exists only from 069, so 064 ships the closed-and-empty check and 069 adds the group check and criterion 4b to the same command. An operator empties a `dev` environment through retention, which is a sanctioned door, and not by dropping the schema out from under it. The reason for the narrowness is precise: `DROP SCHEMA ... CASCADE` would take the answer ledger without passing the `answers_reject_delete` trigger (migration 0004), so a wider drop would be a third whole-session deletion path and ADR-17 says there are two. Under this rule a drop can only ever remove an empty schema, so no door is added, and ADR-17's Note says so.
- **How a credential reaches the API, and how the API learns an environment exists** (scenario finding 1). One role per environment means one credential per environment, and a command that creates an environment at runtime has produced a credential the running API knows nothing about. Three parts, and the design has to name all three rather than leave them to be discovered:
  - **The credential** is a per-environment entry in the typed configuration (ADR-24), one connection string per environment, named after the environment. It arrives the way every other secret does, through the environment, validated at boot and never echoed (SEC-8). It is not read from the database, because a credential the database hands out is a credential the database can be made to hand out.
  - **The environment list** is read from `control.environments`, on a connection the process already has. Postgres is the one place the live set exists, and `data_%` is the fallback shape for a consistency check rather than the source.
  - **A new environment needs a restart**, and that is this task's recommendation rather than a decision this document takes. ADR-24 parses deployment configuration at boot and fails fast, so a reload path would be a new capability in that decision rather than an implementation detail of this one: the process would have to accept a credential it had not validated at startup. Restart is also the honest operational story, since the operator has just run a command with the migration credential and is already in a change window. If reload is wanted, it is an ADR-24 amendment and belongs with one.
- From Q1 again: **the enumeration rule**, that every per-environment job, export, backup, retention pass, reporting view and telemetry attribute reads the live set, found by `data_%`, rather than a compiled-in pair.
- **A check that the control-plane and data-plane table-name sets stay disjoint**, in the `check:all` set so it runs in CI. The search path is `data_<env>, control` and the data plane is first, so a table name present in both schemas resolves to the environment's copy and **nothing anywhere says so**: no error, no warning, and a control-plane read that quietly became a per-environment one. Today the two sets are disjoint, and the check is what keeps that a fact rather than a coincidence, because the failure it prevents is a name somebody adds to the wrong schema module a year from now. It is cheap and derived, in the sense `CONTRIBUTING.md` asks for: once this task splits `packages/db` into a control module and a data-plane module, each set is declared in exactly one place, and the check is their intersection being empty. Leaving the order alone and checking the sets is the right way round, because `control, data_<env>` would shadow the other way and break the resolution half of criterion 3.
- From Q17, as ruled in **Q40 (Code Owner, 2026-09-30)**: **three kinds of application role**, with the SEC-10 recipe in `docs/operations.md` growing all of them beside the two it has today.

  | Role               | On `control`                                                                                                                                                                                                                                                                                                                                                                                          | On `data_<env>`                | Serves                                                                   |
  | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------ |
  | `qcms_app_control` | DML, with the two audit tables carved out **separately**: **nothing at all on `two_factor_resets`**, which stays migrate-only; **`SELECT` on the SEC-15 audit** and no `UPDATE` or `DELETE` on it                                                                                                                                                                                                     | **nothing, on any of them**    | better-auth, authoring, grants, releases, closes, audit reads            |

  **A response read and its SEC-15 audit row are written by the environment role in the same transaction**, which is why that role holds `INSERT` on the audit table and why it holds nothing else on it.

  **The two audit tables are not the same case, and stating them together was ambiguous.** The row above reads per table for that reason:

  - **`two_factor_resets` stays migrate-only for every application role**, `qcms_app_control` included: no `SELECT`, no `INSERT`, no `UPDATE`, no `DELETE`, exactly the four privileges migration 0021 revokes from `qcms_app` today. Issue #432's control is unchanged by this design, and widening it would be a change to that control rather than a consequence of this one.
  - **The SEC-15 audit is the table the "except `UPDATE` and `DELETE`" clause is about.** Each `qcms_app_<env>` holds `INSERT` and nothing else; `qcms_app_control` holds `SELECT`, because owners and the installation administrator read the audit through the authoring surface, and it gains `INSERT` as well once Q47's grant and revoke rows are written, since those are control-pool acts. **Neither role ever holds `UPDATE` or `DELETE`.** Only `qcms_migrate` can change an audit row.

  **Each revoke belongs to the migration that creates its table, which is migration 0021's own rule** ("the only place that runs as the table's owner in the same step that creates it"). So `two_factor_resets`' revoke, widened from the literal `qcms_app` to **every `qcms_app%` role** (finding B), is **this task's baseline migration**. The SEC-15 audit's `INSERT` grant to every `qcms_app_<env>` and its `UPDATE` and `DELETE` revoke from every `qcms_app%` role are **task 069's migration**, which creates that table; 064's baseline has nothing to grant or revoke on there. The `docs/operations.md` recipe and the environment-create command carry both, each **guarded on its table existing**, the way the recipe's existing block already is, so a command creating a role before 069 has landed skips the clause that has no table yet. `apps/api/e2e/security/03-db-least-privilege.e2e.ts` asserts the **table list per role**, so widening a grant fails a test rather than passing a review.

- From Q2, with Q40: **one connection pool per environment inside one API process, plus a control pool**, the request's environment selecting the environment pool and the authoring, identity, grant and release routes running on the control one, with the outbox deliverer and the retention sweep starting once and iterating the live set.
- **The control-only application role, confirmed** (scenario finding 18, ruled as Q40 on 2026-09-30). - From Q20 and Q32: **better-auth's Drizzle adapter verified against a non-default schema, and its string-array additional fields verified on Postgres.** The auth tables move to `control` with everything else, and the library validates the Drizzle schema on the first request through its handler and refuses to run on a mismatch (`apps/api/src/features/auth/instance.ts` maps its models explicitly), so the non-default schema is a real risk item rather than a formality: it is the one table group in this change whose owner is a third party. That is not optional bookkeeping: better-auth's startup check runs in both directions, so a column it declares that the mirror lacks, or a `NOT NULL` column of ours it never writes, is fatal on the first request through its handler (ADR-06's note on that check). `externalGroupId` is declared now even though nothing writes it until task C3, so that C3 is a sync path rather than a migration against a live deployment.

Exit criteria: (1) **a fresh database is created in the target shape** and every guard is present in every environment in the live set, asserted against a real Postgres: `control` holds the twelve control-plane tables the design starts from, plus the `environments` table this task adds, plus **the organisation plugin's five tables, which this task's baseline creates with the mirror** (068 creates them instead only if it lands first), plus `form_releases` when 065 adds it, each `data_<env>` holds the seven data-plane tables with all thirteen guards and all seven foreign keys, and **`public` holds no QCMS object at all**; and the **thirteenth guard holds end to end** (Q46): `sessions.environment` exists in every environment schema and is **`NOT NULL`**, `control.secure_links.environment` exists and is **`NOT NULL`** with a unique key on `(link_id, environment)`, both created by this task's baseline, the `CHECK` pins each `sessions.environment` to its own schema's name, the link key is **composite on `(link_id, environment)`**, an attempt to start a session in one environment from a link row naming another is **refused by the database**, and a **public session with a NULL `link_id` still carries its environment** and is still pinned by the `CHECK`, all asserted against a real Postgres rather than through the API; **Criterion 3 has two halves, and the first draft of this plan had only one.** The **resolution** half: an unqualified data-plane name resolves only inside the connection's own environment schema, asserted with a positive control in each environment, and no query helper in `@roonga/qcms-db` emits a schema-qualified data-plane name, asserted from the source. The first draft asserted only that a statement "cannot read the other's tables", which was unsatisfiable under one shared application role, because `search_path` is a resolution default and not a grant. **065 - Release records, promotion, and the admin's environment switcher.** Depends on 064. Q4, Q5, Q6 and finding 2 are answered and are what it builds.

Deliverables: `form_releases`; the release and promotion API on the admin surface; release resolution replacing "newest published version" on the respondent path; the admin screens that show what is released where and promote between environments. From Q6: **one global environment switcher in the admin shell** that sets the environment for every screen, a **persistent coloured banner** on every page while a non-prod environment is selected, and destructive actions (erasure, closing, releasing) **restating the environment in their confirmation**. From Q4: no ordering requirement, so a release straight to `prod` is allowed and the release row's source environment records the path when there was one. No backfill: green field (Q22) means there is no already-published form to write a first release row for, so the first row any form gets is written by a real release.

**Rollback is releasing an earlier version, and there is no other rollback** (scenario finding 3). Nothing is reverted, undone or deleted: the administrator releases a version that was already released in that environment before, a new `form_releases` row records it, and sessions already open stay on the version they started (Q5). The release history has to **show that as a rollback** rather than as an ordinary release, because "released version 4 after version 7" is the shape an incident review reads, and a history that presents it as just another row makes an operator count backwards to see what happened. That is a presentation requirement on this task, not a second mechanism.

Exit criteria: (1) a form version released to `test` and not to `prod` is served in `test` and not in `prod`; (2) promotion writes a row and copies nothing, with the form id and version number unchanged; (3) a release never re-pins a live session (ADR-07, I4, confirmed as Q5), asserted with a session open across a release; (4) the release history answers who released what, when, from where, and with whose approval, **and marks a release of an earlier version than the one it replaces as a rollback**; (5) a release to `prod` with no prior `test` release succeeds and is recorded as such; (6) the switcher sets the environment for every screen, the banner is present on every page under a non-prod environment and absent under `prod`, and each destructive confirmation names the environment, asserted in the browser suite because a banner nobody renders is the failure mode here; (7) releasing an earlier version leaves every prior release row intact, since the history is append-only.

**And the two churn mitigations finding 2 accepted.** Every `dev` iteration publishes an immutable version and R1 keeps it, so a week of iterating leaves a long version list. That cost is accepted rather than designed away, because promotion is a record and not a copy and no cheaper mechanism keeps the audit promise; what this task builds is presentation, not a second model. A combined **"publish and release to `<env>`"** action, so one intent is one act rather than two. A **"released anywhere"** filter in the version list, so the versions that only ever reached `dev` are hideable. Exit criterion: one action publishes and releases atomically or not at all, and the filter's default shows every version so nothing is hidden by surprise.

Gates: `pnpm verify`, `pnpm verify:browser` (once per environment), forced Docker-backed run.

The slug uniqueness and shared-workspace rules are unchanged by the table's owner moving: they are QCMS domain rules enforced in QCMS code either way.

From Q14: **moving a question between workspaces**, which is one `UPDATE` on the identity row and touches no version. Forms elsewhere that already pin one of its versions keep serving and keep that pin in their next draft (ADR-02, R6); a **new** pin from another workspace onto a question outside the shared workspace is refused, through the same path that refuses a pin to a `deprecated` version, so authors meet one mechanism rather than two.

From Q15: **archiving a workspace, never deleting one.** Archiving requires no open form and no released version, and the workspace's forms and questions are reassigned first, so it is the last step rather than a cascade. No response row is reached, which keeps ADR-17's two whole-session delete doors at two.

From finding 10: **the shared workspace is the org-wide library, and its asymmetry is the design.** Every workspace's editors **see and may pin** its questions; **only the shared workspace's own members edit them.** So it is a read surface to everyone else, which is what makes it a library rather than a place three groups overwrite each other's wording. The question's text is the one thing that crosses a workspace boundary, and no response ever does.

Exit criteria: (1) a form or question cannot exist without exactly one workspace, enforced by the column rather than by a backfill; (2) publish refuses a new pin to a question owned by another non-shared workspace, and a form that already pins one keeps serving and keeps it in its next draft; (3) slugs are unique installation-wide, enforced by the database and not by authoring convention; (4) archiving is refused while an open form or a released version remains, and succeeds once they are reassigned; (5) no code path deletes a workspace, and none reaches a response row from one, asserted rather than reasoned; (6) an editor outside the shared workspace can read and pin a shared question and **cannot edit one**, asserted on both halves; (7) no published version changes and no public address moves.

Gates: `pnpm verify`, forced Docker-backed run.

**069 - Membership on better-auth's organisation plugin: two role families, scope, names, and the access audit.** Depends on 068, and on 064 for the environment command it adds the access-group drop check to (Q44). Q12, Q25, Q27, Q28, Q29, Q31, Q32 to Q37, finding 17 and the rulings Q44, Q45 and finding G are answered and are what it builds; Q47 is this task's one open item. **The permissions matrix in section 6 is this task's specification.**

**The tables are the plugin's, and there is no `workspace_members` table** (Q32). A workspace is an `organization` row; `forms.owner` is the `member` row's role and the plugin's `creatorRole`; **every other grant is a `team`** whose additional fields carry one of the six Q38 roles (`forms.viewer`, `forms.editor`, `forms.approver`, `responses.viewer`, `responses.eraser`) and its scope, `environments` as a set or `all` and `forms` as a list or `all`. Team membership is the grant, so a user in three teams holds three grants, which is the several-rows-per-user shape Q25 asked for. The UI calls a team an **access group**.

Deliverables:

- **Six static roles as disjoint statements** over the resources `question`, `form`, `release`, `link`, `webhook`, `response`, `membership`, `workspace` and `audit`. The environment and form conditions live in the grant's scope and never in a statement. `dynamicAccessControl` **off**, and the default `admin` and `member` role names overridden with empty statements.
- **The declared additional fields**, all typed and none of them in `organization.metadata` (Q39): the role and the scope on the team, **`team.externalGroupId`** (string, `input: false`, unique, written only by the task C3 sync path) and **`organization.seedNewEditorsWithTestData`** (boolean, default off). The onboarding flow **reads that setting** to decide whether a new `forms.editor` also gets the optional `dev` and `test` `responses.viewer` grant, so F17's convenience is a workspace choice rather than an operator habit, and the grant it creates is an ordinary visible one.
- **The resolver and the middleware** (SEC-3): resolve the user's `member` row and teams in the workspace, evaluate the role's statements with the plugin's own authorize function, then narrow by the team's scope against the route's environment and form. The plugin's HTTP `hasPermission` is **not** used, because it needs the signed cookie the API does not hold, so the authorize function is called directly. Never in a BFF (R2) and never only in the UI.
- **QCMS write endpoints for grants and membership, and they are the only write path** (Q45, Code Owner, 2026-09-30). They sit behind the installation claim or the `forms.owner` role, write `member` and `teamMember` rows through `@roonga/qcms-db`, and run the cascades and the SEC-15 audit in code. **The plugin's own team and member write endpoints are not an owner path**: they are **disabled, or refused, for everyone**, including a `forms.owner`. This replaces the earlier shape, which allowed owners through the plugin's endpoints on the auth allowlist and accepted two write paths to one table. One write path is the ruling, for two reasons that the two-path shape could not answer. The QCMS endpoints are where the validation lives and where the **SEC-15 rows** are written, so a second path is a path on which a grant changes without an audit row. And the plugin's **removal cascades** run inside the library, below any endpoint QCMS could gate, so the only way to be sure a removal is audited is for no removal to originate there.
- **The plugin's before-hooks as a backstop, carrying the same validation as the QCMS write path** (the hooks note under Q32, issue #995 comment 5849888413, narrowed by Q45). Since the plugin's write endpoints are disabled or refused for everyone, these hooks are no longer the guard on a second sanctioned path; they are what catches a call that reaches the plugin anyway, through a configuration slip or a library change. `beforeCreateTeam`, `beforeUpdateTeam`, `beforeAddTeamMember` and the member hooks are registered so that nothing arriving that way can get round the rules the QCMS endpoints enforce: the **name is in step with the fields** (Q37), **every environment in the scope exists**, the **workspace is not archived** (Q15), the **role is one of the six** (Q38), the **two non-team targets are never written as teams**, and **`externalGroupId` is never set through a plugin endpoint** (Q39), since only the task C3 sync path writes it. Two write paths, one rule set.

  **A correction, and then a reason the question stopped mattering** (finding D, resolved by Q45). This paragraph said "the plugin fires no hook on its removal cascades", which is not accurate at 1.7.5 as pinned: the **delete endpoints do fire their hooks**, and what fires nothing is the **internal cascade** a delete runs underneath them, so a team removed through the endpoint is visible to a hook while the team-member rows that go with it are not. Under Q45 the distinction is moot for the write path, because no removal originates at a plugin endpoint at all; the hooks are registered as a **backstop** rather than as the mechanism, so a call that somehow reaches one is refused rather than validated.

- **A capability endpoint** (`GET /me/access` or the equivalent) answering which workspaces, roles, environments and forms the caller holds. It is how everybody who is not an owner or the installation admin learns their own grants, since the membership list itself is theirs alone to see (Q35).
- **The configuration guards**, asserted rather than set and forgotten: `allowUserToCreateOrganization: false`, `disableOrganizationDeletion: true`, `teams.enabled: true`, `teams.defaultTeam.enabled: false`, `teams.allowRemovingAllTeams: true`, `membershipLimit` raised from its default of 100, and `activeOrganizationId` and `activeTeamId` never set by QCMS.
- **The access audit** (Q31, **SEC-15**): an append-only `control`-schema table recording every response read, export and erasure with actor, workspace, environment, form, kind and time, readable by the workspace's owners and by the installation admin. `two_factor_resets` is the precedent shape, including its deliberate absence of a foreign key to the account, because an audit row that cascades away with what it describes is not an audit row.

  **Its grants and revokes are this task's migration, not 064's baseline** (Q40, corrected 2026-09-30). The rule is migration 0021's: a revoke lives in the migration that creates its table, because that is the only place that runs as the table's owner in the same step. So this migration grants **`INSERT` to every `qcms_app_<env>`**, grants **`SELECT` to `qcms_app_control`** (plus `INSERT`, once this task's own grant and revoke rows are written, which are control-pool acts), and **revokes `UPDATE` and `DELETE` from every `qcms_app%` role**. The `docs/operations.md` recipe and 064's environment-create command carry the same clauses guarded on the table existing, so a role created before this task lands is correct and stays correct afterwards. 064's baseline owns only `two_factor_resets`' revoke, which is its own table.

  **The environment role cannot verify the actor or the workspace it writes, and no foreign key is added to make it** (noted 2026-09-30). A staff response read spans two pools: membership resolves on the control pool, and the read plus its audit row commit on the environment pool, which holds no `SELECT` on `user` or `member`. So `actor` and `workspace` arrive as values the writing role cannot check. That is the same shape `two_factor_resets` already has and is deliberate: an audit row carrying a foreign key into what it describes is an audit row that cascades away with it. This task must **not** add such a key to close the gap, and the API is where the two values are established, before the write.

- **The section 3.2 matrix extended** in `docs/SECURITY_DESIGN.md` with the new columns (the six roles and the installation claim) and the new rows the permissions matrix names, with `apps/api/e2e/security/01-authorization-matrix.e2e.ts` and `matrix-coverage.e2e.ts` moving in the same change, since that test parses the Action column by exact wording. **That extension is this task's and not the PR that records the design.**
- **A seed `responses.viewer` grant** scoped to `dev` and `test` for a new `forms.editor`, optional, and visible in the access-group list like any other (finding 17), so a convenience is never an implication.
- **The access-group naming convention** (Q37), which is a deliverable rather than a guideline because the write path enforces part of it. The **stored** team name is `<environments>.<role>[.<label>]`, dotted, with the environments segment one name, `all`, or a hyphen-joined set, and the label free text. The **full name and the directory name are derived**, `<workspace>.<team>` and `qcms.<workspace>.<team>`, and neither is stored. The QCMS write path enforces **uniqueness within the workspace**, which the plugin does not, and **refuses a name out of step with the team's fields** on save, since the fields are authoritative and the name is a label. Nothing parses a name to authorise. The UI shows the stored name inside a workspace page and the derived full name in cross-workspace lists, and prints one sentence beside the scope chooser: **`all` on an editor is `dev` and `test` in effect**, because every production action belongs to an approver.

- **Every grant holder carries a `member` row with the empty role** (finding G, Code Owner, 2026-09-30). Team membership is the grant (Q32), and the plugin's own team endpoints and queries assume the user is a member of the organisation the team belongs to, so a person holding only a team grant and no `member` row is a shape the library does not model. So every grant holder gets a `member` row whose role is the **`member` name overridden with empty statements** (Q32's configuration guards), which grants nothing on its own and exists to make the person a member of the workspace. `forms.owner` is the one role that is on the member row rather than on a team, and it is unaffected. **Task 068's seeding uses the server-side `createOrganization` with `userId`** rather than the request-scoped call, because the seeded workspace is created before anybody is signed in and the session-based form has no user to attribute it to.

- **The access-group half of the environment drop check, moved here from task 064** (Q44, Code Owner, 2026-09-30). The environment command's drop **refuses** while any access group names the environment, and **names those groups** in the refusal (Q43). The check lives here rather than in 064 because a team carrying an `environments` field exists only from this task: 064 ships the closed-and-empty half and this task adds the group half to the same command, with **exit criterion 4b and its cases** coming with it.

**Authoring and publishing stay environment-agnostic** (Q25), because publishing a version releases it nowhere, and so does the draft preview (Q36): editor-only, writing nothing and reading no response, so there is no environment to scope it to. The Q6 switcher offers **only the environments the caller holds** in some grant.

**This task's one open item: the self-grant** (item 1 of issue #998, deferred with the authorisation work, Code Owner, 2026-09-30, Q47). Nothing stops a `forms.owner`, or the installation administrator, granting **themselves** a `prod.responses.viewer` group, which would make "an author never sees production personal data" a convention rather than a control. It is **not decided now and SEC-15 is not changed now**; what is recorded is the Code Owner's recommendation, so this task is written against a direction rather than against a blank:

- **Every grant write and every revoke is a SEC-15 row**, which **widens that control's kinds** from read, export and erasure to add **grant** and **revoke**. SEC-15 is amended by this task rather than by the record of the design.
- **A self-grant of a `responses.*` role is refused only when the workspace's `requireSecondApprover` switch is on**, and then it needs a **second `forms.owner`, or the installation administrator, to confirm** it. With the switch off it is allowed and audited.
- **The installation administrator follows the same rule**, so the claim is not a way around it.

The reason the refusal is conditional rather than absolute is Q13's trap, one layer along: a one-account installation has no second owner, so an unconditional refusal would leave that installation unable to read its own responses at all, and the first thing its operator would learn about the control is how to get round it. The switch is the same one that governs the two-person rule for a `prod` release and a `prod` endpoint change (Q30), so an installation turns on one thing and gets the whole two-person posture.

Exit criteria, written to probe **both families against every action** rather than each family against its own, and to walk the permissions matrix row by row:

1. Every role in both families is probed against every action in the matrix, so a right that leaks across the families fails a test rather than a review.
2. **A `forms.editor` with `prod` in scope reaches no response in any environment**, and **a `forms.owner` reads none without a `responses.viewer` grant**. Those are the surprising half of Q27 and the reason this task has this shape.
3. A **`responses.viewer`** holds no authoring right: it cannot edit a draft, publish a version or release one. A **`responses.eraser`** cannot read or export. And a **`forms.viewer`** can do none of it: it cannot release, cannot approve, cannot edit a draft or a preview, and reads no response.
4. **A grant scoped to `test` is refused every environment-scoped action in `prod`** on the same workspace, and a data grant scoped to a form list is refused the responses of a form not on it (Q28).
5. An administrator with **no** grant and no installation claim reaches nothing; one **with** the claim administers settings, users, memberships and environments and **reads no response, exports nothing and erases nothing** anywhere (Q29), which is the matrix's `never` row.
6. **Closing and reopening** follow Q33: a `forms.editor` with the environment in scope for `dev` and `test`, a `forms.approver` with `prod` in scope for `prod`. **A `forms.owner` cannot approve a prod release** (Q34).
7. The **membership list and grants** are readable by owners and the installation admin only (Q35), and the capability endpoint answers each caller's own grants and nobody else's.
8. **Every response read, export and erasure writes one audit row** with the six fields, and no path reads or exports without one.
9. The configuration guards hold, asserted against the running instance: no user can create an organisation, no organisation can be deleted, teams are on, no default team is created, and `activeOrganizationId` is never set.
10. Enforcement is in the API, and a BFF or UI bypass reaches a refusal.
11. The section 3.2 table and the probe inventory stay in step, which `matrix-coverage.e2e.ts` enforces.
12. **A duplicate stored group name in one workspace is refused**, and the same name in another workspace is accepted, since uniqueness is per workspace.
13. **A group name out of step with its team's role or scope is refused on save**, and no such mismatch can change what the group grants: the fields decide, asserted by editing a name to a wrong one through the database and showing the permission unchanged.
14. **A plugin-endpoint call that violates any of the before-hook rules is refused**, asserted one rule at a time: a name out of step with the fields, an environment in the scope that does not exist, an archived workspace, a role outside the six, an attempt to write `forms.owner` or the installation claim as a team, and **an attempt to set `externalGroupId`** (Q39).
15. **Both Q39 fields behave as declared**: `externalGroupId` is unique, is absent from every request body the API accepts, and no code path but the sync seam writes it; `seedNewEditorsWithTestData` defaults **off**, and onboarding a `forms.editor` creates the `dev` and `test` `responses.viewer` grant when it is on and creates nothing when it is off.
16. **The plugin's own team and member write endpoints are refused for everyone, a `forms.owner` included** (Q45), asserted as a refusal from the endpoint and not only as an absent UI affordance; and **every grant write and revoke that does succeed went through a QCMS endpoint**, so no grant changes anywhere without the validation and, once Q47 is built, without its audit row.
17. **Every grant holder has a `member` row carrying the empty role** (finding G), asserted after a grant is created through the QCMS endpoint and after 068's seeding, and that row grants nothing on its own: a person holding it and no team reaches exactly what an administrator with no grant reaches, which is nothing.
18. **The environment command's drop refuses while an access group names the environment, and names those groups** (Q43, Q44), with a drop succeeding once the groups are removed or re-scoped; this is criterion 4b, moved here from task 064.

**070 - The two-person rule for production.** Depends on 065 and 069. Q13, Q30 and finding 5 are answered: **one per-workspace switch**, **off by default** including on the seeded workspace, governs the two-person rule for **both** a `prod` release **and** a `prod` webhook endpoint change, and it gates `prod` alone.

Deliverables: the per-workspace setting, on the workspace's `requireSecondApprover` additional field (Q32) and defaulting off; the check at release to `prod` and at no other release, so a release to `dev` or `test` is self-service for an editor holding that environment in scope; **the same check on a `prod` endpoint change** (Q30), which is why this is one switch and not two; the approval recorded on the ADR-40 release record; the admin flow that asks for it. One person may hold `forms.editor` and `forms.approver` grants together, so the rule is about two accounts rather than two kinds of person.

## 9. Identity, and a later track C

**Status: assessed, decided later, not built.** Written at the Code Owner's request on 2026-09-26 so that track A and track B are built against a known direction rather than an unexamined one. Nothing in this section is scheduled, and the decisions it names are the Code Owner's to take when it is.

### What better-auth carries under this plan

better-auth is the **authenticator**: email and password, TOTP, breach-checked passwords, sign-in throttling and sessions, in process in the API (SEC-1, ADR-06, ADR-35). Its identity tables move to `control` with the rest of the control plane (Q20), and task 064 verifies its Drizzle adapter against a non-default schema, which is the one third-party risk in that move.

**It now carries authorisation as well, and that is a ruling rather than a direction** (Q32, 2026-09-26). The earlier version of this section said the `organization` plugin is not used for membership and then, after the Code Owner asked for a re-evaluation, that the mechanism was under evaluation. Both are superseded. A workspace is an organisation row; `forms.owner` is the member row's role; every other grant is a **team** whose additional fields carry one role and its environment and form scope; the six roles are disjoint statements with `dynamicAccessControl` off; the check runs in the QCMS API middleware; and grant writes are QCMS endpoints. Section 6's Q32 row has the whole ruling and ADR-41's Decision is where it binds.

**What that changes about this section's own subject.** The exit path widens: leaving better-auth was one verifier function and is now the authorisation layer too, because membership, roles and scope live in its tables. `docs/auth-swap.md` and the risk acceptance in `CONTRIBUTING.md` say so. And **track C is no longer a swap**; it is better-auth's own SSO plugins, which is the cheaper shape and the one the Q32 direction points at.

The existing `role` additional field (default `admin`, `input: false`, no request path) becomes the **installation-wide administer-only claim** of Q29. That is the whole of its job.

### Enterprise identity, as a direction rather than a decision

An adopter running Entra ID, Auth0, Okta, Keycloak or AD FS will ask for single sign-on. Since Q32 this is **an extension of better-auth rather than a replacement of it**: track C uses the library's own SSO plugins, so the identity work joins the authorisation work already there instead of prising it out. The shape below is the assessment; each bullet marked **decision** is one to take when track C is scheduled, not now.

- **Protocol: OIDC first, SAML second.** AD FS is the reason SAML is on the list at all. LDAP and Kerberos against on-premises Active Directory are **out of scope**: that estate fronts itself with AD FS or Entra ID, and QCMS should talk to the front rather than to the directory. better-auth's own generic OAuth and SSO plugins are the mechanism, consistent with Q32's direction, and the plugin and its maturity are to be verified against the pinned version at scheduling time rather than assumed from this paragraph.
- **Identity comes in; the authorisation model is unchanged.** Just-in-time user creation on first SSO sign-in, with **no memberships**: a new SSO user can sign in and see nothing until somebody grants them one. Mapping IdP groups to grants means mapping **a directory group to a team** (Q32), by a **stored external-group identifier** on the team and never by a name (Q37), so a group-derived grant is a team-member row visible in the membership list like any other rather than a second invisible mechanism, and a workspace slug rename strands no mapping. The mapping has three targets: a team, the member row's `forms.owner` shown as `<workspace>.forms.owner`, and the installation claim shown as `qcms.admin`.
- **Deprovisioning is the real enterprise ask.** The 12 h absolute session lifetime bounds the window today, which is a bound rather than an answer; SCIM or a periodic check against the IdP is what ends access properly.
- **MFA policy (decision).** Either accept the IdP's MFA assertion from its claims and skip local TOTP, or refuse sign-in without such an assertion. Never both prompts: double-prompting is how operators end up turning one of them off.
- **Break-glass (decision).** Local email and password kept for the installation administrator only, or switchable off per installation. SEC-1's `qcms:create-admin` and `qcms:reset-2fa` are the existing shapes to build on.
- **Account linking by IdP subject, never by email alone.** Email-collision account takeover is the reason, and it is worth stating as a rule rather than leaving to an implementer.
- **One IdP per installation** to begin with; per-workspace IdPs a later option, and a bigger one than it sounds because it interacts with membership.
- **The access audit (Q31) records the IdP subject as actor**, so a read is attributable to a person the adopter's directory knows.
- **Respondents are untouched.** Respondent identity is separate by design (ADR-06): anonymous sessions and secure links. SSO for respondents on a staff-facing form would be its own feature with its own decision.
- **Configuration** is issuer, client id, client secret and redirect URIs as typed installation configuration (ADR-24, SEC-8). The admin hostname has to be stable, because it is in the IdP's redirect allowlist.

A new ADR (enterprise identity) and a Note on ADR-06 are the artifacts, written when the decisions above are taken. Refs #179.

## 10. Non-goals

Multi-tenancy (R7, ADR-04). A second database, a second deployment, a second API process, or replication between environments. Per-workspace configuration, theming or ports. **A seventh role for de-identified or anonymised response data**: that need is served by Q26's reporting views, which are already per workspace and per environment with a read-only role of their own, so it is a grant in the database rather than a role in the model. Per-environment configuration beyond the two settings Q11 names. A workspace segment in any URL. An environment visible in a token, as opposed to in a path. Deleting a workspace. Copying a version between environments, in any form: promotion is a record, and a copy would break R1, R6 and ADR-18 at once.
