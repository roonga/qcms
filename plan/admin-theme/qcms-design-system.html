Two seats

Portal and QCMS: one system, two identities

The design system now has two owners, each with its own document. Portal is the respondent-facing seat; QCMS is the operator-facing seat. This page holds only what both draw from: the foundations below.

Portal - the respondent seat

External, mobile-first, and themeable by the adopter.

Adopter-themeable, 4 predefined themes Respondent runtime controls: mode, font, density Comfortable 44px+ scale Subtle corners WCAG 2.2 AA / AAA in high contrast

See: Portal design doc (Portal group)

QCMS - the operator seat

Internal, dense, and fixed to QCMS's own identity.

Fixed QCMS Cobalt, never respondent-themed Dense 40px scale Sharp industrial corners: 4 / 8 / 2 Translucent mode-following topbar Per-operator light / dark / high contrast

See: QCMS design doc (QCMS group)

Both seats share one token discipline and the foundations below: the same color system, type, radii, and spacing rhythm. They diverge in goals, scale, and corner character.

Foundations

Color, tokens, type, rhythm

Every value is a token. The whole system flips between light and dark from one set of custom properties, and the same set is the single surface an adopter overrides to re-skin the portal. Contrast is verified, not assumed: WCAG 2.2 AA is the floor.

Palette and semantic color

Key text and surface pairs are annotated with their measured contrast ratio. Semantic hues (success, warning, critical) sit apart from the brand accent and never carry state alone: they always travel with text or an icon.

Type

Two roles, both from self-hostable system stacks so the page renders offline with no webfont request. A humanist UI face carries reading and forms (adopter-swappable). A monospace face carries every identifier, version, hash, and JSON fragment, so machine facts read as machine facts.
