# Workspace access: implementation plan

Status: proposal. The rules are in [`docs/WORKSPACE_ACCESS.md`](../docs/WORKSPACE_ACCESS.md), the single source of truth; this plan only orders the work. Where the two differ, the document holds.

- Baseline: `origin/main` at `c901780b`. The ledger in `docs/features/README.md` ends at 083. Task numbers 084 to 105 below are **proposals**; they bind only when the ledger reserves them.
- Every admin UI task is gated on its design batch: no dispatch until its screens are on the design canvas and the Code Owner has seen them ([section 12](../docs/WORKSPACE_ACCESS.md#12-navigation-and-screens)).
- Green field: no data migration, upgrade path or backward compatibility ([section 1](../docs/WORKSPACE_ACCESS.md#1-status-and-authority)). Work orders restate this so reviewers do not read the removal of form scope and old roles as data loss.
- Gates: V = `pnpm verify`; D = `pnpm exec turbo run test --force` (executed, not cached); B = `QCMS_PORT_SEAT=<n> pnpm verify:browser:detached` then `pnpm verify:browser:wait <dir>` (never with D on one checkout); E = `QCMS_PORT_SEAT=<n> pnpm up:e2e`.
- Every task: template mirrors via `packages/create-qcms-app/sync-templates.mjs`, `pnpm openapi:generate` when routes change, dead-key check, logs under `node scripts/agent-scratch.mjs <name>`, and a PR that lists the suites run and skipped.

## 2. Code findings that shape the tasks

- No mail transport, configuration, template or dependency exists (`docs/features/061-forced-password-change.md`).
- The API already has a one-step publish (`publish-batch`, `release-batch`) and a default workflow that refuses draft to `prod`; the Publish work is policy, generalising "prior test" to "prior non-prod", UI, assistant cards and copy.
- `POST /admin/forms/{id}/workspace` exists, needs `workspace:update` on the source only, writes no audit row and has no preview.
- The shared question library API is complete (`PUT /workspaces/{id}/shared`); there is no admin screen.
- `two-person.ts` is a synchronous author-versus-releaser compare with no request lifecycle; the base for approval requests is the `webhook_endpoint_proposals` two-act pattern.
- Every account defaults to the Site administrator claim (`apps/api/src/features/auth/instance.ts`).
- The add-member route answers "no such account" for unknown addresses (`apps/api/src/features/membership/handler.ts`).

- `docs/WORKSPACE_ACCESS.md` and the decision-record cleanup land first, in one docs PR. No task below starts before it merges, except the workspace list fix and 084, which rest on rulings already recorded.
- The handover sections named in section 7 are the document's headings.

## 8. Risks

- Lockout: the last active Site administrator is guarded in 091 and 092; `qcms:create-admin` and `qcms:reset-2fa` remain the break-glass path when no Site administrator can sign in.
- 085 is large and touches every fixture; land it alone, run V, D, B and E, and merge nothing else on `policy.ts` until it is in.
- An unapproved mail dependency stalls 090 to 092 and the whole account UI; bring it to the Code Owner with the precondition PR.
- The approval table serves two scopes; review must confirm a workspace request cannot be decided by a Site administrator who is its requester.
- The fixed `prod` floor changes `releases/workflow.ts`; 094 must prove no workflow configuration lifts it.
- Move form changes who reads responses; the preview must use the same evaluator as access, or it drifts.
- The UI tail waits on design batches 2 to 7; a late batch moves the end date, not the API work.
- The agent builder work shares `workspace-settings-panel.tsx` and migration numbering; whichever merges second rebases.
