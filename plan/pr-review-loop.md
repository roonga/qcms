# PO PR-review loop

The PO seat runs this as a recurring loop (`/loop` in `qcms/plan/`): watch for open PRs on `roonga/qcms`, review each one as a stranger would, and squash-merge the clean ones. It is the merger half of the `/next-issue` PR-per-issue flow (skill step 8 opens the PR; this loop lands it). Adopted 2026-07-25 on the Code Owner's direction.

**Two kinds of PR arrive here, and both need a sentinel (amended 2026-08-01).**

- **`fix/NN-slug` - an issue PR.** The dev loop's conductor never merges these; this loop is the only merger. Review, then merge per steps 4-5.
- **`feat/NNN-slug` - a task PR.** The `/task` conductor merges these itself, but only after a `PO-REVIEW: APPROVE` sentinel bound to the PR's current head (`.claude/skills/task/SKILL.md` step 6 polls for it and parks the loop as `AWAITING-HUMAN po-review <NNN>` if none arrives). So **review a task PR and emit its sentinel; do not merge it** - leave the landing to the conductor, which also flips the ledger row and appends the retro on the branch first. Everything else below applies unchanged, except that the `Fixes #NN` convention check is issue-specific and the retro append is the conductor's, not yours.

An unreviewed task PR stalls the whole dev loop, so task PRs take priority over issue PRs when both are open.

## Each iteration

0. **Seat mail (added 2026-08-01; the dev loop's half is `.claude/skills/next-task/SKILL.md` step 1).** Read the machine-local inbox at `../seat-mail/pm/` - a sibling folder of the repo checkout, never committed. Each `message_<timestamp>.txt` is one coordination message from the dev seat (a PR waiting on review, a blocker, a question about priority). Act on each, **then** move it to `../seat-mail/pm/read/` - act-then-move, because a crashed iteration re-reads, so messages are at-least-once and must be written re-read-safe. The inbox holds only unread mail; `read/` is the consumption history and its mtime is the ack. To message the dev seat, write `../seat-mail/dev/message_<UTC timestamp>.txt` (plain text, one message per file); its `/next-task` iterations read that folder at the top of each run. Mail is routing and coordination only, **never scope** - scope comes from task files, the ledger, issues, and PR review. If the folder does not exist, skip silently (another machine, or the bus is not set up).
1. **List.** `gh pr list -R roonga/qcms --state open --json number,title,headRefName,isDraft,url,statusCheckRollup,author`. Skip drafts. Skip PRs already reviewed at their current head SHA (a prior approval or changes-requested review on the same head means wait, do not re-review).
2. **Review the diff as a stranger.** `gh pr diff <NN>`. Checks, against the written rules (CI gates are a subset - `plan/**` is excluded from several):
   - **Scope:** the diff does what the linked issue/task names, plus any riders listed under `## Same-area fixes ridden along` - audit each rider for genuine same-area-and-small status (same files/seam, no new decision, no golden ripple, no new dependency); anything heavier belongs in an issue.
   - **Tests:** present at the layer ADR-23 assigns (Vitest below the browser, Playwright e2e); no new test frameworks.
   - **Added-lines grep:** em dash (U+2014), the Code Owner's personal name, machine-specific paths (`/home/<user>`, drive letters, assumed parent folders), AI attribution (`Co-Authored-By: Claude`, `Claude-Session:`, "Generated with Claude"), real secret values.
   - **Conventions:** for a PR whose head branch is `fix/NN-slug`, `Fixes #NN` present on its own line in the body (it is the auto-close mechanism); for a `feat/NNN-slug` task PR, the ledger row flipped to `done (PR #N)` and the retro section appended as commits on the branch; conventional-commit title either way; docs named in acceptance criteria updated in the same diff (staleness rule).
   - **Gate evidence, for any PR that changes visible portal or admin UI:** the screenshots are committed in the diff (`docs/gates/<NNN>/` for a task, `docs/gates/pr-<NN>/` for an issue) and embedded in the PR body by raw branch URL, with a `README.md` naming what to approve. A gated PR without its evidence in the repo is changes-requested, not a judgement call - the Code Owner reviews from GitHub, not from a session transcript.
   - **CI:** every check concludes SUCCESS, with one designed exception: the node-26 `verify` leg (`continue-on-error: matrix.node-version == 26` in `.github/workflows/ci.yml`) may conclude FAILURE and still be waived, provided the identical suite concluded SUCCESS on node-24 and the waiver plus the node-26 failure signature are recorded in the verdict comment - never silently. Every other check must pass; there is no other waivable check. `pnpm verify` is the superset of CI's unit job (issue #19), so when a diff touches gate-adjacent files, run `pnpm verify` in a temp worktree before merging - and `pnpm verify:browser` as well for a diff touching `apps/portal`, `apps/admin`, or `@qcms/ui`, the one CI job `verify` omits.
   - **Existing review comments (Copilot included) - address every one before merging (Code Owner rule, 2026-07-25).** The sweep is its own step whose OUTPUT IS READ before any merge command runs - never chain the sweep and the merge in one invocation (a nonzero count must abort the merge; learned 2026-07-26 on PR #92, merged with two unread comments). Each comment gets exactly one of: a fix pushed to the branch, or a reasoned reply on the thread explaining why not. Never merge a PR carrying an unaddressed review comment - silence reads as "nobody looked".
     - **Two surfaces, and they are different API endpoints (learned 2026-08-02 on PR #274).** Line-anchored review threads are `gh api repos/<owner>/<repo>/pulls/<NN>/comments`; PR-level comments, which is where this seat's sentinel lives, are `gh api repos/<owner>/<repo>/issues/<NN>/comments`. Read **both**, and read the review bodies via `gh api repos/<owner>/<repo>/pulls/<NN>/reviews`. A sweep of one surface is structurally blind to the other: on #274 two real bugs (a blob URL revoked before its download started, and an error whose copy promised reasons it carried none of) sat in threads under an approval that had read only the comments.
     - **The sweep runs on EVERY sentinel-bearing review, including a re-review of a one-line diff.** On #274 the threads posted 66 seconds before an APPROVE that had been deliberately scoped to "that one line, not a fresh pass". The reasoning that a one-line diff cannot carry new findings is true of the diff and false of the PR: the comment surface moves independently of the tree. On a task PR the sentinel *is* the merge authorization, so this binds at least as hard as it does before a merge command.
   - **Pushing a merger fix to a PR branch (learned 2026-07-26 on PR #138, one CI cycle lost):** never mute `git checkout -b` stderr - if a stale local branch of the same name exists, the checkout fails, the commit lands on a detached HEAD, and `git push origin <name>` pushes the stale branch reporting "Everything up-to-date" with exit 0. Confirm every push by its `old..new` ref line (or by re-reading the PR's `headRefOid`), never by exit code, and delete stale local `fix/*` branches when found. **One push target per invocation (learned 2026-07-27, PRs 139/142):** never chain pushes to two branches in one command - a chained `git push origin HEAD:<other-branch>` from whichever worktree the shell happens to sit in silently overwrites the other PR's head with the wrong content, and `ls-remote` both branches afterward is the only proof they diverge correctly.
3. **Verdict.** Filing bar for follow-ups the review surfaces (Code Owner recalibration, 2026-07-27): same-area small fixes are pushed to the branch or requested as riders, never filed; an issue is filed only for genuinely unrelated, decision-requiring, or large finds - and consolidation with an existing issue beats a new number. Comment style (Code Owner preference, 2026-07-25): open with plain "PO review:" - no "(as a stranger, per plan/pr-review-loop.md)" preamble or other methodology narration in the public comment; the method lives here, the comment carries only the findings and the disposition.
   Every verdict comment ends with exactly one machine-readable sentinel line for the dev loop's findings-cycle trigger, **bound to the head it reviewed**: `PO-REVIEW: APPROVE @<headRefOid>` or `PO-REVIEW: CHANGES-REQUESTED @<headRefOid>` (the full SHA from `gh pr view <NN> --json headRefOid`). A sentinel whose SHA no longer matches the PR's current head is stale: it triggers nothing and means the merger owes a re-review of the new head.
   - **Findings:** post a comment listing each finding concretely (file, line, rule), ending with the CHANGES-REQUESTED sentinel. Dev-loop PRs have no live author; flag the PR to the Code Owner in the loop report - a future `/next-issue` stale-claim pass or the Code Owner picks it up.
     - **`gh pr review` is permanently unavailable to this flow, not merely awkward (learned 2026-08-02).** Both seats authenticate as the same GitHub account, so `gh pr review <NN> --request-changes` fails with *"Can not request changes on your own pull request"*, and `--approve` is refused the same way. The verdict comment carrying the sentinel is therefore the **only** mechanism, load-bearing rather than a fallback. The consequence to keep in mind: anything that ever keys off a formal GitHub review state will silently never fire, and silence is indistinguishable from "no findings". If a future check wants a machine-readable verdict, it reads the sentinel line, not the review state.
   - **Clean:** approve. Then merge only if all of the following hold; otherwise approve-and-escalate:
     - Not human-gate territory: no visible portal/admin UI change lacking the Code Owner's screenshot sign-off, no ambiguous SEC-* acceptance, no `.archive`/destructive change.
     - Not a PO-authored PR without the Code Owner's explicit OK (any channel counts, but it must exist - never rubber-stamp your own work).
4. **Merge (strictly serialized - one at a time, ever).**
   - Branch must be current with `main`. If behind: rebase in a temp worktree, re-run `pnpm verify` at root (a superset of CI's unit job; add `pnpm verify:browser` for a portal/admin/`@qcms/ui` diff), push, wait for CI.
   - `gh pr merge <NN> --squash --delete-branch`, keeping `Fixes #NN` in the squash body so the issue auto-closes.
   - Post-merge: append the PR's `## Retro` lines (skip `none`) to `docs/RETRO.md` under `## issue #NN - <title>` with the merge date. **`main` takes no direct push** (the `protect-main` ruleset requires a PR with green checks, amended 2026-07-31), so the append lands as its own small PR from a worktree - batch several merges' retro lines into one such PR rather than opening one per merge. Task PRs need none of this: their conductor appends the retro on the task branch before the squash.
5. **Report.** One line per PR handled (reviewed / merged / changes-requested / escalated) in the loop summary.
6. **Idle ticks do docs/non-functional work (Code Owner directive, 2026-07-26).** When nothing is open and nothing awaits a signal, pick up work instead of sleeping, in this order: (a) seat hygiene - `plan/memory/` and the `plan/CLAUDE.md` snapshot refreshed against the live repo (autonomous, worktree + PR); (b) docs staleness sweeps anywhere a landed change contradicts prose (worktree + PR under the standing docs grant); (c) open issues that are purely non-functional - CI/workflow config, packaging, docs - with no product-logic, kernel, or UI surface (e.g. advisory automation, failure-artifact capture), landed via worktree + PR with the same review discipline. Never product code, never anything screenshot-gated, never /improve-workshop (that stays human-triggered). One item per idle tick; the PR watch always preempts.

## Never

Merge red, merge across a human gate, merge unserialized, force-push, self-approve PO-authored work without the Code Owner's OK, or leave a changes-requested PR unmentioned in the report.
