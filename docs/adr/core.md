## Domain model and rules

### ADR-01 - Domain-first compiled UI

**Status:** implemented.

**Decision.** `FormDefinition` is the source of meaning. A pure compiler projects each published snapshot to A2UI documents. Storage and rendering consume those outputs and never redefine domain behavior.

**Note.** The compiler also emits one non-domain node per step (the ADR-12 honeypot decoy), and it also runs outside publish for the admin draft preview, whose output is not the ADR-18 audit copy.

**Note - the compiler emits a template the renderer expands (ADR-42, Code Owner, 2026-09-29).** A repeating group's instance count is answer-dependent and `compileFormWith` is answer-blind, so the compiler cannot expand a group. It emits a **`RepeatGroup` template node** carrying the member controls once, and the renderer clones that template per live instance at render time and qualifies each cloned control's `name`. The stored compiled document is unaffected, which keeps ADR-18 exact: the bytes served are the bytes published, and expansion is a render-time transform on the precedent `withNativeSubmit` and `documentForVisible` already set. `RepeatGroup` is a qcms-owned node type rather than an `@a2ra/core` registry component, on the `HONEYPOT_NODE_TYPE` precedent this Note already records. Decided, not built: tasks 071 and 073.

### ADR-02 - Versioned question library

**Status:** implemented; text corrected 2026-08-31.

**Decision.** Questions are governed, versioned entities. `questionId` is stable identity, a **published** question version is immutable content, and published forms pin exact question versions.

**Note.** The earlier text read "versions are immutable content" without qualification. Draft versions are edited in place by design, and a `deprecated` state exists: existing pins keep serving, new pins are gated.

### ADR-03 - Closed rules DSL

**Status:** implemented.

**Decision.** Branching uses a closed, typed JSON DSL. New operators are versioned core changes. The format must remain machine-emittable and publish-time validatable.

**Note.** Two artifacts now enforce the closed set, one per side. `packages/core/src/visibility-rule.test.ts` pins the thirteen operators as a hand-edited list checked against the `Condition` union, so adding one is a deliberate edit rather than a diff nobody reads. `apps/admin/lib/forms/condition.ts` ties the admin's parallel copy of the set to the same union through a **type-only** import of `Condition`, which R2 permits because it is erased at compile time and carries no kernel code into the app; a new operator in core therefore fails the admin's typecheck. Neither side can move alone.

**Note (flagged).** There is still no DSL **version** constant, and `@roonga/qcms-core` has never been published, so "versioned core change" remains a review convention rather than a released number.

**Amendment - three operators for repeating groups, and `everyInstance` is false over an empty group (Code Owner, 2026-09-29, ADR-42).** The closed set grows from thirteen operators to sixteen: **`anyInstance`** and **`everyInstance`**, each taking a `groupId` and a nested condition, and **`instanceCount`**, taking a `groupId`, one of the existing comparison names as a field and a number. Both nested conditions count toward `CONDITION_MAX_DEPTH`, which stays 8, and `conditionDepth` recurses into them as it does into `not`.

**`everyInstance` over a group with no live instance evaluates to FALSE.** That is a decision and not an implementation accident: it is deliberately **not** vacuous truth, so `everyInstance(G, c)` is not equivalent to `not(anyInstance(G, not c))` on an empty G, and neither the evaluator, the admin's parallel copy nor a golden scenario may treat one as a rewrite of the other. The reason is the sentence an author writes: "every passenger holds a passport" is not true of a booking with no passengers, and an operator whose default reading contradicts its own sentence is a trap rather than a primitive. The evaluator short-circuits an empty roster to false before the per-instance walk; the admin's rule sentence renders the reading explicitly; a committed golden scenario pins the empty case beside the all-match and one-mismatch cases.

**Two publish refusals come with the operators, and both are part of this decision rather than of an implementation.** The first is about meaning: `VisibilityRule.show` is an array, so a rule listing one target inside a group and one outside it would be both per-instance and whole-form at once. **Every `show` target of one rule must share one scope**, all inside the same group or all outside every group, and a mixed list is refused with `RULE_TARGETS_SPAN_SCOPES`; the admin says to split it into two rules, which is always possible and changes nothing about what either rule means. The second is about cost: a rule targeting inside one group whose condition applies a whole-group operator over **another** group costs the product of their maxima, and is refused with `REPEAT_EVALUATION_BUDGET_EXCEEDED` above a fixed `REPEAT_EVALUATION_BUDGET`. ADR-16's amendment carries that bound; it caps no group's size.

**Amendment - three publish refusals the operators need to be usable (Code Owner, 2026-09-29, Q24 to Q26).** Building task 071 found three rule shapes that published cleanly and could never fire, which is worse than a refusal because nothing anywhere says so. All three are refused at publish. **`DANGLING_GROUP_REF`**: a whole-group operator naming a `groupId` the form does not declare, so the two quantifiers are false forever and `instanceCount` reads zero; it is the group-shaped sibling of `DANGLING_QUESTION_REF`. **`REPEAT_OPERATOR_NESTING_NOT_ALLOWED`**: a whole-group operator inside another's condition, reached through `and`, `or` and `not` as well as directly, and including a group nested in itself. **`RULE_READS_GROUP_WITHOUT_OPERATOR`**: a bare reference to a question inside a group from a rule that is not evaluated inside that group, whose message names `anyInstance` and `everyInstance` as the fix; a rule targeting inside group H that reads a member of a different group G is the same defect and the same code, because H's instance is in scope and G's is not. The per-instance case, a rule inside G reading G's own member, is untouched. ADR-16's amendment carries the cost half of the nesting refusal.

Both artifacts this record's first Note names move in the same change: `packages/core/src/visibility-rule.test.ts`'s hand-edited list goes to sixteen, and `apps/admin/lib/forms/condition.ts` follows in the same PR, because the type-only import means the admin does not typecheck otherwise. The operators branch in **`checkCondition`** and **`collectReferences`** in `packages/core/src/rule-graph.ts` and in **`evalCondition`** in `packages/core/src/evaluate-rules.ts`, not in `checkValue`, which switches on `question.type`; `collectReferences` is load-bearing, because its default branch reads `condition.questionId`, which none of the three group nodes carries, and it is what `analyzeRuleGraph` and the cycle graph read. Decided, not built: task 071, with the admin's parallel list carried in that same task.

### ADR-07 - Pinned sessions and submission lock

**Status:** implemented.

**Decision.** A session pins one published form version for its lifetime. Answers append to a ledger. Submission validates visible required questions, excludes hidden answers, and locks the resulting answer set.

**Note.** The lock is enforced by the API and session status, not a database trigger; post-submit updates touch only the moderation flag, never the locked answer set or its hash.

### ADR-11 - Localizable content model

**Status:** implemented.

**Decision.** Human-readable domain content uses `LocalizedText`. Published snapshots carry localized content; application chrome uses app catalogs. Launch may ship one locale, but adding locales must not require a schema migration.

**Note.** True of the content model; the stored compiled copy is single-locale (one compiled document set per form version), so the Phase 4 runtime locale switcher (ADR-27) will need a per-locale compile or a schema change - a decision deferred with it. `resolveText` has no language-only fallback (`en-AU` does not fall back to `en`).

### ADR-14 - Step resolver seam

**Status:** implemented.

**Decision.** `StepResolver` is the compiler extension seam. The shipped resolver is pure and deterministic. Future adaptive behavior must preserve the stored-output contract and cannot put an LLM in the serving path.

**Note.** Today's `StepResolverContext` carries no answers, so an answer-adaptive resolver needs a widened seam; the code acknowledges this as a later seam version.

**Note - the roster reaches the renderer without widening this seam (ADR-42, Code Owner, 2026-09-29).** A repeating group needs a live instance roster to render, and a roster is answer-derived state, which is exactly what the Note above says this seam does not carry. It is **not** carried through the seam. `StepResolverContext` is unchanged, the compiler stays pure and answer-blind, and the roster reaches the renderer from the **API's step projection**, beside `values` and `flowState`, because the API is the only rule evaluator (R2). The seam version stays where it is and repetition does not spend it. Decided, not built: task 073.

### ADR-16 - Forward-only rule evaluation

**Status:** implemented; see note.

**Decision.** Rules evaluate once, in document order. A rule may show only targets that appear after every question it reads. Publish rejects backward targets and cycles. A semantic change requires a new snapshot `semanticsVersion`.

**Note.** The `semanticsVersion` gate runs on the serve and answer paths as well as at submit (issue #723, PR #742): `apps/api/src/features/responses/serve-step/handler.ts` reads the stored stamp through `parseSemanticsVersion` and refuses a snapshot recorded under superseded semantics before the evaluator sees it, so such a snapshot fails at entry rather than only at submit. The stamp is stored as text and parsed on every path that reads it. The evaluator still implements exactly one version at a time, so multi-version evaluation remains unbuilt.

**Amendment - required means non-blank (Code Owner, 2026-08-31, issue #128).** A question is answered when it holds a **non-blank** value: an empty or whitespace-only text value is absence, for the `answered` operator, for every value operator, and for the required accounting alike. The stored value is never rewritten - trimming decides the presence test only, so a respondent's `" "` stays verbatim in the ledger and in exports.

This was corrected **within `semanticsVersion` 1** rather than under a bump, and the reasoning is part of the decision. A bump cannot deliver what this ADR's rule protects: the evaluator implements one version at a time and refuses any other stamp, so `2` would not preserve old snapshots' behavior, it would make every published snapshot fail at submit. Multi-version evaluation is the missing prerequisite, and it is the limitation noted above. Against that, no answer the product can produce changes meaning: both control boundaries have reported an emptied field as absence since issue #98, and the same batch made `""` and `[]` unstorable at the API (ADR-33). One golden scenario that had pinned `""` as answered was amended in place; `packages/core/golden/evaluator/CORPUS.md` records that as a defect-correction precedent and not as licence to edit a golden that disagrees with an intended semantics change.

**Amendment - the forward pass reaches inside a repeating group, within `semanticsVersion` 1 (Code Owner, 2026-09-29, ADR-42).** With a repeating group in a form, `documentOrder` expands the group into a **contiguous span** of its member questions and this decision's rule applies to the span rather than to a single position. Three readings follow, all enforced by `analyzeRuleGraph`: a rule targeting inside a group may read questions before the group and questions earlier **within the same instance**, and a later position inside the instance is `RULE_BACKWARD_TARGET` as it is today; a rule using `anyInstance`, `everyInstance` or `instanceCount` reads **the whole** of the group, so its targets must follow the group's whole span; and a `fromAnswer` count source is a read of its count question by the whole group, so that question must precede the span. **No rule may read a different instance of the same group**, because roster order is not document order and there is no forward-only reading of it.

It is one pass still, and the cost bound has two cases rather than one. For a rule whose target sits outside every group, or inside the group it reads, the cost is `rules x max` with `max` taken from the group's own author-set value and from no installation-wide constant (SEC-16). **For a rule targeting inside group H whose condition applies a whole-group operator over another group G, the cost of that rule is the product `max_H x max_G`**, because the rule is evaluated once per live instance of H and each evaluation walks the whole of G.

**That product is bounded at publish by a fixed evaluator budget (Code Owner, 2026-09-29).** A cross-group rule of that shape is refused with `REPEAT_EVALUATION_BUDGET_EXCEEDED` when `max_H x max_G` exceeds `REPEAT_EVALUATION_BUDGET`, a constant in core **confirmed at `10_000` instance pairs**, and the refusal names both groups, both maxima and the product. **It is a cost bound and not an instance ceiling**, which is what keeps it consistent with the ruling that removed the ceiling: it caps no group's `max`, two large groups with no cross-group rule between them publish, and what is refused is one rule shape whose cost is quadratic. The check runs against declared maxima at publish, not against live counts at runtime, so the cost of serving a published version is known before it is published, which is the property this decision exists to protect.

**Amendment - the budget bounds a rule only because the operators may not nest (Code Owner, 2026-09-29, Q25).** The bound above is charged per pair of `(target group, group read)`, which bounds a **rule** only while a whole-group operator cannot sit inside another. It could: the condition tree is recursive, so `anyInstance(G, anyInstance(H, c))` parsed, and its cost is `max_G x max_H` **whatever the rule targets**, because the outer walk runs once per live instance of G and each of those walks the whole of H. A nested pair aimed at a question outside every group was therefore charged nothing, and two groups at `max: 5000` under one such rule published and cost twenty-five million leaf evaluations per request. Publish now refuses the nesting (`REPEAT_OPERATOR_NESTING_NOT_ALLOWED`, ADR-03's amendment), through `and`, `or` and `not` and for a group nested in itself, and with it refused a rule's whole-group reads are siblings whose costs **add**: a rule's worst case is the budget times the number of whole-group reads it carries. The alternative, charging the product along the nesting chain, was weighed and refused: neither sample use case wants a nested quantifier, and a bound an author cannot predict from reading their own rule is one they trip over.

**`SEMANTICS_VERSION` stays 1**, for the reason the amendment above already gives: a bump would make every published snapshot fail rather than preserve it. Repetition is built to need no bump, and a form with no repeating group produces a byte-identical `FlowState`, asserted by **every** committed golden scenario passing with no `expected` block edited. The criterion is "every" rather than a count deliberately: a count is satisfiable by a corpus that has lost files.

**The `FlowState` debt this creates has a named creditor (Q8).** `visibleSteps`, `missingRequired` and `answeredRequired` cannot widen without the bump that cannot be taken, so repetition adds **parallel optional fields** beside them (`visibleStepViews`, `missingRequiredInstances`, `answeredRequiredInstances`, `rosters`), each absent entirely from a form with no group. That is the ugly part of the design and it is recorded rather than hidden: **collapsing the parallel fields into the widened originals is the first job of multi-version evaluation**, which is the standing limitation this record's first Note names. Decided, not built: task 071.

### ADR-21 - Multi-choice comparison

**Status:** implemented.

**Decision.** Multi-choice equality is set equality. `contains` tests one option and `containsAny` tests a set of options. Publish rejects those operators against non-multi-choice questions.

### ADR-32 - Authored validation messages

**Status:** implemented.

**Decision.** Authors may supply localized messages per question constraint. Blank fields inherit catalog defaults. Stable validation codes remain authoritative; authored messages are presentation content compiled into the form document.

**Note.** The portal routes authored messages by `constraint`, not `code`; the catalog carries one generic fallback rather than per-code entries. The authorable key set is not identical to the constraint set (`required` is authorable but not a constraint; `encoding` and `options` are constraints but not authorable).

### ADR-33 - Answer retraction

**Status:** implemented.

**Decision.** Clearing an answer appends a retraction record; it never mutates an answer row. Latest-answer reads resolve a retraction to unanswered for rules, validation, reporting, and export. Empty text and empty selections are absence, not answers. Whole-session deletion remains governed by ADR-17.

**Note.** "Empty is absence" is enforced at the control boundary (the renderer and the no-JS decoder) _and_, since issue #128's batch, in the kernel: `validateAnswer` refuses `""` and `[]` with `EMPTY_ANSWER_NOT_ALLOWED`, so a direct API post of either is a 422 that stores nothing and whose message names the `null` retraction as the way to clear an answer. The refusal is never a silent conversion into a retraction - clearing keeps exactly one spelling on the wire. Whitespace-only text is a separate rule: it is stored as typed and denied _presence_ instead (issue #128, ADR-16 note). A retraction of a never-answered question is a no-op and appends nothing.

**Note - a retraction is per instance (ADR-42, Code Owner, 2026-09-29).** With repeating groups the ledger's grain is `(question, instance)`, so a retraction names an instance as well as a question and clears **that cell alone**. `answers_retraction_value` is unchanged and the new nullable `answers.instance_id` column is covered by the existing reject-update and reject-delete triggers by construction. Everything this decision says holds per cell: `validateAnswer` still refuses `""` and `[]` with `EMPTY_ANSWER_NOT_ALLOWED` in a table cell exactly as in a standalone question, and `null` is still the one spelling of a clear. A **removed instance is not a retraction**: its answers stay in the ledger and are excluded by the roster, which is I6's semantic rather than this one's. Decided, not built: tasks 071 and 072.

### ADR-36 - Authored boolean labels

**Status:** implemented.

**Decision.** Boolean questions may provide localized `yesLabel` and `noLabel` values with catalog fallback. Stored answers remain booleans and rule, reporting, and export semantics do not change.

**Note.** The fallback source is a compiler lexicon constant frozen by `compilerVersion`, not an app catalog in the ADR-11 sense.

### ADR-42 - Repetition is a form-level group

**Status:** decided; not built (tasks 071 to 077). Code Owner rulings of 2026-09-29, recorded question by question in `plan/repeating-groups-and-table-input.md` section 10. Nothing here is open.

**Decision.** A form may repeat a named group of pinned questions. The group lives in a **step's item list**, not on a question and not on a step, and it is answered once per **instance**. An instance carries a stable, opaque, session-scoped id minted once and never reused or renumbered; the ordinal a respondent reads is its position in the live roster and is presentation only. The id is **never a label**: it appears in field names, DOM ids, anchors, button values and the no-JS fragment, and in no heading, legend, label, message or caption, so a respondent is never asked to read or understand it. A **looping question** is a group of one member. A **looping step** and a **table** are presentations of the same group, not separate constructs. No question type is added: the closed set stays seven and `AnswerValue` is unchanged.

An answer is keyed by `questionId` outside a group and by `instanceId/questionId` inside one, separated by `/`, so a question outside every group keeps the key it has today. A `questionId` is still pinned at most once in a form; a question is either repeated or not, and a question does not know that it is.

The roster is state the server owns, held in its own append-only table with the answer ledger's guards, and passed to the evaluator beside the answers rather than derived from them. **What the evaluator receives is the live roster, already derived**: the table records what was minted and what was explicitly removed, and liveness is then a function of the count source, since a `fixed` group's live set is the first `count` of that list and a `fromAnswer` group's is the first N for the current count answer, clamped to `min` and `max`, while only an `open` group's live set is the event record itself. That derivation runs in the API above the evaluator, so determinism (I7) stays exactly checkable at the evaluator's boundary and the truncation is a separate, testable step. A removed instance is **never deleted**: its answers are excluded from evaluation, from the locked submission and from reporting exactly as a hidden question's answers are (I6), and its removal is an appended row. A count that shrinks and grows again re-lives the same instance with its answers intact, because the id never changed.

**A group may not contain a group**, refused at parse.

**Bounds are per form and there is no installation-wide ceiling.** Every count source that is not `fixed` must declare a `max`, which publish refuses to omit and the API enforces on every add; a fixed count is its own bound. Nothing in core caps that `max`. SEC-16 records what that leaves bounded per form and what it does not bound at all.

**The rules DSL gains three operators**, `anyInstance`, `everyInstance` and `instanceCount`, over a named group. A rule whose target sits inside a group is evaluated once per live instance with no new syntax, and a reference to a question inside the same group resolves to that instance's answer. No rule may read a different instance of the same group: roster order is not document order, so there is no forward-only reading of "the previous passenger's answer".

**Why not a table question type.** A composite `AnswerValue` would break per-cell validation, per-cell retraction and "empty is absence" per cell, would make a partial table unstorable, and would change the grain of the ledger, the export and the reporting view, all of which are one row per question. A table as a presentation keeps every cell an ordinary answer.

**Consequences.** `SNAPSHOT_SCHEMA_VERSION` moves to 2 because the snapshot's shape changes. **`SEMANTICS_VERSION` stays 1, and that is load-bearing rather than convenient:** the evaluator implements one version at a time and refuses any other stamp, so a bump would make every published snapshot fail rather than preserve it. Every change is therefore additive, a form with no group evaluates byte-identically, and the committed golden scenarios pass with no `expected` block edited. `@roonga/qcms-core` and `@roonga/qcms-db` move by a minor: every schema change is additive and no canonical encoding changes.

**Note - the launch cut-line moved for this, and it moved for all of it (Code Owner, 2026-09-29, Q1).** Repetition was designed as Phase 4 work and recommended as such. The Code Owner ruled it into **launch scope**, so `docs/PROJECT_GOAL.md` section 5 enumerates it among what launch includes, `docs/IMPLEMENTATION_PLAN.md` carries it as stage 8c, and tasks 071 to 077 are sequenced against their own dependencies rather than after task 038. **All three presentations are in launch and there is no launch subset**: section 5 promises the stacked, the per-instance-step and the table presentation, so task 038 waits on 076 and 077 as well as on the model. A build order inside the stage exists and is not a scope statement. It is deliberately absent from `docs/features/039-phase4-backlog.md`, which holds deferred work.

**Note - `everyInstance` is false over an empty group (Code Owner, 2026-09-29, Q7).** This is **deliberately not vacuous truth**, so `everyInstance(G, c)` is **not** equivalent to `not(anyInstance(G, not c))` when G holds no live instance: the first is false and the second is true. The reason is what an author means by the sentence they write: "every passenger holds a passport" is not a true statement about a booking with no passengers. The evaluator states it as a base case that short-circuits before the per-instance walk, never as a fold whose identity is true; ADR-03's amendment carries the operator set, a golden scenario pins the empty case, and the admin's rule sentence says the reading out loud rather than leaving it to be inferred. **The negation is the mirror trap and is handled the same way**: `not(everyInstance(G, c))` is true over an empty group, so a warning phrased as a negation would fire for a group with no instances, and the admin renders that reading out loud too rather than leaving the author to discover it. It is the same base case read through `not`, not a second semantics.

**Note - the roster is a table and not an answer (Code Owner, 2026-09-29, Q16).** Encoding the roster as a synthetic answer keyed by the group id was weighed and refused: `answers.question_id` would then hold something that is not a `questionId`, which collides with `prepareSubmission`'s `UNKNOWN_QUESTION` ledger-drift defence, with R6's statement of what a `questionId` is, and with the reporting view's contract that a row is a question. The table is `answer_group_instances`, append-only, with the ledger's reject-update and reject-delete triggers and the same `qcms.allow_answer_delete` door, and it joins the erasure and retention paths in the same change that creates it.

## API and platform

### ADR-04 - Single-tenant core

**Status:** implemented.

**Decision.** QCMS ships as a single-tenant deployment. Multi-tenancy is a derivative recipe, not a schema or runtime cost imposed on the core.

**Note.** Verified: no tenant concept exists in schema or runtime. The derivative recipe itself is not yet written; no such document exists under `docs/`.

**Note - the workspace reading (Code Owner, 2026-09-25, issue #995).** ADR-41 adds workspaces, and this Note records what they do and do not do to this decision, so a reader does not have to infer it. A workspace is an **authorisation grouping between groups sharing one installation**: one operator, one configuration, one identity store, one database, one deployment, with authorisation between workspaces rather than isolation guarantees. It is not multi-tenancy and does not make this decision partly true. The one schema boundary QCMS has is ADR-40's environment, which separates data planes within a single tenant's own deployment; it is not a tenant boundary either. Multi-tenancy stays out (R7), and the derivative recipe named above stays unwritten.

### ADR-09 - Route groups are topology controls

**Status:** implemented.

**Decision.** API route groups are mounted explicitly. An unmounted group does not exist and returns 404 rather than relying on an authorization check.

**Note.** Four groups ride three mount flags (the auth group mounts with `admin`), and mounting also installs the SEC-4 internal-token gate, so a mount is a topology control plus a channel gate.

**Note - ADR-40 needs a mount this record does not have yet (issue #995).** SEC-14 rests on this decision twice, and only one of the two mechanisms exists. An environment's respondent surface as its own mountable group is the straightforward case: an unmounted `test` surface is a 404 exactly as this record says. **Anonymous entry is not, today.** Anonymous and secure-link entry are one route, `POST /sessions` on the `public` group, discriminated by a body refine ("Provide exactly one of formSlug or token"), so "no anonymous entry to test" cannot currently be a routing fact and would be a handler refusal instead. Making it structural means splitting that route so the two entry modes can ride different mount decisions, which changes the count in the Note above. Task 066 owns that split and the amendment to this Note; until it lands, read SEC-14's 404 claim as what has to be built rather than as what holds.

### ADR-10 - Reporting before public API

**Status:** implemented.

**Decision.** Launch integrations are signed webhooks, exports, and documented read-only reporting views. A stable `/api/v1` pull API is Phase 4.

**Note.** "Read-only" for the reporting views is an operator GRANT recipe (`docs/reporting-view.md`), not a shipped role migration.

### ADR-13 - Fetch-pure vertical slices

**Status:** implemented.

**Decision.** The Hono API uses fetch-pure vertical slices with explicit dependencies. Multi-field and multi-row invariants live in core functions; other work uses plain transaction scripts. Background delivery and retention jobs run inside the API process.

**Note.** The schedulers start only where the internal surface is mounted (in the solo topology, always). Fetch purity is lint-enforced for `@roonga/qcms-core` and the compiler but convention-only in `apps/api`. Retention now runs three rules: the session sweep plus the aged redaction of response snippets (#304) and outbox payloads (#329).

### ADR-15 - Runtime baseline

**Status:** implemented.

**Decision.** QCMS targets Node LTS. Experimental runtime flags are not part of the supported execution model.

### ADR-17 - Erasure, retention, and outbox copies

**Status:** implemented; amended 2026-08-02 (task 059) and widened by issues #304 and #305.

**Decision.** Erasure is form-scoped and, in one transaction: deletes the session's answer ledger and submission, retains the session row as a scrubbed shell, writes a content-free tombstone, redacts QCMS's outbox payload and every stored delivery response snippet, and cancels undelivered deliveries. Delivered or in-flight downstream copies cannot be recalled. Retention purge is the other sanctioned whole-session delete path and leaves no tombstone because the session was never submitted; the retention scheduler also ages out outbox payloads and response snippets on time limits. `docs/erasure.md` is the operational contract.

**Note - erasure is per environment, with a cross-environment hint (Code Owner, 2026-09-26, issue #995, ADR-40).** Once the data plane is a schema per environment, an erasure acts in **the currently selected environment only** and never crosses an environment boundary in one act, so `prod` cannot be reached from `test` by accident and the confirmation restates which environment it is about. That is the safety property, and it is bought at a real cost: a data subject's request is not one click. So when the same subject identifier also has sessions in other environments, the screen **says so and offers to repeat the erasure there**, each repetition its own confirmed act in its own environment. The request is completed deliberately, environment by environment, and the tombstones that result are per environment like the sessions they describe. Task 067 builds it; this decision's transaction and its contents are unchanged.

### ADR-24 - Typed deployment flags

### ADR-40 - Environments are release states over shared versions

**Status:** decided; not built (task 064). Code Owner rulings of 2026-09-25, 2026-09-26, 2026-09-27 and **2026-09-29**, issue #995, several of them after the Code Owner scenario-tested this design against a three-environment, two-workspace deployment and again as a government organisation holding personal data, and the last eight after a second-opinion review of the merged design (issue #998). Nothing here is open; `plan/environments-and-workspaces.md` section 6 records all thirty-nine questions with their answers and the eight rulings of 2026-09-29, and ends with the permissions matrix and the naming convention, while section 7 records the two scenario tests and the one item deferred to task 069. **What 2026-09-29 changed in this record:** the drop rule gains the access-group clause, the grants become three kinds of role with table-level rights on `control`, the environment name gains its character, length and ordering rules, the guards become thirteen with a composite link key, and the migration chain is re-baselined. **The reconciliation with ADR-42 is done** and the combined per-environment figures are in the amendment at the end of this record: eight data-plane tables, seventeen guards and eight foreign keys.

**Decision.** A deployment has named **environments**. An environment is a release state over the one immutable version history, never a second copy of it.

**The set is configurable, and changing it is an operator act.** A fresh database is created with exactly two environments: `test` and `prod`. Further environments are created by an **operator command run under the migration role**, never by an administrator and never over HTTP, because creating a schema is DDL and no application role holds any (SEC-10).

**An environment can be dropped only when it is empty and unreferenced, and `prod` never.** The command refuses `prod` unconditionally, and refuses any other environment while a form in it is open, a session exists in it, **or any access group (ADR-41) names it in its scope**, naming the open forms, the session count and those access groups so a refusal tells an operator what to do next. **The access-group clause is a refusal and never an archive** (Code Owner, 2026-09-29): an acceptance case cannot be disjunctive, and a command that quietly archived a grant an owner wrote would be editing the authorisation model as a side effect of an operator act. The operator removes or re-scopes the groups first, then drops. That half of the check lands with task 069 rather than 064, because a group carrying an environment scope exists only from then. Emptying a scratch environment is retention's job, which is a sanctioned door. The narrowness is the whole point: `DROP SCHEMA ... CASCADE` would take the answer ledger with it **without passing the `answers_reject_delete` trigger** (migration 0004), and a command that could do that would be a third whole-session deletion path where ADR-17 says there are two. Under this rule a drop only ever removes an empty schema, so no door is added. It is the same family as `qcms-db-migrate`, `qcms:create-admin` and `qcms:reset-2fa`: a command against the database, guarded by possession of the migration credential. Every per-environment job, export, backup, retention pass, reporting view and telemetry attribute therefore **enumerates the live set** rather than a compiled-in pair, so a third environment is a command and not a code change.

A form version is published once and is shared by every environment (ADR-18). What varies per environment is which published version is **released** there. Promotion is a **release record**, never a copy, so `formId`, `questionId` and version numbers stay continuous across environments (R1, R6, ADR-02). Approval is recorded on the release.

**The release record.** One append-only control-plane row per release, naming the environment, the form, the released version, the environment it was promoted from (absent for a first release), the administrator who released it, the approval recorded with it, and the time. The currently released version of a form in an environment is the newest such row for that pair; nothing else decides it. This row is the audit answer to "what was serving in `prod` on that date, and who put it there", which today's `form_versions.published_at` cannot give, because publishing and releasing are now separate acts.

**The release state carries the closed value, so a form is open or closed per environment.** Closing intake in `prod` while a test run continues, and the reverse, are ordinary operations, so "closed" cannot be one column on the form: `forms.status` and its `form_status` enum go away, or become a value derived from the release states. ADR-39's "the whole-form closed state overrides every public and secure link" becomes **the environment's** closed state overriding every link into that environment, which is the amendment recorded on that decision. A version need not be released to `test` before `prod`, and the release record's source environment makes the path auditable when there was one, so a hotfix straight to `prod` is allowed rather than worked around.

**Rolling back is releasing an earlier version, and there is no second mechanism.** Nothing is reverted, undone or deleted: an administrator releases a version that environment served before, a new release row records it, the history is still append-only, and sessions already open stay on the version they started. The release history presents such a release **as a rollback** rather than as an ordinary row, because "released version 4 after version 7" is what an incident review needs to read at a glance. That this is the whole of rollback is the point: an environment's state is a pointer into an immutable history, so moving the pointer backwards is the same operation as moving it forwards and needs no separate machinery, no reverse migration and no data rewrite.

**Only a published version can be released, and that has a cost worth naming.** Every iteration an author wants to try in a non-prod environment is a published version, and R1 makes it permanent, so a week of iterating leaves versions that were released nowhere but `dev`. That is the honest price of promotion being a record rather than a copy, and no cheaper mechanism keeps the audit promise. Softening it is presentation, not design: a combined publish-and-release action, and a filter for versions released anywhere.

**Releasing never moves an open session.** A session pins the version it resolved at start and stays on it for its lifetime (ADR-07, invariant I4). A release changes only what a session started **after** it resolves, in that environment alone.

**The data plane is isolated by a Postgres schema per environment, and the control plane has a named schema of its own.** Both planes are named by role with the environment as a suffix, so `control`, `data_test` and `data_prod` read as one scheme rather than two, and a per-environment schema is found by `data_%` rather than by a list. Every QCMS object lives in a schema QCMS named, and `public` is left empty. The split is exact:

| Schema                                 | Holds                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `control`, one copy                    | `questions`, `question_versions`, `forms`, `form_drafts`, `form_versions`, `secure_links`, `user`, `session`, `account`, `verification`, `twoFactor`, `two_factor_resets`, the two tables this decision adds (`environments` and `form_releases`), and the organisation plugin's `organization`, `member`, `invitation`, `team` and `teamMember` once ADR-41 lands |
| `data_<env>`, one per environment      | `sessions`, `answers`, `submissions`, `erasure_tombstones`, `outbox`, `webhook_deliveries`, `webhooks` and `answer_group_instances` (ADR-42)                                                                                                                                                                                                                       |
| `reporting_<env>`, one per environment | the view set, one per environment (`reporting_prod.responses`, `reporting_test.responses`), replacing the single `reporting` schema of migration 0003                                                                                                                                                                                                              |
| `public`                               | **nothing.** Off every search path, and `CREATE` on it granted to nobody                                                                                                                                                                                                                                                                                           |

**Three** foreign keys cross from the data plane into the control plane, and the first two are what make a shared version history work with no copying:

| Constraint                                                                       | From                  | Into                                                  |
| -------------------------------------------------------------------------------- | --------------------- | ----------------------------------------------------- |
| `sessions_form_version_fk`                                                       | `data_<env>.sessions` | `control.form_versions`                               |
| the link key, **composite on `(link_id, environment)`**, both columns `NOT NULL` | `data_<env>.sessions` | `control.secure_links`, on a unique key of that shape |
| `webhooks_form_id_forms_form_id_fk`                                              | `data_<env>.webhooks` | `control.forms`                                       |

The third is the price of putting `webhooks` on the per-environment side (migration 0006 declares it). It is named here rather than left to be discovered, because a per-environment table referencing a control-plane one is the shape a migration author has to get right N times. The remaining four foreign keys stay inside one schema: `answers_session_id_sessions_session_id_fk`, `submissions_session_id_sessions_session_id_fk`, `webhook_deliveries_outbox_id_outbox_id_fk` and `webhook_deliveries_webhook_id_webhooks_webhook_id_fk`. **All seven exist once per environment schema**, the in-plane four pointing inside their own `data_<env>` and the crossing three at the single `control` copy, so the per-environment set a generator emits is the guards of the Note below **plus** these foreign keys, which ADR-42's amendment at the end of this record totals at seventeen and eight; `plan/environments-and-workspaces.md` carries the full set under task 064. `erasure_tombstones` keeps its deliberate absence of a foreign key and is per environment because it records a session that lived in one.

**The API selects an environment by search path, not by a predicate.** A connection is opened with `search_path` set to `data_<env>, control`, so every unqualified data-plane name resolves inside exactly one environment's schema, every unqualified control-plane name resolves in `control`, and there is no per-query filter for a handler to forget. `public` is not on the path, so an unqualified name can never resolve to something a tool, an extension or a careless session created there. The data plane is **first** on the path, so a table name declared in both `control` and a `data_<env>` would resolve to the environment's copy with no error and no warning anywhere; the two table-name sets are therefore kept disjoint, and a check in the `check:all` set asserts it rather than leaving it to hold by habit (task 064). A request is served under exactly one environment for its whole lifetime, chosen before any data-plane statement runs. This is the same mechanism migration 0003's `reporting` schema already uses, applied to the operational tables.

**The schema is a resolution boundary and a privilege boundary, and the two are separate mechanisms.** Resolution comes from the search path: there is no filter to omit, so an omission is not expressible. That alone would not stop a **schema-qualified** statement, because `search_path` is a default and not a grant, so `select ... from data_prod.answers` would succeed from a `data_test` connection held by a role with DML everywhere.

So there is **one application role per environment**: `qcms_app_test`, `qcms_app_prod`, and one for every environment the operator command creates. Each is granted DML on its own `data_<env>` and on no other data schema, so a schema-qualified read of another environment's data table fails on **permission** rather than on resolution. The environment command creates the role and its grants under the migration role, because a `CREATE ROLE` is as far outside an application role's rights as a `CREATE SCHEMA` (SEC-10).

**An environment role's rights on `control` are table-level, and there is a control-only role beside them (Code Owner, 2026-09-29).** Granting each environment role DML on the whole of `control` would have made the schema a boundary between environments and no boundary at all between the respondent path and the tables that decide who may read a response: `user`, `session`, `member`, `team` and `teamMember` sit in `control`, so a defect on the anonymous path could rewrite a grant or a staff session. Three kinds of role:

| Role               | On `control`                                                                                                                                                                                                                                                                                                                                                                | On the data schemas                                                                           | Serves                                                               |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `qcms_app_control` | DML, with the two audit tables carved out separately: **nothing at all on `two_factor_resets`**, which stays migrate-only, and **`SELECT` on the SEC-15 audit** with no `UPDATE` and no `DELETE`                                                                                                                                                                            | **`INSERT` on `outbox` only**, and nothing on any `reporting_<env>`                           | better-auth, authoring, grants, releases, closes, audit reads        |
| `qcms_app_<env>`   | `SELECT` on `forms`, `form_versions`, **`question_versions`**, `secure_links`, `environments` and `form_releases`; `UPDATE` on `secure_links`, for one-time link consumption; `INSERT` on the SEC-15 audit. **No privilege of any kind on `user`, `session`, `account`, `verification`, `twoFactor`, `two_factor_resets`, `invitation`, `member`, `team` or `teamMember`.** | DML on its **own** `data_<env>`, plus `USAGE` and `SELECT` on its own `reporting_<env>` views | the respondent path, delivery, retention, reporting reads and export |
| `qcms_migrate`     | owner, DDL                                                                                                                                                                                                                                                                                                                                                                  | owner, DDL                                                                                    | migrations and the operator commands                                 |

So **"an author never reads production personal data" holds at the database** and not only in the API: the connection the authoring routes run on holds **`INSERT` on each environment's `outbox` and no other privilege of any kind on any `data_<env>`**, and `INSERT` on an event queue is not a read of a response. A **response read and its SEC-15 audit row are written by the environment role in the same transaction**, which is why that role holds `INSERT` on the audit table: an audit row written on a second connection is an audit row that can fail while the read it records succeeds. **The two audit tables are separate cases and are stated separately**, because one clause covering both was ambiguous: `two_factor_resets` stays **migrate-only for every application role**, all four privileges, exactly as migration 0021 has it, so issue #432's control is untouched by this decision; the SEC-15 audit is the table the carve-out is about, with `INSERT` for an environment role, `SELECT` for `qcms_app_control`, and `UPDATE` and `DELETE` for neither. Only `qcms_migrate` can change an audit row of either kind. The one API process therefore holds **one pool per environment plus a control pool**, which is what makes the mechanisms line up: a pool is a connection, a connection is a role, and a role is either an environment or the control plane.

**Test is reachable through secure links only.** `/f/{slug}` stays the `prod` address, as does `/f/{slug}/v{version}` when ADR-39 lands. No public non-prod address exists, and `/<env>/f/{slug}` is not a route. A secure link's server-side row carries the **environment** alongside the ADR-39 target version, so redeeming a link decides both which environment the session lands in and which version it resolves; the environment rides the row and not the token, exactly as the target does, and a signature alone remains insufficient (SEC-2).

**A non-prod address carries the environment's name as its first path segment; a `prod` address carries no prefix.** Every address under a non-prod environment is `/<env>/...`, on the portal and on the API alike, so a test secure link reads `/test/l/{token}` and there is no unprefixed test address anywhere. `prod` is the unprefixed shape, which is why every link that exists today keeps working and why production has exactly one address shape rather than two spellings of one thing. Three properties follow and are the reason for the rule:

- **A respondent, a tester or an operator can tell from the link itself that it is not production.** That is the whole point, and it is the one property no server-side field can deliver, because nobody reads a database row before clicking a link.
- **The path is a second network handle.** An ingress or an L7 firewall can allow or deny `/<env>/` on its own, without resolving a hostname or reading a body (SEC-14).
- **The environment is still not in the token.** The path names it, the server-side row decides it, and a token presented under the wrong prefix is **refused** rather than redirected or silently honoured. So the prefix is a routing and legibility fact, and the authority remains the row, exactly as ADR-39 holds for the target version.

Because the environment set is configurable, the prefix is the environment's own name, which makes that name a URL path segment and a Postgres identifier at once. **The name matches `^[a-z][a-z0-9]*$`** (Code Owner, 2026-09-29): lowercase letters and digits, starting with a letter, with **no hyphen and no underscore**, because an access-group name joins a set of environments with hyphens (ADR-41) and `data_<env>` and `reporting_<env>` join on underscores, so a name carrying either makes a derived string impossible to parse back. **Its length is checked against the longest identifier derived from it**, because Postgres truncates an over-long identifier silently and a name that fits `data_<env>` but not a longer derived name would create an object nobody asked for. The limit is **63 minus the longest prefix the name is interpolated into**, computed by the command from that prefix list rather than written as a constant, since a literal goes stale the first time somebody adds a longer prefix and goes stale silently. Today the list is `data_`, `reporting_` and the role prefix `qcms_app_`, so the limit is 53 bytes; the per-(workspace, environment) reporting role of the reporting Note below joins the list when task 067 names it, and re-derives the limit if its prefix is the longer one. **A combined environment set is written in the environments table's order**, so `dev-test` is the spelling and `test-dev` is not a second grant; the write path normalises on write and refuses an out-of-order set rather than rewriting it unannounced. The environment command must also refuse a name that collides with a route either surface already serves at its root. The reserved set and its derivation are task 064's, in `plan/environments-and-workspaces.md`.

**A small set of configuration is per environment; everything else is installation-wide.** Retention TTLs and the challenge provider may be set per environment, through the operator command that owns environments, because a test environment that keeps responses for thirty days or asks a tester to solve a challenge is a cost with no benefit. Rate limits, the session TTL, anti-abuse settings and every other typed setting stay installation-wide. ADR-24 is amended narrowly to name that set rather than opened to per-environment configuration in general.

**Delivery and operations are per environment.** The outbox, the webhook endpoints and the delivery rows live in the environment's schema, so a `test` submission cannot reach a `prod` endpoint through any code path rather than through a filter that holds. Backup, restore and the restore drill, erasure, response export, the retention sweep and the reporting views are per environment, and the environment name is an allowlisted span and log attribute (SEC-13) so a trace can be told apart from one in another environment. The attribute names a deployment configuration and no respondent, which is why it is allowlistable at all.

**The network layer is part of the design and is the operator's to configure.** QCMS must let an operator put test traffic on a distinct hostname or listener so ingress and firewall rules can restrict it to an allowlisted network, and must scope webhook egress per environment. The control is **SEC-14** (`docs/SECURITY_DESIGN.md` section 5a) and the operator recipe is `docs/deploy-ingress.md`. Defence in depth, in order: network, then link, then schema. TLS, HSTS and routing remain operator-provided ingress (ADR-20); what QCMS owns is the distinguishable listener, the per-environment egress rule set and the link and schema layers behind them.

**This is green field: the layout above is created from scratch, and nothing is migrated into it.** A fresh database gets `control`, `data_test`, `data_prod` and a `reporting_<env>` view set per environment from the migrations alone, with the control-plane tables in `control` and the **eight** data-plane tables, with all **seventeen** of their guards and all **eight** of their foreign keys, in each environment schema (ADR-42's roster table included, per the amendment at the end of this record). No data is carried over, no release row is backfilled, and no existing link is defaulted to an environment, because there is nothing existing.

**The chain is re-baselined, which is a one-time exception to the append-only rule (Code Owner, 2026-09-29).** This paragraph said until then that the drizzle chain in `packages/db/migrations` stays append-only and that a new migration creates the schemas and the tables "in their final homes", so that "no table is moved". Both readings are withdrawn, because an appended migration on the end of that chain cannot reach the shape above: it would have to create the schemas and then `SET SCHEMA` the whole chain's worth of tables into them, and the per-environment copies have no expression at all in that shape, there being one `answers` table in the chain and one needed per environment. So **task 064 replaces every migration in the chain as it stands when 064 lands with a single new baseline** that creates `control` and each `data_<env>` in final shape, with **no `DROP` and no `SET SCHEMA` in any migration**. Nothing is moved because nothing exists to move: every database is deleted and recreated manually, the development one, the Docker stack, CI and any adopter of the published `@roonga/qcms-db` migrations. The exception is available exactly once and only because Q22 says there is no installation to break; ADR-18's discipline is otherwise unchanged, and the next migration after the baseline appends to it like any other.

**The baseline restates whatever the chain holds when it is written, which is a live coordination with the repetition work.** That work is launch scope and lands first under Q50 (PR #1012, task 072): it appends `answers.instance_id` and an append-only **`answer_group_instances`** table with two triggers, a CHECK, an index and a foreign key, as an ordinary appended migration, with its two trigger functions single in `control` like the ledger's. `answer_group_instances` is a data-plane table, so it multiplies per environment and its guards join the per-environment set. **If task 072 has landed, the baseline includes its table and its guards in the final layout**, because a baseline that dropped a table the chain had created would delete work rather than restate it; if the baseline were ever to land first, which Q50 forbids, 072 would append to it in the ordinary way. **The reconciliation this sentence used to defer is done.** It said the counts here excluded 072 and would be written by whichever of the two landed second; the repetition work landed second, so **every count in this record now includes the roster table**: eight data-plane tables, seventeen guards and eight foreign keys, derived object by object in the amendment at the end of this record, and the layout table above lists `answer_group_instances` beside the rest. The baseline is **hand-authored where drizzle-kit cannot express the per-environment copies**, in the way migration 0001's triggers already are, and `packages/db/src/migration-chain.test.ts` and `packages/db/src/migrations.test.ts` keep the properties they assert against a one-entry chain and a fixed table list per schema. `plan/environments-and-workspaces.md` section 4a carries the whole of it, including the release-note and changeset impact on `@roonga/qcms-db` and `create-qcms-app`.

**Note - every guard that multiplies, derived rather than remembered.** The criterion is mechanical: any trigger, CHECK, UNIQUE constraint or index declared on one of the data-plane tables exists once **per environment schema**. The derivation below reaches **twelve** off the existing chain, **thirteen** with this design's own, and **seventeen** with ADR-42's roster table, which the amendment at the end of this record adds. Read off `packages/db/migrations/*.sql` by table, that is: two triggers, both on `answers` (`answers_reject_update`, 0001; `answers_reject_delete`, 0004); three CHECKs (`answers_retraction_value`, 0009; `webhook_deliveries_snippet_requires_attempt`, 0015; `outbox_redacted_payload_has_no_answers`, 0016); one UNIQUE (`webhook_deliveries_event_webhook_uq`, 0007); and six indexes (`sessions_status_expires_at_idx`, `answers_session_question_answered_at_idx` and `outbox_delivery_idx`, all 0000; `webhook_deliveries_due_idx`, 0007; `outbox_payload_retention_idx` and `webhook_deliveries_snippet_retention_idx`, both 0018). Primary keys ride the `CREATE TABLE`. **A thirteenth guard is added by this design and is not read off the existing migrations (Code Owner, 2026-09-29).** Each `data_<env>.sessions` carries an **`environment` column, `NOT NULL`**, the crossing key into `control.secure_links` becomes **composite on `(link_id, environment)`** against a unique key of that shape, and a **`CHECK (environment = '<env>')`** pins the column to the schema it sits in. Together they make "a link minted for one environment cannot start a session in another" a database fact rather than a handler check: a row in `data_test.sessions` can reference only a secure link whose own row says `test`. **`control.secure_links` gains its own `environment` column, also `NOT NULL`, and the unique key**; both are control-plane objects, neither is part of the per-environment set, and **the baseline migration creates them**, because a foreign key cannot reference a column a later task adds. **`NOT NULL` on both is load-bearing rather than tidy:** a `CHECK` passes when its column is NULL, and a composite foreign key under the default `MATCH SIMPLE` is not checked at all when any referencing column is NULL, so a nullable `environment` would leave both halves open. `sessions.link_id` stays nullable, because an anonymous session redeems no link, and such a row skips the key by design while the `CHECK` still pins its environment. Task 066's API check stays beside all of it as defence in depth, because a constraint violation is not a legible refusal. **Four more come from ADR-42's `answer_group_instances`** (two triggers, one CHECK and one index), which the amendment at the end of this record derives, taking the set to **seventeen**.

`form_versions_reject_update` and `question_versions_freeze_published` (both 0001) stay single, because their tables are control-plane and live in `control`. The two trigger **functions** also stay single, and they live in `control` with everything else the control plane owns: a trigger in `data_test` executes `control.answers_reject_update()`, so N triggers share one function body. They cannot sit in `public`, which this decision leaves empty and off every search path.

The list is written out because it is what the **generator** has to emit for every environment, including one an operator creates a year from now, and because an environment missing `answers_reject_delete` has an erasable ledger while an environment missing `webhook_deliveries_event_webhook_uq` fans a webhook out twice. Both are silent. Task 064 emits the set from one schema module so that the list is a consequence of the code rather than a paragraph somebody keeps current; this is the list that emission is checked against.

**Note - SEC-10's role split grows a role per environment, and the recipe stops naming `public`.** No application role holds DDL of any kind, so none can create an environment schema; that is the operator command's job under the migration role. `ALTER DEFAULT PRIVILEGES` is keyed on (role, schema, object type) with no per-table filter, so `control` and each `data_<env>` need their own grants and their own ownership by `qcms_migrate`, and the grants are now per role as well as per schema: `qcms_app_test` reaches `data_test` and a named list of `control` tables, `qcms_app_prod` reaches `data_prod` and the same list, and `qcms_app_control` reaches `control`, holds `USAGE` on each `data_<env>` with `INSERT` on its `outbox` and no other table privilege there (Q49), and holds nothing on any reporting schema (Q52). That is the symmetry the named schemas buy: every grant in the recipe reads "this role, that named schema", with no schema that gets its rights by being the default one and no role that reaches an environment it does not serve.

**Amendment - the grant table is completed on all three schemas, and the release carries the event (Code Owner, 2026-09-29 and 2026-09-30, Q48, Q49, Q52, Q54 and Q56).** Two grants above are narrower than the code they serve, and both were found by reading the decision against the call sites rather than against itself.

**Q48: `question_versions` joins the environment roles' read list**, which is therefore **six** tables and not five. The respondent path reads the pinned question version on every step served and every submission (`apps/api/src/features/responses/serve-step/handler.ts`, `submit/handler.ts`, through `getQuestionVersion`), so the five-table list would have failed every respondent request on permission. Nothing else the respondent, delivery, retention or erasure paths run reaches a control-plane table outside that list.

**Q52: the third schema joins the role table.** This record said what each role holds on `control` and on `data_<env>` and said nothing about `reporting_<env>`, which the reporting Note below makes per environment and which every staff response read goes through. So each `qcms_app_<env>` holds **`USAGE` on its own `reporting_<env>` and `SELECT` on that schema's views**, and **nothing on any other environment's**, drawing the same boundary the data-plane grant draws; `qcms_app_control` holds **nothing on any reporting schema**, so the authoring connection cannot reach a production response through a view either. **That is the application role alone**: the per-workspace view sets and the read-only roles their consumers are granted are the reporting Note's and task 067's.

**Q49: publishing queues nothing and releasing queues `form.released`.** The publish transaction today writes the version, deletes the draft and enqueues `form.published` into `outbox` together, and under this decision that transaction spans both planes: `outbox` is per environment, publishing is environment-agnostic, and no role can run it. So **`form.published` is retired** and the event moves to the act that is per environment: a release writes **`form.released`** into **that environment's** `outbox`, in the same transaction as the release record, keeping the property that a record is never observed without its event. `qcms_app_control` therefore holds **`INSERT` on each environment's `outbox`, and no other privilege of any kind in any data schema**: no `SELECT`, no `UPDATE`, no `DELETE`, and nothing at all on any other data-plane table. The property this decision bought is unchanged, because `INSERT` on an event queue is not a read of a response. **No subscriber sees a change** (Q55, Code Owner, 2026-09-30). `form.published` is queued and **never delivered**, the deliverer fanning out `response.submitted` only, and `form.released` behaves the same way, so what changes is the event type in a table nobody outside the deployment reads. The earlier reading of this as a breaking change to what a subscriber receives is **withdrawn**. **Delivering form events to endpoints would be a separate, later feature** with its own payload contract, and nothing here designs it.

**Note - the two enum types are single in `control` (Code Owner, 2026-09-29, Q54).** `access_mode` and `session_status` live in `public` today and are used only by `sessions`. They are created **once, in `control`**, the way the trigger functions are, and every environment's `sessions` uses them: a type per environment would be N copies of one vocabulary with nothing keeping them in step. **Neither joins the per-environment set**, so the guard and object counts are unchanged, and each environment role holds whatever `USAGE` Postgres requires on them.

**Note - a new environment needs a restart, and there is no reload (Code Owner, 2026-09-30, Q59).** The environment command creates the schema, the role and the grants and **tells the operator to restart the API**, which builds the new pool at boot. **ADR-24 is not amended**: it parses deployment configuration at boot and fails fast, and a reload path would be a new capability in that record rather than an implementation detail of this one, the process having to accept a credential it had not validated at startup. Restart is also the honest operational story, since the operator is already in a change window with the migration credential in hand.

**Note - the landing order (Code Owner, 2026-09-29, Q50).** The environments tasks are built now, by the direction recorded in `docs/features/README.md`, and they stay Phase 4. **Task 064 merges to `main` only after the launch-scope repetition tasks 072, 073 and 075 have merged**, so no launch-path lane rebases onto the new baseline or onto the breaking major of `@roonga/qcms-db`, and 064 rebases once. 064 **may** merge before launch validation (038), which would then validate the re-baselined layout. The baseline therefore carries whatever those three tasks added to the database, and 064's per-environment set is re-derived from the chain as it stands at that rebase rather than from any figure written beforehand.

**Because the environment roles' rights on `control` are table-level, part of the recipe is a list rather than a schema-wide pass**, and that is the price of the boundary above: `GRANT ... ON ALL TABLES IN SCHEMA control` is what an environment role may not have. **And the migrate-only revokes now cover every `qcms_app%` role rather than the one shipped name** (Code Owner, 2026-09-29). Each one lives in the migration that creates its own table, which is migration 0021's own rule, so they do not all land together: **`two_factor_resets`' revoke, all four privileges, is the baseline migration's**, and **the SEC-15 audit's `INSERT` grant and its `UPDATE` and `DELETE` revoke belong to the migration that creates that table** (ADR-41's task 069), because a baseline has nothing to revoke on for a table that does not exist yet. The `docs/operations.md` recipe and the environment-create command carry both, each **guarded on its table existing**, since that command creates roles the migrations never saw and may create one before the audit table exists.

Three documents name `public` today and move with this decision, all in task 064: the "Least-privilege database roles" recipe in `docs/operations.md`, whose row says `qcms_migrate` "owns `public` and every object in it" and whose grants are written `IN SCHEMA public`, and which gains the per-environment roles; the SEC-10 paragraph in `docs/SECURITY_DESIGN.md` section 7, which says `qcms_app` gets "no `CREATE` on `public`" and which gains the plural; and the sentence in `docs/reporting-view.md` that `qcms_reporting` "deliberately gets **no** privileges on the `public` schema", which becomes `control` and the data schemas, since those are where the raw ledger, tokens and auth tables then live. All three are correct as they stand and are corrected in the change that moves the tables, not before. `apps/api/e2e/security/03-db-least-privilege.e2e.ts` is where the result is asserted rather than read, and it gains the cross-environment refusal.

`public` itself is left empty and off every search path, with `CREATE` on it granted to nobody. That is the PostgreSQL 15 default rather than a hardening step: the schema documentation says that "in PostgreSQL 15 and later, the default configuration supports this usage pattern", and that on an older or upgraded database you "need to remove the public `CREATE` privilege from the `public` schema (issue `REVOKE CREATE ON SCHEMA public FROM PUBLIC`)". QCMS runs Postgres 16 in every shipped compose file, so the default holds; the recipe states the revoke anyway, because a database an adopter provisioned themselves may have been upgraded from before 15.

The role-per-environment answer (Q17, 2026-09-26) is what makes that listing readable: an operator checking `qcms_app_test` sees `control` and `data_test` and nothing else, so the boundary this design claims is one they can verify with a query rather than infer from a search path.

**Note - the reporting views are per environment and per workspace (Code Owner, 2026-09-26).** `reporting.responses` and `reporting.answers_flat` (migration 0003) read data-plane tables, so a single copy cannot serve more than one environment. The schema is **one per environment**, `reporting_prod` and `reporting_test`, and inside each there is **a view set per workspace**: `reporting_prod.home_responses`, `reporting_prod.vehicle_responses` and the flat-answers twin of each, every set with **its own read-only role**. The single `reporting` schema is replaced rather than kept beside them, which green field (Q22) makes free.

The workspace half is not symmetry for its own sake. A schema per environment alone would show every workspace's responses to any login holding that environment's reporting role, which is a cross-workspace read the authorisation model (ADR-41) refuses everywhere else; and this is the one surface where an API check cannot be the control, because a reporting consumer writes their own SQL against a role an operator granted. So the boundary is expressed in grants. The `qcms_reporting` recipe in `docs/reporting-view.md` becomes per (workspace, environment), and each grant reads the same way as every other grant in this design: this role, that named schema, those views. The dev-tools viewer role `qcms_ro` is unaffected, because it holds `pg_read_all_data` rather than per-schema grants; it is a different role in a different document, and the two are easy to confuse.

**Note - `webhooks` is per environment, and the cost is named (Code Owner, 2026-09-25).** The rulings' enumeration of the data plane did not list this table, and the reading it left open is now decided: `webhooks` is per environment, because "a test submission can never fire a production endpoint" is a Postgres guarantee only if the deliverer running under `data_test` cannot see a `prod` endpoint row at all, and the per-environment egress rules of SEC-14 then restate the same rule where a firewall can enforce it. Two costs come with it and are accepted: endpoint configuration is **authored once per environment** and a promotion does not carry it, so a version released to `prod` fires whatever `prod` has configured; and `webhooks.form_id` becomes the third cross-schema foreign key in the table above.

**Note - one process, one pool per environment (Code Owner, 2026-09-26).** One deployment serves every environment from **one API process holding one connection pool per environment**, and the request's environment selects the pool: from the `/<env>/` route group on the respondent side, from the administrator's switcher on the authoring side. **ADR-20's four containers are unchanged**, which is the reason for choosing this over a process per environment. The outbox deliverer and the retention sweep still start once per process under `config.mount.internal` and **iterate the live environment set**, so `docs/deploy-enterprise.md`'s scheduler-singleton rule holds unchanged rather than multiplying per environment. Per-environment integration tests pin that no path uses the wrong pool, which is the assertion that makes this shape safe rather than merely tidy. The `/<env>/` prefix remains a mountable group in ADR-09's sense, so an operator can leave a non-prod environment unmounted and get a 404 rather than a refusal (that record's own Note records the second mount this needs, since anonymous entry is not separately mountable today). **Both halves of this are decided**: the address half by the prefix rule above, the process half by this Note, recorded as Q21 and Q2 in `plan/environments-and-workspaces.md`. A pool is a connection, a connection is a role and a role is an environment (Q17), so the three decisions line up rather than merely coexist.

### ADR-41 - Workspaces are an authorisation grouping

**Status:** decided; not built (task 068). Code Owner rulings of 2026-09-25, 2026-09-26, 2026-09-27 (Q37 to Q39) and **2026-09-29** (the QCMS endpoints as the only grant write path, and the `member` row every grant holder carries), issue #995. Nothing here is open. One question is deferred rather than open and belongs to task 069: whether an owner or the installation administrator may grant themselves a `responses.*` role, recorded with the Code Owner's recommendation in that task's section of `plan/environments-and-workspaces.md`.

**Decision.** A **workspace** is a named grouping that owns forms and questions and carries the membership that authorises work on them. It is an authorisation boundary between groups sharing one installation, and it is not tenancy (ADR-04).

**The row.** A workspace is **control-plane state**, in the `control` schema ADR-40 names, one row per group: a workspace id, a display name, a slug, whether it is the installation's shared workspace, and whether release to `prod` requires an approver other than the author. That is the logical shape, and its physical home is the mechanism paragraph below rather than a `workspaces` table of QCMS's own: the row is better-auth's `organization` row, and the last two fields above are its `isShared` and `requireSecondApprover` additional fields (Q32).

**Ownership.** Every form and every question belongs to exactly one workspace; `forms` and `questions` each gain a non-null workspace reference. Ownership follows the identity row, so it is a property of a `formId` or a `questionId` and not of a version, and a published version never changes hands because the identity above it moved.

**The shared workspace is optional and is the organisation's question library.** At most one workspace per installation is marked shared. A form may pin a published question version owned by its **own** workspace or by the shared workspace, and by nowhere else; publish rejects any other pin. The access it grants is deliberately asymmetric: **every workspace's editors see and may pin** its questions, and **only its own members edit them**. That is what makes it a library rather than a surface three groups overwrite each other on, and it is what lets an organisation keep one canonical "date of birth" question without making every workspace visible to every other. A shared question's **text** is therefore the one thing that crosses a workspace boundary; no response ever does.

**Membership is a set of grants, and there are two role families that imply nothing about each other.** A grant is **(administrator, workspace, role, environments, forms)**, and an administrator holds **as many grants as their job needs** rather than one with a rank. `environments` is a set or `all`. **Every role name carries its plane as a prefix** (Q38), so the separation is visible in the name rather than explained in a footnote. Where those grants are stored is the mechanism below: `forms.owner` on a member row, every other grant a team. The two families:

| Family                  | Roles                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Acts on                     | Scope                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- | ------------------------------------------- |
| **Authoring**, `forms.` | **`forms.viewer`** (see drafts, published versions, release history and each environment's link and endpoint configuration; changes nothing), **`forms.editor`** (draft, edit, publish, preview; release, close and reopen, links and endpoints in `dev` and `test` with the environment in scope), **`forms.approver`** (the same in `prod` with `prod` in scope, and the second account under the two-person switch), **`forms.owner`** (membership, grants, workspace settings, the access audit) | the control plane           | workspace-wide                              |
| **Data**, `responses.`  | **`responses.viewer`** (view and export responses), **`responses.eraser`** (erase a response)                                                                                                                                                                                                                                                                                                                                                                                                        | an environment's data plane | the environments **and forms** on the grant |

**No role implies a right in the other family, and `forms.owner` implies nothing at all in the data family.** That is the surprising half and it is deliberate: an owner administers a workspace, manages its membership and reads **no response** without holding a `responses.viewer` grant of their own. A `forms.editor` with `prod` in scope authors and publishes and sees no production answer. A `responses.viewer` holds no authoring right.

**`viewer` appears in both families and that is safe, because the prefix distinguishes them**: `forms.viewer` reads authoring state and `responses.viewer` reads answers, and neither is the `viewer` of the single ladder this decision scrapped, which sat below every other rung and was contained by all of them. There is no ladder and no role that contains another, so there is nothing to reason about transitively; a person who genuinely does two jobs holds two rows, and their access is legible as two rows in a membership list rather than inferred from a rank.

**A data row carries a form scope as well**, `all` or a list, so a case officer can be limited to the forms they action. Authoring roles stay workspace-wide, because a draft is not sensitive in the way an answer is and per-form authoring would multiply rows for no protection.

**Both dimensions, and the form scope, are enforced in the API layer**, per route group and per route, never in a BFF (R2) and never only in the UI (SEC-3), on every route touching data-plane or environment-scoped state: response reads, exports, erasure, link minting, endpoint configuration, closing, and release to an environment.

**Three of those routes split the same way, and one does not** (Q33, Q36). **Closing and reopening a form** follows releases, links and endpoints: an editor with the environment in scope for `dev` and `test`, an approver with `prod` in scope for `prod`. **The draft preview** is the exception: it is editor-only and **environment-agnostic**, because it writes nothing and reads no response, so there is no environment for it to be scoped to. The whole of who may do what is the permissions matrix in `plan/environments-and-workspaces.md`, which is task 069's specification.

**The membership list and the grants are visible to owners and to the installation admin, and to nobody else** (Q35). Everybody else reads **their own** grants, through a capability endpoint that answers which workspaces, roles, environments and forms they hold. An administrator does not need to see who else can read a form in order to do their own job, and in a deployment where departments share an installation the membership list is itself information about another department.

**Authoring and publishing are environment-agnostic**, and that asymmetry is load-bearing: publishing a version releases it nowhere (ADR-40), so an author needs one row and not one per environment. What an environment scope gates is everything touching an environment's data or its release state. The admin's environment switcher offers exactly the environments an administrator holds in some row.

**Why two families rather than one ladder.** The single ladder was the decided model until the Code Owner tested it as a government organisation: departments as workspaces, and form authors who must **not** see production response data, with sensitive content visible only to the employees who action it. A ladder cannot express that, because every rung above `viewer` contains it. Two families with nothing implied can, and the same test produced the form scope and the rule that the installation-wide claim reads no data at all. This is where RBAC (issue #179) lands, and the SEC-3 matrix in `docs/SECURITY_DESIGN.md` section 3.2 gains the second family and the environment dimension when task 069 builds it.

**Every response read, export and erasure is recorded** in an append-only control-plane audit table: actor, workspace, environment, form, kind and time, readable by the workspace's owners and by the installation admin. The precedent shape is `two_factor_resets` (issue #432). With PII in play, "who looked at this" is a question a deployment has to be able to answer, and no table answers it today. The control is **SEC-15** and task 069 builds it.

**The mechanism is better-auth's `organization` plugin, with teams as access groups (Code Owner, 2026-09-26, Q32).** The model above is unchanged by this; what it settles is where the rows and the checks live. It was ruled after two read-only evaluations of the plugin source at version 1.7.5, which was the pin when the ruling was made. **The pin is now better-auth 1.7.6** (version note 2026-09-29, moved by PR #1007), and the two plugin directories this decision reads, `organization` and `access`, are byte-identical between the two, so every behaviour cited here holds at the current pin. What the ruling closes is the plugin's one gap, **scope on a role**, by convention on shipped tables rather than by new ones:

- **A workspace is an organisation row**, with `isShared`, `requireSecondApprover` and `archivedAt` as its additional fields.
- **`forms.owner` lives on the member row** as its role, which is the plugin's `creatorRole`, so its creator-role and last-owner protections keep working. **Every other grant holder carries a `member` row too, with the default `member` name overridden to empty statements** (Code Owner, 2026-09-29), because the plugin's team queries assume a team member is a member of the organisation the team belongs to. That row grants nothing; it is what makes the person a member of the workspace so the team grant is expressible. Task 068 seeds the first workspace through the **server-side `createOrganization` with an explicit `userId`**, because the seed runs before anybody is signed in and the request-scoped form has no user to attribute the workspace to.
- **Every other grant is a team.** A team's additional fields carry one role (`forms.viewer`, `forms.editor`, `forms.approver`, `responses.viewer`, `responses.eraser`) and its scope: `environments`, a set or `all`, and `forms`, a list or `all`. **Team membership is the grant**, so a user in three teams holds three grants, which is how the several-rows-per-user shape of the model is expressed. **The role lives on the team beside its scope rather than on the member row** (the role-on-team note under Q32, issue #995 comment 5849920962), because a role on the member row would apply to every team that user is in and turn a grant into the cross product of roles and teams: a `responses.viewer` in `test` who is also a `responses.eraser` in `prod` could not be expressed at all. On the team, each membership is one self-contained grant. The UI calls them **access groups**. A directory group maps to a team when task C3 arrives.
- **Six static roles as disjoint statements** through the plugin's access control, over the resources `question`, `form`, `release`, `link`, `webhook`, `response`, `membership`, `workspace` and `audit`. The environment and form conditions live in the **grant's scope** and never in a statement. `dynamicAccessControl` stays **off**, deliberately: owner-defined roles could recreate the mixed-family role this decision removed, and they cannot be enumerated in the section 3.2 matrix. The default role names `admin` and `member` are overridden with empty statements.
- **The check runs in the QCMS API middleware** (SEC-3): resolve the user's member row and teams in the workspace, evaluate the role's statements with the plugin's own authorize function, then narrow by the team's scope against the route's environment and form. The plugin's HTTP `hasPermission` is **not** used, because it needs the signed cookie the API does not hold.
- **Grant and membership writes are QCMS endpoints, and they are the only write path** (Code Owner, 2026-09-29). They sit behind the installation claim or the `forms.owner` role, write member and team-member rows through `@roonga/qcms-db`, and run the cascades and the SEC-15 audit in code. **The plugin's own team and member write endpoints are not an owner path: they are disabled, or refused, for everyone**, a `forms.owner` included. This replaces an earlier shape that let owners through those endpoints on the auth allowlist and accepted two write paths to one table. One path is the ruling for two reasons. The QCMS endpoints are where the validation lives and where the **SEC-15 rows** are written, so a second path is a path on which a grant changes without an audit row. And the plugin's **removal cascades** run inside the library, below any endpoint this layer could gate: its delete endpoints do fire their hooks, as read at version 1.7.5 and unchanged at the current pin, and the cascades underneath them do not, so the only way to be sure a removal is audited is for no removal to originate there. A QCMS write path is required in any case, because the installation admin holds no membership (see the Note below) while every plugin team-member endpoint checks the caller's own membership. The plugin's before-hooks stay registered as a **backstop** rather than as the mechanism, refusing whatever reaches them.
- **Configuration guards**: `creatorRole: "forms.owner"`, the **six custom roles** with disjoint statements and the default `admin` and `member` overridden with empty statements, `allowUserToCreateOrganization: false`, `disableOrganizationDeletion: true`, `teams.enabled: true`, `teams.defaultTeam.enabled: false`, `teams.allowRemovingAllTeams: true`, `membershipLimit` raised from its default of 100, and `activeOrganizationId` and `activeTeamId` never set by QCMS. A role name containing a dot is a plain string in the plugin's comma-separated role list (Q38).
- **Two more typed additional fields beyond the role and the scope** (Q39). On the team, **`externalGroupId`**: string, `input: false`, unique, the key the task C3 directory mapping joins on rather than any name, and written only by the sync path. It is declared now so the column exists before C3 needs it rather than arriving as a later migration against a live deployment. On the organisation, **`seedNewEditorsWithTestData`**: boolean, default off, the per-workspace setting behind the optional `dev` and `test` `responses.viewer` grant a new `forms.editor` may be onboarded with, so that convenience is a setting somebody chose rather than a habit somebody acquired.

**Any value the API reads to make a decision is a typed additional field, and the organisation's `metadata` column is used for nothing that is enforced** (Q39). That column is a free-form JSON string which any holder of `organization: update` replaces wholesale, so a decision resting on it would be a decision anybody with that statement could rewrite. If it is used at all, it holds display-only text. The rule is worth stating rather than left to taste, because the column is right there and the cost of reaching for it is invisible until somebody has.

**Access groups are named `<environments>.<role>[.<label>]`, and the name is a label rather than a mechanism (Q37, Code Owner, 2026-09-27, amended the same day).** A dot separates every segment. Under workspace `hr` the stored names read `all.forms.editor`, `prod.forms.approver`, `dev-test.responses.viewer`, `prod.responses.eraser`, `prod.responses.viewer.claims`. The grammar is **`<environments>.<plane>.<role>[.<label>]`**, and the role token is always exactly two segments because every one of the six names is (Q38), so a reader takes position 1 as the environments, positions 2 and 3 as the role, and anything after as the label: `prod.responses.viewer.claims` is environments `prod`, role `responses.viewer`, label `claims`, and `all.forms.editor` has no label. **The stored name carries no workspace segment**, because a team already belongs to exactly one organisation and a stored copy of the workspace could drift on a slug rename. The **full name is derived and never stored**, `<workspace>.<team>`, for cross-workspace lists; the **directory group name at task C3 is derived the same way** with the product prefix, `qcms.hr.prod.responses.viewer`.

The environments segment is one environment name, `all`, or a hyphen-joined set such as `dev-test`, which is unambiguous because an environment name carries no hyphen; the optional label is free text for a form-limited group, and a form list never lives in a name. **The dot was chosen over a slash** because a `sAMAccountName` may not contain `/`, so the dot survives on-premises Active Directory group rules, and it cannot collide with a slug, which is lowercase letters, digits and hyphens.

Four rules keep the name from becoming the thing it describes. **The team's fields are authoritative**: role and scope are read from the team row, the name is kept in step with them by the UI, and a mismatch is a **validation error on save, never a permission**. **Nothing parses a name to authorise.** **The name is never the join key**: C3 maps a directory group to a team by a **stored external-group identifier** on the team, so renaming a workspace slug changes display only and strands no mapping. And **uniqueness within a workspace is enforced by the QCMS write path**, because the plugin does not enforce it on team names. Two grants are not teams and appear in the C3 mapping beside them: the member row's `forms.owner` as `<workspace>.forms.owner`, and the installation claim as `qcms.admin`.

**The costs, accepted.** The plugin's `organization`, `member`, `invitation`, `team` and `teamMember` tables and two session columns join the hand-kept mirror in `packages/db/src/schema/auth.ts` and better-auth's two-direction startup schema check, so a plugin upgrade is a reconciliation event like any other (ADR-06's note on that check). The exit path in `docs/auth-swap.md` **widens from one verifier function to the authorisation layer**: leaving better-auth would now mean migrating authorisation too, and that document and the risk acceptance in `CONTRIBUTING.md` say so. Task 064 verifies the string-array additional-field mapping through the Drizzle adapter on Postgres, alongside the non-default schema check it already owns.

**The evaluation recommended QCMS's own tables and middleware; the Code Owner weighed reuse across applications above that coupling.** The survey behind the ruling found no existing plugin or engine that closes the scope gap while keeping the plugin as the membership base: the plugin is byte-identical between 1.7.5 and 1.7.6, teams carry no role and are ignored by its permission check, the ABAC and team-roles requests upstream are closed as not planned, the only instance-aware community plugin is alpha with sixteen tables of its own, and every authorisation engine considered (OpenFGA, SpiceDB, Keto, Cerbos) would be a fifth standing container against ADR-20.

**Slugs stay unique per installation.** `forms.slug` and `questions.slug` are unique across the whole installation, not per workspace, so `/f/{slug}` needs no workspace segment, a slug never changes meaning by context, and no address has to be re-pointed when a form's ownership changes.

**Note - the self-grant, the seed setting and the masked endpoint URL (Code Owner, 2026-09-30, Q56, Q57 and Q58, closing issue #998).** Three consequences of this decision were left open when it was taken and are now ruled.

**A self-grant is audited always and refused conditionally** (Q56). Nothing stopped a `forms.owner`, or the installation administrator, granting themselves a `responses.*` group, which would have made "an author never sees production personal data" a convention rather than a control. **Every grant write and every revoke is a SEC-15 row**, widening that control's kinds; **a self-grant of a `responses.*` role is refused only while the workspace's `requireSecondApprover` switch is on**, and then needs a second `forms.owner` or the installation administrator to confirm; and **the installation administrator follows the same rule**. With the switch off it is allowed and audited, so a one-account installation can still read its own responses.

**A grant on `test` responses is a grant on personal data** (Q57). `seedNewEditorsWithTestData` stays and **defaults off**, and this record, the plan and the **admin's help text for the setting** say in those terms that a test run can involve real respondents. Turning it on is an owner's deliberate act and is written to the audit.

**A `forms.viewer` sees a masked endpoint URL** (Q58). Scheme, host and path are shown and the **query string is masked**; `forms.editor` and above see the whole URL. The **API** masks it in the response it returns to that role, never the admin's rendering. The **URL is not treated as a secret and the signing secret is**, and the operator documentation tells operators not to put credentials in a URL, because masking is a mitigation rather than a control. Task 067 builds it, with the per-environment endpoint routes.

**Release to prod may require an approver who is not the author, and does not by default.** When the requirement is on, the approver must hold the **`forms.approver`** role in the form's workspace with `prod` in scope, and must not be the administrator who published the version being released; the approval is recorded on the ADR-40 release record, which is what makes it auditable rather than procedural. **`forms.owner` does not approve** (Q34): nothing implied holds here either, so an owner who should approve is given a `forms.approver` grant with `prod` in scope, which makes their authority a row somebody can read rather than a rank. The rule gates the release to **`prod` alone**: a release to any other environment is self-service for an editor who holds it, which is what keeps a test cycle usable.

**The rule has two mechanisms, and they are different shapes (Code Owner, 2026-09-29, Q51, closing item 6 of issue #998).** One switch governs both, and what each does was previously described two ways in one record. A **release to `prod` is one act**: it is refused when the releasing account is the one that published that version, and it succeeds for a different `forms.approver` holding `prod` in scope. A **`prod` webhook endpoint change is two acts**: one account proposes it, the change is **stored pending** and does not take effect, and a **different `forms.approver` with `prod` in scope confirms** it. The asymmetry is deliberate: a release names a version that already exists and can be judged in one look, while an endpoint change is a new value somebody has to read before it is live. **"Author" means the account that published the version**, which is what this record already says and is now stated as the definition, so a draft several editors touched has exactly one author. Task 070 builds both; 067's criterion about the endpoint change moves there with the second one. The switch is per workspace and lives on the workspace row, and it is **off by default**, including on the workspace a fresh database is seeded with. That default is deliberate rather than lax: an installation with one administrator cannot satisfy the rule at all, so defaulting it on would mean a bootstrapped deployment could not release to `prod` until a second account existed, and the first thing an operator would learn about the feature is how to turn it off.

**What a workspace is not.** Not a tenant: one operator, one configuration, one identity store, one database, one deployment. Not an isolation guarantee: the boundary is an authorisation check in the API, not a schema, and the only schema boundary in this system is ADR-40's environment, which a workspace sits entirely inside `control` beside rather than cutting across. Not a routing segment: no URL carries a workspace. Not a configuration scope: deployment flags (ADR-24), themes (ADR-30) and the port allocation (ADR-37) remain installation-wide. An administrator with the installation-wide credential and database access reaches everything, exactly as before.

**Note.** `questions.slug` already carries a unique constraint (`questions_slug_unique`, migration 0000). `forms.slug` does not: `packages/db/src/queries/forms.ts` resolves the public address with `limit(1)` and says so in its own comment, calling uniqueness "an authoring-time concern, not a DB constraint yet". The slug rule above is therefore a constraint task 068 adds, not one it inherits. Green field (Q22) makes adding it cheap rather than risky: there is no installation holding a duplicate for the constraint to fail against, so it goes in with the table rather than behind a data check.

**Note - what the installation-wide claim may do (Code Owner, 2026-09-25, amended 2026-09-26).** The SEC-3 `user.role` claim is otherwise unchanged: it is installation-wide, carries `admin` today, and is declared to better-auth with `input: false` so no request body can set it. What it grants is **administration and nothing else**:

- The claim administers **settings, user accounts, memberships and environments**, across every workspace. That is what makes an operator useful during an incident and what keeps the first bootstrapped account from being locked out of the product it just created.
- It grants **no data-plane read anywhere**: no response read, no export, no erasure. An administrator who needs to see an answer holds a **`responses.viewer` grant** like anybody else, and that grant is visible in the membership list.
- **Authoring needs a `forms.` grant** in that form's workspace. The claim alone is not authoring authority anywhere.
- **Approver-not-author applies to that account too.** Holding the claim does not make an administrator eligible to approve their own release; the rule is about the pair of people, not about privilege level.

**The second bullet is an amendment, and it replaces the opposite claim.** This Note said on 2026-09-25 that the claim carried "response reads and exports" across workspaces, and summarised the position as "sees all, edits none without membership". The Code Owner withdrew that on 2026-09-26, after testing the design against an organisation holding sensitive personal data: an installation administrator who can read every department's responses by virtue of being an administrator is exactly what such a deployment cannot have, and "sees all" is not a property worth keeping for the convenience it buys. **A workspace is therefore a confidentiality boundary against an administrator who holds no `responses.viewer` grant**, which is more than the earlier reading promised; what it is still not is an isolation guarantee against somebody with the database credential, consistent with ADR-04's Note. Task 069 enforces this in the API layer, extends the section 3.2 matrix with both role families and this account shape, and records every read that does happen (SEC-15).

**Note - a question may move workspaces, and existing pins are grandfathered (Code Owner, 2026-09-26).** Ownership is on the identity row, so moving a question is one `UPDATE` and touches no version. Forms in other workspaces that already pin one of its versions **keep serving and keep that pin in their next draft**, which is what ADR-02 and R6 require: a published version is immutable content and a `questionId` never changes meaning. What is refused is a **new** pin from another workspace onto a question that is not in the shared workspace, and it is refused the same way a pin to a `deprecated` version is refused today, so the mechanism is one authors have already met rather than a second kind of publish failure.

**Note - a workspace is archived, never deleted (Code Owner, 2026-09-26).** Archiving requires that the workspace holds no open form and no released version, and its forms and questions are reassigned to another workspace first, so archiving is the last step rather than a cascade. **No response row is ever reached**, which is the property that matters: ADR-17 makes erasure and the retention purge the only two whole-session delete paths, and "delete a workspace" is deliberately not allowed to become a third door.

**Note.** Nothing in this decision changes the respondent side. Respondent authorization stays structural: a session token authorizes exactly one session and there is no respondent-facing enumeration of anything (SEC-3). A respondent never learns a workspace exists.

## Deployment and operations

### ADR-20 - Four-container solo topology

**Status:** implemented.

**Decision.** The default deployment runs portal, admin, API, and Postgres. The API publishes no host port. TLS, HSTS, and routing belong to operator-provided ingress; an optional proxy recipe is not a standing product container.

**Note.** The compose file also defines a fifth, run-to-completion `migrate` job; "four standing containers" holds.

### ADR-34 - OpenTelemetry baseline

**Status:** implemented.

**Decision.** API, admin, and portal use official OpenTelemetry instrumentation at composition roots for W3C trace propagation, OTLP traces, and allowlisted trace-correlated application logs. With no OTLP endpoint, telemetry is a hard no-op. Browser telemetry, custom metrics, and identifier hashing are Phase 4. No collector ships in the base topology.

**Note.** The Next apps use `@vercel/otel` and the API uses `@hono/otel` - the documented compositions for those frameworks, not OpenTelemetry-org packages. SEC-13 span redaction is part of the baseline in all three roots, alongside the log allowlist.

### ADR-37 - Port allocation

**Status:** implemented; amended 2026-08-07 (issue #417).

**Decision.** `QCMS_PORT_SEAT` selects one port-allocation index. Stable services use `7Sxx`; ephemeral harnesses use `17Sxx`. The exact table and runbook live only in `docs/PORTS.md`, and `pnpm check:ports` enforces the allocation. The development-tools overlay may use the stable dashboard and database-viewer slots defined there.

## Both frontends

### ADR-08 - Separate frontends, shared renderer

**Status:** implemented.

**Decision.** Admin and portal are separate Next.js applications with different product needs. Both use strict BFF handlers and the same QCMS renderer for form content, so admin previews match the respondent portal.

**Note.** The shared surface is a triple - compiler, `documentForVisible` projection, and renderer - all taken from `@roonga/qcms-ui` by both apps.

### ADR-22 - One UI component stack

**Status:** implemented.

**Decision.** Both frontends use `a2-react-aria`: `@a2ra/core` is exact-pinned and components are vendored into `@roonga/qcms-ui`. No competing component library is allowed. Upgrades are reviewed events and must preserve golden-document conformance.

**Note.** The competing-library lint fence covers `packages/ui/src` **and both apps**: one list of restricted import patterns in `eslint.config.js`, applied to `packages/ui/src/**` (vendored sources and its own tests exempt) and to every `.ts`/`.tsx` file under `apps/portal/` and `apps/admin/`, specs included. **It was scoped to `packages/ui` alone until 2026-09-01 (issue #728, PR #771)**, so the clause that stood here saying the apps hold the rule by consuming `@roonga/qcms-ui/kit` is corrected rather than left standing: consuming the kit was a convention, and nothing stopped a screen taking a widget library as a direct dependency and importing it, which is exactly what this decision says is not allowed. The lint block is the fast fence; `@roonga/qcms-ui`'s exhaustive permitted-import allow-list stays in that package's own import-surface test. **Vendor-tree fidelity became an automated gate on 2026-09-03 (issue #189)**, so the clause that stood here calling it a reviewed artifact and not a gate is corrected rather than left standing: `pnpm check:a2ra-fidelity` compares every file under `src/components/a2ui/` against `packages/ui/a2ra-manifest.json`, a record of upstream's content at the pinned commit, on every `pnpm verify` and in CI, offline. `packages/ui/a2ra-diff.md` remains the reviewed artifact beside it, refreshed at each pin move; the gate is what holds on the days in between. The decision is unchanged - this note records how it is enforced.

### ADR-26 - Different frontend decisions by surface

**Status:** implemented; the admin bullet amended 2026-08-31 (issue #725).

**Decision.**

- **Admin:** internal, desktop-primary, QCMS-branded, and client-heavy where editing demands it. Server components read and Server Actions mutate through the BFF, with scoped client editor state. No client-side server-state library.
- **Portal:** public, mobile-first, adopter-themed, SSR-first, and fetch-only with minimal client state.
- **Shared:** the a2ra component stack, WCAG 2.2 AA, semantic tokens, and the renderer used for form content and previews.

**Note.** The admin bullet named TanStack Query until the Code Owner amended it on 2026-08-31 (issue #725). The library was never adopted; server components plus Server Actions are the shipped mechanism, and the bullet now names it and rules a client-side server-state library out rather than permitting one.

**Note.** The admin runs Tailwind's default type scale rather than the portal's `--type-*` floors (issue #442, Code Owner decision 2026-09-02). The mechanism: the `@theme` block in `packages/ui/src/theme-components.css` that raises `--text-sm` and `--text-xs` to those floors is global to a build and no selector can scope it, and that sheet must be imported so the task-058 preview island shows genuine portal treatment, so `apps/admin/app/globals.css` re-pins the five affected variables to Tailwind's defaults. The portal's floors are unaffected. This is surface-specific in the sense the admin bullet already carries, and `docs/admin-constraints.md` already holds WCAG 2.2 AA as a goal the admin builds toward rather than a blocking gate; raising the admin to the floors would reflow 139 call sites across a shipped internal tool. The comment in `apps/admin/app/globals.css` is the local explanation and points here; this Note is the record.

### ADR-27 - Internationalization in both apps

**Status:** implemented.

**Decision.** User-facing chrome comes from app catalogs; authored content comes from `LocalizedText`. Dates, numbers, and currency use `Intl`. Additional translations and a runtime locale switcher are Phase 4, but the localization machinery is launch scope.

**Note.** Both apps now carry a locale constant and a format module: `apps/admin/lib/i18n/format.ts` exports `ADMIN_LOCALE` and `apps/portal/lib/i18n/format.ts` exports `PORTAL_LOCALE`, and both are `en` (issue #729). The portal used to inline `toLocaleString("en-US", ...)` in `components/completion-view.tsx` and to let its A2UI step views inherit the renderer package's own `en-US` default for react-aria, so a second portal locale meant editing components; both resolve `PORTAL_LOCALE` now. The respondent-facing strings are unchanged: for every value the portal renders, `en` and `en-US` resolve to the same CLDR data, which `apps/portal/lib/i18n/format.test.ts` asserts. No currency value exists in the domain yet; that clause is forward-looking. A runtime locale switcher stays Phase 4 (issue #732).

**Note (issue #906).** The admin's three A2UI preview surfaces were the last call sites on the renderer package's own `en-US` default, one surface behind the portal half above.
`apps/admin/lib/i18n/format.ts` now exports `PREVIEW_LOCALE` and `components/forms/draft-preview.tsx`, `components/forms/version-view.tsx` and `components/questions/question-preview.tsx` all pass it, so the locale react-aria formats and announces the previewed controls on is declared once rather than inherited three times.
**It mirrors `PORTAL_LOCALE` rather than reading the form's own `defaultLocale`, and that is the decision this note exists to record.**
`defaultLocale` selects WHICH localized strings the compiler writes into the stored document (ADR-11, invariant I3); by the time a step reaches the renderer that choice is baked into bytes, and what is left for the `locale` prop is how the controls around that text are formatted and announced.
The portal resolves that from its own app constant and reads `defaultLocale` nowhere, so a preview keyed to the form's tag would render a form whose `defaultLocale` is, say, `en-AU` differently from the portal serving that same form: preview fidelity (ARCHITECTURE section 6) lost from the other side.
Nothing on screen moved, and that is measured rather than asserted: `packages/ui/src/locale.test.tsx` renders every step of the golden corpus under `en` and under `en-US` and the markup is identical, and renders it under a locale that genuinely differs so the prop is shown to be load-bearing.
`PREVIEW_LOCALE` carries the react-aria tag and only that, which is today's whole job because a stored document's text is already resolved.
When issue #732 gives a respondent a locale of their own, this declaration is where the preview's copy of that tag moves, and the compiled document's own locale is a second half that #732 owns rather than anything this constant can express; the operator's chrome stays on `ADMIN_LOCALE`.

### ADR-38 - Theme scope carrier

**Status:** implemented.

**Decision.** Theme and font token sheets target `:is(:root, [data-qcms-theme-scope])`. Component treatments target descendants of the bare carrier attribute. This lets admin previews render portal tokens and treatments without restyling admin chrome, while preserving existing root-based adopter overrides.

**Note.** Two known containment limits: the Tailwind `@theme` block raising the WCAG 1.4.12 floors is global by construction, and the admin neutralizes it manually; portalled overlays (select, calendar, menu popovers) attach to `document.body` outside the carrier, so previews show admin tokens for transient overlays.
