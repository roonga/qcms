## issue #260 / #244 - the container refuses to destroy itself from inside (2026-08-01, PR #261)

- LESSON (PO seat, Code Owner directive): anything that can kill the dev container or the sessions in it must be prevented by construction, not by a rule somebody has to obey. A convention has to be honoured by every agent, in every lane, indefinitely, and its failure mode here is silent and total - the environment vanishes mid-work and no surviving process can report why. The same principle applies to the seat-mail bus, which was lost the same day for the same reason (it lived on the container overlay rather than on a bind mount).
- LESSON (PO seat): the container recorded `ExitCode=0`, `OOMKilled=false` and 4m38s of downtime. A clean, deliberate stop - but the processes inside see SIGKILL and report 137, which reads exactly like an out-of-memory kill, and it was misdiagnosed twice on that basis. When a container dies, read `docker inspect`'s exit code before believing the exit code of anything that was inside it.
- LESSON (PO seat): verifying a guard against self-destruction is awkward, because the naive check is the destructive act. The order that worked: extract the detection function into a standalone probe and confirm it fires; then put a `docker` stub on `PATH` that blocks `stop`/`rm`/`kill`; only then run the real script. The stub earned its keep - running the new tests against the pre-fix script caught the old code attempting `docker rm -f`, which would have **removed** the container rather than merely stopping it.
- LESSON (PO seat): detection for a guard like this needs two sides. A `containerEnv` marker is authoritative but does not reach an already-running container, which is the same trap `warn_if_stale` exists for, so it only arrives on the next rebuild. Matching the shell's hostname against the container id covers every container created before the guard landed - including the one it was developed in, which is the only reason this fix protected anything on the day it was written.
- FRICTION (PO seat): `pnpm exec` in a worktree aborts with `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`, wanting to purge a `node_modules` left stale by a pnpm bump - unsafe while other lanes' worktrees are live. Invoking `node_modules/.bin/vitest` directly with `--root` pointed at the worktree works and leaves the install alone.
- FRICTION (PO seat): `git push` has no credentials inside the dev container while `gh` is authenticated. `git -c credential.helper='!gh auth git-credential' push` works without writing a token into any config.
- FRICTION (executor): `gh pr edit --body-file` silently fails on this repo - it exits with only a Projects-classic GraphQL deprecation error and does not apply the body change, so a lane trusting its exit code reports an update that never happened. `gh api -X PATCH .../pulls/<n> --input <json>` works. Also: `jq` is not installed on this host, so JSON has to be built through `node -e`. Rides #253.

- LESSON (conductor): a fix visible only in a committed gate frame has no automated check behind it. 034's ADR-27 violation was found by a reviewer reading PNGs, and a cycle-1 resolution that was claimed but never landed was invisible for the same reason. Declining to fix something visible, unprompted and against the interest of reporting a clean sweep, is harder judgment than fixing it. The re-review had been deliberately scoped to a one-line ledger diff, and the sweep was skipped on the grounds that the diff was trivial. The diff being trivial is exactly what makes skipping tempting: the *surface* can change under you between two heads even when the diff does not. Two of the three threads were real bugs.
