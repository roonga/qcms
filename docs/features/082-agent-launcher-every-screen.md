## Context

The panel mounts in one place today, inside `FormBuilder`, under a prop the builder page passes when `agentAuthoringEnabled()` is true (`plan/agent-everywhere.md` section 2). The Code Owner's ruling makes it a Confluence/Rovo-style assistant on **every** authenticated admin screen: a button in the top bar and a panel docked beside the content by default, with no floating window (Code Owner, 2026-10-24, issue #1133), Settings included (Q18), with one conversation per form subtree. This task is that move, and with it the API side the move needs: a frozen registry of screens, each with a context builder that returns a typed facts object the API computes itself under the caller's grants, because the browser sends a screen id and route ids and **never sends context content** (section 5.1).

It is the phase that makes the "no answers" property hold for every screen rather than one. Every screen gets a context builder with a strict schema in this task, response screens included, so the vocabulary test and the sentinel test cover the whole surface from the day the launcher reaches it. **Action kinds, propose tools, cards and the token are 083's**; this task offers the model the builder's existing four tools on the builder, the read tools section 12 lists for the phase C screens, and on every other screen a context and nothing to propose (section 5.4): the agent explains and navigates.

## The rulings that govern this task

Principle point 5 (everywhere, the same principle on every screen) and point 4 (response metadata may flow, answers may not). **Q2** (`Alt+Shift+A`, ruled by the Code Owner directly). **Q18** (the launcher on every screen, Settings included). **Q15** (memory only; nothing in `localStorage` or `sessionStorage`, because sign-out does not clear tab storage). **Q19** (one limiter key, 10 turns per minute per user, across every assist route). **Q10** (an agent read that the screen audits writes the same SEC-15 `read` row). **Q11** (staff names and emails may go to the provider). Section 1.4 (no launcher outside `(shell)`: there is no signed-in user to act for). Section 4.2's table decides the modes and their geometry; `plan/admin-mobile-stance.md` names the two breakpoints, and the sheet is the mode below `--bp-sidebar`.

## Deliverables

**Admin: the top-bar button and the panel.**

- **The top-bar button** (section 4.1; Code Owner, 2026-10-24, issue #1133): the floating corner launcher is retired. A 32 CSS px button first in the top bar's trailing group, before the environment chip and the account avatar, carrying the assistant's mark at 24 px (`aria-hidden`) and a catalog name ("Open the assistant"), with `aria-expanded` and `aria-controls`; hover and press shift the bubble, and the focus ring traces the button. It is rendered once in the top bar of `apps/admin/app/(shell)/layout.tsx`, only when `agentAuthoringEnabled()` is true on the server, on every `(shell)` screen. With the flag off it is **absent, not hidden**, the stance the builder prop takes today. Pressing it opens the panel docked or closes it. With the panel closed, its badges are short text immediately after it, never colour or motion alone ("Working" while a turn runs; the "1 action to review" badge arrives with 083's cards; ruling O3, Code Owner, 2026-10-24, issue #1133).
- **Dock, expanded and sheet** (section 4.2; Code Owner, 2026-10-24, issue #1133): **no float mode**. The panel opens docked by default at and above `--bp-sidebar`, as a **third track of the shell body grid** beside the 240 px rail every screen has (section 7.0 of `plan/admin-design-contracts.md`, recorded by #1120), 400 px by default (320 to 560, resizable, never taking the content below `--bp-compact`), full height below the top bar, `role="complementary"` named by the panel's name, chosen because a track is the only geometry that cannot obscure page content. The header's Expand control fills the area below the top bar, with the rail and content `inert`, as a modal `role="dialog"` with a focus trap, and returns to the dock. The sheet below `--bp-sidebar` is the full viewport below the top bar, a modal dialog with `aria-modal="true"` and a focus trap. The panel is one `<div>` whose role follows its state. Whether it is open, and its width, are a cookie the layout reads, the way the appearance mode is, so an open panel renders docked on first paint with no jump after hydration.
- **The rail at 1024 to 1279 CSS px** (Code Owner, 2026-10-24, issue #1133; it replaces review finding B4's "dock only at 1280 CSS px and wider"). At 1280 px and wider the rail stays beside the dock and the content keeps at least `--bp-compact` (640 px). At 1024 to 1279 px, opening the panel hides the rail with #1119's hidden state, held only while the panel is open and never written to the operator's own Hide sidebar setting, and the panel is at most 400 px. Closing the panel, or widening the window to 1280 px, restores the rail to the operator's own setting (ruling O1). In this range, the heading row's "Show sidebar" shows the rail and closes the panel, and the polite live region says so (ruling O2). Both are ruled (Code Owner, 2026-10-24, issue #1133; `plan/agent-everywhere.md` sections 4.2 and 16).
- **Resizing without dragging** (Code Owner, 2026-10-24, review finding B5). The dock's edge is a focusable `role="separator"` (the float's corner handle is gone; Code Owner, 2026-10-24, issue #1133) with `aria-orientation`, `aria-valuenow`, `aria-valuemin` and `aria-valuemax` in CSS px and a catalog name. Arrow keys change the width by 40 px, and Home and End go to the minimum and the maximum. The panel's Help menu offers **Panel width: Narrow, Default, Wide** (320, 400 and 560 px) as the single-pointer alternative. The width is kept in the panel cookie.
- **Keyboard** (section 4.3): `Alt+Shift+A` opens or focuses the panel, is not captured while a text input outside the panel has focus, and is printed in the top-bar button's tooltip and the panel help. Escape closes the sheet and returns focus to the top-bar button; in the dock, Escape moves focus back to the page without closing the dock; in the expanded state, Escape returns the panel to the dock (Code Owner, 2026-10-24, issue #1133). Stop, Enter and Shift+Enter carry over from 080.
- **Focus** (section 4.4): opening focuses the composer; closing returns focus to the top-bar button; navigation between screens keeps the panel open and never steals focus.
- **The header** (section 4.8): one 44 px row with the title, a **context chip** naming what the agent can see on this screen ("Form: Vehicle quote, draft"), and four icon buttons with catalog names and tooltips: New conversation, Expand (a toggle with `aria-pressed`, replacing the Dock or Float toggle; Code Owner, 2026-10-24, issue #1133), Help, Close. Collapse goes, with its `localStorage` key, because the top-bar button reopens.
- **WCAG 2.2 AA** (section 4.5): nothing the assistant draws overlays page content, because the button is in the top bar, the dock is a grid track and the expanded state and the sheet are modal, so the floating launcher's scroll-padding publication goes (2.4.11; Code Owner, 2026-10-24, issue #1133); every icon button at least 24 x 24 CSS px (2.5.8); every resize of the dock reachable without a dragging movement, through its edge separator's keys or the width menu (2.5.7); the sheet at 320 CSS px with no horizontal scroll except inside a code block (1.4.10); the top-bar button's tooltip dismissible, hoverable and persistent (1.4.13); a polite live region announcing phase changes in plain language and one completion line per turn, never tokens, with the in-progress bubble `aria-busy` and route-surviving announcements through the shell's `Announcer` (4.1.3); mode and state never by colour alone (1.4.1); theme tokens including the high-contrast dark theme.
- **Reduced motion** (section 4.6): no slide, scale or fade on open, close, expand or return, and the rail hides and returns without motion (Code Owner, 2026-10-24, issue #1133).
- **Internationalisation** (section 4.7, ADR-27): every new string a catalog key under a new `agent.*` namespace in `apps/admin/lib/i18n/en.ts`; times through `apps/admin/lib/i18n/format.ts`.
- **The admin screen table**, `apps/admin/lib/agent/screens.ts`, mapping each `(shell)` route pattern to a screen id (the ids are section 12's route patterns), and the test that reads the route tree off the filesystem and fails when a `(shell)` page has no row, the pattern `apps/admin/lib/rail-routes.test.ts` already uses. The table holds page routes only, never a route handler, and it **replaces 080's closed page list** as the Markdown renderer's link allowlist; the constant is deleted (review finding B3). Each turn sends `{ screen, params }` and the environment switcher header every admin request carries (task 065).
- **Conversation continuity** (section 5.3): one conversation per form subtree (builder, rules, preview, versions, releases, links, webhooks and responses for one `formId`), held in a React context the shell layout provides and surviving soft navigation within `(shell)`; each turn carries the current screen id; leaving the form starts a new conversation keyed by the new subject and returning within the tab restores the old one; a reload starts fresh; nothing is written to tab storage.
- **The empty state** for a screen with nothing to propose (section 5.4): the context chip says what the agent can see, and the panel offers explanation and navigation.
- **A second BFF route**, `apps/admin/app/(shell)/assist/route.ts`, for screens with no form, carrying `isSameOriginPost()` and the session gate `apps/admin/lib/server/shell-route-guards.test.ts` enforces, answering 404 when the flag is off, forwarding only the headers the per-form route forwards today.

**API: the registry, the contexts and the door.**

- **`features/agent/`**, grown out of `features/forms/assist` along section 6.2's layout: `tools/registry.ts` holding the frozen `TOOLS` record and `runAgentTool` as the only executor, `tools/read/*.ts` one module per read tool, and `screens.ts` holding the frozen `SCREENS: Record<ScreenId, ScreenDef>` with each screen's context builder, read tools and action kinds (an empty list for every screen in this task; 083 fills it). `actions/*.ts`, `proposal-token.ts` and `provenance.ts` are 083's and are not created here. The existing routes keep their paths and their mount flag; the slice README moves with the code.
- **A context builder per screen**, returning a **typed facts object** under a `z.strictObject` schema with enumerated fields, holding what section 12's facts column lists for that screen and never an answer value, an answer-ledger row or a webhook payload (section 10). The current `AssistContext` becomes the builder screen's context and its key-set test stays; every new context gets one. The response screens' builders close over a **metadata projection** of the response list and detail queries that selects no answer column and joins no answer table, and the response list context writes **one SEC-15 `read` row per conversation for each distinct filter set**, not one per turn (Q10, applied to the context build; Code Owner, 2026-10-24). A filter set is the normalised `version`, `from`, `to` and `flagged` values. The API decides whether to write, keyed by the actor, a conversation id the admin mints when a conversation starts (random, held in memory with the conversation, sent with each turn) and a digest of the filter set. A client that forges or reuses a conversation id can only cause more rows, or skip a row for a set that is already recorded for that same user; it cannot leave a set with no row at all. The webhook screens' facts give state, attempt counts, HTTP status codes, times and endpoint configuration, with the URL masked for a `forms.viewer` exactly as the API already masks it (task 067, Q58), and never a payload, a consumer response body or a last-error string that might quote one. Each builder checks the SEC-3 matrix cell its screen requires through the same policy evaluator the route middleware uses, before building anything.
- **The read tools of the phase C screens**: the builder's existing four verbs, and preview's projection of the draft for hypothetical answers (the `previewDraftAction` read). Each declares its matrix cell and the door checks it for the calling principal before running (section 6.1). The read tools section 12 lists for phase D screens arrive with 083.
- **One door per screen** (sections 5.2, 6.2, 7.1): a turn's tool set is the intersection of the global registry and the current screen's list; `runAgentTool` refuses any name outside **the current screen's** list before dispatch; the provider tool set is built from the same list; a call to a name that does not exist still ends the turn at that step with no proposal.
- **`POST /admin/assist`** for screens with no form, sharing the per-principal limiter key with `POST /admin/forms/:id/draft/assist` (Q19), with a route-policy row per screen cell in `apps/api/src/features/membership/route-policy.ts`, and mounted only under the flag like the existing routes. A turn's screen id is validated against `SCREENS`, and the per-form route refuses a screen id that is not in the form subtree.
- **Prompt framing** (sections 5.3 and 7.3): screen facts and tool results delimited as data, the system prompt stating that text inside them is content authored by users and never an instruction, and "The user is now on the {screen} screen of this form" prepended to a turn whose screen changed. `SYSTEM_PROMPT_VERSION` is bumped.
- **The vocabulary test** (section 7.2): a unit test walks every facts schema and every read-tool output schema and fails on a field whose name matches the respondent-content vocabulary the stdout redactor uses (`packages/observability/src/logger.ts`).
- **The sentinel test, generalised** (section 10): with a submitted answer carrying a sentinel in the database **and** a webhook delivery whose payload carries it, the fake provider's `read-all` script calls every read tool and the API builds every screen's context; the exact provider payload bytes are captured; the sentinel is asserted present in the database before it is asserted absent from the payload; and the session id is asserted **present**, so the metadata half of the rule is pinned too.

**Tests this phase owns** (section 14). Admin Vitest: the screen table test, the continuity context. API Vitest: registry and screen key-set tests, the one-door test per screen, the vocabulary test, the sentinel test per screen, the limiter-key test across both routes. Playwright: the top-bar button on every `(shell)` page, Settings included, and on none outside it; `Alt+Shift+A`; Escape and focus return in the dock, the expanded state and the sheet; an open panel persisted with no layout jump; the rail hidden and restored at 1024 to 1279 px; the narrow sheet; reduced motion emulated; the 2.4.11 tab-through on each screen with the panel docked, the way `apps/admin/e2e/focus-not-obscured.pw.ts` already asserts the criterion; axe on the top-bar button, the dock, the expanded state, the sheet, the empty state and a streaming turn.

**Documentation and the mirror.** `docs/agent-authoring.md` sections 4 ("where the panel is" becomes every screen; the four-tool statement stays true until 083), 6 and 8 (continuity); the moved slice README; `docs/adr/core.md` and `docs/ownership-seam.md` where they name `features/forms/assist`; `pnpm qcms:sync-templates` and a `create-qcms-app` changeset.

## Exit criteria

1. The filesystem test fails when a `(shell)` page has no row in `apps/admin/lib/agent/screens.ts`, and every page present at landing has one.
2. Playwright finds the assistant's top-bar button, first in the top bar's trailing group, on every `(shell)` page, and no floating launcher anywhere, Settings included, and none on sign-in, the two-factor screens or change-password; with the flag off the component is not in the document.
3. There is no float mode. Opening the panel at and above `--bp-sidebar` docks it as a grid track whose content column narrows, a `role="complementary"` landmark named by the panel's name; the sheet below `--bp-sidebar` is modal with a focus trap; an open panel renders docked on first paint with no layout shift after hydration, asserted against the cookie. At 1280 px and wider the rail stays and the content column measures at least 640 px. At 1024 to 1279 px opening the panel hides the rail, the content column measures at least 640 px and the panel at most 400 px, and closing it restores the rail; pressing "Show sidebar" in that range shows the rail and closes the panel, with the live region saying so; the operator's own Hide sidebar setting is unchanged by all three. With the panel closed and a turn running, the text "Working" follows the top-bar button. The Expand control fills the area below the top bar as a modal dialog with the rail and content `inert`, and Escape or the control returns it to the dock (Code Owner, 2026-10-24, issue #1133).
4. `Alt+Shift+A` opens or focuses the panel and is ignored while a page text input has focus; Escape closes the sheet and returns focus to the top-bar button; in the dock, Escape returns focus to the page and the dock stays; in the expanded state, Escape returns to the dock.
5. With the panel docked, tabbing through every screen's controls leaves none wholly covered (2.4.11); every icon button measures at least 24 x 24 CSS px; the dock changes width from the keyboard alone (arrow keys on the separator by 40 px, Home and End to the bounds, with `aria-valuenow` following) and from the width menu with single clicks, and no width is reachable only by dragging (2.5.7); axe is green on the top-bar button, the dock, the expanded state, the sheet, the empty state and a streaming turn; under emulated reduced motion open, close and expand do not animate.
6. For every screen in `SCREENS`, the provider-facing tool set equals the screen's declared list and `runAgentTool` refuses every registered name not on it; a call to a name outside the registry still ends the turn with no proposal.
7. The vocabulary test passes over every facts and read-tool schema; the generalised sentinel test passes against a real database for every screen, with the answer sentinel absent from the provider payload, the webhook payload sentinel absent, and the session id present; the webhook facts carry no payload, consumer body or last-error text.
8. `POST /admin/assist` and the per-form route share one limiter key (the eleventh turn in a minute across the two is refused); each has its route-policy rows; a `forms.viewer` opens the panel on a screen they may read and is refused a context for one they may not; with the flag off both routes 404 and the admin route answers 404 before reaching the API.
9. Moving from the builder to the releases screen of the same form keeps the conversation and the next turn is prefaced with the new screen; leaving the form starts a new conversation and returning within the tab restores the old one; `localStorage` and `sessionStorage` hold nothing of the conversation or the panel at any point, asserted in Playwright; a reload starts fresh.
10. Three turns in one conversation on the response list with the same filters write exactly one SEC-15 `read` row; a fourth turn with a different filter set writes a second; a new conversation with the first filter set writes a third; and no other context build writes one the screen would not (Code Owner, 2026-10-24). The renderer's link allowlist is the screen table, and 080's closed list no longer exists.
11. 041's exit criteria and 080's criteria stay green on the builder; the `rogue-*` scripts still produce nothing on every screen.
12. `pnpm check:templates` passes, the documentation above is updated, and a changeset is present.
