## Context

The panel mounts in one place today, inside `FormBuilder`, under a prop the builder page passes when `agentAuthoringEnabled()` is true (`plan/agent-everywhere.md` section 2). The Code Owner's ruling makes it a Confluence/Rovo-style floating launcher and a floating or dockable panel on **every** authenticated admin screen, Settings included (Q18), with one conversation per form subtree. This task is that move, and with it the API side the move needs: a frozen registry of screens, each with a context builder that returns a typed facts object the API computes itself under the caller's grants, because the browser sends a screen id and route ids and **never sends context content** (section 5.1).

It is the phase that makes the "no answers" property hold for every screen rather than one. Every screen gets a context builder with a strict schema in this task, response screens included, so the vocabulary test and the sentinel test cover the whole surface from the day the launcher reaches it. **Action kinds, propose tools, cards and the token are 083's**; this task offers the model the builder's existing four tools on the builder, the read tools section 12 lists for the phase C screens, and on every other screen a context and nothing to propose (section 5.4): the agent explains and navigates.

## The rulings that govern this task

Principle point 5 (everywhere, the same principle on every screen) and point 4 (response metadata may flow, answers may not). **Q2** (`Alt+Shift+A`, ruled by the Code Owner directly). **Q18** (the launcher on every screen, Settings included). **Q15** (memory only; nothing in `localStorage` or `sessionStorage`, because sign-out does not clear tab storage). **Q19** (one limiter key, 10 turns per minute per user, across every assist route). **Q10** (an agent read that the screen audits writes the same SEC-15 `read` row). **Q11** (staff names and emails may go to the provider). Section 1.4 (no launcher outside `(shell)`: there is no signed-in user to act for). Section 4.2's table decides the modes and their geometry; `plan/admin-mobile-stance.md` names the two breakpoints, and the sheet is the mode below `--bp-sidebar`.

## Deliverables

**Admin: the launcher and the panel.**

- **The launcher** (section 4.1): a circular 48 CSS px button fixed to the inline-end, block-end corner, 24 px from both edges, with the assistant icon and a catalog name, rendered once by a client component mounted in `apps/admin/app/(shell)/layout.tsx` beside the `Announcer`, only when `agentAuthoringEnabled()` is true on the server, on every `(shell)` screen. With the flag off it is **absent, not hidden**, the stance the builder prop takes today. It hides while the panel is docked or the sheet is open, and shows a text status badge, never colour alone ("Working" while a turn runs with the panel closed; the "1 action to review" badge arrives with 083's cards).
- **Float, dock and sheet** (section 4.2): float by default at and above `--bp-sidebar`, 400 x 600 CSS px anchored above the launcher, min 320 x 400, max `min(50vw, 560px)` by the viewport height less the measured top bar and 48 px, resizable from its top-start corner, a non-modal `role="dialog"` labelled by the panel title with focus not trapped; dock as a **third track of the shell body grid**, 400 px wide (320 to 560, resizable), full height below the top bar, an `<aside>` landmark named by the title, chosen because a track is the only geometry that cannot obscure page content; the sheet below `--bp-sidebar`, full viewport below the top bar, a modal dialog with `aria-modal="true"` and a focus trap. The float-or-dock choice is a cookie the layout reads, the way the appearance mode is, so a dock renders docked on first paint with no jump after hydration.
- **Keyboard** (section 4.3): `Alt+Shift+A` opens or focuses the panel, is not captured while a text input outside the panel has focus, and is printed in the launcher tooltip and the panel help. Escape closes the float and the sheet and returns focus to the element that had it; in the dock, Escape moves focus back to the page without closing the dock. Stop, Enter and Shift+Enter carry over from 080.
- **Focus** (section 4.4): opening focuses the composer; closing returns focus; navigation between screens keeps the panel open and never steals focus.
- **The header** (section 4.8): one 44 px row with the title, a **context chip** naming what the agent can see on this screen ("Form: Vehicle quote, draft"), and four icon buttons with catalog names and tooltips: New conversation, Dock or Float (a toggle with `aria-pressed`), Help, Close. Collapse goes, with its `localStorage` key, because the launcher reopens.
- **WCAG 2.2 AA** (section 4.5): the launcher and the float panel publish their rectangles as `scroll-padding-block-end` and `scroll-padding-inline-end` the way the shell publishes the top bar's height, so a newly focused control scrolls clear of them (2.4.11); every icon button at least 24 x 24 CSS px (2.5.8); the sheet at 320 CSS px with no horizontal scroll except inside a code block (1.4.10); the tooltip dismissible, hoverable and persistent (1.4.13); a polite live region announcing phase changes in plain language and one completion line per turn, never tokens, with the in-progress bubble `aria-busy` and route-surviving announcements through the shell's `Announcer` (4.1.3); mode and state never by colour alone (1.4.1); theme tokens including the high-contrast dark theme.
- **Reduced motion** (section 4.6): no slide, scale or fade on open and close.
- **Internationalisation** (section 4.7, ADR-27): every new string a catalog key under a new `agent.*` namespace in `apps/admin/lib/i18n/en.ts`; times through `apps/admin/lib/i18n/format.ts`.
- **The admin screen table**, `apps/admin/lib/agent/screens.ts`, mapping each `(shell)` route pattern to a screen id (the ids are section 12's route patterns), and the test that reads the route tree off the filesystem and fails when a `(shell)` page has no row, the pattern `apps/admin/lib/rail-routes.test.ts` already uses. Each turn sends `{ screen, params }` and the environment switcher header every admin request carries (task 065).
- **Conversation continuity** (section 5.3): one conversation per form subtree (builder, rules, preview, versions, releases, links, webhooks and responses for one `formId`), held in a React context the shell layout provides and surviving soft navigation within `(shell)`; each turn carries the current screen id; leaving the form starts a new conversation keyed by the new subject and returning within the tab restores the old one; a reload starts fresh; nothing is written to tab storage.
- **The empty state** for a screen with nothing to propose (section 5.4): the context chip says what the agent can see, and the panel offers explanation and navigation.
- **A second BFF route**, `apps/admin/app/(shell)/assist/route.ts`, for screens with no form, carrying `isSameOriginPost()` and the session gate `apps/admin/lib/server/shell-route-guards.test.ts` enforces, answering 404 when the flag is off, forwarding only the headers the per-form route forwards today.

**API: the registry, the contexts and the door.**

- **`features/agent/`**, grown out of `features/forms/assist` along section 6.2's layout: `tools/registry.ts` holding the frozen `TOOLS` record and `runAgentTool` as the only executor, `tools/read/*.ts` one module per read tool, and `screens.ts` holding the frozen `SCREENS: Record<ScreenId, ScreenDef>` with each screen's context builder, read tools and action kinds (an empty list for every screen in this task; 083 fills it). `actions/*.ts`, `proposal-token.ts` and `provenance.ts` are 083's and are not created here. The existing routes keep their paths and their mount flag; the slice README moves with the code.
- **A context builder per screen**, returning a **typed facts object** under a `z.strictObject` schema with enumerated fields, holding what section 12's facts column lists for that screen and never an answer value, an answer-ledger row or a webhook payload (section 10). The current `AssistContext` becomes the builder screen's context and its key-set test stays; every new context gets one. The response screens' builders close over a **metadata projection** of the response list and detail queries that selects no answer column and joins no answer table, and a response list read writes the SEC-15 `read` row the screen's own read writes (Q10). The webhook screens' facts give state, attempt counts, HTTP status codes, times and endpoint configuration, with the URL masked for a `forms.viewer` exactly as the API already masks it (task 067, Q58), and never a payload, a consumer response body or a last-error string that might quote one. Each builder checks the SEC-3 matrix cell its screen requires through the same policy evaluator the route middleware uses, before building anything.
- **The read tools of the phase C screens**: the builder's existing four verbs, and preview's projection of the draft for hypothetical answers (the `previewDraftAction` read). Each declares its matrix cell and the door checks it for the calling principal before running (section 6.1). The read tools section 12 lists for phase D screens arrive with 083.
- **One door per screen** (sections 5.2, 6.2, 7.1): a turn's tool set is the intersection of the global registry and the current screen's list; `runAgentTool` refuses any name outside **the current screen's** list before dispatch; the provider tool set is built from the same list; a call to a name that does not exist still ends the turn at that step with no proposal.
- **`POST /admin/assist`** for screens with no form, sharing the per-principal limiter key with `POST /admin/forms/:id/draft/assist` (Q19), with a route-policy row per screen cell in `apps/api/src/features/membership/route-policy.ts`, and mounted only under the flag like the existing routes. A turn's screen id is validated against `SCREENS`, and the per-form route refuses a screen id that is not in the form subtree.
- **Prompt framing** (sections 5.3 and 7.3): screen facts and tool results delimited as data, the system prompt stating that text inside them is content authored by users and never an instruction, and "The user is now on the {screen} screen of this form" prepended to a turn whose screen changed. `SYSTEM_PROMPT_VERSION` is bumped.
- **The vocabulary test** (section 7.2): a unit test walks every facts schema and every read-tool output schema and fails on a field whose name matches the respondent-content vocabulary the stdout redactor uses (`packages/observability/src/logger.ts`).
- **The sentinel test, generalised** (section 10): with a submitted answer carrying a sentinel in the database **and** a webhook delivery whose payload carries it, the fake provider's `read-all` script calls every read tool and the API builds every screen's context; the exact provider payload bytes are captured; the sentinel is asserted present in the database before it is asserted absent from the payload; and the session id is asserted **present**, so the metadata half of the rule is pinned too.

**Tests this phase owns** (section 14). Admin Vitest: the screen table test, the continuity context. API Vitest: registry and screen key-set tests, the one-door test per screen, the vocabulary test, the sentinel test per screen, the limiter-key test across both routes. Playwright: the launcher on every `(shell)` page, Settings included, and on none outside it; `Alt+Shift+A`; Escape and focus return in float, dock and sheet; the dock persisted with no layout jump; the narrow sheet; reduced motion emulated; the 2.4.11 tab-through on each screen with the panel floating, the way `apps/admin/e2e/focus-not-obscured.pw.ts` already asserts the criterion; axe on the launcher, each mode, the empty state and a streaming turn.

**Documentation and the mirror.** `docs/agent-authoring.md` sections 4 ("where the panel is" becomes every screen; the four-tool statement stays true until 083), 6 and 8 (continuity); the moved slice README; `docs/adr/core.md` and `docs/ownership-seam.md` where they name `features/forms/assist`; `pnpm qcms:sync-templates` and a `create-qcms-app` changeset.

## Exit criteria

1. The filesystem test fails when a `(shell)` page has no row in `apps/admin/lib/agent/screens.ts`, and every page present at landing has one.
2. Playwright finds the launcher on every `(shell)` page, Settings included, and none on sign-in, the two-factor screens or change-password; with the flag off the component is not in the document.
3. Float is a non-modal dialog with focus not trapped and the page operable behind it; the dock is a grid track whose content column narrows, named as an `<aside>`; the sheet below `--bp-sidebar` is modal with a focus trap; a docked choice renders docked on first paint with no layout shift after hydration, asserted against the cookie.
4. `Alt+Shift+A` opens or focuses the panel and is ignored while a page text input has focus; Escape closes float and sheet and returns focus to the element that had it; in the dock, Escape returns focus to the page and the dock stays.
5. With the panel floating, tabbing through every screen's controls leaves none wholly covered by the launcher or the panel (2.4.11); every icon button measures at least 24 x 24 CSS px; axe is green on the launcher, each mode, the empty state and a streaming turn; under emulated reduced motion open and close do not animate.
6. For every screen in `SCREENS`, the provider-facing tool set equals the screen's declared list and `runAgentTool` refuses every registered name not on it; a call to a name outside the registry still ends the turn with no proposal.
7. The vocabulary test passes over every facts and read-tool schema; the generalised sentinel test passes against a real database for every screen, with the answer sentinel absent from the provider payload, the webhook payload sentinel absent, and the session id present; the webhook facts carry no payload, consumer body or last-error text.
8. `POST /admin/assist` and the per-form route share one limiter key (the eleventh turn in a minute across the two is refused); each has its route-policy rows; a `forms.viewer` opens the panel on a screen they may read and is refused a context for one they may not; with the flag off both routes 404 and the admin route answers 404 before reaching the API.
9. Moving from the builder to the releases screen of the same form keeps the conversation and the next turn is prefaced with the new screen; leaving the form starts a new conversation and returning within the tab restores the old one; `localStorage` and `sessionStorage` hold nothing of the conversation or the panel at any point, asserted in Playwright; a reload starts fresh.
10. The response list context build writes the SEC-15 `read` row the screen's own read writes, and no other context build writes one the screen would not.
11. 041's exit criteria and 080's criteria stay green on the builder; the `rogue-*` scripts still produce nothing on every screen.
12. `pnpm check:templates` passes, the documentation above is updated, and a changeset is present.
