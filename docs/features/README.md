# Active feature work

This directory contains executable work orders only. Completed work orders are removed after their contracts, tests, and documentation land; Git history preserves the original brief.

## Selection order

Use each task's `Depends on` header and the active queue below. Two additional constraints apply:

- 040 must complete before 038.
- 041 never gates 038.

## Execution protocol

1. Read `PROJECT_INSTRUCTIONS.md`, the work order, and its references.
2. Check the active queue, remote claims, open PRs, and `git log`.
3. Stay within deliverables and exit criteria. Ask about genuine decisions.
4. Ship tests and named documentation with the implementation.
5. Run `pnpm verify` and any additional gate required by `CONTRIBUTING.md`.
6. Leave the branch green or commit `HANDOFF.md` with an honest status.
7. Use `feat/NNN-slug`; the pushed branch is the claim.
8. An independent reviewer subagent reviews the exact PR head. Any push invalidates its `AGENT-REVIEW` verdict.

**064 to 070 are drafted, not executable.** They are the task breakdown of ADR-40 and ADR-41 (issue #995, Code Owner rulings of 2026-09-25, 2026-09-26, 2026-09-27 and 2026-09-30), and `plan/environments-and-workspaces.md` holds their deliverables, exit criteria, dependencies and gates. **The design is decided**: nothing in that plan is waiting on a confirmation, section 6 records all thirty-nine questions with their answers plus the eight rulings of 2026-09-30, and ends with **the permissions matrix** and the **access-group naming convention** that are task 069's specification, and section 7 records the two scenario tests the Code Owner ran against the design, what they changed, and the four items deferred to the authorisation work.

What they still lack is a work-order file each, which is why they are drafted rather than executable: this directory holds executable work orders only, and writing seven of them is its own piece of work that the Code Owner has not commissioned. The decided shape, for anyone reading the queue: a configurable set of environments created by an operator command under the migrate role and droppable only when empty and unreferenced; the control plane in a `control` schema and each environment's data plane in `data_<env>`, with `public` left empty; one application database role per environment and a control-only role beside them, so a schema is a privilege boundary as well as a resolution one and the respondent path reaches no identity or grant table; one API process with one pool per environment and one for the control plane; a `/<env>/` path prefix on every non-prod address with `prod` unprefixed; the closed state per form and environment; workspaces with **two role families that imply nothing about each other** and say so in their names, `forms.` on the control plane and `responses.` on an environment's data plane, an environment and form scope on a data grant, an installation-wide claim that administers and reads no response, and an append-only audit of every read, export and erasure (SEC-15), all of it carried by better-auth's organisation plugin with teams as access groups named `<environments>.<plane>.<role>[.<label>]`, the six roles being `forms.viewer`, `forms.editor`, `forms.approver`, `forms.owner`, `responses.viewer` and `responses.eraser`; and green field throughout, so nothing is migrated.

**The authorisation mechanism is ruled** (Q32, 2026-09-26), so 069 no longer waits on a decision: membership, roles and scope live in **better-auth's `organization` plugin**, with a workspace as an organisation row, `forms.owner` on the member row, and every other grant a **team** whose additional fields carry one role and its environment and form scope. The check runs in the QCMS API middleware. Two consequences reach outside this ledger: 064 adds the plugin's five tables and two session columns to the schema mirror and verifies the string-array field mapping on Postgres, and `docs/auth-swap.md` and the risk row in `CONTRIBUTING.md` now say that leaving better-auth would mean migrating authorisation too.

**That recommendation is now ruled, along with seven others** (Code Owner, 2026-09-30, issues #995 and #998). The control-only `qcms_app_control` role is **confirmed**, so nothing on 064 is pending: it holds rights on `control` and on no data schema, while each `qcms_app_<env>` holds DML on its own data schema and only named table-level rights on `control`, with no privilege at all on the identity and grant tables. Seven rulings ride with it: the migration chain is **re-baselined** by 064 into a single new baseline replacing 0000 to 0021, a one-time exception to the append-only rule, with every existing database deleted and recreated manually and a breaking release of `@roonga/qcms-db`; environment names match `^[a-z][a-z0-9]*$` and are length-checked against `reporting_<env>`; a dropped environment is **refused** while an access group names it, never archived, and that half of the check belongs to **069** rather than 064; grants are written **only** through QCMS endpoints, the plugin's own team and member write endpoints being refused for everyone; and a **thirteenth per-environment guard** pins a session to the environment of the link that started it.
