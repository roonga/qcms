This directory contains executable work orders only. Completed work orders are removed after their contracts, tests, and documentation land; Git history preserves the original brief.

## Selection order

Use each task's `Depends on` header and the active queue below. Two additional constraints apply:

- 040 must complete before 038.
- 041 never gates 038.
- **071 to 077 must all complete before 038** (Code Owner, 2026-09-30). Repeating groups are launch scope and `docs/PROJECT_GOAL.md` section 5 promises all three presentations, so launch validation walks, exports and reads back a repeating group and there is no launch subset.

## Execution protocol

1. Read `PROJECT_INSTRUCTIONS.md`, the work order, and its references.
2. Check the active queue, remote claims, open PRs, and `git log`.
3. Stay within deliverables and exit criteria. Ask about genuine decisions.
4. Ship tests and named documentation with the implementation.
5. Run `pnpm verify` and any additional gate required by `CONTRIBUTING.md`.
6. Leave the branch green or commit `HANDOFF.md` with an honest status.
7. Use `feat/NNN-slug`; the pushed branch is the claim.
8. An independent reviewer subagent reviews the exact PR head. Any push invalidates its `AGENT-REVIEW` verdict.

What they still lack is a work-order file each, which is why they are drafted rather than executable: this directory holds executable work orders only, and writing seven of them is its own piece of work that the Code Owner has not commissioned. The decided shape, for anyone reading the queue: a configurable set of environments created by an operator command under the migrate role and droppable only when empty and unreferenced; the control plane in a `control` schema and each environment's data plane in `data_<env>`, with `public` left empty; one application database role per environment and a control-only role beside them, so a schema is a privilege boundary as well as a resolution one and the respondent path reaches no identity or grant table; one API process with one pool per environment and one for the control plane; a `/<env>/` path prefix on every non-prod address with `prod` unprefixed; the closed state per form and environment; workspaces with **two role families that imply nothing about each other** and say so in their names, `forms.` on the control plane and `responses.` on an environment's data plane, an environment and form scope on a data grant, an installation-wide claim that administers and reads no response, and an append-only audit of every read, export and erasure (SEC-15), all of it carried by better-auth's organisation plugin with teams as access groups named `<environments>.<plane>.<role>[.<label>]`, the six roles being `forms.viewer`, `forms.editor`, `forms.approver`, `forms.owner`, `responses.viewer` and `responses.eraser`; and green field throughout, so nothing is migrated.
