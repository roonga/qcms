## Context

This is where RBAC lands (issue #179). Task 068 built the container; this task builds what a person may do inside it, and it is specified by **the permissions matrix in section 6 of `plan/environments-and-workspaces.md`**, which is this task's specification rather than a summary of it.

The shape came out of two Code Owner scenario tests, and the surprising half is the part to build against: a single role ladder **cannot** express "authors may not see production data", because every rung above `viewer` contains it. So there are **two families that imply nothing about each other** (Q27), and since Q38 each role carries its plane in its name, so the separation is visible rather than footnoted.

**The tables are the plugin's, and there is no `workspace_members` table** (Q32). A workspace is an `organization` row; **`forms.owner` is the `member` row's role** and the plugin's `creatorRole`; **every other grant is a `team`** whose typed additional fields carry one role and its scope. Team membership is the grant, so a user in three teams holds three grants, which is the several-rows-per-user shape Q25 asked for. The UI calls a team an **access group**.

## The six roles

`forms.viewer` (sees drafts, published versions, release history and each environment's link and endpoint configuration; changes nothing, reads no response, and does not see the membership list), `forms.editor`, `forms.approver`, `forms.owner` (the member row, the plugin's `creatorRole`), `responses.viewer` and `responses.eraser`. `forms` and `responses` are the nouns the UI and the API already use; `control` and `data` stay ADR-40's words for the schemas. **`viewer` is safe in both families because the prefix distinguishes them.**

**Three things to read off the permissions matrix rather than derive later.** Its last row is a **`never`** rather than an empty cell: the installation admin's inability to read a response is a decision and not an omission. The **`forms.owner` column touches no form, release, link, webhook or response row at all**: an owner administers a workspace and does nothing inside it. And **`forms.viewer` has only the two read rows at the top**, and it reads that configuration **in every environment**, production webhook URLs included, because authoring roles are workspace-wide and only the write actions are environment-scoped. Configuration is not response data, so Q29's boundary holds.

## Deliverables

- **Six static roles as disjoint statements** over the resources `question`, `form`, `release`, `link`, `webhook`, `response`, `membership`, `workspace` and `audit`. **The environment and form conditions live in the grant's scope and never in a statement**, which is the whole of how Q32's mechanism closes the plugin's scope gap. `dynamicAccessControl` **off**, and the default `admin` and `member` role names overridden with **empty statements**.
- **The declared additional fields, all typed and none of them in `organization.metadata`** (Q39): the role and the scope on the team (`environments` as a set or `all`, `forms` as a list or `all`), **`team.externalGroupId`** (string, `input: false`, unique, written only by the task C3 sync path) and **`organization.seedNewEditorsWithTestData`** (boolean, default off). The rule for the record is that **any value the API reads to make a decision is a typed additional field**; the free-form `metadata` column, which any `organization: update` holder replaces wholesale, is used for nothing enforced.
- **The resolver and the middleware** (SEC-3): resolve the user's `member` row and teams in the workspace, evaluate the role's statements with the plugin's own authorize function, then narrow by the team's scope against the route's environment and form. The plugin's HTTP `hasPermission` is **not** used, because it needs the signed cookie the API does not hold, so the authorize function is called directly. Never in a BFF (R2) and never only in the UI.
- **QCMS write endpoints for grants and membership, and they are the only write path** (Q45). They sit behind the installation claim or the `forms.owner` role, write `member` and `teamMember` rows through `@roonga/qcms-db`, and run the cascades and the SEC-15 rows in code. **The plugin's own team and member write endpoints are disabled, or refused, for everyone**, a `forms.owner` included. Two reasons the earlier two-path shape could not answer: the QCMS endpoints are where the validation and the audit rows live, so a second path is a path on which a grant changes without an audit row; and the plugin's **removal cascades** run inside the library, below any endpoint QCMS could gate, so the only way to be sure a removal is audited is for no removal to originate there.
- **The plugin's before-hooks as a backstop, carrying the same validation as the QCMS write path.** Since the plugin's write endpoints are refused for everyone, these hooks are not the guard on a second sanctioned path; they catch a call that reaches the plugin anyway, through a configuration slip or a library change. `beforeCreateTeam`, `beforeUpdateTeam`, `beforeAddTeamMember` and the member hooks enforce that the **name is in step with the fields** (Q37), **every environment in the scope exists**, the **workspace is not archived** (Q15), the **role is one of the six** (Q38), the **two non-team targets are never written as teams**, and **`externalGroupId` is never set through a plugin endpoint** (Q39). Two write paths, one rule set.
- **A capability endpoint** (`GET /me/access` or the equivalent) answering which workspaces, roles, environments and forms the caller holds. It is how everybody who is not an owner or the installation admin learns their own grants, since the membership list itself is theirs alone to see (Q35).
- **The configuration guards, asserted rather than set and forgotten**: `allowUserToCreateOrganization: false`, `disableOrganizationDeletion: true`, `teams.enabled: true`, `teams.defaultTeam.enabled: false`, `teams.allowRemovingAllTeams: true`, `membershipLimit` raised from its default of 100, and `activeOrganizationId` and `activeTeamId` never set by QCMS.
- **The access audit** (Q31, **SEC-15**, widened by **Q56**): an append-only `control`-schema table recording every response read, export and erasure, **and every grant write and every revoke**, with **actor, workspace, environment, form, kind and time**, the kinds being read, export, erasure, **grant** and **revoke**, readable by the workspace's owners and by the installation admin. `two_factor_resets` (issue #432) is the precedent shape, **including its deliberate absence of a foreign key** to the account, because an audit row that cascades away with what it describes is not an audit row.
- **The audit table's grants and revokes, in this task's migration and not 064's baseline** (Q40). A revoke lives in the migration that creates its table, because that is the only place that runs as the table's owner in the same step. So this migration grants **`INSERT` to every `qcms_app_<env>`**, grants **`SELECT` to `qcms_app_control`** (plus `INSERT` once this task's own grant and revoke rows are written, which are control-pool acts), and **revokes `UPDATE` and `DELETE` from every `qcms_app%` role**. The `docs/operations.md` recipe and 064's environment-create command carry the same clauses guarded on the table existing, so a role created before this task lands is correct and stays correct afterwards.
- **A seed `responses.viewer` grant scoped to `dev` and `test` for a new `forms.editor`**, optional, driven by `organization.seedNewEditorsWithTestData` and **visible in the access-group list like any other** (finding 17), so a convenience is never an implication. **The setting defaults off and what it grants is named** (Q57): a grant on `test` responses is a grant on **personal data**, because a test run can involve real respondents, and the admin's **help text for the setting says so in those terms**. Turning it on is an owner's deliberate act and **writes an audit row** like any other grant act.
- **The self-grant rule** (Q56). A self-grant of a `responses.*` role is **refused while the workspace's `requireSecondApprover` switch is on**, and then takes a **second `forms.owner`, or the installation administrator, to confirm**; **the installation administrator follows the same rule**; and with the switch **off** it is **allowed and audited**, which is what keeps a one-account installation able to read its own responses. The switch is the same one Q30 and Q51 use, so an installation turns on one thing and gets the whole two-person posture.
- **The access-group naming convention** (Q37), a deliverable rather than a guideline because the write path enforces part of it. The **stored** team name is **`<environments>.<role>[.<label>]`**, dotted, unique within its workspace, with the environments segment one name, `all`, or a hyphen-joined set, and the label free text. Because every one of the six role names is exactly two segments, a reader takes position 1 as the environments, positions 2 and 3 as the role and anything after as the label. The **full name and the directory name are derived**, `<workspace>.<team>` and `qcms.<workspace>.<team>`, and **neither is stored**, so a workspace slug rename changes display only. The write path enforces **uniqueness within the workspace**, which the plugin does not, and **refuses a name out of step with the team's fields** on save. **It also enforces Q42's combined-set ordering**, moved here from 064 because 064's environment command creates one environment at a time and never writes a set: the environments segment carries the set in **the order of the rows in `control.environments`**, normalised on write and **refused** when it is out of order, so `dev-test` is the one spelling and `test-dev` is never a second grant.
- **The four rules that keep the name from becoming the thing it describes.** The team's fields are authoritative and a mismatch is a **validation error on save, never a permission**. **Nothing parses a name to authorise**: if every name in the installation were wrong, no access would change. **The name is never the join key**: C3 maps a directory group to a team by a stored external-group identifier. **Uniqueness is the QCMS write path's.** The UI shows the stored name inside a workspace page and the derived full name in cross-workspace lists, and prints one sentence beside the scope chooser: **`all` on a `forms.editor` is `dev` and `test` in effect**, because every production action belongs to a `forms.approver`.
- **Every grant holder carries a `member` row with the empty role** (finding G). The plugin's own team endpoints and queries assume the user is a member of the organisation the team belongs to, so a person holding only a team grant and no `member` row is a shape the library does not model. The row carries the **`member` name overridden with empty statements**, which grants nothing on its own and exists to make the person a member of the workspace. `forms.owner` is the one role on the member row rather than on a team, and it is unaffected.
- **The section 3.2 matrix extended** in `docs/SECURITY_DESIGN.md` with the six roles and the installation claim as columns and the permissions matrix's rows, with `apps/api/e2e/security/01-authorization-matrix.e2e.ts` and `matrix-coverage.e2e.ts` moving in the same change, since that test parses the Action column by exact wording. **That extension is this task's and not the PR that recorded the design.**
- **The access-group half of the environment drop check, moved here from task 064** (Q44). The environment command's drop **refuses** while any access group names the environment, and **names those groups** in the refusal the way `dev:seed:clear` names what it leaves, so an operator sees which grants the drop would silence rather than discovering it afterwards. **It refuses and never archives** (Q43). The check lives here because a team carrying an `environments` field exists only from this task: 064 ships the closed-and-empty half and this task adds the group half to the same command.

**Authoring and publishing stay environment-agnostic** (Q25), because publishing a version releases it nowhere, and so does the draft preview (Q36): editor-only, writing nothing and reading no response, so there is no environment to scope it to. The Q6 switcher offers **only the environments the caller holds** in some grant.

## The environment role cannot verify what it writes, and no foreign key closes that

A staff response read spans two pools: membership resolves on the control pool, and the read plus its audit row commit on the **environment** pool, which holds no `SELECT` on `user` or `member`. So `actor` and `workspace` arrive as values the writing role cannot check. That is the same shape `two_factor_resets` already has and is deliberate. **This task must not add a key to close it**, and the API is where the two values are established, before the write.

**Why the audit row rides the same transaction** (Q40): if it were written on the control pool it would be a second connection and a second transaction, so a read that succeeded while the audit write failed would leave no record of itself, which is the one failure an audit may not have.

## Exit criteria

Exit criteria **1 to 18** of the 069 section of `plan/environments-and-workspaces.md` section 8. This task owns those and no others. Criterion **18 is 064's criterion 4b, moved here** by Q44: the drop refuses while an access group names the environment and names those groups, and succeeds once they are removed or re-scoped.

They are written to probe **both families against every action** rather than each family against its own, and to walk the permissions matrix row by row, so a right that leaks across the families fails a test rather than a review.

**Criterion 12 gained a clause with Q42's move**: a stored group name whose environments segment carries a set out of `control.environments`' order is normalised or refused, so `test-dev` is never a second spelling of `dev-test`. That assertion lives here rather than in 064, because 064's environment command writes no set.

## Issue #998, closed

**Every item of issue #998 that was this task's is now ruled.** It carried four; none is open and none is a question for the executor.

**Item 6, the two-person rule** (Q51, 2026-09-29). Two stated mechanisms: a release to `prod` is **one act**, by a `forms.approver` who is not the account that published that version; a `prod` endpoint change is **proposed, stored pending, and takes effect when a different `forms.approver` confirms it**. **"Author" means the account that published the version.** Tasks 067 and 070 carry it.

**Item 1, the self-grant** (Q56, 2026-09-30, superseding Q47's deferral). This task builds it, and its deliverables and criteria above say how: every grant write and every revoke is a SEC-15 row; a self-grant of a `responses.*` role is refused only while the workspace's `requireSecondApprover` switch is on, and then needs a second `forms.owner` or the installation administrator to confirm; the installation administrator follows the same rule; with the switch off it is allowed and audited.

**Item 7, test data** (Q57, 2026-09-30). `seedNewEditorsWithTestData` stays and defaults **off**, and a grant on `test` responses is stated as a grant on **personal data**, in this plan, in ADR-41 and in the admin's help text for the setting. Turning it on is an owner's deliberate act and is written to the audit.

**Item 8, the endpoint URL** (Q58, 2026-09-30). A `forms.viewer` sees scheme, host and path with the **query string masked**; `forms.editor` and above see the whole URL. **Task 067 owns it**, with the per-environment endpoint routes it builds, and this task neither builds nor asserts it.

**This task carries no open item.** Items 2 to 5 and 9 to 11 of that issue were applied earlier, so the issue is disposed of in full.

## Notes for the executor

**Criterion 2 is the reason this task has this shape.** A `forms.editor` with `prod` in scope reaches **no** response in any environment, and a `forms.owner` reads none without a `responses.viewer` grant of their own. Write those two probes first. If either passes before you have built the families, the resolver is reading a ladder.

**The names are labels and the fields are authoritative.** Criterion 13 proves it by editing a name to a wrong one **through the database** and showing the permission unchanged. An implementation that parses a name anywhere on an authorisation path fails that criterion even when every name in the installation is correct.

**`membershipLimit` defaults to 100 and that is a real limit**, not a formality: an installation with more than a hundred people in one workspace would start refusing grants with no message anybody expects. Raise it and assert it, as criterion 9 asks.

**The hook claim in earlier drafts was inaccurate and the correction matters for what you build.** At the better-auth version pinned when Q45 was ruled, the delete endpoints **do** fire their hooks; what fires nothing is the **internal cascade** underneath them, so a team removed through the endpoint is visible to a hook while the team-member rows that go with it are not. Under Q45 that distinction is moot for the write path, because no removal originates at a plugin endpoint at all, and the hooks are a backstop rather than the mechanism.
