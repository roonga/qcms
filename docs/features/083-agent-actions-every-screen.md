## Context

Everything before this task is a panel that reads and proposes a draft. This task is the principle made executable: every act the signed-in user can perform from an admin screen becomes proposable, alone as a **card** or as a step of one **plan card**, nothing runs without the user's Confirm, Confirm runs **the screen's own server action as the user**, and every confirmed step is distinguishable in the audit trail as agent-proposed and human-confirmed. The plan calls it one phase with a foundation and nine screen groups: **D0** is the token, the provenance middleware, the audit table, the grant filter, the propose tools and their SSE events, the card and plan-card shell, the hand-off variant and the sequential runner, with SEC-17's tests; **D1 to D9** then wire each screen group's action kinds through that foundation. Nothing in D1 to D9 is dispatched before D0 is green, because D0 is where every server-side guarantee lives.

Section 11 states the stakes plainly: making every action proposable raises what a prompt injection can aim at, and the mitigation is not a list of forbidden acts but that **a human sees every step that will run, in order, in words the admin wrote, with every argument in full**, and that **no step can do anything the human could not do by hand**. The card therefore carries the weight a denylist would otherwise have carried (section 4.10), and the four card rules are controls in this task, not styling.

## The rulings that govern this task

Principle point 1 (same role, same permissions: a read-only user is offered no write), point 2 (nothing changes until Confirm; the confirmed act is authorised and audited as the user's), point 3 (**one plan, one Confirm**, in order, stop at the first failure, report what ran; it supersedes Q20), point 4 (no answers, the ledger or payloads; metadata flows) and point 5 (no second list; the user's permissions are the list). **Section 1.4** (only an act with an admin screen control is proposable; the installation administrator's workspace create, archive and mark-shared acts have none and get no card until they get a screen). **Q12** (the append-only `control.agent_actions` table, readable by whoever reads the access audit). **Q13** (the token key is derived from `QCMS_APP_KEY` by HKDF-SHA-256 under `qcms/agent-proposal/v1`; no new variable). **Q10** (an agent response read writes a SEC-15 `read` row). **Q9** (no small-count suppression). **Q11** (staff names and emails may go to the provider). **Q19** (one limiter key). The ten-minute token lifetime and the hand-off rule (a step whose arguments include a secret the user must type opens the screen's own control, carries no token, and may only be the last step of a plan). ADR-40's two-person rule and ADR-41's self-grant rule apply **unchanged** because every step runs through the screen's own route.

## Deliverables

**D0: the foundation, first and alone.**

- **`proposal-token.ts`** (section 7.4): an HMAC-SHA-256 token over `{ v: 1, purpose: "agent-proposal", sub, pid, steps: [{ kind, argsDigest }], environment, formId?, iat, exp }`, through WebCrypto (R4), with the key derived by HKDF-SHA-256 from `QCMS_APP_KEY` under the info label `qcms/agent-proposal/v1` (Q13, SEC-7's distinct-key-per-purpose property with no operator burden); the step list **ordered**; each `argsDigest` a SHA-256 over the canonical JSON of that step's arguments **as the card displays them**, with a reference to an earlier step's result kept symbolic (`{ fromStep, field }`); `exp` ten minutes after `iat`. One token covers a card or a plan; a card is a plan of one step.
- **`provenance.ts`**, the API middleware mounted on the admin group **only when the flag is on**, verifying a request that carries `X-QCMS-Agent-Proposal` and `X-QCMS-Agent-Step`: signature, purpose, `sub` equal to the authenticated principal, not expired, the index within the list, the request's route equal to that step's kind's route, the arguments **recomputed from the request** equal to the step's digest with each referenced field equal to the value `control.agent_actions` recorded for the referenced step of this proposal, **steps `0` to `i-1` all recorded for this proposal**, and the environment the request is **performed in** (the route-policy row's declared source) equal to the token's. Any mismatch is a `403` with a stable code and the step does not run; a bad token **never degrades to an ordinary human act**. With the flag off, a request carrying the header is refused with `400`.
- **The `control.agent_actions` migration**, appended at the next number in `packages/db/migrations/`, in SEC-15's precedent shape (`0004_access_audit.sql`, `packages/db/src/schema/control/access-audit.ts`): append-only, no foreign key, `INSERT` without `RETURNING` for application roles, no `UPDATE` or `DELETE` for any role, a grant set that mirrors `control.access_audit`'s exactly and is asserted in `apps/api/e2e/security/03-db-least-privilege.e2e.ts` and carried by the restore re-grant path `04-db-restore-regrant.e2e.ts` asserts. Columns: proposal id, step index, step count, actor, workspace, environment, form, action kind, screen, proposed-at, confirmed-at, and a **non-content detail** (a version number, an environment name, a count, a role name) that doubles as the record later steps' references are checked against. `(proposal id, step index)` is unique, which is the per-step single-use property. No `LocalizedText`, no answer value, no secret. One no-`RETURNING` helper in `packages/db/src/queries/`, called by a handler when `c.var.agentProposal` is set, **in the step's own transaction**, so a failed step writes no row and the card's report and the audit agree. A read of the table is authorised exactly as the access-audit read is (workspace owners and the installation administrator), with its own route-policy row; its admin surface is D8's (below).
- **The grant filter** (section 6.1): before a turn starts, the action kinds offered in the propose tools' schemas are filtered to the kinds whose SEC-3 matrix cell the caller holds in the current environment, through the same policy evaluator the route middleware uses; a user holding none is offered read tools only, and the system prompt says so ("this user cannot change anything here; explain and navigate"). The filter is a courtesy that keeps proposals honest; **the API's authorisation at execution is the limit**, and a step the filter missed fails at its own route.
- **The propose tools**: `propose_action` takes one action; `propose_plan` takes an ordered list of steps, each an action kind with its arguments, where an argument may reference a field of an earlier step's result. Each validates every step's arguments against the kind's own schema, checks each step against the caller's grants, refuses a hand-off step anywhere but last, and on success records the proposal in the turn's state, emits it at once as an `action` or `plan` SSE event, and returns `{ proposed: true, proposalId }` to the model. A failed check returns the reason to the model and is not a turn-ending refusal. **Neither tool executes anything.** The turn-ending refusal stays where it is: a name outside the registry.
- **The `ActionKind` descriptor** (section 6.2), one module per kind under `features/agent/actions/`: its API route, matrix cell, argument schema, how to recompute its arguments from a request, which result fields later steps may reference, its card template keys, whether it is a hand-off step, and its **result allowlist** (section 7.6).
- **The `action` and `plan` SSE events** on both sides of the wire, and the **`action-result` turn variant** in the request schema (section 5.3) with a closed schema: kind, outcome, and the allowlisted non-secret result fields, so the next turn learns "minted 20 links, expiring 2026-11-30" and never a URL, "rotated the endpoint's secret" and never the secret, "export started, CSV long, version 3" and never a byte, and for a plan which steps ran, failed and did not run.
- **The card and the plan card** (section 4.10's four rules, each a test): **the admin writes the card** from the kind, its structured arguments and catalog templates, using the same consequence sentences the screen's own dialog uses, and the model's text appears only as a visibly quoted plain-text reason; **every step and every argument is displayed**, in run order, in full (a webhook URL with its query string, the old and new target of a retarget, the member and the role, the environment, the erasure reason, the export filters), with a step that uses an earlier result saying so in words, nothing collapsed; **a card is never weaker than the screen's dialog** (the typed confirmation for an erasure entered on the card before Confirm is enabled, the production band on a production act, ADR-40 unchanged); **one plan, one Confirm**. Further: per-step progress announced through the live region; a revealed secret shown once exactly as the screen shows it; Cancel local, telling the next turn and sending nothing; "Open the screen" on a single-action card; cards not editable; "Expired - ask again" with Confirm disabled after ten minutes; the launcher's "1 action to review" badge; focus to the card heading only when focus is already inside the panel and to the result line after Confirm or Cancel (080's rule, extended); Escape mid-flight cancels the card, never the turn (section 4.3).
- **The hand-off variant**: Confirm opens the screen's own control with focus in its first field and the non-secret arguments filled; the user types the secret there; it carries no token.
- **The sequential runner**, client-driven (section 6.4): for each step in order, Confirm calls **that step's screen's own exported server action**, imported by the card, with the step's arguments and one trailing `{ agentProposal: token, step: i }` that the action forwards as the two headers, which is proxying (R2); the same `requireAdminSession()` gate, Next origin check, API route, authorisation and revalidation as the screen's control; actions that take `FormData` from `useActionState` get the `FormData` the screen's form would post; a reference resolved by the card from the earlier step's returned state, which the API checks against the recorded detail; the card waits for each result, **stops at the first failure** (an action's error state, a refused token or a network error), never retries, and reports Done, Failed with the action's own message, or Not run per step; Stop during a run lets the running step finish and sends no further step.
- **SEC-17's tests**, owned by D0 and listed in the exit criteria; the fake provider's `plan-three`, `plan-fails-at-2`, `unknown-tool`, `injection-follow` and `read-only-user` scripts; the `two-proposals` and `plan-26-steps` scripts only if P1 and P2 are ruled (open items below).

**D1 to D9: the screen groups**, each carrying its action-kind descriptors, its result allowlist, its card templates and `agent.*` catalog strings, the trailing token argument on its server actions, the audit helper call in the handlers they reach, `propose-<kind>` fake scripts, unit and integration tests, a Playwright confirm and cancel path per kind alone and inside a plan, and axe over every card state. The kinds are section 12's proposable column and the read tools its read-tools column.

- **D1 builder and rules**: today's proposal panel becomes the **`apply-draft`** kind with the same diff and the same two advisory lists, its Accept running through the builder's own save and the sticky `agentAssisted` mark, usable as the first step of a plan; update settings; publish; publish and release to any environment, `prod` included; close or reopen in the current environment; the rules screen's rule test against hypothetical answers as a read tool.
- **D2 releases and versions**: release, promote or roll back to any environment under ADR-40's approval rule; publish the draft from the versions screen; release a version from its detail; the version diff read tools.
- **D3 links**: mint links in the current environment with the URLs to the user only; revoke a link; count links by state.
- **D4 responses and one response**: the list and count read tools under the metadata projection (writing the SEC-15 `read` row, Q10); export with format, shape, version and filters, Confirm triggering the existing streaming download route in the user's browser so not one byte reaches the agent code or the provider; erase, with the reason and the typed confirmation the dialog asks for; unflag.
- **D5 per-form webhooks and dead letters**: create an endpoint with the secret to the user only; rotate a secret, likewise; deactivate and reactivate; retarget with the old and new URL on the card; redeliver one or all, on the form's screen and on the dead-letter screen; the delivery status and dead-letter count read tools; on a `prod` endpoint the card runs task 070's propose-and-confirm mechanism as the screen does.
- **D6 question library and question detail**: create a question; save a draft version; publish, deprecate or open a new version; library search and version diff as read tools.
- **D7 forms list and new form**: create a form, in a workspace the user may create in; search forms.
- **D8 workspace administration**: create or remove an access group; grant or revoke a group; set a member's role; save workspace settings, each under ADR-41's self-grant rule exactly as the screen applies it; and the agent audit surfaced beside the access audit the same readers already see on `workspaces/[workspaceId]`.

## Exit criteria

1. **Token.** Tests refuse a tampered token, an expired one, one issued to another user, one presented on a route other than its step's kind's route, one whose request arguments differ from the digest, one performed in an environment other than the token's, an out-of-order step, a skipped step, a reordered list, a reference resolved to a value other than the recorded one, and any token with the flag off (`400`); and a replayed step fails on the unique constraint and rolls back, against Postgres.
2. **Provenance, never rights.** A request with a token and the same request without one are authorised identically by route policy, in both directions: an allowed act stays allowed and a refused act stays refused, and the token changes only whether an audit row is written.
3. **Grant filter.** A `forms.viewer` is offered no action kind on any screen and the `read-only-user` script, run as one, asserts the prompt says so and no `action` or `plan` event is emitted; a `forms.editor` without `prod` in scope is offered no production release kind; a kind the filter missed (a grant revoked mid-conversation) fails at its own route with the route's own code.
4. **One plan, one Confirm.** `plan-three` (publish, release the version step 1 publishes, mint links) runs end to end with the reference resolved and checked; `plan-fails-at-2` stops at step 2, step 3 is never sent, the card reports Done, Failed, Not run, `control.agent_actions` holds exactly one row for the proposal, and the state step 3 would have changed is unchanged.
5. **Card rules.** From the same arguments, a model reason cannot change a title, hide an argument or hide a step; a plan whose hand-off step is not last is refused at the propose tool; a hand-off step never carries a token; an erasure step's Confirm is disabled until its typed confirmation is entered on the card; a production step shows the production band.
6. **Injection.** `injection-follow`, obeying an instruction planted in a fixture question title, slips a production release and a webhook retarget into a plausible plan: nothing runs without Confirm, the plan displays every step with its true arguments and the production band, and a user who does not hold `prod` is not offered the kind and is refused at the route if the step is sent anyway.
7. **Audit.** Every confirmed step writes one `control.agent_actions` row in its own transaction and a failed step writes none; the table's grant set equals `control.access_audit`'s in `03-db-least-privilege.e2e.ts` and survives the restore re-grant; a read of it is refused to a user who may not read the access audit; each step's own trail (release record, SEC-15 export, erasure and grant rows, `agentAssisted`) is written unchanged beside it.
8. **Result redaction.** Minted URLs, a created or rotated webhook secret and regenerated recovery codes reach the user's card once and never the next turn's request body; an export's bytes reach the browser's download and never the agent code or the provider; the allowlist is asserted per kind.
9. **Never weaker than the screen.** A gated production release proposed by the account that published the version is refused exactly as the screen refuses it (ADR-40, task 070); a `prod` endpoint change under the workspace switch is held pending exactly as the screen holds it; a plan proposed under `test` with the switcher moved to `prod` before Confirm is refused with the stable environment code and no step runs.
10. **Expiry.** A card older than ten minutes shows "Expired - ask again" with Confirm disabled, and the API refuses the stale token independently of the card.
11. **Per screen, D1 to D9.** For every action kind: a Playwright confirm path alone and inside a plan asserting the screen's own state changed and the audit rows exist, a cancel path asserting nothing changed, and axe green over proposed, running, done, failed, not run, cancelled and expired states; a hand-off step opens the screen's own field with focus in it and the non-secret arguments filled.
12. **The response read** writes the SEC-15 `read` row (Q10), and the generalised sentinel test of 082 stays green with every D4 read tool in the `read-all` script.
13. **Goal 7, rehearsed.** With the fake provider, the assisted run 038 specifies (a change on the builder, the releases screen and a response screen; one card and one plan confirmed through the screens' own controls; one cancel; a read-only user offered no write; no answer value anywhere in the conversation) completes end to end as a Playwright scenario.
14. The records listed above are updated in the completing PR, `pnpm check:templates` passes, and `@roonga/qcms-db` and `create-qcms-app` have changesets.

## Out of scope (binding)

Autonomous execution of any kind: no auto-confirm, no scheduled or background run, no Confirm reaching beyond the card or plan it sits on (section 3). The serving path, the portal, `evaluateRules`, the stored snapshot and the respondent API. Any read of an answer value, an answer-ledger row or a webhook payload, by any tool, on any screen (principle point 4). A server-side plan executor (section 6.4 chose client-driven sequencing so every step stays on the screen's own server action). Editable cards (an edited argument is a different proposal). A second list of permitted or forbidden acts, in code or in a prompt (principle point 5). Cards for acts with no admin screen control: the installation administrator's workspace create, archive and mark-shared stay API-only until they get a screen (section 1.4). Cross-session memory or any server-side conversation store (Q15). Small-count suppression (Q9). A new provider, framework or dependency. The launcher, the modes and the registry themselves (082); thinking (081).

## Open items, with the recommendation on record

Two caps are **proposed, not ruled** (`plan/agent-everywhere.md` section 16), and D0 cannot write its propose tools cleanly without them, because each decides a refusal branch and a card shape: **P1**, one proposal per turn (a second propose call in the same turn is refused with "put the steps in one plan"); **P2**, at most 25 steps per plan, a payload bound in the spirit of the conversation cap rather than a permission rule. The plan recommends both and SEC-17 names both as open. **The conductor obtains the Code Owner's ruling on P1 and P2 before dispatching D0.** If D0 is dispatched without it, the executor builds the propose tools to the recommended defaults behind a single constant each, builds the `two-proposals` and `plan-26-steps` scripts against those defaults, and parks the branch with a committed `HANDOFF.md` whose first line reads `HANDOFF: AWAITING-HUMAN` before opening the PR, rather than choosing. Nothing else in this task is a question for the executor: if a case arises that the principle and the rulings do not reach, the executor parks the same way and reports it.

## Notes for the executor

**D0 is a security control and ships complete or not at all.** A D0 that lands the token without the in-order check, or the audit row outside the step's transaction, or the grant filter without the route-level refusal behind it, has shipped a weaker SEC-17 than the one that was decided, while looking like the whole thing. Criteria 1, 2 and 7 are the ones that say so.

**The admin writes the card.** Criterion 5 is the control section 11 rests on. A card whose title or consequence line is built from any model text, however it is sanitised, fails it; the model's words appear only in the quoted reason.

**References are symbolic in the token and checked at the API.** The card resolves `{ fromStep: 1, field: "version" }` from step 1's returned state so the user sees the real value run, and the API compares that value with the `detail` it recorded for step 1 of the same proposal. Resolving on the client without the server check, or binding the resolved value into the token, both lose the property criterion 1's "reference resolved to a value other than the recorded one" asserts.

**A hand-off step is the one step that carries no token.** It opens the screen's own control and the user completes it there, so it writes no `control.agent_actions` row of its own and may only be last (a step after it would have nothing recorded to order itself behind). D9 is where this matters most and is why it comes last.

**Each D1 to D9 PR is small by design.** The descriptors, templates, the trailing argument and the audit call for one screen group, with its tests; the conductor dispatches them in order and may run two with disjoint handlers in parallel once D0 is in.
