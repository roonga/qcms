## Context

QCMS has no notion of an environment. Every table lives in `public`, one application role holds DML on all of it, and there is no way to change a form, try it with real respondents and only then make it live. ADR-40 answers that with a **schema per environment for the data plane**, the control plane in a `control` schema of its own, and a configurable environment set created by an operator command.

This task is the foundation of track A and nothing else builds until it lands. It is also the task that carries the **re-baseline** (Q41), which is a one-time, Code Owner-approved exception to the append-only migration rule: **every migration in the chain as it stands when this task lands** is replaced by one new baseline that creates every schema in final shape, with **no `DROP` and no `SET SCHEMA` anywhere**. An appended migration on the end of that chain cannot reach the target shape, because the per-environment copies have no expression in it at all: the chain has one `answers` table and the design needs one per environment. **The range is deliberately not written as a count.** It is 0000 to 0021 at the base this work order was written against, 072 appends the next, and 073 and 075 may append more before this task rebases under Q50.

**There is nothing to migrate** (Q22). This is green field, so every existing database is deleted and recreated manually: the development database, the Docker stack, CI and any adopter who has applied the published `@roonga/qcms-db` migrations. No upgrade path is written.

**The Code Owner's direction of 2026-09-29** was to kick off environments and workspaces and question looping in subagents, after saying earlier the same day to use parallel agents when possible, so **both tracks are being built at the same time** and 064 to 070 may be dispatched ahead of task 038. `docs/features/README.md` is the record. That is a dispatch direction and nothing more: the Phase 4 classification is unchanged and this task does not gate launch.

## The per-environment set, and why you re-derive it

Per environment the generator emits **eight data-plane tables**, and on them **seventeen guards and eight foreign keys, which is the twenty-five objects.** **Twenty-five is not a sum of three figures**: it is seventeen plus eight, and the eight tables are counted apart because they are what the guards and the keys are declared on rather than members of the same set. Those figures are the reconciled totals with task 072's roster table included, and they are in the plan and in ADR-40's amendment.

**Re-derive them from the criterion rather than copying the number.** The criterion is mechanical: `grep` the migration SQL for each data-plane table name and take every `CREATE TRIGGER`, `CONSTRAINT ... CHECK`, `CONSTRAINT ... UNIQUE` and `CREATE INDEX` that names it, then add Q46's thirteenth guard and ADR-42's four. The first draft of the design listed four of the twelve it then had, which is exactly why the list is derived and why the durable form is code. A number copied from a document is a number that goes stale silently; the arithmetic does not.

The **trigger functions stay single, in `control`**: a trigger in `data_test` executes `control.answers_reject_update()`, so N triggers share one body, and the roster's pair follows the same rule.

## The thirteenth guard, in full

Each `data_<env>.sessions` carries an **`environment` column, `NOT NULL`**; the crossing foreign key into `control.secure_links` becomes **composite on `(link_id, environment)`**; and a `CHECK (environment = '<env>')` pins the column to the schema it sits in. `control.secure_links` carries a **matching `environment` column, also `NOT NULL`**, and a **unique key on `(link_id, environment)`** for the composite key to reference. This task's baseline creates all of it, the `secure_links` column and its unique key included, because a foreign key cannot reference a column a later task adds.

**`NOT NULL` on both columns is what makes the guard a guard.** A `CHECK` **passes when the column is NULL**, because SQL comparison with NULL is unknown and a CHECK refuses only on false; and a composite foreign key under the default `MATCH SIMPLE` is **not checked at all** when any referencing column is NULL. A nullable `environment` would therefore skip both halves.

**Two `NOT NULL` columns mean two writers change in this task, and they do not change the same way** (Q53). `createSession` (`packages/db/src/queries/sessions.ts`) runs on an **environment** pool, so it writes **that connection's own environment**. `insertSecureLink` (`packages/db/src/queries/secure-links.ts`) does not, and the earlier wording of this paragraph was wrong about it: the mint (`apps/api/src/features/links/handler.ts`) runs on the **control** pool, because `qcms_app_<env>` holds `SELECT` and `UPDATE` on `secure_links` and **no `INSERT`**, and a control connection has no environment of its own. So the mint takes an **explicit `environment` argument** from the links handler, and **between this task and 066 that argument is `'prod'`**.

**Widening the environment role to `INSERT` on `secure_links` is not the way out of this, and this task may not take it.** That grant is one Q40 narrowed deliberately, and an environment role that could mint could mint into any environment.

**Task 066 owns the behaviour**: choosing the environment at minting, requiring it on the API, refusing a caller that omits it, and refusing a token presented under the wrong prefix. This task adds none of that and must not.

**A public session has no link, and that is correct.** `sessions.link_id` stays nullable, because an anonymous session on `prod` starts from `/f/{slug}` and redeems nothing; under `MATCH SIMPLE` such a row skips the composite key entirely, which is what it should do. What binds it to its schema is the `CHECK`, which is why that half has to hold on its own.

The reporting and type grants are part of the expected list per role, not separate assertions beside it.

## Sequencing against the repetition track

**The repetition track, tasks 071 to 077, is launch scope and is being built now, in the same period as this task.** Both tracks are in flight; what is fixed is the order in which they reach `main`.

**The landing order is a rule, not an expectation** (Q50, Code Owner, 2026-09-29). **This task merges to `main` only after tasks 072, 073 and 075 have merged.** The reason is one-directional: this task's baseline is a breaking major of `@roonga/qcms-db`, so a launch-scope lane that merged after it would rebase onto a replaced migration chain and run doubled gates for the rest of its life, while this task rebasing onto their appended migrations costs one rebase, here, once. This task **may** merge before launch validation (038), which would then validate the re-baselined layout; it stays Phase 4 either way.

**So the baseline always carries their work, and the derivation is done at the rebase.** 072 adds `answers.instance_id` and the append-only **`answer_group_instances`** table as an ordinary **appended migration**, with two triggers, a CHECK, an index and a foreign key, plus two trigger functions that stay single in `control`. 073 and 075 may append migrations of their own. **Re-derive the per-environment set from the chain as it stands when you rebase**, not from this work order and not from the figures below: they are the reconciled totals with 072 included and nothing else, and 073 or 075 may have added objects since.

**This task's re-baseline replaces the whole chain, so it must carry 072's table and its guards.** A baseline that replaced the chain and dropped a table the chain had created would delete work rather than restate it. `answer_group_instances` is a **data-plane** table, so it multiplies per environment exactly as the other seven do: the baseline creates **eight** data-plane tables per environment, not seven, and emits 072's two triggers, its CHECK, its index and its foreign key with the rest. The reconciled figures are **eight data-plane tables, seventeen guards, eight foreign keys and twenty-five objects** per environment.

There is no branch of this work order for landing first: Q50 forbids it. If the order is ever changed, it is changed by the Code Owner and this section is what gets rewritten.

**Four tasks change the same two areas, and whichever lands second rebases.** This task and the repetition tasks **072, 073 and 075** all change `packages/db` and the response handlers in `apps/api`. The likely conflict sites, named so they are not discovered in a merge:

## Notes for the executor

**Do not copy the counts.** Eight, seventeen, eight and twenty-five are the reconciled totals **with 072 alone included**, and they are in the plan and in ADR-40, but the deliverable is a generator whose output is checked against a derivation. Under Q50 this task rebases after 072, 073 and 075, and **073 or 075 may have added data-plane objects of their own**, so re-derive the set from the criterion against the migration SQL **as it stands at that rebase** and let the assertion be what proves the number. A derivation that disagrees with the document is a finding to report and the document's figure is what gets corrected, not the derivation.

**The in-plane foreign keys are the ones a generator gets wrong quietly.** Written once against `data_test` and copied, they can end up pointing at another environment's `sessions` or `webhooks`, which is a cross-environment reference the search path would never reveal. Criterion 1a asserts each in-plane key references a table in **its own** schema, from `pg_constraint`, by name. Write that assertion before the generator.

**The re-baseline is the change most likely to hollow out its own tests.** Both migration tests must keep the properties they assert against a one-entry chain: `migration-chain.test.ts` still needs every journal entry to have a snapshot and every snapshot to name its predecessor, and `meta/` must hold nothing the journal does not account for, so delete the superseded snapshots rather than leaving them orphaned. `migrations.test.ts` must stay an **exact** comparison, per schema, or a migration creating an unlisted table stops failing.

**better-auth is the one table group whose owner is a third party.** The library validates the Drizzle schema on the first request through its handler and refuses to run on a mismatch, so a non-default schema and the string-array additional fields are real risk items rather than formalities. Do the string-array verification first: the whole grant model rests on it, and finding it out after the baseline is written is expensive.

**The exception to the append-only rule is available exactly once**, because Q22 says there is no installation to break. Nothing in this task establishes a precedent for a second re-baseline, and a later one would be a new Code Owner decision.

**Two things about this task's grants are wider or thinner than they look, and both are recorded rather than fixed here.**

**Q52's reporting grant is wider than today's reads, by design and by ruling.** `SELECT` on the schema's **views** covers `answers_flat` as well as `responses`, which is all the API reads today, and it will cover every workspace's view set once Q26's split lands with 067. That is consistent with the API enforcing the workspace scope in middleware rather than in the grant, and the Code Owner has ruled the grant in that shape (Q52). Do not narrow it to one view name on your own initiative, and do not widen it past the environment's own schema.

**Between this task and 069, an admin's response reads write no SEC-15 row.** Identity resolves on the control pool and the read runs on the environment pool, and the audit table does not exist until 069 creates it. That is **today's behaviour** and not a regression this task introduces, but it is worth knowing while this task is on `main` and 069 is not: for that window, "who read this" is answerable only from whatever the log shipper kept. 069's context says the same from its side.
