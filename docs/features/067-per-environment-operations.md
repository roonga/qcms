## Context

Once the data plane is a schema per environment, everything that reaches it has to be told which one: the outbox and its deliverer, the endpoint rows, the retention sweep, the export, the erasure flow, the backup and restore drill, the reporting views and the telemetry attribute. This task is that pass, and it is the one with a person on the other end of it, because erasure is in it.

Two properties come out of the layout rather than from a check. A test submission cannot reach a prod endpoint, because the test deliverer cannot see a prod endpoint row (Q3). And a reporting consumer writing their own SQL is held by a **grant** rather than by an API check, which is the one place in this design where the authorisation model is expressed in the database.

## The rulings that govern this task

Q2 (one process, the deliverer and the sweep starting once and iterating the live set), Q7 (an erasure acts in the selected environment only, with a cross-environment repetition offer), Q8 (the environment in the export filename and in no column), Q9 (the suites and the drill run once per environment, with a recorded sunset that is not this task's to take), Q10 (`reporting_<env>`, one schema per environment, replacing the single `reporting` schema), Q11 with finding 6 (the retention TTLs and the challenge provider are per environment; rate limits are not), Q26 (reporting is per environment **and** per workspace, each view set with its own read-only role), Q30 with Q51 (a `prod` endpoint change and a `prod` link mint are a `forms.approver`'s act with `prod` in scope; the switch's pending-and-confirm mechanism is task 070's), Q33 (closing and reopening split the same way). ADR-40 and ADR-41 bind it; ADR-17's Note binds the erasure shape.

## Deliverables

- **The outbox, the endpoint rows and the deliveries per environment**, with per-environment egress stated in SEC-14's firewall vocabulary where a firewall can enforce what the schema split already guarantees.
- **The authorisation split on the environment-scoped operations** (Q30, Q33): configuring a **`prod`** webhook endpoint and minting a **`prod`** link require the **`forms.approver`** role holding `prod` in scope; closing and reopening `prod` require the same. The same operations in `dev` or `test` stay a **`forms.editor`**'s with that environment in scope. The state itself is task 066's; **who may set it is this task's**. **The workspace switch's second account is task 070's**: this task builds the role check and the `prod` endpoint route, and 070 adds the propose, pending and confirm mechanism on top of it (Q51).
- **Export per environment**, with the environment in the **filename and in no column** (Q8). One file never mixes environments already, so a column would change a file adopters parse for no information they do not have from its name. The formula-injection guard in `@roonga/qcms-csv` applies exactly as it does today (issue #470).
- **The per-environment retention TTLs read from the environment row**, which are **this task's half of Q11** and not 066's, since the sweep that reads them is here; 066 owns the challenge provider. Rate limits stay installation-wide (Q11, finding 6). A per-environment limiter would be a second place for the replica-count caveat of issue #488 to be got wrong.
- **Reporting per environment** (Q10): `reporting_<env>`, one schema per environment holding the same view names. **The application role's own grant on that schema is Q52 and is task 064's**; what this task owns is the per-workspace split and the read-only roles the outside consumers are granted (Q26). Each schema holds the same view names, so a BI tool connects to one environment's schema and its queries are otherwise unchanged. The single `reporting` schema of migration 0003 is replaced rather than kept beside them, which green field makes free.
- **Reporting per workspace, when 068 exists** (Q26): each environment's schema holds **a view set per workspace**, `reporting_prod.home_responses`, `reporting_prod.vehicle_responses` and the flat-answers twin of each, **every set with its own read-only role**, so a workspace's analysts are granted exactly their workspace's views in exactly their environment and nothing else. **The per-workspace split belongs to whichever of 067 and 068 lands second**, so it has an owner in either order and 068's work order says the same from its side. If 068 has already landed, this task ships the split with the schemas and asserts criterion 7. If it has not, this task ships the per-environment schemas with one view set each, and **068 builds the split and carries criterion 7 with it**. `docs/reporting-view.md`'s `qcms_reporting` recipe becomes per (workspace, environment). The dev-tools viewer role `qcms_ro` holds `pg_read_all_data`, is a different role in a different file, and is not touched.
- **The reporting role's prefix joins task 064's length derivation.** Q26's read-only role is per (workspace, environment), so its name is interpolated with an environment name and its prefix belongs in the prefix list 064's environment command computes the name-length limit from. **This task names that prefix and re-derives the limit if it is longer than `reporting_`.** 064 owns the derivation; this task owns adding to its input.
- **Erasure per environment** (Q7). An erasure acts in the **selected environment only** and its confirmation restates which one, so no single act crosses a boundary and `prod` cannot be reached from `test` by accident. When the same subject identifier also has sessions in other environments, the screen **says so and offers to repeat the erasure there**, each repetition its own confirmed act in its own environment. The cost is that a data subject's request is several deliberate acts rather than one click; the benefit is that none of them is the wrong one.
- **Scheduler ownership unchanged** (Q2): the outbox deliverer and the retention sweep start **once per process** under `config.mount.internal` and **iterate the live environment set**, so `docs/deploy-enterprise.md` section 5's scheduler-singleton rule holds rather than multiplying. Each pass claims and delivers under exactly one environment's pool and role, and no pass ages a row in another environment.
- **The environment as an allowlisted telemetry attribute** (SEC-13), naming no respondent.
- **The restore drill covering `control` and every environment schema in the live set**, `pnpm qcms:drill-restore` iterating rather than naming a pair. Green field removed the migration and it did not remove the drill: `docs/backup-restore.md` opens with the claim that a backup nobody has restored is not a backup, and that is as true of a database created in this shape as of one migrated into it.
- **The documentation this task updates**: `docs/backup-restore.md`, `docs/erasure.md`, `docs/operations.md` and `docs/reporting-view.md`.

## Exit criteria

Exit criteria **1 to 8** of the 067 section of `plan/environments-and-workspaces.md` section 8. This task owns those and no others, with two stated moves.

**Criterion 8a belongs to task 070** (Q51), the way Q44 moved 4b to 069: with the workspace switch on, a `prod` endpoint change proposed by one account is stored **pending** and takes effect only when a **different `forms.approver`** confirms it. That is the two-person rule's second mechanism, 070 is what builds the switch, and this task cannot assert it. What stays here is the role check: a `prod` endpoint change and a `prod` link mint are refused without `forms.approver` holding `prod` in scope, and a `dev` or `test` endpoint change stays an editor's.

**Criterion 7 moves to 068 when this task lands first**, with the per-workspace reporting split it asserts.

Criterion 1 is asserted **against a real Postgres rather than argued**: a test submission cannot reach a prod endpoint. Criterion 7 is asserted the way `apps/api/e2e/security/03-db-least-privilege.e2e.ts` already asserts the reporting role's limits: a reporting role granted one workspace's views in one environment reads those and **cannot read another workspace's views or another environment's schema**.

## Notes for the executor

**The erasure screen is the deliverable to build last and test hardest.** Criterion 4 asks that the cross-environment repetition is **offered** and that nothing is performed without its own confirmation. An implementation that helpfully erases everywhere on one confirmation fails the criterion and is not undoable.

**The reporting split lands in two pieces on purpose.** There are no workspaces to name views after until 068, so ship the per-environment schemas with one view set each and leave the per-workspace split to 068's landing. Do not invent a placeholder workspace to make the split land early.

**The scheduler must stay a singleton.** One deliverer and one sweep start per process and iterate; starting one per environment would multiply the scheduler and break `docs/deploy-enterprise.md` section 5. Criterion 5 asserts both halves: every environment is reached, and no pass ages or claims a row in another.

**`qcms_ro` is not `qcms_reporting`.** They are different roles in different files and the two are easy to confuse. This task touches the second and leaves the first alone.
