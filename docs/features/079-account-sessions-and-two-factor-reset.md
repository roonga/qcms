## Context

The Settings screen has three panels: Account, which says "Signed in as {email}" and nothing else, Change password, and Two-factor, which reports whether two-factor is on and offers a fresh set of recovery codes (`apps/admin/app/(shell)/settings/`, `apps/admin/lib/settings-sections.ts`). Review finding A19 recorded that there is no way to see your sessions, revoke one, or re-enrol an authenticator.

**The Code Owner ruled on 2026-10-21** that both are built: a signed-in session list with revoke, and self-service two-factor reset and re-enrolment, with the SEC-1 and auth-allowlist changes that implies.

**What is actually missing is narrower than A19 states, and the correction matters for the design.** A19 says "someone who loses an authenticator spends recovery codes with no way to mint more", and that half is already solved: issue #319 added `POST /two-factor/generate-backup-codes` to the allowlist and the Settings panel offers it, password-gated. The real dead end is the next step. An operator who has lost their authenticator signs in with a recovery code at the challenge, reaches the shell, and then **cannot bind a new authenticator**, because nothing offers a reset and `/two-factor/disable` is deliberately denied by the mount allowlist. Their only route is `qcms:reset-2fa`, which needs the migration role's database credential (SEC-10) and is a break-glass rather than an operation.

**Three existing decisions bound this, and none of them is being reopened.** `two-factor/disable` is off the allowlist because "no screen offers it and an unreachable endpoint is one fewer thing to reason about" (`apps/api/src/features/auth/route.ts`); `list-sessions` is off it because nothing read it. `auth-mount.test.ts` asserts both by request, so the allowlist is the control and the test is what makes the control true of the whole composition. And the break-glass is recorded as the recovery path precisely because it has no HTTP surface. This task adds operations for an operator **who can still sign in**, which is a different person from the one the break-glass exists for, and SEC-1 has to say which is which when this lands.

**069 was checked, as A19 asks.** Task 069 built the membership screens, the access-group screens and `GET /me/access`, all of which are about what an account may do inside a workspace. This task is about the account's own credentials and sessions. There is no overlap and no shared screen, and the two should not be merged into one Settings area.

## What better-auth gives, and what it does not

Checked against the installed **better-auth 1.7.7** (the version `apps/api/package.json` pins) and the vendor documentation on **2026-10-21**, per the plan-against-official-docs rule. **Re-read this section at the version in the lockfile when you start**, because three of the facts below are read off the library's compiled source rather than its documentation, and `check:vendor-pin`'s own note says a bump means re-reading the vendor rather than running `sed`. The Dependabot bump to 1.7.10 is open as PR #1074; `packages/better-auth/src/api/routes/session.ts` is unchanged between the two tags.

**Documentation.** Session management: https://www.better-auth.com/docs/concepts/session-management, including its "Session freshness" subsection. Two-factor plugin, which does publish an `Endpoint:` line per operation: https://www.better-auth.com/docs/plugins/2fa. The password-or-freshness pattern in prose: https://www.better-auth.com/docs/concepts/users-accounts#authentication-requirements. The in-repo reference that is authoritative over all three is the OpenAPI schema the library generates (https://www.better-auth.com/docs/plugins/open-api).

**The documentation does not publish the paths or methods of the four session endpoints.** `list-sessions`, `revoke-session`, `revoke-other-sessions` and `revoke-sessions` appear on that page only as client method names and heading anchors. The paths below are read from `dist/api/routes/session.mjs` at the pinned version, and the work order says so rather than implying a doc citation exists.

| Endpoint                         | Method | Body                                    | Guard in the library                             |
| -------------------------------- | ------ | --------------------------------------- | ------------------------------------------------ |
| `/list-sessions`                 | GET    | none                                    | `freshSessionMiddleware` (see "Freshness" below) |
| `/revoke-session`                | POST   | `{token}`                               | `sensitiveSessionMiddleware`                     |
| `/revoke-other-sessions`         | POST   | none                                    | `sensitiveSessionMiddleware`                     |
| `/revoke-sessions`               | POST   | none                                    | `sensitiveSessionMiddleware`                     |
| `/two-factor/disable`            | POST   | `{password}`                            | `sensitiveSessionMiddleware` plus the password   |
| `/two-factor/enable`             | POST   | `{password, method?, issuer?}`          | the password                                     |
| `/two-factor/verify-totp`        | POST   | `{code, trustDevice?}`                  | the live session                                 |
| `/two-factor/verify-backup-code` | POST   | `{code, disableSession?, trustDevice?}` | the live session                                 |

**Seven facts that shape what you build.** Each is read from the pinned source, and each is a thing the design would get wrong without it.

1. **`sensitiveSessionMiddleware` is not a password check and not a freshness check.** It requires an authoritative, database-backed session rather than a cached cookie payload. **No session endpoint accepts or requires a password**, so a live session alone revokes sessions.
2. **`/list-sessions` requires a fresh session**, meaning `session.createdAt` within `session.freshAge`, and answers `403 SESSION_NOT_FRESH` otherwise. The default `freshAge` is `3600 * 24` and QCMS sets none, while the absolute session cap is `QCMS_ADMIN_SESSION_MAX_AGE_MS`, default 12h and operator-configurable. So the list works today **by arithmetic rather than by decision**, and an operator who raises that knob above a day gets a Settings panel that starts answering 403 for a reason nothing in QCMS names. A deliverable below closes that.
3. **`/revoke-session` takes the session's `token`, which is the bearer value in the session cookie.** `/list-sessions` returns it, along with `id`, `userId`, `expiresAt`, `createdAt`, `updatedAt`, `ipAddress` and `userAgent`. **A list rendered with tokens in it hands every one of the operator's live credentials to the browser**, which is the one thing this screen must not do.
4. **`/revoke-session` answers `{status: true}` even when the token is not the caller's.** The delete is conditional on ownership; the response is not. So the status is not evidence that a session existed or was removed.
5. **`/revoke-other-sessions` keeps the caller's current session and does not rotate it.** `/revoke-sessions` removes every session including the caller's own, **without clearing the caller's cookie**, leaving the browser holding a stale one.
6. **`/two-factor/disable` requires the password, deletes the whole `twoFactor` row (the TOTP secret and the recovery codes), sets `user.twoFactorEnabled = false`, clears the trusted-device cookie and record, and rotates the caller's session**: it creates a new session, sets the new cookie, then deletes the old token. It leaves the user's **other** sessions alone. None of that is in the documentation.
7. **There is no re-enrolment without a disable.** `/two-factor/enable` on an account with a verified TOTP row throws `TOTP_ALREADY_ENABLED`, which the documentation states. So rotating an authenticator is disable-then-enable, and **between the two calls the account has no second factor at all**.

**And the fact the ruling turns on.** The ruling asks for re-authentication with the password **plus** a current TOTP code or a recovery code. better-auth's `disable` takes only a password. The second factor is still checkable, and the path is not obvious from the documentation: with a **live session**, `verifyTwoFactor`'s success path returns the caller's existing session token and sets no cookie, so `POST /two-factor/verify-totp` on an enrolled account (`twoFactor.verified === true`) is a **pure check with no session side effect**, and `POST /two-factor/verify-backup-code` is the same except that it consumes the code. Two riders: on the live-session path the plugin's own attempt accounting is a no-op (`beginAttempt` returns no-op functions when a session exists), so the only brute-force control is SEC-1's `/two-factor/*` throttle of three attempts per ten seconds; and `verify-totp` on an **unverified** row completes an enrolment rather than checking one, which is why the check runs only for an account that is already enrolled.

## Deliverables

### The session list and revoke

- **`GET /list-sessions`, `POST /revoke-session` and `POST /revoke-other-sessions` added to `ALLOWED_AUTH_ENDPOINTS`** in `apps/api/src/features/auth/route.ts`, with the header comment extended one line per operation in the shape the other eight have. **`POST /revoke-sessions` is not added**: it signs the caller out while leaving them holding a cookie the server has deleted, and "sign out everywhere" is `sign-out` plus `revoke-other-sessions`, which is already expressible.
- **`auth-mount.test.ts` updated rather than relaxed.** `/api/auth/list-sessions` moves out of the `denied` list, `/api/auth/two-factor/disable` **stays in it** (see below), and the three new entries gain the channel-token and composition assertions the allowlisted endpoints already carry (SEC-4). The SEC-1 registration-shaped and organisation-shaped filters are unaffected and must stay green.
- **`session.freshAge` set explicitly** in `apps/api/src/features/auth/instance.ts`, derived from the same configuration as the absolute cap (`QCMS_ADMIN_SESSION_MAX_AGE_MS`) rather than left to the library's one-day default, with a comment saying what it is for. The property to hold is that **a session the QCMS cap still accepts is a session `list-sessions` still accepts**, asserted rather than reasoned about, so raising the cap cannot break the panel.
- **A named BFF operation per endpoint** in `apps/admin/lib/server/auth-api.ts`, in the shape that file's header requires: one named operation per handler, over the internal channel, returning a `Response`, cookies carried back with `getSetCookie()`. No browser-facing `/api/auth/*` proxy, which that header explains at length.
- **The session token never reaches the browser.** The panel renders each session by its **`id`**, which is stable and is not a credential; the revoke handler re-reads the list server-side and maps the submitted `id` to that row's `token` before calling `/revoke-session`. An index into the rendered list is **not** acceptable: the list can change between render and post, and revoking row three is then a different session than the one the operator read. A submitted `id` that is not in the caller's own list is refused without saying which it was.
- **A Sessions panel**, a fourth section in `apps/admin/lib/settings-sections.ts` with its own id, panel id and label key. Read that file's header first: the three ids are literal strings for a reason (`change-password` is a published anchor), the panel ids come from the POC verbatim, and the list is read by the rail, the screen and the page heading. Adding a section means a row in `SETTINGS_SECTIONS`, a marker list for the new panel's redirect messages, and a branch in `settingsSectionFromParams` so a refusal lands on the panel that produced it (issue #437's lesson, applied again).
- **What each row shows, and what it costs to show it.** Signed-in-at, last-seen, expiry, the user agent rendered as something an operator can recognise, the client address, and "this is the session you are using". The address is a **direct identifier** under SEC-13: it is fine in the operational database and on the operator's own screen, and it must not reach a log line, a span attribute or an OTLP record. Assert that, because "we display it" and "we export it" are one careless logger apart.
- **An explicit "sign out every other session" control**, which is `revoke-other-sessions`. Note in the panel's copy that a password change already does this (`settings.passwordIntro` says so today, through `revokeOtherSessions` on `/change-password`), so the two controls do not contradict each other.
- **Plain posts, for the reason the existing auth routes are plain posts.** Both controls are `<form method="post">` to named admin routes, landing back on the Sessions panel through a marker. **This is not a no-JS requirement:** the admin requires JavaScript, gated in the root layout (Code Owner, 2026-09-27; `apps/admin/app/requires-js.test.tsx`, `plan/admin-design-contracts.md`). It is the shape every auth surface in this app already has, and `apps/admin/lib/server/route-helpers.ts` records why: the flow works before hydration and no credential passes through client JavaScript. Matching it is cheaper than departing from it and keeps the credential handling identical.

### The self-service reset and re-enrolment

- **One QCMS-owned API endpoint that composes the whole reset**, and **`/two-factor/disable` stays off the allowlist.** This is the load-bearing design decision of this half, and the reason is arithmetic rather than taste: allowlisting `disable` makes the password **sufficient** to remove a second factor, because an attacker holding a session and the password can call it directly and nothing binds it to a prior factor check. The ruling asks for password **plus** a factor. Composing both in one QCMS endpoint, which calls `auth.api.verifyTOTP` or `auth.api.verifyBackupCode` and then `auth.api.disableTwoFactor` **in process**, is the only shape where the two cannot be separated, and it is the distinction SEC-1 has always drawn and Q45 drew again: a function the API calls is not a surface the network can reach. **Open item 1** records the alternative and the Code Owner decides.
- **The re-authentication, exactly as the ruling states it**: the account password **and** either a current TOTP code or one recovery code, both in the same request, both verified before anything is written. A missing or wrong value is one opaque refusal (SEC-1's no-enumeration rule), with the `429` separated out as issue #845 ruled, because this endpoint draws on the `/two-factor/*` throttle bucket and an operator who is already unsure of their credentials must not be told "wrong password" when the truth is "not right now".
- **The re-enrolment in the same operation.** `disable` followed by `enable` with `method: "totp"`, so the account never rests without a factor longer than the one request takes, and the returned `otpauth://` URI and fresh recovery codes land on the existing enrolment screen through the short-lived cookies `apps/admin/lib/server/enrollment.ts` already defines. Nothing new is invented for the display: the enrolment screen, its 15-minute cookie, its "I have saved these" confirm and its no-logging rule are all reused. `enable` wants the password too, which the one composed endpoint already holds for the length of the call and must not store anywhere.
- **The caller's session carried through the rotation.** `disable` creates a new session, sets its cookie and deletes the old token, so a handler that drops the `Set-Cookie` signs the operator out mid-reset. The BFF hop copies `getSetCookie()` onto its own 303, which is what the existing handlers do and what makes the attributes better-auth wrote survive the hop.
- **What happens to the account's other sessions**, decided and asserted. **Recommendation: revoke them**, in the same operation, because the factor those sessions passed no longer exists and a reset is usually prompted by a device the operator no longer controls. This is a departure from the recorded reasoning for the break-glass, which deliberately does not revoke, and the two differ in a way worth writing down: the CLI is run by an operator at a database credential, usually for themselves, while this is run from a browser by whoever holds that browser. **Open item 2.**
- **The trusted-device state, stated rather than discovered.** `disable` clears the trusted-device cookie and its verification record. Say so in SEC-1, because an operator who reads "two-factor was reset" and still gets no challenge on their next sign-in would have found a hole where there is none.
- **The forced-enrolment gate reached deliberately, not accidentally.** `apps/admin/lib/server/session.ts` redirects a session with `twoFactorEnabled === false` to `ENROLL_PATH` unless `QCMS_ADMIN_2FA=optional`, after the `mustChangePassword` gate (061). A reset sets that flag false, so the gate catches the operator on the next request whatever the handler does. The handler **redirects to the enrolment screen itself** rather than to Settings, so the operator is never shown a Settings page that immediately bounces, and the ordering with 061's gate is left exactly as 061 decided it. Assert both: that the enrolment screens are reachable in that state (`requireEnrollingSession`) and that nothing else is.
- **`QCMS_ADMIN_2FA=optional` handled honestly.** With two-factor optional and an account not enrolled, there is nothing to reset and the panel must say so rather than offering a control that refuses. With it optional and an account enrolled, the reset works and the gate does not force re-enrolment, so the operator can end up with no factor; that is what the flag means and the panel's copy should not pretend otherwise.

### Which audit this writes to

- **The auth audit, not SEC-15.** SEC-15's `control.access_audit` records acts on **response data** and the grants that reach it, and it carries no kind for an authentication event. The existing auth audit is `control.two_factor_resets` (issue #432), whose shape is the precedent SEC-15 itself cites: append-only, no foreign key to the account, write privilege narrowed against the credential that serves traffic. **A self-service reset is the same act as the break-glass by a different door, so it belongs in the same table**, with a column distinguishing the two sources so neither reading is lost.
- **That table is migrate-only today, and this task cannot simply write to it.** The Code Owner's decision of 2026-09-09 took `SELECT`, `INSERT`, `UPDATE` and `DELETE` back from every `qcms_app%` role, in migration 0021 and again in the role recipe, so the API's credential holds nothing on it. Granting the control pool an `INSERT` is a deliberate narrowing of that decision and is **open item 3**, with the recommendation there. If it is granted, it is `INSERT` alone, **with no `RETURNING`**, for the reason SEC-15's helper records: a role holding `INSERT` and not `SELECT` is refused a `RETURNING`, so the write path has to be written as a plain insert and asserted as the application role.
- **Whether a session revoke is audited at all** is **open item 4**. Nothing records one today, and `better-auth`'s own tables keep no history of a deleted session.
- **The paired log event**, if one is added, carries **no attributes at all**, which is what the break-glass already does and what SEC-13 requires of an export.

## Exit criteria

1. An operator sees their own live sessions in Settings, with the current one marked, and sees **no other account's** sessions. Asserted with two accounts, not one.
2. **No session token appears in the rendered HTML, in a form value, in a URL or in a log line.** Asserted by searching the response body for the token value rather than by inspecting the template.
3. Revoking one session removes that session and leaves the others, including the caller's. The revoked session's next request is refused and lands on sign-in.
4. A submitted session id that is not in the caller's own list is refused, and the refusal names nothing about it. This is the criterion that covers fact 4 above: `{status: true}` from the library is not evidence, so the guard is QCMS's own list.
5. "Sign out every other session" leaves the caller signed in on the session they are using, and signs out the rest.
6. A reset with the password and a **valid TOTP code** succeeds; with the password and a **valid recovery code** succeeds and consumes that code; with a wrong or missing password, a wrong code, or a code and no password, it is refused with one opaque message and **nothing is written** (asserted on the `twoFactor` row, not only on the response).
7. **`POST /api/auth/two-factor/disable` still answers 404**, by request, after this task lands. If open item 1 is ruled the other way this criterion changes with it, and the ruling is what changes it.
8. After a successful reset the operator is on the enrolment screen with a new TOTP URI and a new set of recovery codes, is **still signed in** (the rotated session's cookie survived the BFF hop), and the old recovery codes no longer verify.
9. From that state no admin route other than the enrolment screens is reachable, which is 061's gate doing its job and is asserted by navigating to a deep route.
10. A full round trip in Playwright: sign in, open Settings, read the session list, revoke a second session created in another browser context, reset two-factor with a recovery code, complete re-enrolment with the new secret, and reach the shell.
11. Integration tests against a real Postgres and the real library for the composed endpoint, in the shape `apps/api/src/features/auth/auth.integration.test.ts` and `reset-two-factor.integration.test.ts` already use: the refusals, the rotation, the destroyed codes, the cleared trusted-device record, and the audit row if open item 3 is granted.
12. The audit row exists for a self-service reset and names its source, or open item 3 was declined and the work order records that no row is written. Either way it is a decision in the document rather than a gap in the code.
13. `docs/SECURITY_DESIGN.md` SEC-1 updated in the four places named above, in the same PR, and `auth-mount.test.ts` green with `two-factor/disable` still denied.
14. `pnpm verify` green; `QCMS_PORT_SEAT=<0-9> pnpm verify:browser` green, run detached, since this touches `apps/admin`; and the forced Docker-backed run if `packages/db` is touched.

## Open items for the Code Owner

Each carries a recommendation and **decides nothing**.

1. **One composed QCMS endpoint, or `two-factor/disable` on the allowlist?** **Recommendation: the composed endpoint**, for the reason in the deliverable: allowlisting `disable` makes the password sufficient, which is not what the ruling asks for, and no better-auth endpoint takes both factors. The cost is a QCMS endpoint that orchestrates three library calls and therefore owns their failure modes, and a second place (beside the workspace routes) where QCMS calls `auth.api.*` in process. The alternative is cheaper to write and weaker as a control.
2. **What happens to the account's other sessions after a reset?** **Recommendation: revoke them**, in the same operation. Against it: the break-glass deliberately does not, on the recorded reasoning that any session that exists already passed the second factor, and that reasoning is as true here. For it: the self-service door is a browser rather than a database credential, the usual reason to reset is a device out of the operator's hands, and `/change-password` already revokes others, so the Settings screen would otherwise be inconsistent with itself about what a credential change costs.
3. **May the control pool hold `INSERT` on `control.two_factor_resets`?** It holds nothing today, by the Code Owner's decision of 2026-09-09, which made the table migrate-only against exactly the credential this task would write with. **Recommendation: grant `INSERT` and nothing else**, with no `RETURNING`, a `source` column distinguishing the CLI from self-service, and `UPDATE` and `DELETE` still revoked from every `qcms_app%` role, which keeps the property that decision bought: the credential serving traffic can add a row and cannot rewrite or remove one. The alternatives are a second table for self-service events, which splits one question across two places, or no audit row at all, which is not recommended for an act that removes an authentication factor.
4. **Is a session revoke audited?** **Recommendation: not in this task.** A revoke is an act on the operator's own credential and is self-evident to them; auditing it would mean deciding where auth events live in general, which is a larger question than this screen. Flagged because the opposite view is reasonable: "who signed my other sessions out" is a question an incident review can ask, and nothing can answer it.
5. **`freshAge`, set to what?** **Recommendation: the absolute cap**, so the two knobs cannot disagree and the list cannot start refusing because an operator raised an unrelated one. The alternative is to leave the library's one-day default and document the interaction, which keeps the code smaller and leaves a trap in the operator surface.
6. **Does the session list show the client address?** **Recommendation: yes**, because "a session from an address I do not recognise" is the question the panel exists to answer, and SEC-13 governs export rather than display. Flagged because it puts a direct identifier on a screen, which is a judgement this document should not make silently.
7. **Does this gate launch?** Written as 8b and as not gating 038, matching 061. Against that: an operator locked out of their own authenticator at an adopter site has a recovery path that requires a database credential, which is a real support cost on day one. **Recommendation: does not gate launch**, and it is small enough to land before it anyway.

## Out of scope (binding)

**Self-service password reset.** There is no email transport in the product, which is why 061 put it out of scope, and nothing about this task changes that.

**Removing or weakening `qcms:reset-2fa`.** It stays exactly as it is, including its migration-role guard, its refusals and its deliberate non-revocation of sessions. This task adds a door for a different person and says so in SEC-1.

**Any change to how recovery codes are stored or verified.** The encrypted-at-rest deviation and its recorded reasoning (issue #319) stand. This task spends a code and generates a new set through the library; it does not touch the storage hook.

**OTP, social sign-in, passkeys and any second-factor method other than TOTP and recovery codes.** OTP delivery is Phase 4 and `/two-factor/send-otp` and `/two-factor/verify-otp` stay off the allowlist.

**`POST /revoke-sessions`**, for the reason in the deliverables.

**Trusted devices as a feature.** `trustDevice` is a request field this task never sets and `trustDeviceMaxAge` is a plugin option nothing configures; the only interaction is that a reset clears the existing trust state, which is documented rather than built.

**Multi-admin administration.** Nothing here lets one account see or revoke another account's sessions, or reset another account's second factor. That is a membership question and it belongs with the role families, not in Settings.

**`update-user` and `change-email`.** Still off the allowlist, still not offered.

## Notes for the executor

**Write the allowlist test before the screen.** The control in this task is a short list of strings and a 404, and the thing most likely to go wrong is that `two-factor/disable` quietly becomes reachable because the composed endpoint was easier to write that way. `auth-mount.test.ts`'s `denied` list is where that is caught, and it catches it by request rather than by reading the configuration.

**Read `apps/admin/app/(shell)/settings/recovery-codes/route.ts` first.** It is this task's shape already built once: a password-gated Settings POST, a same-origin check, the session policy applied in the handler because the shell layout's gate does not cover a direct browser POST (issue #177), an opaque refusal, the `429` separated out, markers chosen so the message lands on the panel that produced it, and nothing logged. Copy that handler's structure rather than designing a new one.

**The session rotation inside `disable` is the thing that will break first.** A handler that forgets to move `Set-Cookie` onto its 303 signs the operator out in the middle of a reset, and the symptom (bounced to sign-in after a successful reset) looks like a gate bug rather than a dropped header. Assert the new cookie's presence on the redirect.

**Do not reach into the plugin's storage to check a TOTP code.** The secret is encrypted under the versioned admin auth key and better-auth's verify path is the only thing that should decrypt it. `auth.api.verifyTOTP` on a live session is a pure check, which is the whole reason the composed endpoint is possible; if it turns out not to be at the version in the lockfile, stop and raise it rather than writing a second verifier.

**The two kinds of "fresh" are different things and the names do not help.** better-auth's `freshAge` measures from `session.createdAt` and is not extended by a refresh; QCMS's idle window is `expiresAt` and is. Both exist, they measure different things, and the absolute cap is enforced in QCMS's own session read rather than in the library. Get that straight before touching `instance.ts`.

**The admin requires JavaScript, and this task does not change that.** Its forms are plain posts because every auth route in this app is one, not because a scriptless path is a requirement here. Do not read a no-JS obligation into the admin on the strength of this file, and do not weaken the root layout's gate to make one.
