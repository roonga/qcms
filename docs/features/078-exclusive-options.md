# 078 - Exclusive choice options

**Stage:** 9 (Phase 4; whether it is launch scope is open item 1) · **Apps/packages:** `@roonga/qcms-core` (the schema, the parse-time refinements, the answer-time refusal), `@roonga/qcms-a2ui-compiler` (carrying the flag onto the compiled node), `@roonga/qcms-ui` (the wrapper that unticks), `apps/portal` (the no-JS refusal, which is server-side), `apps/admin` (the control in the option editor) · **Depends on:** nothing
**References:** the new ADR this task writes, in `docs/adr/core.md` (see "The decision this task records") · ADR-21 (multi-choice comparison, which this task does not change) · ADR-22 (one UI component stack; the vendored tree is frozen) · ADR-32 (authored validation messages, and the prop-extension precedent) · ADR-01 · ADR-16 · ADR-18 · R1 · R6 · I2 · I8 · `docs/DOMAIN_SCHEMA.md` sections 2.2, 2.4 and 3 · `packages/core/golden/evaluator/CORPUS.md` · `docs/COMPONENT_GUIDELINES.md` · UX review finding **P6** in `plan/ux-review-2026-10.md` (branch `docs/ux-review-2026-10`) · Code Owner ruling, 2026-10-21

## Context

A respondent ticked "Diabetes" and "None of the above" in the same multi-choice question, the answer was accepted, and it locked as `opt_diabetes; opt_none`. The contradiction is now stored and an operator reading the response detail sees both. That is review finding P6, observed live rather than inferred from code.

There is no exclusive concept anywhere to appeal to. `grep -i exclusive` over `docs/DOMAIN_SCHEMA.md`, `docs/adr/` and `packages/core/src` finds nothing about options: `ChoiceOption` is `{ optionId, label }` and that is the whole of it (`docs/DOMAIN_SCHEMA.md` section 2.2). The "None of the above" that produced the finding is `opt_none` of `packages/core/fixtures/questions/valid/multi-choice.json`, whose constraints are `minSelected: 1, maxSelected: 3`, so nothing in the question is even in tension with the selection the respondent made.

The review offered two short-term fixes (rename the fixture's option, or warn at publish on a "none"-shaped label) and one longer-term one. **The Code Owner ruled for the longer-term fix on 2026-10-21:** an optional `exclusive` flag on a choice option, enforced by the kernel, carried by an ADR and a `docs/DOMAIN_SCHEMA.md` change. The two short-term fixes are not taken and are out of scope below.

**The kernel is the enforcement point, and the scripted untick is a courtesy.** An unticking browser control is what a respondent sees, but it is not where the rule lives: the no-JS path has no script to run, a client can post whatever it likes, and ADR-18 means a published document keeps serving forever. So the refusal is `@roonga/qcms-core`'s, every path reaches it, and the control exists so that a respondent on the ordinary path never has to see the refusal.

## The decision this task records

A **new ADR in `docs/adr/core.md`**, because this binds the data model and the engine rather than one surface: the flag is in `@roonga/qcms-core`, the refusal is the kernel's, and both frontends and the compiler carry it. It takes the **next free number after the last row of the index in `docs/adr/README.md`**, and the index row lands in the same PR.

**Write the index row before you cite the number anywhere.** `pnpm check:adr-citations` fails any `ADR-NN` in tracked text that the index does not define, so a work-in-progress commit citing the new number with no index row is a red gate rather than a missing paragraph. That is also why this work order names no number for it.

The ADR has to say four things, and the first is the one a reader will come looking for:

1. **What the kernel enforces**, in one sentence: a multi-choice answer containing an option marked `exclusive` is valid only when it contains nothing else.
2. **Where the flag lives**: on the option, in the question definition, so it travels with the pinned question version and the published snapshot, and an exclusive option is a property of the question rather than of a form or a step.
3. **Why the enforcement is in the kernel and not in the control**, which is the paragraph above.
4. **That rule semantics are untouched**, naming ADR-21: `contains`, `containsAny` and whole-answer set equality mean exactly what they meant, and an exclusive option is an ordinary `optionId` to every one of them.

It is a decision record and not a specification: the deliverables below are this document's, and the open items are the Code Owner's.

## Deliverables

- **`exclusive` on `ChoiceOption`**, optional, in `docs/DOMAIN_SCHEMA.md` section 2.2 and in `packages/core/src/question-definition.ts`. **Absent means exactly today's behaviour**, asserted rather than assumed: every existing fixture, seed and corpus input parses unchanged and compiles to the same bytes.
- **`SNAPSHOT_SCHEMA_VERSION` to 3, with `SEMANTICS_VERSION` held at 1.** The snapshot's shape changes, which is the same reason ADR-42 gives for moving it to 2, and the stamp is a record of the shape rather than a gate on reading it (nothing refuses a snapshot by `schemaVersion`, unlike `semanticsVersion`, which the evaluator refuses when it is not 1). Say that in the ADR's consequences so the next reader does not have to re-derive which of the two stamps is load-bearing.
- **Parse-time refinements, in the shape section 2.2's existing list uses**: a typed error with a code and a path, reported together with every other violation rather than short-circuiting. The codes are this task's to name in the `DUPLICATE_OPTION_ID` and `MAX_SELECTED_ABOVE_OPTION_COUNT` register. **What they refuse is open items 2, 3 and 4**, and the recommendations are recorded there.
- **The answer-time refusal in the kernel**, in the `multiChoice` branch of `packages/core/src/validate-answer.ts`. It follows the `UNKNOWN_OPTION` precedent exactly: **one error however many options accompany the exclusive one**, because the constraint failed once; the message **echoes no option id**; and it is pushed into the same `errors` array as the selection-count failures so a respondent who broke two rules is told about both.
- **The validation message key**, and whether an author may word it. ADR-32's authorable set is `packages/core/src/validation-message.ts`'s `ValidationMessageKey`, mirrored in `packages/ui/src/author-messages.ts`'s `AuthorMessagesSchema`, and widening it is a two-file change plus the admin's messages editor. **Open item 5**, with the recommendation there.
- **The flag onto the compiled node, through a qcms-owned prop extension**, modelled on `packages/ui/src/author-messages.ts` and for the identical reason: every `@a2ra/core` props object is `.strict()`, `A2Renderer` throws on an unknown prop rather than ignoring it, and the vendored schemas must stay byte-identical to upstream. `packages/ui/src/components/a2ui/checkbox/checkbox.schema.ts` is **not** editable here: it is inside `packages/ui/src/components/a2ui/**`, which ADR-22 freezes and `pnpm check:a2ra-fidelity` measures against `packages/ui/a2ra-manifest.json` on every `pnpm verify`. Read that file's header before writing the wrapper; it is a worked example of this exact problem.
- **The compiler change** in `packages/a2ui-compiler/src/mapping.ts`, whose `multiChoice` case builds the `CheckboxGroup` and its `checkboxChild` children. The flag is per option, so the natural carrier is the child rather than the group; whichever you choose, a question with no exclusive option must compile to **the same document it compiles to today**, asserted against the appended corpus rather than argued.
- **The scripted untick in the qcms-owned wrapper**, which is `CheckboxGroupField` in `packages/ui/src/registry.tsx`. That function already exists and already overrides group behaviour for a QCMS reason (issue #974's native validation seam), so this is the seam rather than a new one. Ticking an exclusive option clears the others; ticking a non-exclusive option clears the exclusive one. State in the code which of those two directions is implemented and why, because "tick Diabetes while None is ticked" is as reachable as the other order.
- **What the untick says out loud.** Checkboxes change state without the respondent touching them, which is a `docs/COMPONENT_GUIDELINES.md` matter and not a styling one: decide whether the change is announced, keep focus where the respondent put it, and do not move the page (ADR-28's rule that answering never navigates by itself applies here unchanged).
- **The no-JS refusal, server-side, through the channel that already exists.** A kernel refusal arrives back at the step as a per-question error, which `apps/portal/components/native-step.tsx` renders into the field and into the `role="alert"` error summary through `apps/portal/lib/error-summary.ts`. **No new route, no new cookie and no client gate**: the respondent posts the contradiction, the API refuses it, and the step re-renders saying so beside the question. Assert it with scripting disabled, which is the only way this path is honestly tested (`docs/DEVELOPER_GUIDE.md`).
- **The control in the admin question editor**, in `apps/admin/components/questions/option-grid-editor.tsx`, one per option row. Read that file's header first: it is deliberately built so that **no input is bound to an `optionId`** (R6), and the flag is a per-row property that must not become a second way to edit identity. Chrome through the admin i18n catalog (ADR-27), keyboard operable, visible focus, and one line of help text saying what the flag does in the respondent's terms rather than the schema's.
- **The statement that rule semantics are unaffected**, written down in `docs/DOMAIN_SCHEMA.md` section 3 beside the containment-operator paragraph, and **asserted**: a rule using `contains` on an exclusive option, one using `containsAny` over a set including it, and one using `equals` against a single-element set all evaluate exactly as they do for any other option. This is a deliverable because "unaffected" is a claim, and an unasserted claim about the rules DSL is how I2 gets quietly broken.
- **New fixtures and new goldens, appended.** A new valid fixture carrying an exclusive option, new invalid fixtures for each refusal this task adds, and new corpus entries for the compiled document and the evaluator. **Nothing existing is edited:** `packages/core/fixtures/questions/valid/multi-choice.json` keeps its four options and its `opt_none`, every committed golden keeps its `expected` block, and `pnpm check:golden-append-only` passes with **no new recorded exception and no new hash pin** in `scripts/check-golden-append-only.mjs` or `packages/core/golden/evaluator/CORPUS.md`. If you find yourself wanting one, stop and raise it: the two exceptions on record are both defect corrections and this is a feature.
- **R6 and R1 held, and stated.** No stored `optionId` changes meaning: `opt_none` keeps meaning "None of the above" everywhere it is already stored. Marking an existing option exclusive is a **new question version** through the ordinary authoring path, never an edit to a published one, and a published form keeps serving the pinned version it pinned. Say so in the ADR, because "add a flag to the option" reads like an edit to an existing row until somebody writes down that it is not.
- **A changeset** naming `@roonga/qcms-core`, `@roonga/qcms-a2ui-compiler` and `@roonga/qcms-ui`. Every change is additive and no canonical encoding changes, so this is a minor rather than a major (`docs/DOMAIN_SCHEMA.md` section 2.4 is unchanged: the canonical multi-choice encoding is still a deduplicated set).

## Exit criteria

1. A multi-choice answer containing an exclusive option and anything else is **refused by `@roonga/qcms-core`**, with one error, no option id in the message, and the existing selection-count errors still reported beside it when they also fail.
2. The same answer is refused **through the API**, asserted at the HTTP layer rather than only in the kernel, so the refusal is a property of the product and not of a function.
3. **Without scripting**, a respondent who posts the contradiction gets the step back with a field error on that question and an entry in the error summary, and the answer is **not** stored. Asserted with scripting disabled.
4. **With scripting**, ticking the exclusive option clears the others and ticking another option clears the exclusive one, focus stays where the respondent left it, and the page does not move.
5. An answer containing the exclusive option **alone** is valid, and an answer containing none of the exclusive options is valid, including when the question also carries `minSelected` or `maxSelected`.
6. A question with **no** exclusive option behaves identically to today at every layer: it parses to the same definition, compiles to the same document (asserted against the appended compiler corpus), evaluates to the same `FlowState`, and renders the same DOM.
7. **Every committed golden passes with no `expected` block edited**, and `pnpm check:golden-append-only` is green with no new exception and no new hash pin. The criterion is "every" rather than a count, for the reason ADR-42 gives: a count is satisfied by a corpus that has lost files.
8. The parse-time refusals this task adds each have a test naming their code and their path, and each is **reported together with** any other violation in the same definition rather than instead of it.
9. A rule using `contains`, one using `containsAny` and one using `equals` over an exclusive option evaluate exactly as they do over an ordinary one, asserted in `packages/core`.
10. The admin editor can set and clear the flag on an option row, the setting survives a save and reload, and **no input in that editor is bound to an `optionId`** after the change (R6, the property that file's header exists to protect).
11. `docs/DOMAIN_SCHEMA.md` sections 2.2 and 3, and the new ADR with its row in `docs/adr/README.md`'s index, land in the same PR. `pnpm check:adr-citations` green.
12. `pnpm verify` green; `QCMS_PORT_SEAT=<0-9> pnpm verify:browser` green, run detached, since this touches `apps/portal`, `apps/admin` and `@roonga/qcms-ui`.

## Open items for the Code Owner

Each carries a recommendation and **decides nothing**. Items 2 and 3 are the two the ruling named explicitly.

1. **Is this launch scope?** It is written as Phase 4 and as not gating 038, which is the default under R7. The argument the other way is that the finding is a stored contradiction rather than a missing convenience, and that an operator reading `opt_diabetes; opt_none` cannot tell which the respondent meant. **Recommendation:** Phase 4, with the fixture question in item 6 answered before launch so the shipped corpus stops demonstrating the defect.
2. **At most how many exclusive options per question?** **Recommendation: one**, refused at parse time with its own code. Two exclusive options are individually coherent and jointly a shape nothing has defined: "None of the above" and "Prefer not to say" in one question are either mutually exclusive of each other as well, which no flag says, or not, which makes "exclusive" mean something narrower than its name. One is the shape the finding is about, it is what every comparable product offers, and refusing the second is reversible later while permitting it is not.
3. **`exclusive` on a `singleChoice` option: refuse or ignore?** **Recommendation: refuse at parse time**, with its own code, because the flag is meaningless there (a single choice is already exclusive of every other option) and a flag that parses but does nothing is a thing an author will set and then rely on. The cost is that `ChoiceOption` is shared by both types, so the refusal is a cross-field refinement on the question rather than a property of the option's own schema. Ignoring it is cheaper and is what a permissive schema would do; it is not recommended, and the ruling asked for this to be flagged either way.
4. **A question with `minSelected` above 1 and an exclusive option.** The exclusive option can then never be part of a valid answer: selecting it alone fails `minSelected`, and selecting it with anything else fails exclusivity. **Recommendation: refuse at parse time**, in the same register as `MIN_SELECTED_ABOVE_OPTION_COUNT`, because it is an unsatisfiable question and the existing refinements already refuse that class. The alternative is to permit it and let the respondent meet a dead end, which is the defect this task exists to remove, one layer up.
5. **May an author word the message?** ADR-32 lets an author supply a message per constraint. **Recommendation: yes**, a new authorable key, because this refusal is the one in the set most likely to want product-specific wording ("Choose either None of the above or one or more conditions"). The cost is a widening of `ValidationMessageKey` in `@roonga/qcms-core` and of `AuthorMessagesSchema` in `@roonga/qcms-ui`, plus a row in the admin's messages editor. Declining it means the catalog default is the only wording, which is a smaller change and a worse message.
6. **What becomes of `packages/core/fixtures/questions/valid/multi-choice.json`.** This task leaves it alone, as the ruling's constraints require, which means the shipped fixture corpus still carries a non-exclusive "None of the above" after this lands. Three options: leave it (the corpus demonstrates the pre-flag shape, which is true but reads as an oversight), append a second fixture beside it carrying the flag and leave the first (recommended, and this task does the appending either way), or amend it in place, which is a separate decision about a file the golden guard covers downstream of it. **Recommendation: append and leave**, and say in `packages/core/fixtures/` or the ADR that the older fixture is deliberately the unflagged shape.

## Out of scope (binding)

**The two short-term fixes the ruling did not take.** Renaming the fixture's option, and a publish warning on an option label that reads like a "none" choice. Open item 6 is about what becomes of the fixture and is a question, not a licence to edit it.

**Any amendment to a committed golden or to the existing multi-choice fixture.** New files only.

**Any `SEMANTICS_VERSION` bump.** The evaluator implements one version and refuses any other stamp, so a bump fails every published snapshot rather than preserving it. If this task appears to need one, it has grown a rule the evaluator has to apply, and that is a different design.

**Multi-choice as a table cell type.** `TABLE_COLUMN_TYPES` in `packages/core/src/step.ts` is `shortText`, `number`, `date`, `boolean` and `singleChoice`, so a `table`-presented group has no multi-choice column to be exclusive in (Q12, task 077). Assert that this task changes nothing there rather than reasoning about it.

**Cross-question exclusivity**, an exclusive option that disables a whole step, an "other" option with free text, and any form-level or group-level exclusivity. All are different features and none is ruled.

**Changing `contains`, `containsAny` or set equality** (ADR-21). The deliverable is a statement that they are unaffected, plus the tests that hold it.

## Notes for the executor

**Start at `packages/ui/src/author-messages.ts` and read its header.** It is the same problem solved once already: a QCMS-only prop on a vendored `.strict()` schema that `A2Renderer` would otherwise throw on. Copy the shape (validate the node in two halves, hand the vendored schema exactly the upstream shape) rather than inventing a second mechanism, and do not reach for the vendored file.

**The hard part is not the untick.** It is that there are four places a contradiction can arrive and only one of them runs your script: the hydrated control, the no-JS post, a client posting directly, and a published document that has been serving since before this task existed (ADR-18). The kernel refusal is what covers all four. Write that test first, and write the control afterwards.

**The no-JS path has no new mechanism in it.** Issue #964's missing-required path and the refused-answer channel it feeds already carry a per-question error from the API onto the re-rendered step; `apps/portal/components/native-step.tsx` composes refused answers and missing answers into one summary through `stepSummaryEntries`. Your refusal joins that, and if it does not fit, say so rather than adding a second error channel beside it.

**Do not put the rule in `maxSelected`.** An exclusive answer is one selection, and `maxSelected: 1` looks like the same thing until the question also offers three non-exclusive options that may legitimately be ticked together. They are different constraints and they compose.

**Check the dedupe order.** `validate-answer.ts` applies selection counts to the **canonical, deduplicated** selection, and the exclusivity check must read the same canonical value for the same reason: a posted `[opt_none, opt_none]` is one selection and is valid.
