RED-FIRST PROOF: the row menu's roving focus dead-ends on a disabled item (issue 517)
=====================================================================================

What this file is
-----------------
The three tests added in this change, run against the PRE-FIX `components/row-menu.tsx`
(the file reverted to the branch's previous commit for the duration of the run, then put
back). Each one fails, and it fails at the exact press that used to do nothing. That is
the point of keeping the output: a test that only ever ran green proves the assertion
compiles, not that it catches the defect.

The defect
----------
`RowMenu`'s ArrowUp/ArrowDown handler collected `[role='menuitem']` with no
`:not([disabled])` filter, unlike the open-focus effect beside it. `.focus()` on a
disabled `<button>` is a silent no-op, so arrowing onto a disabled item did nothing and
the next press recomputed the same index and did nothing again. Everything behind it was
unreachable by keyboard.

It was latent on `main` because the option grid's one disabled item (Remove, at one
option) is LAST, so no live item sat behind it. The pin list puts Move up and Move down
in the MIDDLE of five items and disables them at the ends of the list, which is what
exposes it.

The three configurations, and what each loses
---------------------------------------------
1. First row of a step (pin list): Move up is dead and sits third of five, so
   Move down and Remove are unreachable.
2. Single-pin step (pin list): both moves are dead and adjacent, so Remove is
   unreachable - and Remove is the only route to unpinning a question.
3. Option grid, one option (Remove dead and LAST): nothing is stranded behind it, but
   the roving ring is still open - ArrowDown on the last live item aimed at the dead
   Remove and did nothing, so the wrap never happened. This is the shared component's
   other caller, in the other item order.

Why this proof is in two parts
------------------------------
`pin-grid.pw.ts` runs `test.describe.configure({ mode: "serial" })`, so the first failure
skips every test after it. Part 1 runs the pin-grid and questions-lifecycle files whole
and catches cases 1 and 3; the single-pin test never ran. Part 2 re-runs the pin-grid
file with the first-row test excluded so the serial chain reaches case 2.

Seat 5, admin-chromium project, from the branch worktree.

The green side is the full `verify:browser` run recorded in the PR conversation: the same
three tests pass against the fixed component, with the rest of the browser suite.
