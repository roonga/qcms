Issue 558: nine screens render byte-identically, proved by sha256 rather than by reading
the code.

Method. `apps/admin/e2e/gate-558.pw.ts` shoots fifteen of the sixteen authenticated screens
at 390px and 1280px. It was run twice against the same seeded fixture: once with
`app/(shell)/layout.tsx` and `app/globals.css` restored to the base commit and
`lib/measure.ts` / `components/measured-main.tsx` absent (the `before/` set), and once on
the branch.

The base is commit `d78e0ba`. Naming the commit rather than the branch is deliberate: this
set was first shot against `fix/557-breakpoint-tokens`, which has since merged and been
deleted, which left that description true but no longer re-derivable (issue 600).

Both sides are also shot within minutes of each other, on the same calendar day, and that
is a requirement rather than a convenience. Some of these screens render a date at
day granularity (`formatDay`, in the version list) and one renders a timestamp
(`formatDateTime`, in the secure-links table). A `before/` set shot on one day against an
after set shot on the next would differ on those screens for a reason that has nothing to
do with a width cap, and the table would report the difference as though it did.

Both sides stand on that one base, and the shared base is the whole reason a pair means
anything: it is what leaves the width cap as the only difference between two frames. So
when `main` moves under this branch, BOTH sides are re-shot together. Re-shooting the after
set alone would quietly turn "the same tree twice" into "two different trees", and this
table would go on printing IDENTICAL without it meaning anything.

This set has been re-shot twice as `main` moved under the branch, most recently at
`d78e0ba` after issue 613 landed. Each time, only the frames whose bytes actually changed
were re-committed; the rest came back byte-identical to what was already here and were left
alone, so the diff carries what the base move moved and nothing else. At `d78e0ba` that was
seven pairs: `forms` and `questions` and `form-links` at 1280, `form-versions` and
`question-detail` at both widths.

Which is NOT the same seven screens the table marks DIFFERS, and the distinction is the
point. DIFFERS is about a pair, before against after on one base, and it is what this gate
claims. The re-shot list is about one side of the set against its own older copy on an
older base, and it claims nothing: a frame lands there whenever anything at all on that
screen changed, from a merged PR's markup to the calendar. Both known contributors are
visible in this last re-shoot: issue 613 edited the secure-links table that `form-links`
photographs, and the version list renders a `formatDay` date that had rolled over since the
previous set was shot.

What survives every re-shoot is the verdict column: the same twenty-three pairs come back
IDENTICAL and the same seven come back DIFFERS, and the seven are the seven screens issue
558 moves. That is the claim standing up to a change of base rather than being quietly
restated on a new one. Two screens worth naming because they were expected to move and did
not: the responses pair, since the seeded fixture never reaches the warning banner or the
empty-state sentence issue 553 rewrote, and the builder, since issue 613's edits to it are
failed-read states a healthy seeded read does not render.

One string is hidden in both runs: the signed-in operator's address, which the shell footer
prints on every authenticated screen and the Settings account card prints a second time.
The suite mints its admin account per run, so that address is the only pixel here that
cannot repeat, and left visible it makes every pair differ for a reason that is not a width
cap. It was found by comparing an unhidden sweep and pixel-diffing the frames that
disagreed. Nothing else on any of these screens varies between runs.

Reading it. IDENTICAL means the two PNGs are the same bytes. Every 390 frame is identical,
because a max-width cap is fluid below itself and no media query is involved at any width.
At 1280 exactly the seven screens issue 558 moves differ, and the eight unchanged ones do
not. The ninth unchanged screen, `/forms/[formId]/responses/[sessionId]`, is absent from
this sweep because its subject is a session created at run time; it is measured instead in
`apps/admin/e2e/measure.pw.ts`.

This sweep used to warn of one SOFT failure at `d78e0ba`: the builder reported
`document.scrollWidth` 391 in a 390px viewport, and the note here said so, said it was not
this branch's, and asked the next reader not to read it as a width-cap problem. That was
correct at the time and is no longer true of the code. Issue 616 owns and has fixed it (the
version cell's `white-space: nowrap` set a 209px column minimum on a table with no scroll
box, which became the document's floor at every viewport). The observation stays recorded
because it is what the finding was made of; the instruction to expect it is gone, because
re-running this sweep now reports no such failure.
