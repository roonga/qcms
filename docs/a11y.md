# Accessibility policies (QCMS portal and admin)

**Status:** established by task 030 (portal accessibility pass) · **Standard:** WCAG 2.2 AA · **Inherited by:** admin app (031-035) and any future respondent-facing surface.

This document is the normative record of the flow-level accessibility behaviors a
component library cannot supply on its own: focus management across branch
changes, live-region announcements, keyboard/tab-order policy, and error UX. The
`@qcms/ui` renderer (028) supplies per-control semantics (labels, roles,
`aria-describedby` error wiring); the behaviors here are owned by the host app
(the portal today, the admin preview tomorrow) because only the host knows the
flow. ARCHITECTURE.md §11 is the commitment; this is the how.

## The focus-target primitive (@qcms/ui)

Every control the renderer draws is wrapped by the qcms-owned registry adapter in
a `display:contents` element carrying `id={questionId}` and
`data-qcms-field={questionId}` (task 030). The wrapper adds no box and no
accessibility-tree node, so the accessibility outline is unchanged; it exists
only so a host app can find "the DOM for question X" without reverse-engineering
each control type's internal markup. Everything below is built on this handle.

The honeypot (026) is deliberately NOT given this handle and stays `aria-hidden`
and out of the tab order: it must remain invisible to assistive tech.

## Focus management on branch changes

A forward-pass answer can insert or remove downstream questions (ADR-16). Policy:

- **Insertion (a branch reveals questions):** focus STAYS on the control the
  respondent just answered. We never yank focus forward to the new question - that
  would strand a keyboard or screen-reader user mid-thought. The insertion is made
  perceivable by an announcement (below), not by a focus move.
- **Removal of a question that does NOT hold focus:** nothing to do for focus; the
  removal is announced.
- **Removal of the question that DOES hold focus:** focus moves to a stable,
  sensible target so it is never dropped to `<body>`. Target order:
  1. the next question that was visible after the removed one and still is, in the
     pre-change document order (`nextFocusTargetAfterRemoval`);
  2. if none follows, the step heading (`h1`, made programmatically focusable).
- **Focus preservation across re-render:** re-rendering the step from a new flow
  projection can remount the focused control. If the focused question survives the
  projection but the remount dropped focus, the host restores focus to that same
  question. Net effect: focus "stays put" even though the DOM was rebuilt.

Implementation: `apps/portal/lib/a11y.ts` (`diffFlow`, `nextFocusTargetAfterRemoval`,
`focusQuestion`, `questionIdOf`) driven by an effect in
`apps/portal/components/step-flow.tsx`. The question that holds focus is captured
at the instant an answer post returns (before the re-render), so the post-render
effect knows what to recover.

## Live-region announcements

A single visually-hidden `aria-live="polite"` region (the "announcer",
`data-testid="flow-announcer"`) carries flow narration; error summaries use
`role="alert"` (assertive). All strings come from the shell i18n catalog
(`apps/portal/lib/i18n/en.ts`, single locale) - never hard-coded in components.

| Event | Politeness | Message |
| --- | --- | --- |
| Step change | polite | `Step {current} of {total}: {title}` (title read from the step `h1`) |
| Branch insertion | polite | `1 question was added below.` / `{n} questions were added below.` |
| Branch removal | polite | `1 question was removed.` / `{n} questions were removed.` |
| Blocked submit | assertive (`role="alert"`) | error summary heading + one entry per missing question, each naming its own question (`{label} needs an answer.`) |
| Answer rejected (422) | via the control's own error slot | server message in `aria-describedby` (028) |
| Submission success | page navigation | the `/done` heading announces on load; no live region needed |

Priority when several changes coincide in one projection: a step change outranks a
branch change (it is the larger context shift); otherwise an insertion outranks a
removal. One announcement per projection - we never stack messages.

## Keyboard traversal and tab order

- The full flow is completable keyboard-only: no pointer-only affordance exists.
- A skip link (`Skip to content` -> `#portal-main`) is the first focusable element
  and becomes visible on focus.
- **Tab order is DOM order.** Because insertion keeps focus on the answered
  control and the inserted question is placed after it in the document, the new
  question is simply the next Tab stop - no tabindex management, no focus trap.
  Positive `tabindex` is never used anywhere.
- No keyboard traps: every composite control (react-aria radio group, number
  field, date picker, select) is enter-and-leave by Tab per its ARIA pattern.

## Focus visibility (WCAG 2.2 - 2.4.11)

The vendored `@qcms/ui` controls carry their own focus rings. Every other
focusable element (skip link, error-summary "jump to field" links, a step heading
focused after a branch removal) gets a guaranteed high-contrast outline from a
zero-specificity `:where(...):focus-visible` rule in `globals.css`, using
`--color-focus-ring`, which clears 3:1 against its background in EVERY predefined
theme and every mode (Light, Dark, High-contrast), asserted by
`packages/ui/src/theme-tokens.test.ts`. High-contrast replaces the 2px outline
with a 3px one (`theme-components.css`).

## Colour, contrast and text spacing (WCAG 1.4.3, 1.4.11, 1.4.12)

The token contract (ADR-30, `docs/theming.md`) is what carries these:

- **Contrast.** Four predefined themes, each authored Light and Dark, plus one
  shared High-contrast mode layer. Every critical text pair meets 4.5:1 in Light
  and Dark and **7:1 (AAA)** in High-contrast; UI, border and focus pairs meet
  3:1. The ratios are recomputed from `theme.css` by
  `packages/ui/src/theme-tokens.test.ts`, so a palette edit that drops a pair
  below target fails the build.
- **Text spacing (1.4.12).** The five floors are token values, not guidance: body
  >= 16px, line-height >= 1.5, letter-spacing >= 0.12em, word-spacing >= 0.16em,
  paragraph spacing >= 2em. No theme, mode or density level may lower one - a
  density level may set only the five `--space-*` tokens, which is asserted.
  `apps/portal/e2e/theming.pw.ts` measures them on rendered text.
- **Target size (2.5.8).** `--space-control-h` is the control-height token and
  never drops below 24px, at any density level. Compact is the level that matters,
  so it is the one measured: `apps/portal/e2e/appearance.pw.ts` reads every rendered
  control target at all three levels, and the smallest dimension anywhere in the
  sweep is 34px against the 24px minimum. That is also why the header's chip
  controls hide a full-size radio input rather than a 1px-clipped one - 2.5.8
  measures the target, and the target is the input.
- **High-contrast is a distinct respondent mode, not Dark:** heavy black borders,
  flat surfaces (no shadows), a heavy focus ring, and `color-scheme: light`.
- **The respondent chooses, and the choice sticks.** The portal header carries an
  Appearance disclosure with three controls: colour mode (Light / Dark / High
  contrast), font (over the curated registry, so a dyslexia-friendly or
  high-legibility face is one selection away), and density. Each persists in a
  cookie, which is what lets the SERVER apply it: the root class is correct in the
  first byte of HTML, so there is no flash, and the choice survives a reload, a step
  navigation and a resumed session. A first visit defaults from
  `prefers-color-scheme` and `prefers-contrast: more`, with the contrast signal
  outranking the colour one. Full contract: `docs/theming.md`.
- **A selected control state is never colour alone.** The selected chip carries a
  check glyph, a bolder label and a heavier border as well as a fill, so it reads in
  High-contrast (a two-colour palette) and for a colour-blind respondent. This is
  asserted in all three modes, not only in Light: the appearance control is the one
  a respondent has to operate in order to fix their own experience.
- **Without scripting the appearance controls are hidden**, because a radio a
  respondent can move that changes nothing reads as a broken page. The deployment's
  configured defaults still apply and the page is still server-rendered.

## Error UX (WCAG 3.3)

- A blocked submit renders an error SUMMARY above the first field
  (`role="alert"`, focusable), and focus moves to it so it is announced.
- Each summary entry is a link that moves focus to its offending field via the
  focus-target handle (`focusQuestion`), scrolling it into view. This is the
  standard "error summary that jumps to the field" pattern.
- **Each entry NAMES its question** (`{label} needs an answer.`, the label read
  from the compiled step document), so the links have distinct accessible names and
  a screen-reader user hearing the list can tell which field each one jumps to
  (WCAG 3.3.1, issue #21). A question the document carries no label for falls back
  to the unnamed `This question needs an answer.`
- Inside the field, the target is that control's VALUE control, chosen by
  `firstFocusableIn` (`apps/portal/lib/a11y.ts`): a segmented date field's first
  editable segment (`[role=spinbutton]`), else the first input / textarea / select,
  else the first focusable. Candidates inside an `aria-hidden` subtree (react-aria's
  native form mirrors, the honeypot) and candidates the browser does not render are
  skipped, because `.focus()` on either is a silent no-op. `focusQuestion` reports
  success only when focus really landed in the field, so the branch-removal
  recovery falls back to the step heading instead of leaving focus stranded
  (issue #76). These are layout-dependent, so they are verified in Playwright
  (`apps/portal/e2e/a11y-focus-target.pw.ts`) and not in the node-env Vitest
  project, where no element has a box.
- Per-field errors are the server's (the authority); the renderer surfaces each in
  the control's error slot, associated by `aria-describedby` (028). The portal
  never invents client-side validation copy beyond the catalog.

## Reduced motion (WCAG 2.3.3)

`globals.css` honors `prefers-reduced-motion: reduce` with the conservative reset
(transitions/animations collapse to near-instant, `scroll-behavior: auto`). The
design uses little motion; this guarantees none is imposed on users who opted out.

## Automated enforcement (CI)

- **axe** (`@axe-core/playwright`) runs against EVERY portal state in the fixture
  walkthroughs, including post-branch-insertion, post-branch-removal, and the
  blocked-submit error-summary state - not just first render. Zero violations is
  the gate. It also runs over **every predefined theme in all three modes**
  (Light / Dark / High-contrast) on the flow page, plus every theme in
  High-contrast on the error-summary state (`theming.pw.ts`); a colour switch is
  settled (running CSS transitions are
  awaited) before any contrast measurement, or axe samples a blended mid-transition
  colour that belongs to no palette. Since 053 it also runs over the **appearance
  panel itself, open, in every mode x every density** (nine combinations,
  `appearance.pw.ts`) - a collapsed `details` hides its contents from axe, so the
  controls would otherwise never be scanned at all.
- **Proving an absence of flash (or of layout shift) needs first-frame sampling, not
  an end-state assertion.** The end state is correct whether or not a flash happened,
  so asserting it proves nothing. The house pattern is `recordFirstFrames` in
  `apps/portal/e2e/appearance.pw.ts`: an init script samples `<html class>` and the
  painted background on each of the first animation frames, and the first sample
  containing a `<body>` is the earliest frame that could have painted. Assert every
  sampled frame already carries the settled value. Verified falsifiable by delaying
  the pre-paint script past first paint, which turns the spec red naming the case.
  Note `document.body === null` is genuinely true during parsing even though the DOM
  lib types it non-nullable, which is the frame that matters most.
- **Target size (2.5.8)** is measured, not reasoned about: every rendered control
  target at all three density levels, against the 24px minimum
  (`appearance.pw.ts`, table written to
  `apps/portal/.playwright/appearance-target-sizes.txt`).
- **The 1.4.12 floors** are re-measured on rendered text across **every density x
  every registry font** (69 combinations, `appearance.pw.ts`), on top of the
  per-font sweep at the default density in `fonts.pw.ts`.
- **No-flash** is measured on the first animation frame the browser could have
  painted, for all three persisted modes and both OS-derived defaults
  (`appearance.pw.ts`), rather than asserted about the end state.
- **Lighthouse** (`lighthouse`, accessibility category, threshold 100) runs on the
  page-load states that a fresh navigation can reach: entry, the flow page (session
  cookie injected), an error message screen, and completion. Interactive-only
  states (branch changes, the blocked-submit summary) are covered by axe, which
  runs inside the real, cookie-bearing browser context. The cookie-context
  rationale (why Lighthouse needs the session cookie injected as a request header)
  is documented in the header of `apps/portal/e2e/a11y-lighthouse.pw.ts`.
- **Reduced-motion and 200% zoom** smoke checks run on the flow page.

## Manual pass (human-in-the-loop)

Automated tools catch roughly half of WCAG issues. Each release also runs a manual
screen-reader pass (NVDA + VoiceOver) against the kitchen-sink form, driven by
`docs/a11y-manual-pass-checklist.md` and logged as `docs/a11y-pass-<date>.md`.
Zero open severity-1 issues is a Stage 7 gate.

## Inheritance note for the admin app (031-035)

The admin preview renders through the same `@qcms/ui` renderer, so the
focus-target primitive is already present there. When the admin builds its own
flow preview it MUST reuse these policies (announcer region, focus-on-branch,
error summary, skip link, focus-visible fallback) rather than reinventing them;
admin has its own axe gate but the flow-level behaviors are defined here.

That admin gate exists as of task 031: `apps/admin/e2e/a11y-axe.pw.ts`, a project
on the same root Playwright config, so CI's browser job runs it without a second
job. It covers **every** shell and auth state rather than first render only (the
signed-out screen, each failure state, enrollment with its QR and setup key, the
one-time recovery-code display, the challenge and its recovery variant, all five
shell areas) plus a keyboard walkthrough of the whole sign-in loop, because axe
cannot tell whether a control is *reachable* - the defect class issue #144
shipped. Lighthouse is deliberately NOT run against the admin: its performance
and SEO categories are meaningless for an internal tool behind auth, and its
accessibility category is what axe already covers here per state.

One admin-specific lesson, general enough to repeat: the vendored `Alert` always
renders `role="alert"`, so it is a live region and belongs only to something that
just happened. Standing state (a 2FA status line, a "this area lands in task NNN"
note) is prose. Using `Alert` for it announces on every page load and competes
with the real message when one arrives, and wrapping it in a second `role="alert"`
produces two live regions for one sentence.
