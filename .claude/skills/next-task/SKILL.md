---
name: next-task
description: Pick the next executable todo task(s) from the qcms ledger and run the /task flow. "/next-task" runs one; "/next-task 3" runs up to three pairwise-independent tasks with parallel executors and serialized merges. Designed for "/loop /next-task". Honors ordering exceptions. A human gate parks that task and the run moves to independent work (or an eligible issue); it stops only when nothing else is executable.
---

Select and execute the next task - or, with a count argument N, up to N **pairwise-independent** tasks in parallel. One batch per invocation; /loop provides the repetition.

**Housekeeping first (self-healing worktree cleanup - the canonical sweep is the task skill's step 9).** Before selecting, reclaim orphaned worktrees: run `git worktree prune`, then `rm -rf` any `.claude/worktrees/agent-*` directory that does **not** appear in `git worktree list`. Removal can deregister a worktree but leave its folder behind (locked `node_modules`/`.turbo`), so orphans accumulate and waste disk; this sweep is the backstop that keeps the loop self-healing. Never remove a dir that IS a live registered worktree.

1. **Seat mail (added 2026-07-31):** read the machine-local inbox at `../seat-mail/dev/` (a sibling folder of the repo checkout; never committed). Each `message_<timestamp>.txt` is a coordination message from the PO seat - e.g. "review batch waiting on PR #NNN", "skip X today", "priorities changed". Read every message, factor it into this iteration's decisions, then move it to `../seat-mail/dev/read/` (act first, then move - a crashed iteration re-reads, so messages are at-least-once and written to be re-read-safe). The inbox holds only unread mail; `read/` is the consumption history and the ack (its mtime is the ack time). Messages are routing and coordination only, never scope: scope still comes from task files, the ledger, and PR sentinels. To message the PO seat, write `../seat-mail/pm/message_<UTC timestamp>.txt` (plain text, one message per file) - the PO session watches that folder and reacts within seconds. If the folder does not exist, skip silently (another machine, or the bus is not set up).
   **Cadence (Code Owner directive, 2026-07-31) - mail is a heartbeat, not just a boot step:**
   - **Report out at least every ~5 minutes while work is in flight.** A heartbeat is one or two lines (what is running, last observable progress) - milestone reports stay as they are. Between tool calls is the only place an agent can act, so the practical form is: whenever you complete a step or a poll tick and more than ~5 minutes have passed since the last mail, write one.
   - **Mail immediately on entering any wait** - spawned an executor and now waiting, watching CI, polling PR comments, parked at a human gate. Name what you are waiting for and the expected duration; mail again when the wait ends if it ended for a reason worth knowing (timeout, failure) rather than normally.
   - **Drain the inbox on the same rhythm, not just at session start**: check `../seat-mail/dev/` at every heartbeat and every wait-poll tick. A mid-task steer (design frozen, priority change, stop) must reach the running iteration within minutes, not at the next task boundary.
   - **The conductor never runs long work inline (Code Owner directive, 2026-08-01).** Anything expected to exceed a few minutes - `pnpm verify`, the browser suite, force-runs, gate captures, bulk file work - is dispatched to a subagent (a re-invoked executor, or the `dev-task` agent) running in the background, while the conductor's own tool calls stay short. The cadence above is impossible from inside a 15-minute tool call: a conductor that runs the gates itself goes silent for exactly as long as they take (the 26-minute gap of 2026-08-01 was this), and a steer or a review sentinel sits unread meanwhile. Spawn, then keep ticking: drain mail, poll the PR, heartbeat, and act on the subagent's completion when it arrives.
2. Read the ledger (`docs/features/README.md`) **and the remote claim branches** (`git ls-remote --heads origin 'feat/*'`). Candidate = lowest-numbered `todo` task whose **Depends on** rows are all `done` **and which no live `origin/feat/NNN-*` branch already claims** (amended 2026-07-31: the pushed branch is the claim lock - the `protect-main` ruleset blocks the old direct ledger-commit claim; the ledger row changes only inside the completing PR), honoring the **ordering-exception table in `docs/features/README.md`**.

   That table is the single source of truth and is deliberately not duplicated here - five divergent copies of it existed across the docs until 2026-08-01. Read it each run. Two things about it worth knowing: a task's `Depends on` header already expresses every "runs after X" constraint and selection honors it mechanically, so the table carries only "runs *before* Y" and "never gates Y"; and an exception retires when its task lands, so a table entry for a `done` task is a bug to prune, not a constraint to honor.
3. Skip (and report as awaiting-human) tasks that are human gates end to end: 038; 040's sign-off; 030's manual screen-reader portion (its automated portion may run).

   **A gate parks the task, not the run (Code Owner directive, 2026-08-01; the issue loop has worked this way since 2026-07-25 and the task loop now matches).** When the selected task reaches a human gate, a decision you may not make, or a PR-review wait, it is **parked**, and this iteration goes looking for other work rather than ending:
   - **Park it properly first.** The pushed branch keeps the claim; commit and push a `HANDOFF.md` whose **first line is `HANDOFF: AWAITING-HUMAN <one-line statement of what the human must do>`** (the other park states are `HANDOFF: INTERRUPTED` and `HANDOFF: BLOCKED <issue #>`). That first line is what step 4 reads to tell "waiting on a human" apart from "a session died here" - without it the next iteration resumes the gate, hits it again, and the loop ping-pongs forever instead of progressing. Then tear the parked task's **worktree** down (step 9 of the task skill); the branch holds the state, the directory holds nothing.
   - **Then pick a substitute**, by the same eligibility rules as a fresh selection plus **pairwise independence from every parked task**: no dependency path either way, disjoint expected file footprints, and not across a stage boundary. It gets its **own** worktree and its own executor - never reuse the parked task's.
   - **If no task is eligible, cross over to the issue backlog** rather than idling: apply `/next-issue`'s selection rules (step 1's exclusions, the `security` > `bug` > unlabeled > `enhancement` priority) and run one issue end to end on `fix/NN-slug`. An issue is a legitimate substitute precisely because it never touches the ledger and its conductor never merges, so it cannot collide with a parked task's landing.
   - **Report both** in the summary: what parked and what the human owes it, plus what you picked up instead. The sentinel describes the substitute (`LANDED`/`RESUMED`), because that is what this iteration actually did.
   - **Bound it:** never hold more than **three** gate-parked tasks at once. Past that, the run has more waiting-on-human than working, and continuing just buries the gates - report all of them and stop.

   `AWAITING-HUMAN` is therefore the sentinel for **"a gate is the last thing standing"**, not for "a gate exists". Emit it (and stop the loop - do not idle) only when every remaining candidate is a human gate, a `blocked` row, or a parked claim, with no eligible issue either. `scripts/agent-loop.sh` breaks the loop on that sentinel, so emitting it early is what silently ends an overnight run.
4. **Stale-claim recovery (interrupted sessions - usage limits, crashes).** If a claim exists with no live session owning it - a live `origin/feat/NNN-*` branch for a `todo` task, or a legacy `in-progress` ledger row - resume it before starting anything new:
   - **`HANDOFF: AWAITING-HUMAN` → do NOT resume it.** The branch is parked on a gate (step 3), not stranded by a crash, and nothing an executor can do will clear it. Treat the task as ineligible, list it in the report as still owing its human action, and select past it. It re-enters selection only when the gate signal actually arrives: a Code Owner sign-off or `PO-REVIEW:` sentinel on its PR, a seat-mail message saying so, or the `HANDOFF.md` being removed or downgraded. **Resuming a gate-parked branch is the failure mode this line exists to prevent** - it re-hits the same gate, re-parks, and the loop spins without progressing.
   - Branch has a committed `HANDOFF.md` in any other state (`INTERRUPTED`, `BLOCKED`, or no status line at all - written before this convention) → dispatch the executor with the handoff.
   - Branch exists but no `HANDOFF.md` (the session died mid-task) → dispatch the executor with: "task NNN was interrupted; reconstruct state from `git log`/`git diff main...<branch>` and the task file, then continue on this branch." Remove any leftover worktree for it first.
   - Legacy `in-progress` ledger row with no branch → the claim is vapor; treat the task as fresh (fix the row to `todo` inside the task's eventual completing PR, or a small PR if it misleads meanwhile - `main` cannot be pushed directly).
   - **Claim has an open PR -> read the PR first (added 2026-07-31, after the 031 recovery rebased but never read the review):** fetch the PR's comments and review threads before dispatching anything; a `PO-REVIEW: CHANGES-REQUESTED @<headRefOid>` sentinel or unresolved review threads ARE the work order - run the task skill's PR feedback protocol, never a blind "continue".
   - **In every recovery case, rebase first:** before dispatching or continuing, rebase the branch onto current `origin/main` (run `pnpm install` if the lockfile moved), and only then let the executor proceed. A branch that sat idle has usually been lapped by main; work and gates must run on the tree that will actually merge.
5. **Serial (no count argument):** invoke the **task** skill with the selected number and let it run to completion. If it comes back parked rather than landed (gate, decision, or an unanswered PR-review wait), that is not the end of the iteration: park it per step 3 and select a substitute. The task skill hands a parked outcome back to you; **deciding whether to pick up other work is yours, not its** - a human running `/task 032` directly wants it to stop and say so, whereas the loop wants to keep moving.
   - **No stale-base PRs (added 2026-07-31, after 031 arrived carrying a rebase IOU; same rule as the task skill's step 6, with the exact commands):** a task PR is opened only from a branch already rebased onto current `origin/main`, with the full gates (`pnpm verify` at root; `pnpm verify:browser` when `apps/portal`, `apps/admin` or `@qcms/ui` is touched; `pnpm exec turbo run test --force` showing `0 cached`, since a fresh worktree resolves turbo's cache to the main checkout's and reports the whole test phase as `FULL TURBO` without running it) run on the rebased tree. Never open a PR whose body promises to rebase later - the CI run reviewers and gates rely on must test the tree that merges. If main moves again while the PR is open, rebase and re-run before merge as usual.
6. **Parallel (count N given):** extend the selection to up to N candidates that are **pairwise independent**:
   - No dependency path between any two selected tasks (check `Depends on` transitively).
   - Disjoint expected file footprints - different packages or different slice folders. When in doubt about overlap, don't parallelize; drop to the smaller set.
   - Claim all selected tasks first (push each `feat/NNN-slug` branch - the /task claim step; the pushed branch is the lock), then spawn one **task-executor** per task in parallel worktrees.
   - Executors run concurrently; **review and land strictly one at a time** as each finishes, per /task steps 5–7 (each merge rebases onto the moved main, re-runs the gates, and lands via `gh pr merge --squash`). The conductor is the only merger, ever; nobody pushes `main` directly (the ruleset rejects it).
7. End the invocation with a one-line human summary **and, as the very last output line, a machine-readable sentinel** (the supervisor script keys off it): `NEXT-TASK: LANDED <NNN>` · `NEXT-TASK: RESUMED <NNN>` · `NEXT-TASK: AWAITING-HUMAN <gate>` · `NEXT-TASK: BLOCKED <NNN> <reason>` · `NEXT-TASK: NOTHING`. Emit exactly one sentinel, always.

   **The sentinel describes what the iteration achieved, not what it started on.** Parking task A on a gate and landing task B is `LANDED B`; the parked gate belongs in the human summary above it, which is where a human reads what they owe. Only three sentinels stop the supervisor - `AWAITING-HUMAN`, `BLOCKED`, `NOTHING` - so reach for them only when the run genuinely has nothing left to do (step 3's bound), and never as a way of flagging something interesting. Anything that merely deserves the Code Owner's attention goes in the summary or in seat mail, while the loop continues.

Safety rails: merges are serialized no matter how many executors run; never reorder past a human gate; if the working tree is dirty at start, stop and report instead of stashing someone's work; parallel batches never span a stage boundary (a stage's exit criteria gate the next stage).
