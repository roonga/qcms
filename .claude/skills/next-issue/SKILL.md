---
name: next-issue
description: Pick the next actionable open GitHub issue and fix it end to end with the multi-agent flow - task-executor implements on fix/NN-slug, task-reviewer verifies, and the conductor opens one PR per issue whose body carries "Fixes #NN" so the squash-merge closes it. Designed for "/loop /next-issue". Skips phase-4, needs-ADR, and task-folded issues; parks human-gated fixes as open PRs and keeps looping - the loop ends only when nothing is executable or a stated repo-wide blocker exists (step 10).
---

Select and fix exactly one open GitHub issue per invocation; /loop provides the repetition. You coordinate; the subagents do the work. The issue text stands in for the task file; everything else mirrors the /task flow, with one deliberate difference: the conductor never merges. Each issue lands as its own PR, reviewed and squash-merged by the PO review loop or the Code Owner (merger duties: `plan/pr-review-loop.md`).

**Housekeeping first (same sweep as /next-task).** `git worktree prune`, then `rm -rf` any `.claude/worktrees/agent-*` directory that does not appear in `git worktree list`. Never remove a dir that IS a live registered worktree. If the shared checkout's working tree is dirty, stop and report instead of stashing someone's work.

1. **Select.** `gh issue list -R roonga/qcms --state open --json number,title,labels,body`. Exclude:
   - Labels `phase-4`, `wontfix`, `duplicate`, `invalid`, `question` (post-launch backlog and non-work), and the routing labels `needs-decision` (awaiting the Code Owner), `blocked-upstream` (report BLOCKED, never claim), `workshop` (routed via /improve-workshop), `admin-stage` (delivered by tasks 031-035).
   - Issues that need an ADR or a Code Owner decision before code can be written (title/body says "needs ADR", or the issue poses an open product question). These are awaiting-human, not executable.
   - Issues a `todo` or `in-progress` ledger task already folds in - grep `docs/features/*.md` for `#NN` (e.g. "folds #25"); the task will deliver them, do not race it.
   - Claimed issues: an origin branch `fix/NN-*` exists, or the issue carries a claim comment (step 3) with no later release comment.

   Priority among the rest: `security` first, then `bug`, then unlabeled, then `enhancement`. Ties break to the smaller, better-specified issue (clear repro plus acceptance criteria beats vague). If nothing is eligible, report why in one line per skipped issue and emit the NOTHING sentinel - under /loop, end the loop; do not idle.
2. **Stale-claim recovery and review-findings cycles (before fresh selection).** A branch with an **open PR** is awaiting review - leave it alone, **unless the review requested changes**: an open loop PR whose latest merger/PO review requests changes (or threads a confirmed unresolved finding) is a **review-findings cycle**, and it outranks fresh selection. Dispatch the executor onto the existing PR branch with the findings as the work order (fix plus the tests that prove it; no scope growth; reply on each addressed thread), push, and report `RESUMED #NN` - the PR updates in place and the merger re-reviews. Otherwise, a claimed issue with no live session owning it resumes before anything new starts:
   - `fix/NN-*` branch with a committed `HANDOFF.md` at its tip - dispatch the executor with the handoff.
   - Branch, no `HANDOFF.md` - dispatch the executor with: "issue #NN was interrupted; reconstruct state from `git log`/`git diff main...<branch>` and the issue, then continue on this branch." Remove any leftover worktree for it first.
   - Claim comment, no branch - the claim is vapor; reply on the issue releasing it, then treat the issue as fresh.
3. **Claim.** Comment on the issue before spawning anything: `Claimed by the dev loop - branch fix/NN-slug.` The comment is the claim lock (issues have no ledger row); anyone selecting work treats a claim comment without a release reply as taken.
4. **Execute.** Write the executor a work order distilled from the issue: number, title, URL, full body, deliverables (the fix, tests at the layer ADR-23 assigns, and any doc the fix touches), and an explicit out-of-scope line (anything the issue does not name; discoveries become new issues, never scope growth). Spawn **task-executor** (worktree isolation) on `fix/NN-slug`. The executor's protocol applies with the work order standing in for the task file; ledger dependency checks do not apply.
5. **Human gates - never automate, but never stall the loop either.** A fix that changes visible portal/admin UI stops at the static-render screenshot gate for Code Owner sign-off, exactly like a UI task. A fix that alters SEC-* behavior (scopes, tokens, CSP, erasure) lands only with the issue's acceptance criteria proven by tests; if acceptance is ambiguous, stop and surface the question instead of choosing. A gate parks **that issue** (as its open PR plus claim), not the run: the gated work waits for the Code Owner while the loop moves on to the next eligible issue.
   **The gate evidence lives ON the PR (Code Owner rule, 2026-07-25): a gated PR must contain its screenshots.** Capture the changed state (phone 390px and desktop 1280px minimum) with the e2e harness, hiding dev-server chrome first (the Next dev-tools indicator is not product UI - remove its element before the screenshot or capture against a production build), commit the PNGs on the fix branch under `docs/gates/pr-<NN>/` with a one-line `README.md` naming what to approve, and embed each image in the PR body via its raw branch URL (`https://github.com/<owner>/<repo>/raw/<branch>/docs/gates/pr-<NN>/<file>.png`). "Screenshots were handed over in the session" is not a gate handover - the Code Owner reviews from GitHub, not from a session transcript. The evidence merges with the squash (audit trail of what was approved); it is small, bounded, and per-PR.
6. **Review.** Spawn **task-reviewer** with the branch and the same work order (the issue's acceptance criteria are the exit criteria). On REJECT, relay findings to the executor (SendMessage) - at most two fix cycles, then park with `HANDOFF.md` and report. On APPROVE, continue.
7. **Open the PR (one per issue - the conductor never merges).** Rebase onto current `main` (never `git reset --hard origin/<branch>` an executor branch), re-run **`pnpm verify`** at root after the rebase (one command, a superset of CI's unit job - issue #19 folded the `check:*` gates into it), add **`pnpm verify:browser`** when the fix touched `apps/portal`, `apps/admin`, or `@qcms/ui` (the Playwright suite is the one CI job `verify` omits), and force-run Docker-backed suites (`turbo run test --filter=<pkg> --force`) when the fix touched db/integration/e2e. Green? Push the branch and open the PR (`gh pr create`): title is the conventional-commit line the squash will use (`fix(<scope>): <summary> (#NN)`); body contains the issue's acceptance criteria as a checked-off checklist, `Fixes #NN` on its own line (so the squash-merge auto-closes the issue), a short summary of the task-reviewer's verdict, and a `## Retro` section holding the executor and reviewer `FRICTION:` lines (or `none`). No AI attribution anywhere - title, body, or commits. Never open a PR red. **After pushing, confirm CI is green on the PR head commit before moving on** (`gh pr checks <NN> --watch`, or `gh run list --commit $(git rev-parse HEAD)`): a local `verify` pass is evidence, not proof, and a red PR handed to the merger costs a full review cycle. If CI is red, fix on the branch and push again; report the state honestly if it stays red. Do not merge; do not push `main`.
8. **Cleanup and handoff.** Remove the executor's worktree (`git worktree remove --force`, then prune) but keep the pushed `fix/NN-slug` branch - it is the PR head; the merger deletes it after squash-merge. The issue stays claimed (claim comment plus open PR; step 1's branch check keeps it off future selections). Merging is the PR reviewer's job - the PO review loop or the Code Owner, per the merger duties in `plan/pr-review-loop.md`: merges strictly serialized, CI green and branch current with `main` required, squash-merge preserving `Fixes #NN`, delete the branch, then append the PR's `## Retro` lines (skip `none`) to `docs/RETRO.md` under `## issue #NN - <title>` dated with the merge date. On abandonment, comment the honest state on the issue - parked branch plus `HANDOFF.md`, or the blocking reason - never leave a claim comment that reads as active work.
9. **Sentinel.** End with a one-line human summary and, as the very last output line, exactly one machine-readable sentinel: `NEXT-ISSUE: PR #NN <url>` / `NEXT-ISSUE: RESUMED #NN` / `NEXT-ISSUE: AWAITING-HUMAN <what the human must do>` / `NEXT-ISSUE: BLOCKED #NN <reason>` / `NEXT-ISSUE: NOTHING`.
10. **Loop continuation (Code Owner rule, 2026-07-25: keep going unless specifically blocked).** Under /loop, exactly one sentinel ends the run: `NOTHING` (no eligible issue remains - gated/claimed/awaiting-decision issues do not count as eligible, so a backlog consisting only of those IS `NOTHING`). Every other sentinel - `PR`, `RESUMED`, `AWAITING-HUMAN`, `BLOCKED #NN` - parks or lands **that one issue** and the loop schedules the next iteration. A repo-wide blocker (main red, gates broken for every issue) is reported as `BLOCKED` with that scope stated, and only then may it end the run. **Discretionary pauses are not stop conditions:** "the findings deserve a read", "several diagnoses changed meaning", "the human might want to weigh in" go in the summary for the Code Owner to read later, while the loop continues. The Code Owner interrupts when they want a pause; the loop never presumes one.

Never: open a PR red, merge a PR yourself, skip the reviewer, widen an issue's scope, batch multiple issues onto one branch, perform a human sign-off on the Code Owner's behalf, or end the loop for anything short of `NOTHING` / a stated repo-wide blocker. Branch prefix is always `fix/` - issue numbers share the numeric space with ledger task numbers, and `feat/NNN-*` is reserved for tasks.
