name: next-issue
description: Pick the next actionable open GitHub issue and fix it end to end with the multi-agent flow - task-executor implements on fix/NN-slug, task-reviewer verifies, and the conductor opens one PR per issue whose body carries "Fixes #NN" so the squash-merge closes it. Designed for "/loop /next-issue". Skips phase-4, needs-ADR, and task-folded issues; parks human-gated fixes as open PRs and keeps looping - the loop ends only when nothing is executable or a stated repo-wide blocker exists (step 10).
---

Select and fix open GitHub issues - one per invocation by default, or up to N in parallel with `/next-issue N` (and `/loop /next-issue N`), Code Owner-enabled 2026-07-27. You coordinate; the subagents do the work. The issue text stands in for the task file; everything else mirrors the /task flow, with one deliberate difference: the conductor never merges. Each issue lands as its own PR, reviewed and squash-merged by the PO review loop or the Code Owner (merger duties: `plan/pr-review-loop.md`).

**Housekeeping first (the canonical sweep is the task skill's step 9; `/next-task` runs the same one).** `git worktree prune`, then `rm -rf` any `.claude/worktrees/agent-*` directory that does not appear in `git worktree list`. Never remove a dir that IS a live registered worktree. If the shared checkout's working tree is dirty, stop and report instead of stashing someone's work.

**Seat mail, same protocol as `/next-task` step 1 (added 2026-08-01).** Read `../seat-mail/dev/`, act on each message, then move it to `../seat-mail/dev/read/` as the ack; write to `../seat-mail/pm/message_<UTC timestamp>.txt` to reach the PO seat, which is this loop's merger. Mail is routing and coordination only, never scope. Skip silently if the folder does not exist. **A supervisor may assign a different mailbox** in the prompt (e.g. `../seat-mail/dev2/`) - then that inbox and its `read/` are yours, and outbound mail is signed with that lane name.

**Second-lane discipline (added 2026-08-01, for an issue lane running beside the task loop):** when this skill runs as a second agent alongside a live `/next-task` lane, four rules keep the lanes from colliding:
1. **Scope tier per the standing aim** (`plan/CLAUDE.md`): while the e2e chain (033/034/035) is executable, pick `security` and `bug` issues only - enhancements, workshop items, and polish wait behind 035, however small.
2. **Stay out of the live claim's footprint:** read `git ls-remote --heads origin 'feat/*'`, open the claimed task's file, and skip any issue whose expected footprint overlaps that task's named apps/packages seam. When in doubt, not eligible - there is no shortage of bugs elsewhere.
3. **Heavy gates are serialized across lanes, and each lane runs them on its own port seat.** The two are not redundant: the seat (`QCMS_PORT_SEAT`, R8/`docs/PORTS.md`) stops two lanes silently *sharing* a dev server, the lock stops two lanes running heavy suites *at once*. Distinct ports do not make one machine able to run two Chromium suites. `agent-loop.sh` exports the seat for your lane; the harness refuses an unset seat in a worktree. Wrap `QCMS_PORT_SEAT=<0-9> pnpm verify:browser` and any Docker-backed force-run in `flock -w 2400 ../seat-mail/.gates.lock <command>` - two concurrent browser/Testcontainers runs on one machine is the documented load-flake recipe. If the lock wait times out, mail the PO seat rather than running unlocked.
4. **The two-conductor rule is per-lane:** this lane conducts issues only; it never touches ledger tasks, never merges, and treats every `feat/NNN-*` branch as another conductor's property.

1. **Select.** `gh issue list -R roonga/qcms --state open --json number,title,labels,body`. Exclude:
   - Labels `phase-4`, `wontfix`, `duplicate`, `invalid`, `question` (post-launch backlog and non-work), and the routing labels `needs-decision` (awaiting the Code Owner), `blocked-upstream` (report BLOCKED, never claim), `workshop` (routed via /improve-workshop), `admin-stage` (delivered by tasks 031-035).
   - Issues that need an ADR or a Code Owner decision before code can be written (title/body says "needs ADR", or the issue poses an open product question). These are awaiting-human, not executable.
   - Issues an unfinished ledger task already folds in - grep `docs/features/*.md` for `#NN` (e.g. "folds #25"); if that task is not yet `done`, it will deliver them, so do not race it.
   - Claimed issues: an origin branch `fix/NN-*` exists, or the issue carries a claim comment (step 4) with no later release comment.

   Priority among the rest: `security` first, then `bug`, then unlabeled, then `enhancement`. Ties break to the smaller, better-specified issue (clear repro plus acceptance criteria beats vague). If nothing is eligible, report why in one line per skipped issue and emit the NOTHING sentinel - under /loop, end the loop; do not idle.
2. **Stale-claim recovery and review-findings cycles (before fresh selection).** A branch with an **open PR** is awaiting review - leave it alone, **unless the review requested changes**: an open loop PR whose newest `PO-REVIEW:` sentinel says `PO-REVIEW: CHANGES-REQUESTED @<sha>` **with `<sha>` equal to the PR's current `headRefOid`** (same-account PRs cannot carry GitHub's formal review state, so the head-bound sentinel is the machine-checkable signal; a sentinel whose SHA mismatches the current head is stale - the fix was pushed and the merger owes a re-review, so leave the PR alone) is a **review-findings cycle**, and it outranks fresh selection. Dispatch the executor onto the existing PR branch with the findings as the work order (fix plus the tests that prove it; no scope growth; reply on each addressed thread), push, and report `RESUMED #NN` - the PR updates in place and the merger re-reviews. Otherwise, a claimed issue with no live session owning it resumes before anything new starts:
   - `fix/NN-*` branch with a committed `HANDOFF.md` at its tip - dispatch the executor with the handoff.
   - Branch, no `HANDOFF.md` - dispatch the executor with: "issue #NN was interrupted; reconstruct state from `git log`/`git diff main...<branch>` and the issue, then continue on this branch." Remove any leftover worktree for it first.
   - Claim comment, no branch - the claim is vapor; reply on the issue releasing it, then treat the issue as fresh.
3. **Batching (`/next-issue N`).** Walk the priority order picking up to N issues that are **pairwise independent**: no dependency between them, and disjoint expected footprints (different packages/apps/seams, judged from the issue texts - when in doubt, NOT independent; never batch two issues expected to touch the same package or the same seam). Open findings cycles (a live `PO-REVIEW: CHANGES-REQUESTED @<current head>` sentinel) fill batch slots FIRST. Each batch member then runs the full per-issue flow below concurrently - own claim, own executor worktree, own reviewer, own PR - with no cross-batch barrier: an issue finishing review opens its PR immediately, never waiting for batch siblings. The conductor still never merges, so N-way batching adds no merge races; the PO review loop serializes landings.
4. **Claim.** Comment on the issue before spawning anything: `Claimed by the dev loop - branch fix/NN-slug.` The comment is the claim lock (issues have no ledger row); anyone selecting work treats a claim comment without a release reply as taken.
5. **Execute.** Write the executor a work order distilled from the issue: number, title, URL, full body, deliverables (the fix, tests at the layer ADR-23 assigns, and any doc the fix touches), and an explicit out-of-scope line. **Discovery discipline (Code Owner recalibration, 2026-07-27):** a discovery that is SAME-AREA and SMALL - touches files already in the diff or the same seam/function, needs no new decision, no golden/append-only ripple, no new dependency - is **fixed in the same PR**, listed in the body under `## Same-area fixes ridden along` so the reviewer can audit the riders. Only genuinely unrelated, decision-requiring, golden-rippling, or large discoveries become new issues. The point of the old never-expand rule was stopping runaway tasks, not converting one-line same-file fixes into full loop cycles. Spawn **task-executor** (worktree isolation) on `fix/NN-slug`. The executor's protocol applies with the work order standing in for the task file; ledger dependency checks do not apply.
6. **Human gates - never automate, but never stall the loop either** (the task loop adopted this same policy on 2026-08-01; if no issue is eligible here but an independent ledger task is, the reciprocal move is to cross over to `/next-task`'s selection rather than idle). A fix that changes visible portal/admin UI stops at the static-render screenshot gate for Code Owner sign-off, exactly like a UI task. A fix that alters SEC-* behavior (scopes, tokens, CSP, erasure) lands only with the issue's acceptance criteria proven by tests; if acceptance is ambiguous, stop and surface the question instead of choosing. A gate parks **that issue** (as its open PR plus claim), not the run: the gated work waits for the Code Owner while the loop moves on to the next eligible issue.
   **The gate evidence lives ON the PR (Code Owner rule, 2026-07-25): a gated PR must contain its screenshots.** Capture the changed state (phone 390px and desktop 1280px minimum) with the e2e harness, hiding dev-server chrome first (the Next dev-tools indicator is not product UI - remove its element before the screenshot or capture against a production build), commit the PNGs on the fix branch under `docs/gates/pr-<NN>/` with a one-line `README.md` naming what to approve, and embed each image in the PR body via its raw branch URL (`https://github.com/<owner>/<repo>/raw/<branch>/docs/gates/pr-<NN>/<file>.png`). "Screenshots were handed over in the session" is not a gate handover - the Code Owner reviews from GitHub, not from a session transcript. The evidence merges with the squash (audit trail of what was approved); it is small, bounded, and per-PR.
7. **Review.** Spawn **task-reviewer** with the branch and the same work order (the issue's acceptance criteria are the exit criteria). On REJECT, relay findings to the executor (SendMessage) - at most two fix cycles, then park with `HANDOFF.md` and report. On APPROVE, continue.
8. **Open the PR (one per issue - the conductor never merges).** Rebase onto current `main` (never `git reset --hard origin/<branch>` an executor branch), re-run **`pnpm verify`** at root after the rebase (one command, a superset of CI's unit job - issue #19 folded the `check:*` gates into it), add **`QCMS_PORT_SEAT=<0-9> pnpm verify:browser`** when the fix touched `apps/portal`, `apps/admin`, or `@roonga/qcms-ui` (the Playwright suite is the one CI job `verify` omits), and force-run Docker-backed suites (`turbo run test --filter=<pkg> --force`) when the fix touched db/integration/e2e. Green? Push the branch and open the PR (`gh pr create`): title is the conventional-commit line the squash will use (`fix(<scope>): <summary> (#NN)`); body contains the issue's acceptance criteria as a checked-off checklist, `Fixes #NN` on its own line (so the squash-merge auto-closes the issue), a short summary of the task-reviewer's verdict, and a `## Retro` section holding the executor and reviewer `FRICTION:` lines (or `none`). No AI attribution anywhere - title, body, or commits. Never open a PR red. **After pushing, confirm CI is green on the PR head commit before moving on** (`gh pr checks <NN> --watch`, or `gh run list --commit $(git rev-parse HEAD)`): a local `verify` pass is evidence, not proof, and a red PR handed to the merger costs a full review cycle. If CI is red, fix on the branch and push again; report the state honestly if it stays red. Do not merge; do not push `main`.
9. **Cleanup and handoff.** Remove the executor's worktree (`git worktree remove --force`, then prune) but keep the pushed `fix/NN-slug` branch - it is the PR head; the merger deletes it after squash-merge. The issue stays claimed (claim comment plus open PR; step 1's branch check keeps it off future selections). Merging is the PR reviewer's job - the PO review loop or the Code Owner, per the merger duties in `plan/pr-review-loop.md`: merges strictly serialized, CI green and branch current with `main` required, squash-merge preserving `Fixes #NN`, delete the branch, then append the PR's `## Retro` lines (skip `none`) to `docs/RETRO.md` under `## issue #NN - <title>` dated with the merge date. On abandonment, comment the honest state on the issue - parked branch plus `HANDOFF.md`, or the blocking reason - never leave a claim comment that reads as active work.
10. **Sentinel.** End with a one-line human summary per issue and then the machine-readable sentinel block - exactly one sentinel line per issue handled this invocation (a single-issue run emits one line): `NEXT-ISSUE: PR #NN <url>` / `NEXT-ISSUE: RESUMED #NN` / `NEXT-ISSUE: AWAITING-HUMAN <what the human must do>` / `NEXT-ISSUE: BLOCKED #NN <reason>` / `NEXT-ISSUE: NOTHING`.
11. **Loop continuation (Code Owner rule, 2026-07-25: keep going unless specifically blocked).** Under /loop, exactly one sentinel ends the run: `NOTHING` (no eligible issue remains - gated/claimed/awaiting-decision issues do not count as eligible, so a backlog consisting only of those IS `NOTHING`). Every other sentinel - `PR`, `RESUMED`, `AWAITING-HUMAN`, `BLOCKED #NN` - parks or lands **that one issue** and the loop schedules the next iteration. A repo-wide blocker (main red, gates broken for every issue) is reported as `BLOCKED` with that scope stated, and only then may it end the run. **Discretionary pauses are not stop conditions:** "the findings deserve a read", "several diagnoses changed meaning", "the human might want to weigh in" go in the summary for the Code Owner to read later, while the loop continues. The Code Owner interrupts when they want a pause; the loop never presumes one. **Mechanically: under /loop, ENQUEUE the next iteration (the scheduling action) before composing the summary** - step 10's output format is unchanged (human summary, then the sentinel as the very last line); what moves earlier is the internal re-arm, so continuation is never a judgment made while holding interesting findings. Anything needing the Code Owner is escalated in place (PR comment, issue, push notification), never by ending the run. This ordering exists because the drift happened twice (2026-07-25 after #59, 2026-07-26 mid-run) despite the written rule.

Never: open a PR red, merge a PR yourself, skip the reviewer, widen an issue's scope, batch multiple issues onto one branch, perform a human sign-off on the Code Owner's behalf, or end the loop for anything short of `NOTHING` / a stated repo-wide blocker. Branch prefix is always `fix/` - issue numbers share the numeric space with ledger task numbers, and `feat/NNN-*` is reserved for tasks.
