---
name: task
description: Execute one numbered qcms plan task end to end with the multi-agent flow - task-executor implements on a branch, task-reviewer verifies, merge on approval, ledger updated. Use "/task 002" or "/task 017". Stops at human gates instead of simulating them.
---

Orchestrate exactly one plan task. You coordinate; the subagents do the work.

Input: a task number NNN (from the argument). Resolve it to `docs/features/<NNN>-*.md`.

1. **Pre-flight.** Read the ledger (`docs/features/README.md`). Refuse if: the task isn't `todo` (report its state - `in-progress` means another session/agent has claimed it), a **Depends on** entry isn't `done`, or the task is a human gate that cannot be executed autonomously (038 launch validation; 040's sign-off; 042's sign-off - preparation parts may run, the sign-off may not). Announce the plan: task title, branch name `feat/NNN-slug`.
2. **Claim (amended 2026-07-31: the pushed branch is the claim; direct pushes to `main` are blocked by the `protect-main` ruleset).** Before spawning anything, create the task branch from current `origin/main` and push it: `git push origin origin/main:refs/heads/feat/NNN-slug`. The live `origin/feat/NNN-slug` branch is the claim lock - anyone selecting work treats a live `origin/feat/NNN-*` branch as a claim on task NNN. After pushing, re-list remote branches (`git ls-remote --heads origin 'feat/*'`); if another live branch already claims this task and it is not yours, delete yours and re-pick. The ledger row is **not** touched at claim time - it changes exactly once, `todo` -> `done (PR #N; …)`, inside the completing PR (step 7).
3. **Execute.** Spawn the **task-executor** agent (worktree isolation) with the task number and branch name. Do not implement in this session - context separation is the point. Executors never touch the ledger or `main`.
4. **Handle the executor's report.**
   - *Not done / parked:* the branch with its committed `HANDOFF.md` is the park record (the live branch is also the claim). If a `blocked (issue #)` ledger marker is warranted, land that one-line row change as its own small PR (`main` cannot be pushed directly). Relay the handoff to the user, stop.
   - *Blocked on a decision:* relay the question to the user verbatim, stop.
   - *Screenshot gate reached (UI tasks):* present the screenshot set to the user for sign-off; on approval, re-invoke the executor (SendMessage - same agent, context intact) to wire behavior.
   - *Done:* continue.
5. **Review.** Spawn the **task-reviewer** agent with the task number and branch. On REJECT: relay findings to the executor (SendMessage) for fixes - at most two fix cycles, then park with `HANDOFF.md` and report to the user. On APPROVE: continue.
6. **PR feedback protocol (added 2026-07-31; applies to any task that ships a PR - always for human-gate tasks).** A PR is a conversation, not a hand-in: after pushing it (rebased branch, full gates - see the next-task skill), WATCH it. Poll every ~3 minutes for up to 30 minutes: `gh pr view <n> --json comments,reviews` for issue comments plus `gh api repos/<owner>/<repo>/pulls/<n>/comments` for review threads. The latest `PO-REVIEW:` sentinel governs:
   - `REQUEST-CHANGES` -> that comment plus every unresolved review thread IS the work order. Address every numbered item, reply to each thread with what changed (or a reasoned why-not), rebase if main moved, re-run the full gates, push, then resume polling for a fresh sentinel on the NEW head.
   - `APPROVE @<head>` bound to the CURRENT head -> authorization to squash-merge (keeping `Fixes #NN`), still subject to any declared human gate: both the gate sign-off and the sentinel must hold before merging.
   - No sentinel after the polling window -> end the iteration with `NEXT-TASK: AWAITING-HUMAN po-review <NNN>`.
   Never merge a PR whose latest sentinel is `REQUEST-CHANGES`, or whose `APPROVE` is bound to a stale head. On resume of a task that already has an open PR, run this protocol FIRST, before any other work. **Each poll tick also drains the seat-mail inbox (`../seat-mail/dev/`) and, if ~5 minutes have passed since the last mail out, writes a one-line heartbeat to `../seat-mail/pm/`** - and entering this polling wait is itself mailed when it starts (what is being waited for, the window length), per the cadence rule in the next-task skill.
7. **Land (serialized - one merge at a time, ever).** Rebase the task branch onto the *current* `main` (it may have moved while this task ran) - **reconcile by rebase only; never `git reset --hard origin/<branch>` an executor branch** (executors don't push their work, so the local ref is the source of truth - a reset-to-origin silently discards their commits). Re-run **`pnpm verify`** at root **after** the rebase - one command, a superset of CI's unit job (issue #19), and checks are snapshots that vouch only for the tree they ran against. Add **`pnpm verify:browser`** when the task touched `apps/portal`, `apps/admin`, or `@qcms/ui`: the Playwright suite is the one CI job `verify` omits. If the task touched a Docker-backed package (db/integration/e2e), **force-run its suite** (`turbo run test --filter=<pkg> --force`) before merging - turbo cache replays logs that mimic a live pass without booting a container - and confirm nonzero per-file test counts (a misresolved test `root` matches zero files and still reports green). Then land **through GitHub, never by pushing `main`** (amended 2026-07-31: the `protect-main` ruleset requires a PR and green checks, and a locally-created squash SHA cannot be associated with its PR - that is how PR #205 sat OPEN after its content landed): as final commits on the task branch, flip the ledger row to `done (PR #N; …)` and append the task's retro section (step 8), push, wait for the required checks to go green on that head, then **`gh pr merge <N> --squash`** with a Conventional Commit title carrying the task number (keep `Fixes #NN`). GitHub deletes the head branch on merge. **Then confirm CI is actually green on the merge commit on `main` before starting anything else** (`gh run list --commit $(git rev-parse HEAD) --limit 5`, or `gh run watch`) - a local `verify` pass is evidence, not proof, and the loop must never land a second task on a red `main`. If CI is red, fix forward **via a fresh PR** (protection applies to fixes too; `gh pr merge` once its checks pass) or revert through GitHub, and say so in the report. If the rebase conflicts nontrivially, hand the conflict back to the executor (SendMessage) rather than resolving blind. Report: what landed, suites run, discoveries that need issues filed.
8. **Log the retro.** Append the executor's and reviewer's `FRICTION:` lines (skip `none`) to `docs/RETRO.md` under `## NNN - <task title>` with today's date - as a commit **on the task branch before the merge** (step 7), since `main` cannot be pushed directly. Capture only - improving the workshop is `/improve-workshop`'s job, run deliberately at stage boundaries, never mid-task.
9. **Clean up the worktree - always.** After landing (or abandoning), remove the executor's worktree: `git worktree remove --force <path>` for anything under `.claude/worktrees/` belonging to this task, then `git worktree prune`. **On Windows, `git worktree remove` frequently deregisters the worktree but fails to delete its directory (locked `node_modules`/`.turbo`, long paths); after prune, also `rm -rf` any `.claude/worktrees/agent-*` dir that no longer appears in `git worktree list`.** This is safe in every outcome: merged work lives on main, parked work lives on the task branch (with its committed `HANDOFF.md`) - the worktree directory itself never holds the only copy of anything. After a merge, also delete the merged `feat/NNN-slug` branch.
10. **On abandonment** (parked, blocked, or fix cycles exhausted): keep the claim honest - the live branch with its committed, pushed `HANDOFF.md` reads as parked work; add a `blocked (issue #)` ledger row via a small PR when an issue gates it; if the task is truly abandoned with nothing to keep, delete the remote branch so the claim releases. Never leave a stale claim that reads as active work. The worktree still goes (step 9).

Never: merge red, skip the reviewer, extend the task's scope yourself, or perform a human sign-off on the user's behalf.
