name: task
description: Execute one numbered qcms plan task end to end with the multi-agent flow - task-executor implements on a branch, task-reviewer verifies, merge on approval, ledger updated. Use "/task 002" or "/task 017". Never simulates a human gate: it parks the task on its branch with a HANDOFF record and hands control back to the caller.
---

Orchestrate exactly one plan task. You coordinate; the subagents do the work.

Input: a task number NNN (from the argument). Resolve it to `docs/features/<NNN>-*.md`.

1. **Pre-flight.** Read the ledger (`docs/features/README.md`) **and the remote claim branches** (`git ls-remote --heads origin 'feat/*'`). Refuse if: the task isn't `todo` (report its state), **a live `origin/feat/NNN-*` branch already claims it** (that branch, not any ledger status, is the claim - see step 2), a **Depends on** entry isn't `done`, or the task is a human gate that cannot be executed autonomously (038 launch validation; 040's sign-off; 030's manual screen-reader pass - preparation parts may run, the sign-off may not). Announce the plan: task title, branch name `feat/NNN-slug`.
2. **Claim (amended 2026-07-31: the pushed branch is the claim; direct pushes to `main` are blocked by the `protect-main` ruleset).** Before spawning anything, create the task branch from current `origin/main` and push it: `git push origin origin/main:refs/heads/feat/NNN-slug`. The live `origin/feat/NNN-slug` branch is the claim lock - anyone selecting work treats a live `origin/feat/NNN-*` branch as a claim on task NNN. After pushing, re-list remote branches (`git ls-remote --heads origin 'feat/*'`); if another live branch already claims this task and it is not yours, delete yours and re-pick. The ledger row is **not** touched at claim time - it changes exactly once, `todo` -> `done (PR #N; …)`, inside the completing PR (step 7).
3. **Execute.** Spawn the **task-executor** agent (worktree isolation) with the task number and branch name. Do not implement in this session - context separation is the point. Executors never touch the ledger or `main`.
4. **Handle the executor's report.** Every non-`Done` outcome below **parks** the task and returns control to your caller; it does not end the run by itself. Parking means: the pushed branch keeps the claim, a `HANDOFF.md` is committed and pushed with a **first line of `HANDOFF: AWAITING-HUMAN <what the human must do>` / `HANDOFF: BLOCKED <issue #>` / `HANDOFF: INTERRUPTED`** (the next-task skill's recovery step reads that line to decide whether resuming is even possible), and the worktree is torn down per step 9. Invoked by a human, you then stop and report. Invoked by `/next-task`, the caller decides whether to pick up independent work while this one waits - **that decision is not yours to make.**
   - *Not done / parked:* the branch with its committed `HANDOFF.md` is the park record (the live branch is also the claim). If a `blocked (issue #)` ledger marker is warranted, land that one-line row change as its own small PR (`main` cannot be pushed directly). Relay the handoff, `HANDOFF: BLOCKED` or `INTERRUPTED` as fits.
   - *Blocked on a decision:* relay the question verbatim; park as `HANDOFF: AWAITING-HUMAN <the question>`.
   - *Screenshot gate reached (UI tasks):* present the screenshot set to the user for sign-off; on approval, re-invoke the executor (SendMessage - same agent, context intact) to wire behavior. **The gate evidence lives in the repo, not in the session (Code Owner rule, 2026-07-25).** Capture the changed state at phone 390px and desktop 1280px minimum with dev-server chrome hidden (the Next dev-tools indicator is not product UI - remove its element, or capture against a production build), and commit the PNGs on the task branch under `docs/gates/<NNN>/` with a one-line `README.md` naming what to approve. (Task gates use the bare task number; the issue loop's are `docs/gates/pr-<NN>/`, keyed to the *issue* number - two conventions, deliberately distinct.) Once the PR exists, embed each image in its body via the raw branch URL (`https://github.com/<owner>/<repo>/raw/<branch>/docs/gates/<NNN>/<file>.png`): the Code Owner reviews from GitHub, and "screenshots were shown in the session" is not a gate handover. The evidence merges with the squash as the record of what was approved. **If sign-off does not come back promptly, park rather than wait** (`HANDOFF: AWAITING-HUMAN screenshot gate, evidence at docs/gates/<NNN>/`): the gate is genuinely the Code Owner's and may take hours, and holding an executor and a worktree idle through it buys nothing. On approval the task resumes from the branch - re-dispatch the executor with the handoff to wire behavior.
   - *Done:* continue.
5. **Review.** Spawn the **task-reviewer** agent with the task number and branch. On REJECT: relay findings to the executor (SendMessage) for fixes - at most two fix cycles, then park with `HANDOFF.md` and report to the user. On APPROVE: continue.
6. **Open the PR, then work it.** Landing requires one: the `protect-main` ruleset takes no direct push to `main`, so every task ends in a PR whatever its size.
   - **Open it** once the reviewer approves, from a branch **already rebased onto current `origin/main` with the full gates run on the rebased tree** (never a PR whose body promises to rebase later - the CI run the gates rely on must test the tree that merges). `gh pr create` with: title = the Conventional Commit line the squash will use, carrying the task number (`feat(core): 006 forward-pass evaluator`); body = the task's exit-criteria checklist checked off, a short summary of the task-reviewer's verdict, `Fixes #NN` on its own line for any issue the task closes, and a `## Retro` section holding the executor and reviewer `FRICTION:` lines (or `none`). No AI attribution in title, body, or commits. Never open a PR red - confirm CI green on the PR head (`gh pr checks <N> --watch`) before treating it as handed over.
   - **Then watch it (added 2026-07-31; a PR is a conversation, not a hand-in).** Poll every ~3 minutes for up to 30 minutes: `gh pr view <n> --json comments,reviews` for issue comments plus `gh api repos/<owner>/<repo>/pulls/<n>/comments` for review threads. The latest `PO-REVIEW:` sentinel governs:
     - `PO-REVIEW: CHANGES-REQUESTED @<headRefOid>` -> that comment plus every unresolved review thread IS the work order. Address every numbered item, reply to each thread with what changed (or a reasoned why-not), rebase if main moved, re-run the full gates, push, then resume polling for a fresh sentinel on the NEW head.
     - `PO-REVIEW: APPROVE @<headRefOid>` bound to the CURRENT head -> authorization to squash-merge (keeping `Fixes #NN`), still subject to any declared human gate: both the gate sign-off and the sentinel must hold before merging.
     - No sentinel after the polling window -> **park the task on its open PR** (`HANDOFF: AWAITING-HUMAN po-review on PR #<n>`) and hand back. Do not sit on the poll: an unanswered review is a wait, and a wait is exactly when the caller should be spending the time on independent work. `/next-task` picks a substitute and reports the parked review; a human caller gets told what is waiting. Emit `NEXT-TASK: AWAITING-HUMAN po-review <NNN>` only if nothing else turns out to be executable.

   The two sentinel words are exactly `APPROVE` and `CHANGES-REQUESTED`, with the full head SHA from `gh pr view <n> --json headRefOid` - match those literals, since the reviewing seat emits no others (`plan/pr-review-loop.md` step 3 is the emitter). Never merge a PR whose latest sentinel is `CHANGES-REQUESTED`, or whose `APPROVE` is bound to a stale head. On resume of a task that already has an open PR, run this protocol FIRST, before any other work. **Each poll tick also drains the seat-mail inbox (`../seat-mail/dev/`) and, if ~5 minutes have passed since the last mail out, writes a one-line heartbeat to `../seat-mail/pm/`** - and entering this polling wait is itself mailed when it starts (what is being waited for, the window length), per the cadence rule in the next-task skill.
7. **Land (serialized - one merge at a time, ever).** Rebase the task branch onto the *current* `main` (it may have moved while this task ran) - **reconcile by rebase only; never `git reset --hard origin/<branch>` an executor branch** (executors don't push their work, so the local ref is the source of truth - a reset-to-origin silently discards their commits). Re-run **`pnpm verify`** at root **after** the rebase (add **`pnpm verify:browser`** when the task touched `apps/portal`, `apps/admin`, or `@qcms/ui`) - checks are snapshots that vouch only for the tree they ran against, so a pre-rebase green proves nothing about the tree that merges. Gate contents and the CI mapping: `CONTRIBUTING.md`. If the task touched a Docker-backed package (db/integration/e2e), **force-run its suite** (`pnpm exec turbo run test --filter=<pkg> --force` - never `pnpm test --force`, which appends the flag to the chained script and kills the bare-Vitest leg on `CACError`) before merging - turbo cache replays logs that mimic a live pass without booting a container - and confirm nonzero per-file test counts (a misresolved test `root` matches zero files and still reports green). Then land **through GitHub, never by pushing `main`** (amended 2026-07-31: the `protect-main` ruleset requires a PR and green checks, and a locally-created squash SHA cannot be associated with its PR - that is how PR #205 sat OPEN after its content landed): as final commits on the task branch, flip the ledger row to `done (PR #N; …)` and append the task's retro section (step 8), push, wait for the required checks to go green on that head, then **`gh pr merge <N> --squash`** with a Conventional Commit title carrying the task number (keep `Fixes #NN`). GitHub deletes the head branch on merge. **Then confirm CI is actually green on the merge commit on `main` before starting anything else** (`gh run list --commit $(git rev-parse HEAD) --limit 5`, or `gh run watch`) - a local `verify` pass is evidence, not proof, and the loop must never land a second task on a red `main`. If CI is red, fix forward **via a fresh PR** (protection applies to fixes too; `gh pr merge` once its checks pass) or revert through GitHub, and say so in the report. If the rebase conflicts nontrivially, hand the conflict back to the executor (SendMessage) rather than resolving blind. Report: what landed, suites run, discoveries that need issues filed.
8. **Log the retro.** Append the executor's and reviewer's `FRICTION:` lines (skip `none`) to `docs/RETRO.md` under `## NNN - <task title>` with today's date - as a commit **on the task branch before the merge** (step 7), since `main` cannot be pushed directly. Capture only - improving the workshop is `/improve-workshop`'s job, run deliberately at stage boundaries, never mid-task.
9. **Clean up the worktree - always (canonical sweep; `/next-task` and `/next-issue` run the same one before selecting).** After landing (or abandoning), remove the executor's worktree: `git worktree remove --force <path>` for anything under `.claude/worktrees/` belonging to this task, then `git worktree prune`. Removal can deregister a worktree but leave its directory behind (locked `node_modules`/`.turbo`), so after the prune also `rm -rf` any `.claude/worktrees/agent-*` dir that no longer appears in `git worktree list` - **never one that IS a live registered worktree.** This is safe in every outcome: merged work lives on main, parked work lives on the task branch (with its committed `HANDOFF.md`) - the worktree directory itself never holds the only copy of anything. After a merge, also delete the merged `feat/NNN-slug` branch.
10. **On abandonment** (parked, blocked, or fix cycles exhausted): keep the claim honest - the live branch with its committed, pushed `HANDOFF.md` reads as parked work; add a `blocked (issue #)` ledger row via a small PR when an issue gates it; if the task is truly abandoned with nothing to keep, delete the remote branch so the claim releases. Never leave a stale claim that reads as active work. The worktree still goes (step 9).

Never: merge red, skip the reviewer, extend the task's scope yourself, or perform a human sign-off on the user's behalf.
